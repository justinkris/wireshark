Questions

Q1

Open app-iradio.pcapng. What DSCP values are used in this communication? Which traffic direction has higher priority? Can the larger packets be fragmented as needed?

Your Answer
Model Answer
DSCP (Differentiated Services Code Point) is the 6-bit QoS marking in the IP Differentiated Services field. Expand the IP header's "Differentiated Services" field in Wireshark to read the DSCP value. Internet radio streaming media (from server to client) is typically marked with DSCP EF (Expedited Forwarding, value 46) to indicate high-priority, delay-sensitive traffic. Check the Don't Fragment (DF) bit in the IP Flags field — a set DF bit means the packet cannot be fragmented in transit; if it encounters a link with a smaller MTU, it will be dropped and the sender notified via ICMP.
Q2

Open ftp-ioupload-partial.pcap. Can fragmentation be used if needed? Is the client using an acceptable MTU size? What DSCP values are seen?

Your Answer
Model Answer
FTP bulk data transfer is typically marked DSCP 0 (Best Effort, CS0) since it is not latency-sensitive. Check the More Fragments and Don't Fragment bits in the IP Flags field — if DF=0, fragmentation is allowed. A client using the standard Ethernet MTU of 1500 bytes is normal; a smaller MSS (visible in TCP options during the SYN handshake) suggests a VPN tunnel, WAN link, or PPPoE overhead is reducing the effective MTU. If the DF bit is set throughout the session, Path MTU Discovery (PMTUD) is in use.
Q3

Open ip-127guy.pcapng. What is wrong with the IP addressing in this trace file? Can you look at the MAC header to identify the original sender?

Your Answer
Model Answer
A source IP address of 127.0.0.1 (the loopback address) should never appear in a packet on the network. The loopback address is intended for internal host communication only and any packet with this source address reaching the wire indicates a software bug or misconfiguration in the sending host's networking stack. Examining the MAC header can identify the physical hardware address of the device sending these malformed packets.
Q4

Open ip-checksum-invalid.pcapng. Which host's traffic has IP header checksum problems? Did the communication work properly regardless? What could be causing the checksum errors? What can you do to make the trace file more readable?

Your Answer
Model Answer
The checksum errors are caused by checksum offloading — the network interface card calculates the IP, TCP, and UDP checksums in hardware after Wireshark has already captured a copy of the outbound packet. Because Wireshark captures the packet before the NIC fills in the checksum, the field appears as zeros or an invalid value. The communication worked correctly, proving the checksums were valid on the wire. Disabling IP/TCP/UDP checksum validation in Wireshark preferences or disabling the Checksum Errors coloring rule will make the trace more readable.
Q5

Open ip-fragments.pcapng. What is the difference when you view this trace with and without IP fragment reassembly enabled (Edit | Preferences | Protocols | IP)?

Your Answer
Model Answer
When IP fragment reassembly is enabled, Wireshark collects all fragments with the same IP ID value and presents the last fragment as if it contained the complete reassembled datagram, with links to the other fragments shown in the packet details. With reassembly disabled, each fragment is shown independently with only its portion of the data, making it possible to see the fragment offset and more-fragments flag values for each individual fragment.
Q6

Open ipv6-general.pcapng. Is IPv4 used anywhere? What is the IPv6 Hop Limit on each DHCPv6 packet? Are DHCPv6 packets embedded in IPv4 headers?

Your Answer
Model Answer
In a pure IPv6-only trace, no IPv4 packets should appear — filter with `ip` to check. DHCPv6 packets use link-local source addresses and multicast destination addresses, with a Hop Limit of 1 for packets that must not leave the local link (such as Solicit and Advertise). DHCPv6 is a native IPv6 protocol — it is not encapsulated inside IPv4 headers unless a tunneling mechanism like 6to4 or Teredo is in use. Apply `dhcpv6` filter to isolate DHCPv6 packets and inspect their IPv6 Hop Limit field directly.
Q7

Open ipv6-mcasts.pcapng. Check out your IPv6 and ICMPv6 display filters. Can you see the duplicate address test at the start? Why won't the display filter 'ip' work well here?

Your Answer
Model Answer
The Duplicate Address Detection (DAD) process sends ICMPv6 Neighbor Solicitation packets sourced from `::` (the unspecified address) to the solicited-node multicast address for the tentative IP before assigning it. You can see the DAD at the start by filtering `icmpv6.type==135 && ipv6.src==::`. The display filter `ip` matches only IPv4 traffic in Wireshark — it will not show any IPv6 frames. Use `ipv6` to display IPv6 packets, or `ip or ipv6` to see both. This is a common mistake when working in dual-stack environments.
Q8

Open ipv6-pinginipv4.pcapng. Can you tell why this is a 6to4 encapsulation and not a Teredo encapsulation?

Your Answer
Model Answer
6to4 encapsulation places an IPv6 header inside an IPv4 packet where the IPv4 Protocol field is set to 41 (IPv6). The IPv6 address in a 6to4 packet is derived from the IPv4 address using the 2002::/16 prefix followed by the hexadecimal representation of the IPv4 address. Teredo encapsulation, by contrast, uses UDP port 3544 as its carrier, making it easy to distinguish the two methods.
Q9

Open pcaprnet-ip-sec.pcapng. What display filter could you use to show only IPsec traffic?

Your Answer
Model Answer
IPsec uses two distinct IP protocols: ESP (Encapsulating Security Payload, IP protocol 50) and AH (Authentication Header, IP protocol 51). Display filters: `esp` shows ESP traffic only, `ah` shows AH traffic only. IKE (Internet Key Exchange) key negotiation uses `isakmp` (UDP port 500) or `udp.port==4500` for NAT-traversal IKE. To catch all IPsec-related traffic in one filter: `esp or ah or isakmp`. The actual tunneled payload inside ESP is encrypted and cannot be read without the decryption key.
Q10

Open voip-extension.pcapng. What DSCP values are used throughout the trace? Would IP fragmentation be allowed in this VoIP communication?

Your Answer
Model Answer
VoIP RTP media packets are marked with DSCP EF (Expedited Forwarding, value 46) to guarantee low-latency, low-jitter delivery through QoS-aware networks. SIP signaling packets typically use DSCP AF31 or CS3. The Don't Fragment bit is always set for VoIP RTP packets — fragmentation would add unacceptable reassembly delay and jitter to real-time audio. Any VoIP packet that needs fragmentation indicates an MTU mismatch that should be corrected to avoid audio quality degradation.
