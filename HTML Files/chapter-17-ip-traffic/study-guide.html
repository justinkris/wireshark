💭 THINK FIRST · IPv4 HEADER FIELDS

The IPv4 header is 20 bytes minimum and contains every field a router needs to make a forwarding decision. Every field has a specific job — and knowing what each field does tells you what to look for when a connection misbehaves.

  • What happens when a router receives a packet with TTL=1? What protocol is used to notify the sender, and from what IP does that notification come?
  • What is the purpose of the Protocol field in the IPv4 header, and what values would you expect for TCP, UDP, and ICMP?
Q1 — TTL=1 AND ICMP TIME EXCEEDED
When TTL=1, the router decrements it to 0 and drops the packet. It sends an ICMP Time Exceeded message (type 11, code 0) back to the original source IP. The notification comes from the router's own IP address — not from the destination. This is exactly how traceroute works: by sending packets with deliberately low TTLs (starting at 1), it collects the IP address of each hop in the path via the ICMP Time Exceeded responses.
Q2 — PROTOCOL FIELD VALUES
The Protocol field is an 8-bit field that identifies which Layer 4 protocol is carrying the payload. Common values: TCP=6, UDP=17, ICMP=1, OSPF=89, GRE=47, ESP=50. Wireshark decodes the correct Layer 4 protocol based on this field. If you see an unexpected Protocol field value, it may indicate a tunneling protocol or an unusual application.
Section 1

IPv4 Header Fields

IPv4 (RFC 791) is a connectionless, best-effort delivery protocol with a minimum 20-byte header. Routers read the header to make forwarding decisions; they never examine the payload. Understanding every field is essential for diagnosing routing, fragmentation, and QoS issues.

TTL in the wild Windows sets initial TTL=128, Linux=64, Cisco routers=255. The TTL in a capture tells you roughly how many hops the packet has traveled. A packet arriving with TTL=56 from a Linux host has traversed 64 - 56 = 8 hops.

💭 THINK FIRST · IP FRAGMENTATION

IP fragmentation happens when a packet is larger than the MTU of the path it must traverse. While IP fragmentation is transparent to higher layers, it's expensive — and its appearance in a capture often signals a path MTU problem or misconfiguration.

  • A host sends a 1500-byte IP packet onto a link with an MTU of 576 bytes. What happens? How many fragments are created and what are their approximate sizes?
  • If DF (Don't Fragment) is set on a packet that is too large for a link's MTU, what happens and what does the sender receive back?
Q1 — FRAGMENTATION ON A SMALL MTU LINK
The router fragments the packet. With a 1500-byte packet (20-byte IP header + 1480 bytes data) on a 576-byte MTU: Fragment 1 carries the first 556 bytes of data (576 - 20 byte header = 556 bytes data, offset=0, MF=1). Fragment 2 carries the next 556 bytes (offset=556, MF=1). Fragment 3 carries the remaining 368 bytes (offset=1112, MF=0). The Identification field is the same in all three fragments. The destination reassembles them using Identification + Fragment Offset. If any fragment is lost, the whole datagram must be retransmitted.
Q2 — DF BIT SET AND PACKET TOO LARGE
When DF is set and the packet is too large, the router CANNOT fragment it and drops the packet. The router sends an ICMP Destination Unreachable — Fragmentation Needed (type 3, code 4) back to the sender, including the MTU of the blocking link. The sender should then reduce its packet size to fit within the MTU. This is the basis of Path MTU Discovery (PMTUD). If a firewall blocks ICMP type 3 code 4, PMTUD breaks and the connection "black holes" — it appears to hang indefinitely.
Section 2

IP Fragmentation

Fragmentation occurs when a packet exceeds the link's MTU (Maximum Transmission Unit). IPv4 routers may fragment packets; the destination host reassembles the fragments into the original datagram. Each fragment carries the same Identification value, allowing the receiver to group fragments together.

The three key fields used in fragmentation: Identification (same in all fragments of one datagram), MF flag (More Fragments — set in all fragments except the last), and Fragment Offset (position of this fragment's data in the original datagram, in 8-byte units).

Modern fragmentation practice Modern networks avoid fragmentation by setting the DF bit and using Path MTU Discovery. Fragmentation in a capture often means an MTU mismatch or a VPN adding overhead without reducing the original packet size.
PMTUD black hole Fragmentation + DF bit blocked = PMTUD black hole. Symptom: large transfers hang while small packets (ping) work fine. Fix: allow ICMP type 3 code 4 through firewalls.
🧠
MENTAL NOTE
Fragmentation = ID field same in all fragments, MF=1 (more coming), offset in 8-byte units. DF bit blocks fragmentation; ICMP type 3 code 4 sent if packet too big. PMTUD black hole = ICMP type 3/4 blocked by firewall.

💭 THINK FIRST · DSCP / QUALITY OF SERVICE

The DSCP field lets network devices prioritize certain traffic. Understanding it helps you explain why voice traffic gets priority over downloads, and how to detect QoS mismarking in a capture.

  • A VoIP call is experiencing jitter and delay. You check the packets and find DSCP=0 (Best Effort) on the RTP audio stream. What does this tell you?
  • What is the difference between DSCP and the older ToS (Type of Service) byte? Are they mutually exclusive?
Q1 — DSCP=0 ON VOIP RTP STREAM
DSCP=0 means the RTP packets are being treated as best-effort traffic — the same priority as regular web browsing. VoIP requires low latency and low jitter (EF — Expedited Forwarding, DSCP=46 is the standard marking for real-time voice). If the packets are marked DSCP=0, either the IP phone or PBX is not marking them correctly, or a network device is re-marking (downgrading) them. Fix: ensure the voice endpoint marks RTP with DSCP=46 (EF) and that no device on the path is stripping or changing the DSCP marking.
Q2 — DSCP VS ToS
DSCP (Differentiated Services Code Point) is defined in RFC 2474 and uses the upper 6 bits of the same byte that was historically called the ToS (Type of Service) byte in RFC 791. The lower 2 bits of that byte became the Explicit Congestion Notification (ECN) field in RFC 3168. So DSCP and ToS are not mutually exclusive — they occupy the same 8-bit field, but DSCP redefines how those bits are interpreted. Old ToS used 3 IP Precedence bits (the top 3); DSCP uses 6 bits for finer-grained classification. Wireshark displays this field as "Differentiated Services Field" and shows the DSCP codepoint name (e.g., CS0, AF41, EF).
Section 3

Differentiated Services (DSCP/ToS)

The 8-bit Differentiated Services Field (formerly ToS) allows network devices to classify and prioritize traffic. The upper 6 bits are DSCP (Differentiated Services Code Point); the lower 2 bits are ECN (Explicit Congestion Notification).

💭 THINK FIRST · IPv6 OVERVIEW

IPv6 was designed to solve IPv4's address exhaustion, but it also simplified the header and removed fragmentation from routers entirely. These changes have real implications for what you see — and don't see — in IPv6 packet captures.

  • IPv6 has a simpler, fixed-size header compared to IPv4. What features from the IPv4 header were removed, and why?
  • On a dual-stack host, what triggers IPv6 to be preferred over IPv4 when connecting to a website that supports both?
Q1 — IPv6 HEADER SIMPLIFICATIONS
The IPv6 header is fixed at 40 bytes (no Options field and no Header Checksum). Features removed: Header Checksum (removed because Layer 2 and Layer 4 both have checksums, making a third one redundant and expensive to compute at each hop), IP Options (moved to extension headers which are optional and processed only at endpoints), Fragmentation fields (IPv6 routers do not fragment — only the source host fragments, using a Fragmentation extension header, and only when needed). The fixed header length also removes the IHL field that was needed to account for variable options in IPv4.
Q2 — IPv6 PREFERENCE ON DUAL-STACK HOSTS
On a dual-stack host, the OS uses the Happy Eyeballs algorithm (RFC 6555) and address selection rules (RFC 6724) to prefer IPv6 when both A (IPv4) and AAAA (IPv6) records are available. IPv6 is generally preferred because the OS implementation typically ranks IPv6 Global Unicast addresses above IPv4 in its source/destination address selection policy. In practice, you'll see both A and AAAA DNS queries in the capture, and if the AAAA query returns an address, the SYN is sent to the IPv6 address. If the IPv6 connection attempt fails or is slow, the OS falls back to IPv4 after a short timer.
Section 4

IPv6 Overview

IPv6 uses 128-bit addresses (written in hex as 8 groups of 4 hex digits, e.g., 2001:0db8:85a3::8a2e:0370:7334), providing 2128 addresses. The header is fixed at 40 bytes — simpler and faster to process than the variable-length IPv4 header.

FieldSizePurpose
Version4 bitsAlways 6 for IPv6
Traffic Class8 bitsDSCP + ECN (same as IPv4 DS field)
Flow Label20 bitsIdentifies flows for QoS treatment
Payload Length16 bitsLength of data after the 40-byte header
Next Header8 bitsEquivalent to Protocol field in IPv4
Hop Limit8 bitsEquivalent to TTL; decremented by routers
Source Address128 bitsSource IPv6 address
Destination Address128 bitsDestination IPv6 address

IPv6 address types: Global Unicast (2000::/3, routable on the internet), Link-Local (FE80::/10, auto-configured, scope = single link), Loopback (::1), Multicast (FF00::/8). There is no broadcast in IPv6 — multicast is used instead for all one-to-many communication.

Link-Local addresses Link-Local addresses (FE80::) are automatically assigned and used for neighbor discovery and routing protocols. They should be present on every IPv6-capable interface. You'll often see FE80:: source addresses in NDP traffic.
🧠
MENTAL NOTE
IPv6 = 128-bit addresses, fixed 40-byte header. No fragmentation at routers (source-only). No header checksum. Next Header replaces Protocol field. Hop Limit replaces TTL. Link-Local = FE80::/10 (auto). No broadcast; uses multicast (FF00::/8).

💭 THINK FIRST · FILTERING IP TRAFFIC IN WIRESHARK

IP-level filters let you isolate traffic by address, TTL, fragmentation status, or DSCP marking. Combined with protocol-specific filters, they form the foundation of any targeted analysis.

  • You want to find all packets in a trace that were fragmented (either fragments or original oversized packets). What display filter would you use?
  • A suspect host is using an abnormally low TTL (e.g., TTL=1) on packets it sends. How would you filter for this?
Q1 — FILTER FOR FRAGMENTED PACKETS
Use ip.flags.mf == 1 (packets with More Fragments flag set — all fragments except the last) OR ip.frag_offset > 0 (non-first fragments). To see all packets involved in any fragmentation: (ip.flags.mf == 1) || (ip.frag_offset > 0). The first fragment has offset=0 and MF=1; middle fragments have offset>0 and MF=1; the last fragment has offset>0 and MF=0.
Q2 — FILTER FOR LOW TTL PACKETS
Use ip.ttl == 1 to find packets with TTL=1. An attacker might set a low TTL to limit how far packets travel (so they only affect the local subnet) or to probe the network. Alternatively, filter ip.ttl < 10 to catch unusually low values that suggest traffic that has already traversed many hops or was crafted with a low initial TTL.
