💭 THINK FIRST · THE DHCP DORA PROCESS

DHCP's four-step DORA exchange happens at a special time — before the client has an IP address. Understanding that the client uses 0.0.0.0 as source and 255.255.255.255 as destination for certain steps is key to recognizing normal vs. broken DHCP in Wireshark.

  • Why does the DHCP Request (step 3 of DORA) still broadcast to 255.255.255.255 even though the client already received an Offer?
  • A client sends a DHCP Discover but receives no Offer for 30 seconds, then retransmits. What are three possible causes?
Q1 — WHY DHCP REQUEST IS STILL A BROADCAST
When multiple DHCP servers receive the Discover, they may all send Offers. The client chooses one and must broadcast the Request so all the other servers that made offers see it and know to reclaim their offered IP addresses. If the Request were unicast only to the chosen server, the other servers would never know their offers were rejected and would keep those IPs reserved. The broadcast Request is the mechanism for politely declining the non-chosen servers.
Q2 — THREE CAUSES OF NO OFFER RESPONSE
(1) No DHCP server reachable — the server is down or DHCP port 67 is blocked by a firewall. (2) No DHCP relay agent configured — the client is on a different subnet from the DHCP server but no relay agent is forwarding the client's broadcasts as unicasts to the server. (3) DHCP pool exhausted — all available IP addresses in the scope are already leased and the server cannot offer another address until a lease expires.
Section 1

The DHCP DORA Process

DHCP DORA stands for Discover, Offer, Request, Acknowledge — the four-step exchange that assigns an IP address to a client. The unique challenge: the client has no IP address at the start.

  1. Discover — Client broadcasts UDP from 0.0.0.0 to 255.255.255.255, source port 68, destination port 67. Client has no IP yet. Contains client MAC address (chaddr field).
  2. Offer — Server replies (unicast or broadcast depending on the broadcast flag) offering an IP address with lease time, subnet mask, and other configuration.
  3. Request — Client broadcasts its formal acceptance of the offered IP. Broadcast so all DHCP servers that sent Offers know which one was chosen and can reclaim their reserved addresses.
  4. Acknowledge — Server confirms the lease with full configuration options included.

💭 THINK FIRST · DHCP HEADER FIELDS

The DHCP header carries critical identification fields that tie the four DORA messages together and reveal the network topology. The xid ties all four packets together; the giaddr reveals whether a relay agent is in use — indicating a multi-subnet deployment.

  • You capture DHCP traffic and see a packet with giaddr = 10.10.5.1. What does this tell you about the network topology?
  • How do you filter Wireshark to show only one specific client's complete DORA exchange?
Q1 — WHAT GIADDR REVEALS ABOUT TOPOLOGY
giaddr (Gateway IP Address) being non-zero means a DHCP relay agent is involved — the client is on a different subnet (10.10.5.x probably) from the DHCP server. The relay agent at 10.10.5.1 is forwarding the client's broadcast DHCP messages as unicasts to the DHCP server across subnets. This is the normal enterprise DHCP setup — one central DHCP server serving many subnets via relay agents configured on each subnet's router or layer-3 switch.
Q2 — FILTERING ONE CLIENT'S DORA EXCHANGE
Find any packet from the client's DORA exchange, expand the DHCP header in Wireshark's packet details, and note the xid (Transaction ID) value. Then apply the display filter: dhcp.id == 0xXXXXXXXX where XXXXXXXX is the hex xid value. All four DORA packets (Discover, Offer, Request, ACK) share the same xid value because it is randomly chosen by the client at the start of the exchange and carried through all four steps.
Section 2

DHCP Header Fields

DHCP is based on the older BOOTP protocol. The header carries fixed fields followed by a variable-length options section. Key fields to know for Wireshark analysis:

  • op — Operation code: 1 = client request (BOOTREQUEST), 2 = server reply (BOOTREPLY)
  • htype — Hardware type: 1 = Ethernet
  • hlen — Hardware address length: 6 bytes for MAC
  • xid — Transaction ID: random 32-bit number generated by client, ties all four DORA packets together
  • ciaddr — Client IP address: 0.0.0.0 if client has no address yet
  • yiaddr — "Your" IP address: the IP being offered or assigned by the server
  • siaddr — Server IP address
  • giaddr — Gateway/relay agent IP: nonzero means a relay agent is forwarding this packet
  • chaddr — Client hardware address: the client's MAC address
  • options — Variable-length field carrying all configuration data
xid — the DORA correlation key xid is the key to correlating the DORA exchange in Wireshark. Filter: dhcp.id == 0xXXXXXXXX to isolate one client's complete four-packet exchange. All four steps share the same xid. Display filter for all DHCP traffic: dhcp or bootp.
giaddr in enterprise networks giaddr being non-zero is normal in enterprise networks. It identifies the relay agent, not the client. The client's subnet is revealed by giaddr's address, not the IP packet headers (which show the relay agent's IP as source once the packet crosses the subnet boundary).
🧠
MENTAL NOTE
Key DHCP fields: xid (ties DORA together), yiaddr (offered/assigned IP), chaddr (client MAC), giaddr (relay agent — nonzero = relay in use, enterprise deployment). Display filter: dhcp or bootp. Transaction filter: dhcp.id == 0x[xid]. Discover + Request use 0.0.0.0 source (no address yet).

💭 THINK FIRST · DHCP OPTIONS

DHCP options carry all the network configuration beyond just the IP address — gateway, DNS, domain, lease timers. The message type is itself an option (option 53), which means you can filter for specific DORA steps using that option's value.

  • A laptop gets an IP address but can't reach any websites. Looking at the DHCP ACK's options in Wireshark, what two options would you check first?
  • A client's DHCP Discover contains option 55 (Parameter Request List) listing options 3, 6, 15, and 51. What is it asking for?
Q1 — TWO OPTIONS TO CHECK FOR NO-WEBSITE ACCESS
Option 3 (Default Gateway/Router) and Option 6 (DNS Server). A missing or wrong gateway means the client has no route to reach the internet. A missing or incorrect DNS server means hostnames can't be resolved even if routing is fine. Check yiaddr first to confirm the IP was actually assigned, then verify options 3 and 6 contain valid addresses for your network. These two options cover the most common reason a host gets an IP but can't reach external sites.
Q2 — WHAT OPTION 55 IS REQUESTING
The client is using the Parameter Request List (option 55) to ask the server for: option 3 (Default Gateway), option 6 (DNS Servers), option 15 (Domain Name), and option 51 (Lease Time). The Parameter Request List is the client's wishlist — it tells the server which configuration options the client wants included in the Offer and ACK. The server is not obligated to provide all of them, but will include what it has configured for the scope.

💭 THINK FIRST · TROUBLESHOOTING DHCP

DHCP failures show up as recognizable packet patterns. A client that sends repeated Discovers with no Offer response has a connectivity problem to the server. Multiple Offers for one Discover suggests a rogue DHCP server. Knowing these signatures means you can identify the failure type from the capture within seconds.

  • You see a DHCP Decline packet in your capture. What network event triggered the client to send it?
  • How would you detect a rogue DHCP server using Wireshark?
Q1 — WHAT TRIGGERS A DHCP DECLINE
The client received a DHCP ACK but before using the offered IP, it performed an ARP probe (ARP who-has for that IP address). If another host on the network responded to the ARP probe, the client knows the IP is already in use by another device. The client sends DHCP Decline (option 53 = 4) to tell the server "this address is already in use — don't assign it to me." The server should mark that IP as conflicted and offer a different address on the next Discover. A Decline followed by a new DORA exchange is the normal recovery sequence.
Q2 — DETECTING A ROGUE DHCP SERVER
Filter to DHCP Offer packets: dhcp.option.dhcp == 2. Group by xid value — if you see two different Offer packets with the same xid value, two different DHCP servers responded to the same Discover. Check the "DHCP Server Identifier" (option 54) field in each Offer — the one that doesn't match your legitimate DHCP server's IP is the rogue. The rogue server may be assigning addresses from a different scope, wrong gateway, or no gateway, causing partial or complete connectivity failures for affected clients.
Section 4

Troubleshooting DHCP Failures

Common DHCP failures each produce a distinct packet pattern in Wireshark. Recognizing the pattern immediately narrows the cause.

  1. No server reachable — Repeated Discovers with no Offer response. Filter: dhcp.option.dhcp == 1 and look for retransmissions without subsequent Offers. Causes: server down, port 67 blocked, no relay agent.
  2. NAK (option 53 = 6) — Server rejected the Request. Client receives a NAK and must restart the DORA process. Causes: client tried to renew a lease from a previous VLAN, IP conflict detected, or requested IP is outside the server's pool.
  3. Rogue DHCP server — Multiple Offers for the same xid. Filter: dhcp.option.dhcp == 2, check option 54 (Server Identifier) for unexpected server IPs.
  4. IP conflict (Decline) — Client sends Decline (option 53 = 4) after ARP probe detects the offered IP is already in use. Server must offer a different address.
  5. DHCPv6 — For IPv6 address assignment. Exchange: Solicit → Advertise → Request → Reply. UDP ports 546 (client) and 547 (server). Wireshark filter: dhcpv6.
DHCP NAK — server rejected the request DHCP NAK (option 53 = 6) means the server rejected the client's Request. Common causes: client tried to renew a lease from a previous VLAN, IP address conflict detected, or the client's requested IP is outside the server's configured scope. The client must start the DORA process over from Discover.
Rogue DHCP detection Filter dhcp.option.dhcp == 2 to show only Offer packets. Check option 54 (Server Identifier) in each Offer. Multiple different server IDs for the same xid transaction = rogue DHCP server is present on the network.
🧠
MENTAL NOTE
DHCP failure patterns: No Offer = server unreachable or pool exhausted. Multiple Offers = rogue DHCP (check option 54 Server ID). Decline = ARP conflict (IP already in use). NAK = server rejected (wrong VLAN or expired lease). DHCPv6: UDP 546/547, Solicit → Advertise → Request → Reply.
