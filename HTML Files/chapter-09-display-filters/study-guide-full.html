💡THINK FIRST · DISPLAY FILTER BASICS

Display filters hide packets that don't match — but don't delete them. What are two key workflows where this 'non-destructive' behavior is essential?

HINT

Think about what you'd lose if display filters permanently removed packets like capture filters do.

MODEL ANSWER

(1) Iterative narrowing: apply 'http' to find HTTP traffic, then narrow to 'http.request.method == GET', then further to a specific host — each step just hides more packets; backspace through the filter to widen again. (2) Comparison: filter to see retransmissions in context (surrounding ACKs and data packets visible) rather than in isolation — the 'hidden' packets provide context that capture filters would permanently remove.

Display Filter Basics

Display filters use Wireshark's own filter language (not BPF). They are applied post-capture in the filter bar above the packet list.

  • Green background = valid filter
  • Red background = invalid syntax
  • Yellow background = valid but possibly unintended (e.g. always-true expression)

Applying a filter hides non-matching packets — they remain in the capture file and reappear when you clear the filter (click X in the filter bar or press Ctrl+Shift+F).

Building Filters from the Packet Details

Right-click any field in Packet Details → Apply as Filter or Prepare as Filter. 'Apply' immediately filters; 'Prepare' puts the expression in the filter bar without applying (so you can edit it first).

FASTEST WAYRight-click any field → Apply as Filter. This generates the correct field name and value automatically. Drill into a packet, right-click the field you want to filter on, and Wireshark builds the expression for you.
🧠
MENTAL NOTE
Display filters: non-destructive (hidden, not deleted). Green=valid, Red=invalid, Yellow=suspicious. Right-click field → Apply as Filter = fastest way to build a filter. Clear filter: Ctrl+Shift+F or click X. BPF (capture) vs display filter: completely different syntax.

💡THINK FIRST · SYNTAX AND OPERATORS

Display filter syntax uses field names and comparison operators. What is the difference between '==' and 'contains', and when would you use 'matches' with a regex?

HINT

Think about filtering for a specific string in an HTTP header field. Would '==' work if the field contains more than just the search string?

MODEL ANSWER

'==' requires exact match of the entire field value. 'contains' checks if the field contains a substring — essential for partial matches in HTTP headers, DNS names, and TLS SNI. 'matches' uses PCRE regular expressions for complex pattern matching (e.g. 'http.host matches ".*google.*"' for any Google subdomain). Use '==' for exact fields (IP addresses, port numbers, error codes); 'contains' for string search in variable-length fields; 'matches' for complex patterns.

Existence Test

http.cookie (just the field name alone) — tests if the field exists in the packet, regardless of value.

IMPORTANT TRAPip.addr != 10.1.1.1 does NOT mean 'packets where 10.1.1.1 is not involved'. It means 'packets where at least one address (src OR dst) is not 10.1.1.1'. Almost every packet matches this. Use !(ip.addr == 10.1.1.1) instead to exclude all packets involving that IP.
🧠
MENTAL NOTE
!= trap: 'ip.addr != X' matches any packet where at least one address is not X — nearly everything. Use '!(ip.addr == X)' to truly exclude. 'contains' = substring; '==' = exact match. Existence test: just write the field name alone (e.g. 'http.cookie' = packets with a Cookie header).

Common Display Filters by Protocol

IP / Network Layer

  • ip.addr == 192.168.1.10 — all traffic to/from this IP
  • ip.src == 10.0.0.0/8 — from RFC 1918 range
  • ip.ttl < 10 — low TTL (near hop limit)
  • ipv6 — all IPv6 traffic

TCP

  • tcp.port == 443 — HTTPS (either direction)
  • tcp.flags.syn == 1 and tcp.flags.ack == 0 — SYN only (new connections)
  • tcp.flags.reset == 1 — RST packets
  • tcp.analysis.retransmission — retransmissions
  • tcp.analysis.duplicate_ack — duplicate ACKs
  • tcp.analysis.zero_window — zero window advertisements

HTTP

  • http.request.method == "GET" — HTTP GET requests
  • http.response.code == 404 — 404 responses
  • http.response.code >= 400 — all errors
  • http.host contains "example.com" — requests to a domain

DNS

  • dns — all DNS
  • dns.flags.response == 0 — queries only
  • dns.flags.rcode != 0 — DNS errors (NXDOMAIN, SERVFAIL)
  • dns.qry.name contains "google" — DNS queries for Google

General / Frame

  • frame contains "password" — frame payload contains string
  • frame.len > 1400 — large frames (near MTU)
  • eth.addr == aa:bb:cc:dd:ee:ff — specific MAC address
🧠
MENTAL NOTE
Key filters: tcp.analysis.retransmission (retransmits), tcp.flags.reset==1 (RSTs), http.response.code>=400 (errors), dns.flags.rcode!=0 (DNS failures), frame.contains 'string' (payload search). The '!=' trap: use !(ip.addr==X) not ip.addr!=X to truly exclude a host.

💡THINK FIRST · FILTER BUTTONS AND BOOKMARKS

Wireshark lets you save display filters as buttons in the toolbar. How does having a pre-built filter library change your analysis workflow?

HINT

Think about how long it takes to type 'tcp.analysis.retransmission or tcp.analysis.fast_retransmission or tcp.analysis.spurious_retransmission' from memory vs. clicking a button.

MODEL ANSWER

Pre-built filter buttons turn complex filters into one-click operations. During a live troubleshooting session, speed matters — you want to switch between 'show all TCP errors', 'show retransmissions only', 'show zero-window events' instantly. A filter library also standardizes the team's analysis — everyone uses the same filter expressions, reducing discrepancies between analysts' results.

Filter Buttons and Bookmarks

Save frequently used display filters for quick access:

Filter Bookmarks

Click the bookmark icon (☆) in the filter bar → Save this filter. Give it a name. Saved filters appear in the dropdown when you click the filter bar. Stored in the active profile.

Filter Expression Buttons

In Edit → Preferences → Filter Expressions, add named buttons that appear in the display filter toolbar. Click once to apply. These appear as small buttons below the main toolbar.

Filter Chaining

Right-click a packet → Prepare as Filter → And Selected / Or Selected / And Not Selected. This appends a condition to the existing filter bar expression without clearing it — build complex compound filters incrementally.

ANALYST LIBRARYBuild a personal filter library for your environment: 'TCP problems', 'HTTP errors', 'DNS failures', 'New connections', 'Zero window'. Share via profile export. A well-stocked filter library cuts average triage time significantly.

Review Questions

Q9.1
What is the key difference between a display filter and a capture filter in terms of data retention?
HINT

What happens to packets that don't match each filter type?

ANSWER

Capture filters permanently discard non-matching packets — they are never written to disk and cannot be recovered. Display filters only hide non-matching packets in the UI — all captured packets remain in the trace file and can be revealed by changing or clearing the display filter. Display filters are non-destructive and allow iterative, flexible analysis post-capture.

Q9.2
You want to find all packets where host 10.1.1.5 is NOT involved in the conversation. Write the correct display filter and explain why 'ip.addr != 10.1.1.5' is wrong.
HINT

Consider what 'ip.addr' matches and what != means for a field that can appear as either source or destination.

ANSWER

Correct filter: !(ip.addr == 10.1.1.5). The wrong version: ip.addr != 10.1.1.5 matches any packet where at least one address (src OR dst) is not 10.1.1.5 — which is nearly every packet, including packets where 10.1.1.5 is the source but the destination is different. The '!(' form negates the entire test, correctly excluding all packets where 10.1.1.5 appears in any address field.

Q9.3
Write a display filter to show all HTTP requests using the GET method going to a host containing 'example.com', but only where the response code is 200.
HINT

You need to combine HTTP request fields and HTTP response code — but those are in different packets. How does Wireshark handle this?

ANSWER

For the request: http.request.method == "GET" and http.host contains "example.com". For responses: http.response.code == 200. Wireshark's TCP stream reassembly links request and response — use http.request.method == "GET" and http.host contains "example.com" to find the requests, then use Statistics → HTTP → Requests to see associated response codes, or apply the response filter http.response.code == 200 to see 200 OK responses separately.

Q9.4
What does the display filter 'http.cookie' (with no operator or value) match?
HINT

What is the 'existence test' in Wireshark display filter syntax?

ANSWER

Writing a field name alone (without an operator or value) tests for the existence of that field in the packet. 'http.cookie' matches all HTTP packets that contain a Cookie header field, regardless of the cookie's value. This is useful for finding all authenticated HTTP requests, or filtering on packets that have optional headers present.
