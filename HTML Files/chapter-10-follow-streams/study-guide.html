💭 THINK FIRST · FOLLOW TCP STREAM

Following a TCP stream jumps from individual packets to the complete application conversation. The stream view reveals what two endpoints actually said to each other — including credentials, commands, and error messages invisible at the packet level.

  • You Follow a TCP Stream and see only garbled binary characters instead of readable text. What are two possible causes?
  • You close the Follow TCP Stream window and notice the main packet list is now filtered. What happened, and how do you return to seeing all packets?
Q1 — GARBLED BINARY IN STREAM VIEW
Two causes: (1) The data is encrypted — TLS/SSL-protected connections like HTTPS show ciphertext, which appears as random binary garbage. You cannot read it without decryption keys. (2) The protocol transmits binary data rather than text — file downloads, image transfers, compiled data, or binary protocol formats will show as non-ASCII bytes. Switch the encoding from ASCII to Hex Dump to see the raw bytes, or check whether the protocol is using TLS by looking at the port or the protocol column in the packet list.
Q2 — MAIN WINDOW FILTERED AFTER CLOSING STREAM
When you close the Follow TCP Stream dialog, Wireshark automatically applies the stream filter (tcp.stream eq N) to the main packet list — this keeps your analysis focused on that one conversation. To return to all packets, simply clear the display filter by clicking the X button in the filter bar, or delete the text in the filter bar and press Enter.
Section 1

Follow TCP Stream

Right-click any TCP packet → Follow → TCP Stream. This opens a new window showing the reconstructed application data as readable text. Wireshark reassembles all TCP segments belonging to the same connection and presents the full bidirectional conversation.

The default view shows both directions — client data in red (by default) and server data in blue. You can switch the dropdown to view only one direction. Encoding options: ASCII (text), Hex Dump, EBCDIC, Raw bytes, or C arrays.

When the stream window opens (or closes with "Filter"), Wireshark automatically applies a display filter: tcp.stream eq N — where N is the stream index. This filter is reusable in the main filter bar.

TCP stream filter The TCP stream number tcp.stream eq N is automatically applied as a display filter when you close the stream window with "Filter" — use this to keep your analysis focused on one conversation.
Cleartext credentials and commands In the stream content, look for plaintext credentials, error messages, and application commands — HTTP Basic auth, FTP passwords, SMTP, and many other protocols transmit in cleartext and are fully readable in the Follow Stream view.
🧠
MENTAL NOTE
Follow TCP Stream: right-click → Follow → TCP Stream. Shows reassembled bidirectional data. Red = client, Blue = server (default). Switch view: both/client/server. Filter auto-created: tcp.stream eq N. Shows plaintext app data — HTTP, FTP, SMTP, credentials all visible.

💭 THINK FIRST · FOLLOW UDP STREAM

UDP has no connection state — yet Wireshark still groups related UDP datagrams into "streams" by tracking the four-tuple. Understanding what UDP streaming can and cannot show you sets the right expectations for DNS and TFTP analysis.

  • A DNS query for "evil.example.com" appears in your capture. Using Follow UDP Stream, what would you look for to determine if this is suspicious?
  • You're analyzing a TFTP file transfer. Why is Follow UDP Stream more useful than looking at individual packets?
Q1 — DETECTING SUSPICIOUS DNS IN STREAM VIEW
In the Follow UDP Stream view for a DNS exchange, look for: (1) Unusually large response payloads — DNS responses are typically small; large payloads could indicate DNS tunneling. (2) The response content — does the resolved IP make sense, or does it point to a known malicious IP? (3) Repeated queries or high frequency — a burst of DNS queries for subdomains of the same domain is a classic DNS tunneling signature. (4) Non-standard query types (TXT, NULL records) in the stream's raw content — tunneling tools often abuse TXT records to carry encoded data.
Q2 — FOLLOW UDP STREAM FOR TFTP
TFTP is a block-based file transfer protocol over UDP. Individual packets show only one block of data (typically 512 bytes) plus the protocol header. To see the full file being transferred, you need to see all blocks in sequence. Follow UDP Stream reassembles all TFTP data blocks for the session and presents the file contents in one view — you can then switch the encoding to Raw or Hex to see the actual file bytes, or use File → Export Objects → TFTP to extract the file entirely. Looking at individual packets would require manually reconstructing the sequence of blocks.
Section 2

Follow UDP Stream

Right-click any UDP packet → Follow → UDP Stream. Works similarly to TCP stream but for UDP conversations. UDP has no connection state — Wireshark identifies UDP "streams" by the 4-tuple (source IP, source port, destination IP, destination port).

Follow UDP Stream is especially useful for: DNS (see the full query + response pair), TFTP file transfers, and DNS-over-UDP analysis. The same encoding options (ASCII, Hex, etc.) apply. The stream filter applied is udp.stream eq N.

UDP ordering caveat UDP doesn't guarantee ordering — the Follow UDP Stream view shows datagrams in the order Wireshark received them, which may differ from the order the sender transmitted them if there was reordering in the network.
🧠
MENTAL NOTE
Follow UDP Stream: right-click → Follow → UDP Stream. UDP "streams" identified by 4-tuple. Great for DNS query/response pairs, TFTP, and DNS analysis. No connection state — just packets grouped by address+port. Stream filter: udp.stream eq N. May show out-of-order if network reordered.

💭 THINK FIRST · TLS/SSL STREAM DECRYPTION

TLS decryption in Wireshark requires the right key material — and the method depends on the TLS version. The key log file method works universally, but the RSA private key method is limited to older cipher suites. Understanding why separates confident analysts from those who get stuck.

  • Your colleague set SSLKEYLOGFILE before starting Chrome but forgot to restart Wireshark. The TLS traffic shows as encrypted. What went wrong?
  • A server uses TLS 1.3. Can you decrypt the traffic with the server's private RSA key? Why or why not?
Q1 — KEY LOG FILE NOT BEING USED
Setting SSLKEYLOGFILE before starting Chrome is correct — Chrome writes session keys to that file. But Wireshark also needs to be configured to read that file: go to Edit → Preferences → Protocols → TLS and enter the path in the "(Pre)-Master-Secret log filename" field. If this path isn't set, Wireshark doesn't know the key log file exists even though Chrome is writing to it. The colleague likely set the environment variable but didn't configure Wireshark's TLS preferences to point at the file.
Q2 — TLS 1.3 AND RSA PRIVATE KEY
No — you cannot decrypt TLS 1.3 traffic with the server's RSA private key. TLS 1.3 mandates ephemeral key exchange (ECDHE — Elliptic Curve Diffie-Hellman Ephemeral), which means each session generates a unique ephemeral key pair that is never transmitted over the wire and discarded after the session. The RSA private key is only used for authentication (verifying the certificate), not for key derivation. The only way to decrypt TLS 1.3 is via the SSLKEYLOGFILE/pre-master secret log method, where the browser writes out the session keys itself.
Section 3

TLS/SSL Stream Decryption

Modern HTTPS uses TLS (formerly SSL), which encrypts the stream content. Follow → TLS Stream only shows readable data if Wireshark has decryption keys. Two methods:

  1. Pre-Master Secret Log File (SSLKEYLOGFILE) — set the SSLKEYLOGFILE environment variable in Chrome or Firefox before starting the browser. The browser writes session keys to that file. In Wireshark: Edit → Preferences → Protocols → TLS → set "(Pre)-Master-Secret log filename" to that file. This decrypts HTTPS without the server's private key and works for all TLS versions including TLS 1.3.
  2. RSA Private Key — for RSA key exchange cipher suites only (older TLS, not TLS 1.3+). Add the server's private key in Preferences → Protocols → TLS → RSA Keys list. TLS 1.3 always uses ephemeral key exchange, so this method does NOT work for TLS 1.3.
TLS 1.3 cannot be decrypted with private key RSA private key decryption only works with RSA key exchange cipher suites. TLS 1.3 always uses ephemeral key exchange — the ONLY way to decrypt TLS 1.3 is via the SSLKEYLOGFILE method (pre-master secret log).
🧠
MENTAL NOTE
TLS decryption methods: (1) SSLKEYLOGFILE env var → key log file → Prefs → TLS (works for all TLS including 1.3). (2) RSA private key → Prefs → TLS → RSA Keys (ONLY works for RSA cipher suites, NOT TLS 1.3). Follow → TLS Stream shows decrypted payload after setup. Requires the key before or at capture time.

💭 THINK FIRST · USING STREAMS FOR APPLICATION ANALYSIS

The stream view is where packet analysis meets application forensics. It bridges the gap between network data and application behavior — letting you recover files, find credentials, and understand what the application actually did.

  • During forensic analysis, you want to recover a file that was downloaded over HTTP. What Wireshark feature do you use, and where do you find it?
  • You see in a Follow TCP Stream that an HTTP response starts with "HTTP/1.1 200 OK" followed by what looks like HTML — but also includes a password field. What conclusion do you draw, and what should you report?
Q1 — RECOVERING A FILE FROM HTTP
Use File → Export Objects → HTTP. This feature inspects all HTTP responses in the capture and extracts any embedded objects (HTML pages, images, documents, downloads, scripts) as individual files you can save to disk. It's a core forensics technique for recovering files transferred over unencrypted HTTP. You can also use it for other protocols: File → Export Objects → SMB (Windows file shares), TFTP, FTP-DATA, DICOM, and IMF (email).
Q2 — PASSWORD IN HTTP RESPONSE STREAM
The conclusion is that the application is transmitting sensitive data — specifically a password value — in an HTTP response over an unencrypted connection. This is a serious security vulnerability: the password is exposed to any party that can observe the network traffic (via capture, ARP poisoning, or a man-in-the-middle). You should report: (1) the specific URL and endpoint returning the password, (2) the fact that it's transmitted over HTTP (not HTTPS), (3) a recommendation to encrypt all transmissions containing credentials and to audit what data the API is returning — it should never return passwords in responses.
Section 4

Using Streams for Application Analysis

Streams are the highest-level view of a conversation's data — they reveal what the application actually sent and received. Key analysis uses:

  1. Finding cleartext credentials — look for "Authorization: Basic" in HTTP streams, or "PASS" commands in FTP/SMTP.
  2. Identifying protocol abuse — see if a "DNS" connection is tunneling non-DNS data (large payloads, unusual patterns).
  3. Confirming application errors — HTTP 4xx/5xx response bodies show the exact error message from the server.
  4. Extracting files — File → Export Objects → HTTP extracts images, documents, and downloads. File → Export Objects → FTP-DATA extracts FTP file transfers.
  5. Comparing request/response timing — note timestamps at the start and end of the stream to measure total transaction time.
Export Objects — key forensics technique File → Export Objects → HTTP extracts every HTTP object (images, HTML, scripts, downloads) from the capture as individual files. This is a key forensics technique for recovering files sent over unencrypted HTTP.
🧠
MENTAL NOTE
Key stream analysis uses: cleartext credentials (HTTP Basic Auth, FTP PASS), protocol tunneling detection (DNS with large payloads), HTTP error body inspection, file extraction (File → Export Objects → HTTP/FTP-DATA). Stream reveals what app actually exchanged — not just headers.
