💭 THINK FIRST · NETWORK FORENSICS OVERVIEW

Network forensics differs from log analysis in one critical way: packet captures contain the verbatim bytes exchanged — the payload, not just the metadata. This completeness makes captures powerful evidence but also creates storage and privacy challenges at scale.

  • An investigator has only NetFlow logs showing the attacker connected to a database server on port 5432. Can they determine what SQL queries were executed? Why or why not?
  • Why is it critical to work on a copy of the capture file and never the original?
Q1 — NETFLOW VS FULL PACKET CAPTURE FOR SQL QUERIES
No. NetFlow records only the 5-tuple (source IP, source port, destination IP, destination port, protocol) plus byte counts and timestamps — it's metadata, not payload. To see SQL queries, you need full packet capture (pcap/pcapng) which contains the actual PostgreSQL (or other database) protocol data. With full packet capture and the right protocol dissector, you can Follow TCP Stream and read the actual query text. NetFlow can prove A connected to B on port 5432 and transferred X bytes at time T — but not what was queried, what data was returned, or whether authentication succeeded.
Q2 — WHY WORK ON A COPY
Two reasons. First, forensic integrity: any write operation to the original (even Wireshark adding a comment) changes the file's SHA-256 hash, making it impossible to prove the evidence was unaltered from the time of seizure. Defense attorneys can challenge evidence that doesn't match its original hash. Second, accidental corruption: analysis tools crash, disks fail, and operations go wrong. Working on the original risks permanent loss of irreplaceable evidence. Always copy first, hash both the original and copy, verify they match, then work only on the copy.
Section 1

Network Forensics Overview

Network forensics is the capture and analysis of network traffic as security investigation evidence. Unlike logs (summarized metadata), packet captures contain verbatim bytes including payloads, credentials, and commands. They can answer: What was communicated? Who communicated? When? What data was exfiltrated?

Forensics workflow:

  1. Identify — recognize that an incident may have occurred.
  2. Preserve — collect and protect evidence before it is lost or overwritten.
  3. Analyze — reconstruct events from captured data.
  4. Document — create defensible, reproducible findings.

Full pcap vs NetFlow: pcap = headers + payload (complete record of what was communicated); NetFlow = 5-tuple + byte counts (metadata only — proves who talked to whom and when, not what was said).

Know what evidence type you have before drawing conclusions Full packet capture contains payload data but requires significant storage. NetFlow contains only metadata. Know which you're working with before concluding what evidence is available — the difference determines whether you can read content or only connection records.
🧠
MENTAL NOTE
Network forensics = verbatim network evidence. Full pcap = complete (headers + payload). NetFlow = metadata only (5-tuple + bytes). Forensics workflow: Identify → Preserve → Analyze → Document. Packet captures can prove what was said (payload visible); NetFlow can only prove who talked to whom and when.

💭 THINK FIRST · EVIDENCE PRESERVATION

Evidence handling errors can make forensic findings inadmissible or legally challengeable. The hash of a file before and after analysis, the chain of custody documentation, and working only on copies are not bureaucratic requirements — they are what makes your findings defensible in court or an internal investigation.

  • After hashing a forensic capture, a colleague adds a Wireshark packet comment and saves. What happened to the SHA-256 hash, and what does this mean for evidence integrity?
  • A forensic capture shows all events occurring at 3:00 AM local time, but the incident is suspected to have happened at 9:00 AM. What should you investigate?
Q1 — WIRESHARK COMMENT CHANGES SHA-256 HASH
Adding a comment and saving modifies the file — even one bit change produces a completely different SHA-256 hash. The modified file's hash will not match the original hash documented at seizure. This means it's now impossible to prove the file is the same as when it was collected. Defense counsel can argue the evidence was tampered with (even if accidentally). In forensic practice: never work on the original file; keep the original read-only; work on a verified copy; any changes made during analysis are to the working copy, not the original.
Q2 — TIMESTAMP DISCREPANCY INVESTIGATION
Investigate the capture machine's clock accuracy. The timestamp in a packet capture is set by the capturing machine's system clock — if that clock was wrong, all timestamps are wrong. Check: was the capture machine synced to NTP? Is there a known clock offset? Was the time zone configured correctly? If the machine's clock was 6 hours slow (off by -6 hours), events that happened at 9:00 AM would appear as 3:00 AM. Document the clock offset in your forensic report so timestamps can be corrected during analysis, and note the limitation explicitly.
Section 2

Evidence Preservation and Chain of Custody

Evidence preservation requirements for forensically sound analysis:

  1. Copy first — never analyze the original. Compute SHA-256 of the original capture file BEFORE analysis. Make a working copy and verify its hash matches the original.
  2. Write protection — use read-only file permissions or physical write blockers on original media to prevent accidental modification.
  3. Chain of custody — document every person who accessed the evidence: who, when, what they did, and where the file was stored at each step.
  4. Timestamp verification — Wireshark timestamps reflect the capture machine's system clock. Verify NTP sync status and document any known clock offset.
  5. Metadata recording — document the capture interface, OS, capture filter used, Wireshark version, and the date/time the capture was collected.
Never analyze the original capture file If you analyze the original capture and Wireshark makes any write operation (adding a comment, saving preferences with the file open), you've modified the evidence file and changed its hash. Always work on a verified copy. Store the original as read-only and document the SHA-256 hash before any analysis begins.
🧠
MENTAL NOTE
Evidence handling: Copy first → hash both (SHA-256) → verify match → work on copy only. Never modify original. Chain of custody: who, when, what, where. Capture timestamps = capture machine's clock (verify NTP, document offset). Metadata: interface, OS, filter, Wireshark version, date/time. SHA-256 mismatch = evidence integrity broken.

💭 THINK FIRST · SESSION RECONSTRUCTION

Packet captures contain everything needed to reconstruct what happened — not just that a connection occurred, but exactly what was exchanged, what commands were run, and what files were transferred. The reconstruction techniques range from simple (Follow Stream) to sophisticated (Export Objects, timeline assembly).

  • You believe a user downloaded malware via HTTP. What Wireshark feature extracts that file from the capture?
  • A Telnet session between two hosts is captured. How would you reconstruct the exact commands the attacker typed?
Q1 — EXTRACTING MALWARE DOWNLOADED VIA HTTP
File → Export Objects → HTTP. Wireshark reassembles all HTTP response bodies from the TCP stream and presents them as individual objects (files). You can see the URL, content type, file size, and filename for each object. Select the suspicious download and click "Save As" to extract the file for malware analysis. The extracted file is the actual bytes that were transferred — suitable for hash comparison against malware databases or for submission to a sandbox.
Q2 — RECONSTRUCTING TELNET SESSION COMMANDS
Right-click any Telnet packet → Follow → TCP Stream. Since Telnet transmits everything in cleartext (including keystrokes and their echoes), the stream window shows the full terminal session: every command typed, every response displayed. In the stream view, client-to-server (red by default) shows keystrokes; server-to-client (blue) shows responses and echoes. You can reconstruct the exact sequence of commands, any files accessed, any credentials used, and any output the attacker received — all from the raw packet data.
Section 3

Session and Data Reconstruction

Reconstruction techniques from packet captures:

  1. TCP session reconstruction — Follow TCP Stream (right-click any packet in the session → Follow → TCP Stream) shows the complete bidirectional conversation as reassembled text.
  2. File extraction — File → Export Objects → HTTP / FTP-DATA / SMB / TFTP / IMF extracts reassembled transferred files directly from the capture.
  3. Credential harvesting — Follow TCP Stream for plaintext protocols (FTP, HTTP Basic Auth, Telnet, SMTP) reveals credentials in the stream output.
  4. Command reconstruction — for Telnet, HTTP POST to web shells, or similar, Follow Stream reads the exact commands and responses exchanged.
  5. Timeline reconstruction — use absolute timestamps to order events chronologically. Statistics → Flow Graph visualizes the conversation sequence and timing.
  6. DNS reconstruction — filter dns to find all domain lookups — reveals C2 domains, data exfiltration channels, and attacker infrastructure.
File → Export Objects: your first tool after identifying a suspicious session It extracts every transferred file — malware downloads, exfiltrated documents, configuration uploads — without manually decoding packets. Supports HTTP, FTP-DATA, SMB, TFTP, and IMF (email). The extracted bytes are the actual transferred content.
🧠
MENTAL NOTE
Reconstruction order: Follow TCP Stream (read session) → Export Objects (extract files) → DNS filter (find C2 domains) → Flow Graph (visualize exchange) → Absolute timestamps (build timeline). Plaintext protocols: FTP PASS, HTTP Basic, Telnet = credentials visible in Follow Stream. File extraction: File → Export Objects → HTTP/FTP-DATA/SMB.

💭 THINK FIRST · ATTACKER IDENTIFICATION

Network forensics can provide behavioral evidence of an attack, but IP-based attribution is inherently unreliable. IPs can be spoofed, attacks can originate from compromised hosts, and VPNs/proxies obscure real origins. Focus on behavioral patterns and technical artifacts rather than "the attacker was at IP X."

  • A capture shows an attack originating from a Chinese IP address. Can you conclude the attacker is in China?
  • Two packets in the same capture appear to come from the same IP but have completely different TCP SYN option sets. What might this indicate?
Q1 — IP GEOLOCATION AND ATTRIBUTION LIMITS
No. IP geolocation only tells you where an IP address is registered — not where the person controlling it is physically located. The attacker might be: (a) using a VPN server or proxy located in China while physically elsewhere; (b) using a compromised Chinese server as a stepping-stone (the real attacker is unknown); (c) using IP spoofing. Geolocation is indicative at best. Behavioral evidence (what was done, what vulnerabilities were exploited, what tools were used) is more forensically meaningful than source IP location.
Q2 — DIFFERENT TCP SYN OPTIONS FROM THE SAME IP
Different TCP SYN option sets from the same IP address suggest different operating systems generated those packets — unusual if both came from the same genuine source. Possible explanations: (a) IP spoofing — different hosts are forging the same source IP; (b) different hosts behind a NAT device sharing one public IP; (c) a virtual machine rebooted with a different OS configuration between packets; (d) an attacker switching tools or platforms mid-session. Passive OS fingerprinting from TCP SYN options (window size, option order, MSS values) can characterize the true sender and reveal inconsistencies in claimed identity.
Section 4

Attacker Identification Techniques

Attacker identification in packet captures uses multiple signals, each with different reliability:

  1. Source IP and MAC — starting point only. IPs may be spoofed; MACs are only reliable on the local segment (rewritten at each router hop).
  2. Passive OS fingerprinting — TCP SYN options reveal the OS without sending active probes: MSS value, Window Scale factor, SACK support, Timestamps option, and the order of options together create an OS signature. Initial window size is also a strong indicator.
  3. HTTP User-Agent — reveals the claimed OS and browser/tool. Can be spoofed but often isn't, especially by automated attack tools.
  4. Behavioral patterns — what ports targeted, what protocols used, what data accessed, attack timing, scan patterns, and tool signatures are often more reliable than IP identity.
  5. DNS lookups — what domains did the attacker contact, revealing C2 infrastructure and attacker-controlled resources.
  6. Timing analysis — when attacks occurred (active hours) can infer approximate timezone.
Source IP does not prove attacker identity IPs can be spoofed, relayed through proxies, or originate from compromised hosts. Focus on behavioral evidence (what was done, in what sequence, with what tools) over location evidence (where the packets say they came from). Behavioral signatures are far harder to fake than source addresses.
🧠
MENTAL NOTE
Attacker ID: Source IP = starting point (can be spoofed). MAC = local segment only. TCP SYN options → passive OS fingerprint (window size + option order + MSS). User-Agent = claimed client (can be spoofed). Behavioral signatures = most reliable. DNS = what domains contacted. Timing = timezone inference. Never over-rely on IP attribution alone.
