    Chapter 30: Network Forensics

    Chapter 30 covers network forensics — using Wireshark to investigate security incidents by reconstructing attacker activity, extracting transferred files, recovering credentials, and building a timeline of events from packet captures.

    Guided Analysis — Forensic Investigation
    Concept — Q1
    What is the first step in a network forensics investigation when you receive a packet capture? What metadata should you document before beginning analysis?
    First, verify capture integrity — check if the pcap was generated from a trusted source and document its chain of custody for any legal proceedings. Metadata to document: capture start/end time (UTC), capture point location, interface, capture filter applied, total packet count, and file hash (MD5/SHA256). Then open Statistics > Summary to get the high-level picture before diving into packet-level analysis.
    Concept — Q2
    How would you use Wireshark to extract a file that was transferred via HTTP during a security incident? Walk through the steps.
    (1) Apply filter http. (2) Find the HTTP GET request for the file and the corresponding 200 OK response. (3) Go to File > Export Objects > HTTP. Wireshark lists all HTTP objects (files) transferred in the trace. (4) Select the file and save it. You can then analyze it with antivirus or a sandbox. Alternatively, use Follow TCP Stream and save the raw stream to reassemble the file manually.
    Concept — Q3
    During a forensic investigation, you find DNS queries to unusual domains. What filter helps identify potential DNS-based C2 (command-and-control) traffic? What characteristics of DNS queries suggest malicious use?
    Filter: dns.qry.name to examine all queried domains. Suspicious characteristics: (1) High query volume for randomly-named domains (DGA — Domain Generation Algorithm). (2) Unusually long domain names (>50 characters, often used for DNS tunneling). (3) Queries for TXT record types (dns.qry.type == 16) — often used for C2 data exfiltration. (4) Very high TTL responses allowing long-lived C2 connections.
    Optional Traces
    sec-strangescan.pcapng
    Apply filter tcp.flags.syn==1 && tcp.flags.ack==0 to see SYN packets (scan probes). Look at the destination ports — are they sequential (port scan) or random? Count unique destination IPs.
    Any trace — credential extraction
    Apply ftp || smtp || pop || http.authorization to find clear-text authentication. Use Follow TCP Stream on each result to see if credentials are visible. Document any findings.
    Any trace — timeline reconstruction
    Sort by time. Use Edit > Find Packet (Ctrl+F) to search for string patterns in packet data. Try searching for 'password', 'login', 'cmd', 'shell'. Note the timestamps of any findings to build an attack timeline.
    Review Questions
    Review Q30.1
    What Wireshark feature allows you to extract files transferred via HTTP from a capture file?
    File > Export Objects > HTTP. This opens a list of all HTTP objects in the capture, showing filename, content type, size, and the host that served each file. You can save individual files or all files at once. For other protocols: File > Export Objects > SMB (for Windows file shares) or FTP-DATA (for FTP transfers).
    Review Q30.2
    What characteristics in a DNS trace suggest DNS tunneling is occurring?
    DNS tunneling indicators: (1) Unusually long subdomain labels (base64-encoded data embedded in queries). (2) High volume of TXT record queries (dns.qry.type == 16). (3) Large DNS response sizes (>500 bytes). (4) Consistent query intervals (automated beaconing). (5) Queries to a single authoritative server for a rarely-seen domain. Apply dns && frame.len > 100 to find abnormally large DNS packets.
    Review Q30.3
    What is the Wireshark filter to find all TCP connections that were reset (abrupt termination), and why might this matter forensically?
    tcp.flags.reset == 1. Forensically, RSTs from a server IP indicate: port scan results (RST/ACK = port closed, no SYN-ACK = filtered). RSTs from an unknown IP mid-session suggest a TCP injection attack or IDS actively terminating connections. A sudden burst of RSTs from a previously quiet IP could indicate an attacker probing services or an IDS responding to detected malware.
