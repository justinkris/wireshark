💡THINK FIRST · PURPOSE OF CAPTURE FILTERS

Capture filters run in the OS kernel before Wireshark sees a packet. Why does this fundamentally differ from display filters, and what is the major tradeoff?

HINT

Once a packet is captured, can you 'uncapture' it? What happens to a packet that doesn't match each type of filter?

MODEL ANSWER

Capture filters use BPF evaluated in the kernel at wire speed — unmatched packets are discarded immediately, never written to disk. This dramatically reduces CPU, memory, and storage overhead. The tradeoff: captured traffic is permanent. Packets excluded by a capture filter are gone forever — you can't go back and see them. Display filters, by contrast, only hide packets in the UI; all captured packets remain on disk and can be revealed again.

What Capture Filters Do

Capture filters are BPF (Berkeley Packet Filter) expressions evaluated by the OS kernel. Only packets matching the filter reach Wireshark. Unmatched packets are discarded at wire speed.

Unlike display filters (which are post-capture), capture filters are permanent — you cannot change them mid-capture and cannot recover filtered-out packets.

KEY LIMITATIONCapture filters cannot be changed mid-capture. You must stop, clear, and restart with a new filter. Plan before starting. If unsure what to filter, capture everything and use display filters later.
WHEN TO USEUse capture filters when: (1) the link is fast and dropping packets without filtering; (2) you only need a specific protocol or host; (3) disk space is limited. Use display filters when you need the full picture for flexible post-capture analysis.
🧠
MENTAL NOTE
Capture filters = BPF in kernel = permanent exclusion. Display filters = UI-only = all packets still on disk. Cannot change capture filter mid-capture. Capture filters improve performance; display filters provide flexibility.

💡THINK FIRST · BPF SYNTAX BASICS

BPF primitives have three qualifier types. Given the expression 'dst port 443', identify each qualifier and what happens if you omit the direction qualifier.

HINT

Consider: 'port 443' without 'dst' — does it match traffic going to port 443, from port 443, or both?

MODEL ANSWER

'dst' is the direction qualifier, 'port' is the type qualifier, '443' is the ID. Without the direction qualifier, BPF matches both source AND destination — 'port 443' matches packets going to port 443 AND packets coming from port 443 (i.e., server responses). Without a protocol qualifier, BPF applies to all protocols that use ports (TCP and UDP). So 'port 443' matches both TCP and UDP port 443 in both directions.

BPF Syntax Basics

BPF primitives follow the pattern: [proto] [direction] type id

Type Qualifiers

  • host — single IP/hostname: host 192.168.1.10
  • net — subnet: net 10.0.0.0/8
  • port — single port: port 443
  • portrange — port range: portrange 1024-65535

Direction Qualifiers

  • src — source only
  • dst — destination only
  • (omitted) — match src OR dst

Protocol Qualifiers

  • ether — Ethernet (MAC addresses)
  • ip / ip6 — IPv4 or IPv6
  • tcp / udp / icmp / arp

Special Keywords

  • broadcast / multicast
  • less N / greater N — packet size comparison
🧠
MENTAL NOTE
BPF primitive: [proto] [direction] type id. Omit direction = both src and dst. Omit proto = all protocols using that type. 'port 80' matches TCP and UDP port 80 in both directions. 'tcp port 80' matches only TCP. 'dst port 80' matches only traffic going to port 80.

💡THINK FIRST · COMBINING FILTERS

BPF operator precedence: not > and > or. What does 'host 10.1.1.1 and port 80 or port 443' actually match? How do you fix it?

HINT

Apply the precedence rules step by step: which operators bind first?

MODEL ANSWER

Precedence evaluation: 'and' binds before 'or', so the expression parses as '(host 10.1.1.1 and port 80) or (port 443)'. This captures: all traffic to/from 10.1.1.1 on port 80, PLUS all traffic on port 443 from any host. That's almost certainly not the intent. Fix: parenthesize — 'host 10.1.1.1 and (port 80 or port 443)' — now both ports are restricted to the specified host.

Combining Capture Filters

Combine primitives with boolean operators:

  • and (&&) — both must match
  • or (||) — either matches
  • not (!) — negate

Operator Precedence (highest first)

  1. not
  2. and
  3. or

Always use parentheses when mixing and and or.

Examples

  • tcp and dst port 80 — TCP to port 80
  • host 10.1.1.1 and not port 22 — all traffic to/from host except SSH
  • src net 192.168.0.0/16 and (dst port 80 or dst port 443) — web from private net
  • not broadcast and not multicast — unicast only
PRECEDENCE TRAPhost X and port 80 or port 443 captures port 443 from ANY host, not just X. Always write: host X and (port 80 or port 443)
🧠
MENTAL NOTE
BPF precedence: not > and > or. Common bug: 'host X and port A or port B' — the 'or port B' matches all hosts. Fix: always parenthesize 'or' groups. Use parentheses liberally — they are free and prevent subtle mistakes.

Review Questions

Q4.1
What is the fundamental difference between a capture filter and a display filter?
HINT

Think about when each runs and what happens to packets that don't match.

ANSWER

A capture filter runs in the OS kernel before packets are stored — unmatched packets are permanently discarded and never appear in the trace file. A display filter runs in the Wireshark UI after capture — unmatched packets are hidden but remain in the capture file and can be revealed by changing or clearing the filter. Capture filters reduce file size and CPU load; display filters provide flexible post-capture analysis without data loss.

Q4.2
Write a BPF filter that captures TCP traffic to/from host 10.1.2.3 on ports 80 or 443, excluding SSH.
HINT

Use parentheses. What is the precedence trap here?

ANSWER

host 10.1.2.3 and tcp and (port 80 or port 443) and not port 22. Without parentheses around 'port 80 or port 443', the expression would be parsed as '(host 10.1.2.3 and tcp and port 80) or (port 443) and (not port 22)' — capturing port 443 from all hosts, not just 10.1.2.3.

Q4.3
What does 'not broadcast and not multicast' capture?
HINT

What traffic types are excluded by broadcast and multicast?

ANSWER

Only unicast traffic — one-to-one communication. Excluded: Ethernet broadcast (ff:ff:ff:ff:ff:ff), IP broadcast (255.255.255.255 or subnet broadcast), Ethernet multicast (01:xx:xx:xx:xx:xx OUI), IP multicast (224.0.0.0/4). Useful for reducing noise dominated by ARP broadcasts, DHCP, and routing protocol multicast.

Q4.4
You start a capture with 'port 80' but realize you also need UDP port 5353. What must you do?
HINT

Can you modify a capture filter mid-capture?

ANSWER

No — capture filters cannot be modified while running. Stop the capture (saving it if needed), update the filter to 'port 80 or (udp port 5353)', and start a new capture. mDNS traffic that occurred during the first capture is permanently lost if it wasn't matched. This is why it's often better to start with no capture filter and use display filters post-capture unless performance requires filtering.
