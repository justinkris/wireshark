💭 THINK FIRST · WHAT CAPTURE FILTERS DO

Capture filters and display filters solve different problems — one works before packets hit disk, the other works after. They use completely different syntax, and confusing them is one of the most common Wireshark mistakes. Think about the tradeoffs of filtering at capture time vs at display time.

  • You apply a capture filter for only TCP port 80. Later, you discover the failure you were troubleshooting was caused by a DNS resolution issue. What did you lose, and what does this tell you about aggressive capture filtering?
  • Why do capture filters use BPF syntax while display filters use Wireshark's own filter language? What does each language need to be optimized for?
Q1 — OVER-FILTERING AND LOST CONTEXT
You lost the DNS packets entirely — they were never captured. Filtering for only port 80 means all DNS traffic (port 53), ARP broadcasts, and any other protocol traffic is permanently discarded at capture time. If the web connection failed because DNS returned NXDOMAIN, a wrong IP, or timed out, you have no evidence of that in your capture file. This illustrates the core tradeoff of capture filtering: less data means faster analysis and smaller files, but if your filter assumption is wrong, you may miss the root cause entirely. The lesson: use capture filters when you are confident about the protocol causing the issue. For unknown problems, capture broadly (no filter or a wide one like a subnet), and use display filters to narrow your focus during analysis.
Q2 — WHY TWO DIFFERENT FILTER LANGUAGES
BPF (Berkeley Packet Filter) for capture filters is designed for kernel-level performance — it runs in the OS kernel or NIC driver before packets even reach Wireshark, so it must be extremely fast and low-overhead. BPF uses simple byte-level matching operations on raw packet bytes (offsets, masks, comparisons) that the kernel can execute with minimal overhead. Wireshark's display filter language, by contrast, runs in userspace after packets are fully decoded. It can reference named protocol fields (ip.addr, tcp.flags.syn, http.response.code) because Wireshark has already decoded the packet layers. It can express complex multi-field conditions that would be impractical in BPF. The two languages solve fundamentally different problems: BPF = fast pre-capture triage, Wireshark filters = rich post-capture analysis.
Section 1

What Capture Filters Do

Capture filters are applied during the capture process — packets that don't match are never written to the capture buffer. This differs from display filters (Chapter 9), which hide packets after they're captured but keep them in the file. Capture filters use Berkeley Packet Filter (BPF) syntax, not Wireshark display filter syntax. Using capture filters reduces: (1) file size, (2) CPU overhead, (3) packet drops on busy links. The tradeoff: if you filter too aggressively, you may miss context (e.g., filtering only TCP port 80 might miss the DNS query that caused a failure).

Different syntax — do not mix them up Capture filters and display filters use DIFFERENT syntax. A display filter ip.addr == 192.168.1.1 will not work as a capture filter. The capture filter equivalent is host 192.168.1.1.
🧠
MENTAL NOTE
Capture filter = BPF syntax, applied during capture, packets not matching are DISCARDED. Display filter = Wireshark syntax, applied after capture, packets hidden but kept. Trade-off: aggressive filtering may lose context. Reduce volume on busy links with capture filters.

💭 THINK FIRST · BPF SYNTAX BASICS

BPF primitives are minimal but composable — just a handful of keywords cover the vast majority of real-world scenarios. Before reading the reference table, try to write the BPF expression for: all traffic to or from 10.0.0.1, and all ICMP traffic excluding your own IP.

  • Write a BPF capture filter to capture only traffic between hosts 10.1.1.1 and 10.1.1.2 on TCP port 443. Think through the logic before checking.
  • What is the difference between port 80 and tcp port 80 as a BPF capture filter?
Q1 — FILTER FOR TWO HOSTS ON HTTPS
The filter is: host 10.1.1.1 and host 10.1.1.2 and tcp port 443. This combines three primitives with "and": both host conditions must be true (traffic must involve both IPs — not just either one), and the port must be 443 TCP. The "host A and host B" combination is the standard BPF idiom for a conversation between exactly two specific hosts, since "host A" alone would include traffic from A to any destination. Alternatively you could write: (host 10.1.1.1 and host 10.1.1.2) and tcp port 443 — parentheses make the grouping explicit and are recommended for clarity when mixing operators.
Q2 — port 80 VS tcp port 80
port 80 matches any packet with source or destination port 80 regardless of transport protocol — it would match both TCP port 80 (HTTP) and UDP port 80 (theoretically possible, though rare in practice). tcp port 80 explicitly restricts the match to TCP only — UDP packets on port 80 are excluded. In most practical scenarios the difference is academic (port 80 is almost always TCP HTTP), but for ports like 53 (DNS) which genuinely uses both TCP and UDP, the difference matters: port 53 captures both UDP DNS queries and TCP DNS transfers, while tcp port 53 would miss the common UDP queries entirely. Best practice: be explicit — use tcp port N or udp port N rather than bare port N.
Section 2

BPF Syntax Basics

BPF expressions use primitives and can be combined with operators. Key primitives: host X (traffic to/from IP or hostname X), src host X (source only), dst host X (destination only), port N (traffic on TCP or UDP port N), src port N, dst port N, net X.X.X.X/N (traffic in subnet), proto X (protocol: tcp, udp, icmp, arp, ip, ip6), ether host XX:XX:XX:XX:XX:XX (MAC address).

💭 THINK FIRST · COMBINING CAPTURE FILTERS

Boolean operator precedence is a subtle but critical detail — writing not host A or host B does not mean "neither A nor B." Operator precedence determines which subexpression gets negated. Think through the precedence rules before reading.

  • What does not host 10.0.0.1 or host 10.0.0.2 actually capture, given BPF precedence rules? Is it the same as not (host 10.0.0.1 or host 10.0.0.2)?
  • Write a BPF filter that captures all TCP traffic from the 192.168.0.0/16 subnet going to port 53 (DNS over TCP). What does this tell you that a simpler filter could not?
Q1 — PRECEDENCE TRAP WITH NOT OR
Due to BPF operator precedence (not > and > or), the expression not host 10.0.0.1 or host 10.0.0.2 is parsed as (not host 10.0.0.1) or host 10.0.0.2. This means: capture packets that are either NOT from/to 10.0.0.1, OR that are from/to 10.0.0.2. In practice this captures almost everything — any packet not involving 10.0.0.1 passes the first condition. This is NOT the same as not (host 10.0.0.1 or host 10.0.0.2), which correctly means: capture traffic involving neither host. This is exactly why parentheses are essential: never rely on implied precedence when combining not with or. Always parenthesize: not (host A or host B).
Q2 — TCP DNS FROM SUBNET
The filter is: src net 192.168.0.0/16 and tcp dst port 53. This captures TCP DNS queries (not UDP) originating from the local subnet going to port 53 on any destination. What this reveals that a simpler filter cannot: TCP DNS is used for zone transfers and for large DNS responses that exceed 512 bytes (DNSSEC records, long TXT records). Seeing TCP on port 53 from internal hosts is interesting — it means DNS responses were too large for UDP, which could indicate DNSSEC is in use or that something is generating oversized DNS responses. A bare port 53 filter would include both TCP and UDP and both directions, making it harder to isolate this specific pattern.
Section 3

Combining Capture Filters

Filters are combined using boolean operators: and (or &&) — both conditions must be true; or (or ||) — either condition must be true; not (or !) — condition must be false. Parentheses group sub-expressions. Order of precedence: not > and > or. Always use parentheses to be explicit when mixing operators.

💭 THINK FIRST · COMMON CAPTURE FILTER PATTERNS

Real-world capture filters are rarely invented from scratch — experienced analysts reuse a core set of patterns. Before reading, try to write the BPF filter for: "capture only traffic between my host and a specific server, excluding SSH."

  • You're monitoring a VoIP system that uses SIP (port 5060) and RTP (ports 16384–32767). Write a single BPF filter that captures both protocols.
  • Why would you use not broadcast and not multicast as a baseline capture filter on a busy LAN, and what types of traffic does it remove?
Q1 — SIP + RTP VOIP CAPTURE FILTER
The filter is: port 5060 or portrange 16384-32767. The portrange primitive is the correct BPF way to match a contiguous range of ports — it's far more efficient than writing individual port N or port N+1 or ... expressions. SIP on port 5060 handles call signaling (INVITE, BYE, REGISTER, OPTIONS). RTP carries the actual audio/video stream on dynamically negotiated ports, typically in the 16384–32767 range (varies by implementation; some use 49152–65535). Without the portrange, you'd see SIP signaling but miss the actual media stream entirely, making it impossible to diagnose audio quality or RTP packet loss.
Q2 — NOT BROADCAST AND NOT MULTICAST
On a busy LAN, a significant fraction of traffic is Layer 2 broadcasts (destination MAC ff:ff:ff:ff:ff:ff) and multicast frames. Broadcasts include ARP requests, DHCP discovery/requests, NetBIOS/SMB announcements, Windows browser elections, and various discovery protocols (SSDP, mDNS). Multicast includes OSPF, PIM, IGMP, and application-layer multicast streams. On a busy enterprise LAN, these can account for thousands of packets per minute while contributing zero value to diagnosing a specific application problem. Removing them with not broadcast and not multicast dramatically reduces capture volume and makes the remaining unicast traffic much easier to analyze. The tradeoff: if ARP or DHCP is actually part of the problem, you'd miss it — so use this filter only when you're confident the issue is unicast-based.
