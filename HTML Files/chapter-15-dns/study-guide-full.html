💭 THINK FIRST · DNS PURPOSE & TRANSPORT

DNS converts symbolic host names to IP addresses — but it can do much more: inverse lookups (IP to name), MX record lookups, zone transfers between servers. It runs over UDP port 53 for most queries but switches to TCP when responses exceed 512 bytes.

  • Why does DNS use UDP by default instead of TCP? Under what specific condition does it fall back to TCP, and what happens in the packet flow when it does?
  • What is Multicast DNS (mDNS) and why would a small network use it instead of a traditional DNS server?

Model Answer 1: DNS uses UDP because most queries and responses are small and speed matters more than guaranteed delivery — a failed DNS lookup just results in a retry, not a broken stream. UDP avoids the TCP handshake overhead. When a response exceeds 512 bytes (the RFC 1035 payload limit), the DNS server sets the truncation flag bit in the response. The client's resolver sees the truncated flag and immediately retransmits the exact same query over TCP, which allows for larger payloads. You'd see the UDP query, a truncated UDP response, then a TCP connection and the full response.

Model Answer 2: mDNS (Multicast DNS) provides name resolution without a central DNS server by using multicast group 224.0.0.251 (or FF02::FB for IPv6). Any host can respond to a query for its own name. This is ideal for small home or office networks where setting up and maintaining a DNS server would be overkill. mDNS names end with .local — those queries are never forwarded to a regular DNS server.

The Purpose of DNS

DNS is used to convert symbolic host names, such as www.wiresharktraining.com, to IP addresses. DNS can also be used to transfer name information between DNS servers, identify the host name associated with an IP address (an inverse or pointer query) and look up other name elements such as the MX (mail exchange) record.

DNS is one of the most important applications on the network. A DNS failure will prevent hosts from locating each other when using host names.

DNS can run over UDP or TCP. Most commonly you will see DNS queries and replies using UDP. Zone transfers will run over TCP. The default port for DNS is port 53.

RFC 1035 limits DNS over UDP packet payload to 512 bytes. When a response requires more than 512 bytes, a truncation flag bit is sent in the response. This triggers the resolver to send the DNS query again using TCP which allows for a larger packet size.

CAUTION RFC 2671 (EDNS0) allows for greater than 512 bytes over UDP. This caused problems when the Microsoft DNS server added EDNS0 support, but Cisco PIX Firewall versions prior to 6.3(2) dropped DNS packets greater than the default maximum configured length of 512 bytes.

Multicast DNS (mDNS) offers name resolution for smaller networks without a DNS server. Top-level mDNS names end with .local. Any mDNS query for a name ending with .local must be sent to the mDNS multicast address (224.0.0.251 or its IPv6 equivalent FF02::FB).

💭 THINK FIRST · DNS PROBLEMS

Three major DNS failure modes are visible in Wireshark: Name Error (no such name exists), Server Failure (the DNS server couldn't complete the lookup), and Port Unreachable (no DNS daemon listening on port 53). Each appears as a specific Rcode value or ICMP response.

  • You see a DNS query go out and immediately receive an ICMP Destination Unreachable / Port Unreachable reply. Is the DNS server misconfigured, or could the client be misconfigured? How would you determine which is at fault?
  • A client makes 4 DNS queries for the same name with increasing gaps between them (1s, 1s, 2s...). What does this tell you about the client's DNS retry behavior?

Model Answer 1: The ICMP Port Unreachable means the target host is reachable at the IP layer but is not listening on UDP port 53. This could mean: (a) the client has the wrong DNS server IP configured (correct host, wrong service) or (b) the DNS daemon on the correct server has crashed. To determine which: try to connect to the same IP on another known-open port. If that succeeds, the IP is correct but the DNS service is down. Check whether the IP matches the intended DNS server's actual address in DHCP/network configuration.

Model Answer 2: The client is using an exponential backoff retry strategy: wait 1s, retry; wait 1s, retry; wait 2s, retry — roughly doubling the wait time. This is the standard resolver behavior when a DNS server doesn't respond. It reveals that the client has only one DNS server configured (otherwise it would try the second server sooner) and that the DNS server is either unreachable or unresponsive rather than actively refusing the query.

Analyze DNS Problems

The most common DNS problem is a Name Error because a name does not exist in the name server database — caused by entering an incorrect name or entering a new name that has not yet propagated through the Internet name servers.

💭 THINK FIRST · DNS PACKET STRUCTURE

Every DNS packet — query or response — has the same four-section structure: Questions, Answer Resource Records, Authority Resource Records, and Additional Resource Records. Understanding each field helps you filter precisely and correlate queries with responses.

  • What is the purpose of the Transaction ID field, and why did Wireshark 1.8 start including it in the Info column?
  • What is the difference between a recursive and an iterative DNS query, and which one does a typical client use?

Model Answer 1: The Transaction ID is a 16-bit random identifier that associates a specific query with its corresponding response — since DNS uses connectionless UDP, there's no other mechanism to match them. Multiple queries can be outstanding simultaneously, and without the Transaction ID there'd be no way to know which response answers which query. Wireshark 1.8 started displaying it in the Info column so you can visually match query/response pairs without expanding every packet's detail pane.

Model Answer 2: In a recursive query, the DNS server takes full responsibility for finding the answer — it will query other servers on the client's behalf and return a complete answer. In an iterative query, the server returns the best answer it has locally; if it doesn't know, it returns the address of another DNS server to ask. Typical clients use recursive queries (Recursion Desired flag = 1) because they want the DNS server to do all the work.

Dissect the DNS Packet Structure

DNS utilizes both UDP and TCP. All DNS packets use a single basic structure consisting of four primary parts:

  1. Questions
  2. Answer Resource Records (RRs)
  3. Authority Resource Records
  4. Additional Resource Records

Resource Record Time to Live (TTL)

The TTL field is contained in the Answer section of DNS responses and indicates how long the receiver can maintain the DNS information in cache. DNS servers continually count down the remaining TTL — making the same DNS query ten seconds apart will show a ten second difference in the TTL value offered.

💭 THINK FIRST · DNS FILTERS

Wireshark's display filter dns shows both standard DNS and mDNS traffic. The capture filter uses port numbers since tcpdump format doesn't understand the string "dns." Knowing the right filter for each scenario saves significant analysis time.

  • Why can't you use "dns" as a capture filter syntax the way you can as a display filter? What do you use instead?

Model Answer: Capture filters use libpcap/WinPcap syntax (tcpdump-style BPF filters), which only understands layer 2-4 information available at capture time — MAC addresses, IP addresses, and port numbers. Application-layer protocol recognition (like "dns") requires deep packet inspection that happens during dissection, which is a post-capture step. So for capture, you must use port 53 for standard DNS or port 5353 for mDNS. Display filters run on already-captured and dissected packets, so dns works there.

Filter on DNS/mDNS Traffic

The capture filter syntax for DNS traffic is based on port number because the tcpdump filter format does not understand the string "dns":

ScopeFilterCaptures
Capture (standard DNS)port 53UDP and TCP DNS
Capture (mDNS)port 5353Multicast DNS
DisplaydnsBoth DNS and mDNS
CAUTION Wireshark does not automatically colorize DNS errors the way it does TCP errors. Consider creating a Filter Expression button and coloring rule for DNS errors: dns.flags.rcode != 0. You will see a yellow background when you make this display filter, but this is expected because != triggered the yellow; in this case the filter is valid since dns.flags.rcode can only apply to one field.

Case Studies

Case Study 1
DNS Killed Web Browsing Performance
Submitted by: Laura Chappell

One customer complained about slow web browsing. They said that sometimes it would take 10 or 15 seconds to load a website — other times sites just wouldn't load at all. The problem seemed to have started overnight.

We placed a full-duplex tap on the network between one of the more "outspoken" users and the local switch. We watched traffic as the user hit a number of web sites. Initial visits were fast because the user had already visited these sites — no DNS queries and HTTP GET requests all contained "IfModified-Since" modifiers.

We asked the user to visit a number of new sites — www.mensa.org, www.apa.org and www.angermgmt.com. Invariably, if you ask a user to browse to new sites they can't think of a single one. We had the user browse to about 20 sites while we captured the traffic.

Sitting next to the complainer allowed us to experience their pain. Some web sites were excruciatingly slow. Others loaded just fine.

Watching the web browsing traffic revealed the problem. We saw three DNS queries go out to one DNS server and then a DNS query go out to a second DNS server. For every page that needed to be loaded there were way too many DNS queries.

The IT staff recognized the issue right away — the primary DNS server was located at a branch office. The user's DNS queries were traveling across the Internet all the way to a remote office, and there were obviously some communication problems because many queries got no response. After unsuccessfully trying to resolve the name to the remote DNS server, the system would then make a DNS query to the local DNS server.

We built a simple IO Graph comparing the number of DNS requests and responses:

  • DNS Requests: dns.flags.response==0
  • DNS Responses: dns.flags.response==1

The graph showed a higher number of requests than responses — confirming that many queries were going unanswered.

Why was this station talking to the remote DNS server first? The client received its DNS configuration through DHCP. A review of the DHCP server showed that all local hosts were pointed to the remote DNS server first. Someone had configured the local DHCP server incorrectly.

The problem wasn't a web browsing problem — it was a name resolution problem. We could prove it by revisiting a website after clearing the web cache (but not the DNS cache). The second and successive times it loaded fast because there were no DNS delays.

TL;DR — Chapter Summary

DNS is used to resolve name information. Most commonly, DNS requests and replies provide hosts with the IP address(es) associated with the name used by an application. DNS can also resolve PTR (pointer) records, MX (mail exchange) records, and more.

When the name resolver process is launched, a host must first look in local cache to see if the information is already known. If no entry exists in cache, the client checks for an entry in a local hosts file. If no entry is found, the host can generate a DNS request to a predefined DNS server. DNS requests can be recursive or iterative, as defined in the DNS flags field.

DNS servers respond with a numerical code (Rcode) indicating if the lookup was successful. A reply code 0 indicates success. Codes 2 and 3 indicate server failure and name error respectively. Port Unreachable ICMP responses indicate no DNS daemon is listening on the target host.

Review Questions

Q15.1 What is the purpose of DNS?
A15.1 DNS offers a name resolution service. Most commonly, DNS is used to obtain the IP address associated with a host name, but it can also be used to discover the host name associated with an IP address (a PTR query), mail exchange server names and IP addresses, and more.
Q15.2 When does DNS traffic use TCP as the transport?
A15.2 DNS uses TCP as the transport for zone transfers and large DNS packets. If a DNS response is too large to fit into the default 512 byte DNS payload size limitation, the DNS server sets the truncation flag bit in the response. The resolver process generates a new DNS query over TCP.
Q15.3 What is the difference between recursive and iterative DNS queries?
A15.3 In a recursive query (Recursion Desired = 1), the DNS server takes full responsibility for resolving the name — it will query other servers on behalf of the client and return a complete answer. In an iterative query, the DNS server returns the best answer it has locally; if it doesn't have the answer, it returns the address of another DNS server to ask instead of looking it up itself. Most client DNS queries use recursion.
Q15.4 What are the four sections of DNS queries and answers?
A15.4 The four sections of DNS packets are: (1) Questions, (2) Answer Resource Records, (3) Authority Resource Records, and (4) Additional Resource Records.
