💡THINK FIRST · PURPOSE OF DNS

DNS translates domain names to IP addresses. What is the typical sequence of events when a user browses to a website, and what happens if the DNS step fails?

HINT

Think about whether the TCP connection can be established before DNS completes. What does the OS use to initiate a TCP connection?

MODEL ANSWER

The browser calls the OS resolver → OS sends a DNS query (UDP, port 53) to the configured DNS server → DNS server returns an A/AAAA record with the IP → the OS returns the IP to the browser → browser initiates a TCP SYN to that IP. If DNS fails: the OS cannot resolve the name → the browser never gets an IP → no TCP connection is possible. The user sees a 'name not resolved' or 'server not found' error. Even if the web server is perfectly healthy, a broken DNS resolver makes it inaccessible.

The Purpose of DNS

DNS (Domain Name System) translates human-readable domain names into IP addresses. Defined in RFC 1035, DNS uses UDP port 53 for standard queries and TCP port 53 for zone transfers and large responses (EDNS0 responses > 512 bytes).

DNS Hierarchy

  • Root servers — know the authoritative servers for all TLDs (.com, .org, .net)
  • TLD servers — know the authoritative servers for each domain under the TLD
  • Authoritative servers — hold the actual records for a domain
  • Recursive resolver — the server clients contact; performs the full resolution chain and caches results

Recursive vs. Iterative Resolution

Client queries its recursive resolver → resolver queries root → root returns TLD referral → resolver queries TLD → TLD returns authoritative server → resolver queries authoritative → authoritative returns answer → resolver caches and returns answer to client. Client only sees one query/response pair; resolver does all the work.

DNS IS UDPStandard DNS queries use UDP for speed (no handshake). The 'don't fragment' approach means responses > 512 bytes may be truncated (TC bit set). EDNS0 (RFC 2671) extends this limit to 4096 bytes. Zone transfers (AXFR) use TCP.
🧠
MENTAL NOTE
DNS uses UDP port 53 (queries), TCP port 53 (zone transfers and large responses). Recursive resolver does the work; client sees one query/response. Cache poisoning attack exploits: guess transaction ID + source port to inject false answers. mDNS (multicast DNS) uses UDP port 5353 and the 224.0.0.251 multicast address for local name resolution without a server.

💡THINK FIRST · NORMAL DNS OPERATIONS

A normal DNS query/response pair takes how long? What would you expect to see in a healthy network, and what does an unusually slow response look like in Wireshark?

HINT

DNS is a critical path dependency before any application can connect. Think about what 'slow DNS' looks like in the delta time column.

MODEL ANSWER

A healthy recursive DNS response should return in < 100ms for a cached record and < 500ms for a fresh lookup requiring full resolution. In Wireshark with a display filter of 'dns', set the time column to 'delta displayed' — each response shows time since the preceding query. Anything > 1-2 seconds indicates a slow resolver. The Wireshark field dns.time (auto-calculated from query/response timestamps) allows filtering: dns.time > 1 to find slow responses directly.

Normal DNS Queries and Responses

A Record Query (IPv4)

Client → DNS server: Standard query 0x1234 A www.example.com

DNS server → Client: Standard query response 0x1234 A www.example.com A 93.184.216.34

The Transaction ID (0x1234) matches query to response. Both use the same UDP source/destination port.

CNAME Resolution

A CNAME record is an alias — the resolver follows the chain: query for www.example.com → CNAME → example.com.edgekey.net → A record → IP. A single query may return multiple records in the Answer section including the CNAME chain and the final A record.

AAAA Record (IPv6)

AAAA queries return 128-bit IPv6 addresses. Modern clients send parallel A and AAAA queries. The first response wins the race and is used for connection.

PTR Record (Reverse DNS)

Query: PTR 34.216.184.93.in-addr.arpa → Response: www.example.com. Used by Wireshark's name resolution and by some authentication systems.

TRANSACTION IDThe 16-bit Transaction ID links query to response. In the display filter: dns.id == 0x1234 to show a specific query/response pair. Wireshark auto-matches them using this ID + source port.
🧠
MENTAL NOTE
Normal DNS: UDP port 53, query then response with matching Transaction ID. A record = IPv4, AAAA = IPv6, CNAME = alias, PTR = reverse lookup, MX = mail. dns.time field = auto-calculated response time. Filter: dns.time > 1 to find slow responses. Healthy cache hit < 100ms, fresh lookup < 500ms.

💡THINK FIRST · DNS PROBLEMS

A user reports 'websites don't load but I can ping the server by IP'. What does this tell you, and what Wireshark filter would you apply to diagnose the DNS issue?

HINT

If pinging by IP works but names fail, which component is broken? What are the possible failure modes?

MODEL ANSWER

DNS is the broken component — IP connectivity is fine (ping by IP succeeds). Possible failures: (1) DNS server unreachable — queries sent but no response (timeout, then retry); (2) DNS server returns NXDOMAIN — domain doesn't exist (typo, wrong domain, DNS poisoning); (3) DNS server returns SERVFAIL — server error (misconfigured, upstream failure). Wireshark filter: 'dns' — look for queries with no matching response, or responses with non-zero rcode. Also check 'dns.flags.rcode != 0' for error responses.

DNS Problems and Error Codes

NXDOMAIN (rcode=3)

Non-Existent Domain — the queried name does not exist in DNS. Causes: typo in domain name, domain expired, DNS record deleted, DNS spoofing with false NXDOMAIN. Filter: dns.flags.rcode == 3

SERVFAIL (rcode=2)

Server Failure — the DNS server could not process the query. Causes: DNSSEC validation failure, misconfigured resolver, upstream server unreachable. Filter: dns.flags.rcode == 2

REFUSED (rcode=5)

Query Refused — the server refuses to answer from this client. Causes: access control list on the DNS server, querying an authoritative server that doesn't allow recursion.

No Response / Timeout

No matching response packet for a query. Causes: DNS server unreachable (ICMP unreachable in trace), firewall blocking port 53, DNS server overloaded. Spot this by looking for a query with no corresponding response — or by filtering: dns.flags.response == 0 (queries) and checking which queries have no matching response packet.

Client Retry Behavior

When a query times out, the OS retransmits after 1-2 seconds, often 3-4 times. In Wireshark this appears as multiple identical queries to the same server (or to an alternate server) with 1-2 second intervals. The user's application waits 5-15 seconds before receiving an error.

ICMP UNREACHABLEIf DNS server is down, client sends query → receives ICMP Port Unreachable (no UDP service on port 53). Look for ICMP Type 3 Code 3 from the DNS server IP immediately after the DNS query.
🧠
MENTAL NOTE
DNS error codes: NXDOMAIN (3) = doesn't exist, SERVFAIL (2) = server error, REFUSED (5) = access denied. No response = server down or firewalled. Client retries 3-4x at 1-2s intervals → 5-15s total user wait. Filter: dns.flags.rcode != 0 for all DNS errors. ICMP Unreachable after DNS query = DNS port blocked or service not running.

DNS Packet Structure

DNS Message Header (12 bytes)

FieldSizeDescription
Transaction ID16 bitsMatches query to response
Flags16 bitsQR, Opcode, AA, TC, RD, RA, Z, RCODE
QDCOUNT16 bitsNumber of questions
ANCOUNT16 bitsNumber of answers
NSCOUNT16 bitsNumber of authority records
ARCOUNT16 bitsNumber of additional records

Key Flags

  • QR — 0=Query, 1=Response
  • RD — Recursion Desired (client asks resolver to recurse)
  • RA — Recursion Available (server supports recursion)
  • TC — TrunCated (response truncated; retry over TCP)
  • AA — Authoritative Answer (came directly from authoritative server)
  • RCODE — 4-bit response code: 0=No Error, 2=SERVFAIL, 3=NXDOMAIN, 5=REFUSED

TTL (Time to Live)

Each answer record has a TTL in seconds — how long the resolver may cache the record. Low TTL (60s) = frequent updates expected. High TTL (86400 = 24h) = stable record. DNS response time for a cached record = fast; for a record with expired TTL = requires fresh lookup.

🧠
MENTAL NOTE
DNS header: 12 bytes. Key flags: QR (query/response), TC (truncated → retry over TCP), RD (recursion desired), RA (recursion available), AA (authoritative), RCODE (error code). TTL = cache lifetime. Transaction ID = 16-bit random number linking query to response.

Review Questions

Q15.1
What DNS error code (rcode) represents NXDOMAIN, and what does it mean?
HINT

NXDOMAIN = Non-Existent Domain. What are common causes?

ANSWER

RCODE 3 = NXDOMAIN (Non-Existent Domain). The queried name does not exist in DNS. Causes: typo in domain name, domain expired or deleted, DNS record removed but not propagated, DNS spoofing injecting false NXDOMAIN responses. Filter in Wireshark: dns.flags.rcode == 3. Symptom: browser shows 'This site can't be reached' or 'ERR_NAME_NOT_RESOLVED'.

Q15.2
A user can ping a web server by IP but cannot browse to it by name. What is the likely cause and what Wireshark display filter confirms it?
HINT

If IP connectivity works, which component must be failing?

ANSWER

DNS is failing — IP connectivity is fine (ping by IP succeeds), but name resolution is broken. The DNS server may be: (1) unreachable (queries time out, ICMP unreachable follows); (2) returning errors (NXDOMAIN or SERVFAIL); (3) blocked by firewall on port 53. Confirm with Wireshark: apply display filter dns — look for queries with no response (timeout), or dns.flags.rcode != 0 for error responses.

Q15.3
What is the Transaction ID in a DNS message, and how does Wireshark use it?
HINT

How does a client match a DNS response to the correct query?

ANSWER

The Transaction ID is a 16-bit random number in the DNS header, set by the client when sending a query. The DNS server copies the same ID into the response. The client matches the response to its outstanding query by comparing Transaction IDs. Wireshark uses the Transaction ID (plus source port) to calculate dns.time — the elapsed time between the matching query and response packets. Filter: dns.id == 0xABCD to find a specific query/response pair.

Q15.4
When does DNS use TCP instead of UDP?
HINT

Think about response size limitations and zone transfers.

ANSWER

DNS uses TCP for: (1) Zone transfers (AXFR) — copying all records from an authoritative server requires reliable transport; (2) Large responses — when a UDP response exceeds the negotiated EDNS0 buffer size (typically 4096 bytes or the standard 512-byte limit), the server sets the TC (TrunCated) flag; the client then retries the query over TCP. Filter for DNS over TCP: tcp.port == 53.

Q15.5
What does a TTL value of 60 seconds on a DNS A record indicate, and how does this affect client behavior?
HINT

TTL controls how long a cached answer is valid.

ANSWER

A 60-second TTL means resolvers and clients must discard the cached A record after 60 seconds and re-query for a fresh answer. This is intentionally low — used when the administrator expects the IP address to change soon (e.g. during a migration, failover, or load balancer reconfiguration). High TTL (86400 = 24h) means the record rarely changes and caching is beneficial. Low TTL increases DNS query volume but enables faster IP changes to propagate.
