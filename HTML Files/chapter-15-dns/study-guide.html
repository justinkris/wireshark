💭 THINK FIRST · THE PURPOSE OF DNS

DNS is the invisible first step behind almost every network conversation. Before a packet can leave your machine headed for "www.example.com", the name must be turned into an IP address — and DNS is the system that does it. The choice of transport (UDP vs TCP) isn't random; it's a deliberate performance trade-off baked into the protocol design.

  • Why does DNS use UDP by default instead of TCP, and what specific conditions force it to switch to TCP?
  • What happens at the client when a DNS response is truncated under RFC 1035's 512-byte UDP limit?
  • How does mDNS differ from standard DNS in terms of transport, addressing, and the names it resolves?
Q1 — WHY UDP BY DEFAULT, WHEN DOES IT SWITCH?
UDP is connectionless and has no handshake overhead — a DNS query is typically a single small packet, and UDP can fire it off immediately without establishing a connection first. DNS switches to TCP when a response exceeds 512 bytes (RFC 1035 limit) because TCP allows larger, segmented payloads. Zone transfers (copying an entire DNS zone between servers) always use TCP because they involve large amounts of data and require reliable, ordered delivery.
Q2 — WHAT HAPPENS ON TRUNCATION?
When a DNS response is too large for a 512-byte UDP payload, the server sets the Truncation (TC) flag bit in the response. The client, seeing TC=1, knows the answer was cut off and immediately retransmits the same query using TCP on port 53. TCP allows the server to send the full, multi-segment response. EDNS0 (RFC 2671) was introduced to extend UDP payloads beyond 512 bytes, reducing the need for this TCP fallback in modern networks.
Q3 — HOW DOES mDNS DIFFER?
mDNS (Multicast DNS) is a peer-to-peer name resolution system for small networks with no dedicated DNS server. Instead of unicasting queries to a known server on port 53, mDNS sends queries to the multicast group address 224.0.0.251 (IPv6: FF02::FB) on port 5353. mDNS only resolves names ending in .local — it has no concept of a central authority or zone hierarchy. In Wireshark, you capture mDNS with the capture filter port 5353, and the display filter dns covers both standard DNS and mDNS.
Section 1

The Purpose of DNS

DNS (Domain Name System) converts symbolic host names — like www.wireshark.org — into IP addresses that routers can forward packets to. It also resolves other record types: MX records identify mail servers, PTR records reverse-resolve an IP back to a name, and NS records delegate zones to authoritative servers.

DNS is one of the most critical services on any network. A DNS failure doesn't just break one application — it breaks every application that references hosts by name. When troubleshooting "the internet is down," always check DNS first.

Transport & Port DNS uses UDP port 53 for standard queries and responses. It switches to TCP port 53 for zone transfers and when a response payload exceeds 512 bytes (triggering the Truncation flag).

RFC 1035 and EDNS0

RFC 1035 limits DNS-over-UDP payloads to 512 bytes. When a response needs more space, the server sets the Truncation (TC) bit and the client retries over TCP. RFC 2671 (EDNS0) extended this by allowing larger UDP payloads — but this caused compatibility problems with older firewalls like the Cisco PIX pre-6.3(2) that dropped DNS packets exceeding 512 bytes.

Multicast DNS (mDNS)

mDNS provides name resolution for small networks without a dedicated DNS server. All mDNS queries for names ending in .local are sent to the multicast address 224.0.0.251 (IPv6: FF02::FB) on port 5353. Wireshark capture filter: port 5353

🧠
MENTAL NOTE
DNS = port 53 UDP (queries/responses) and port 53 TCP (zone transfers + truncated responses). EDNS0 extends UDP beyond 512 bytes. mDNS = port 5353, multicast 224.0.0.251, .local names only. A DNS failure breaks every application that uses hostnames — always rule it out first.
Analogy
DNS is like a phone directory service. When you want to call "Central Hospital," you don't know their number — you call the directory, give them the name, and they give you the number to dial. Standard DNS is like calling a large national directory (with a server that looks it up for you). mDNS is like shouting "Does anyone here know the number for the coffee shop?" in a small office — your neighbours answer directly, no central switchboard needed.

💭 THINK FIRST · NORMAL DNS QUERIES & RESPONSES

A DNS response doesn't always give you what you asked for directly. Sometimes the server returns a chain of aliases before landing on the IP address. And on dual-stack hosts, one website visit can trigger two DNS queries simultaneously — one for IPv4, one for IPv6.

  • When a client receives a CNAME record in a DNS response, is the lookup complete? What must happen next?
  • Why would a host send both an A record query AND an AAAA record query for the same hostname at the same time?
  • In recursive querying, who does the "heavy lifting" of finding the answer — the client or the DNS server? How does this differ from iterative querying?
Q1 — CNAME: IS THE LOOKUP COMPLETE?
No — a CNAME response gives the canonical (true) name for an alias, but not an IP address. The client must send a second DNS query for the canonical name to get the actual IP. In Wireshark, you'll see the Answer RR Count as 2 in these responses: one record for the CNAME, and one A record for the IP address of the canonical name. If the server can't resolve the CNAME in the same response, a second query is visible in the capture.
Q2 — WHY BOTH A AND AAAA QUERIES?
A dual-stack host supports both IPv4 and IPv6, so it queries for both simultaneously to find the best available address. The A record query returns an IPv4 address; the AAAA query returns an IPv6 address. The client will use whichever address type its routing table prefers — usually IPv6 when available. In a capture, you'll see the two queries close together in time, often with back-to-back transaction IDs.
Q3 — RECURSIVE VS ITERATIVE
In recursive querying, the client asks its configured DNS server to fully resolve the name — the server does all the work, asking other DNS servers on the client's behalf until it has a final answer. In iterative querying, the DNS server only returns the information it has locally, or refers the client to another server to ask next — the client is responsible for following the chain. Most end-user DNS queries are recursive (the RD bit is set), which is why home networks work even though clients only know one DNS server address.
Section 2

Normal DNS Queries & Responses

A normal DNS lookup starts when an application (like a browser) submits a hostname to the OS resolver. If the address isn't already in DNS cache, the resolver sends a query to the configured DNS server and waits for a response.

A Record Query (IPv4)

The most common DNS query asks for an A record — mapping a hostname to an IPv4 address. The client sends a UDP packet to the DNS server on port 53. The server responds with the IP address. In Wireshark, the Info column shows the query name and the response code.

CNAME Records (Alias Chains)

A CNAME (Canonical Name) record tells the client "the name you asked for is actually an alias — here's the real name." The client must then query for the real name to get an IP address. In Wireshark, a CNAME response shows Answer RR Count = 2 (the CNAME record + the A record for the canonical name).

Example: www.msnbc.com Querying www.msnbc.com returns: CNAME → msnbc.com, A record → 207.46.245.32. The Answer RR Count is 2 — one for the alias, one for the resolved IP.

AAAA Record Query (IPv6)

On a dual-stack host (running both IPv4 and IPv6), the resolver sends both an A query and an AAAA query for the same hostname. If the server returns no IPv6 address for the AAAA query (only authority/NS records), the client falls back to IPv4 only — it simply cannot communicate over IPv6 with that host.

Recursive vs Iterative Queries

  • Recursive — Client sets the RD (Recursion Desired) bit. The DNS server does all the lookups on the client's behalf and returns a final answer. Most client queries are recursive.
  • Iterative — The DNS server returns whatever it knows locally, or refers the client to another server. The client must follow the chain itself. Used between DNS servers (server-to-server lookups).
🧠
MENTAL NOTE
CNAME = alias chain, expect Answer RR Count ≥ 2 (CNAME + A record). Dual-stack hosts send both A and AAAA queries — no AAAA answer means IPv6 unavailable for that host. RD bit = "please do the lookup for me" (recursive). Most end-user queries are recursive; server-to-server lookups are iterative.
Analogy
Recursive DNS is like calling directory assistance and asking them to find a restaurant's number — the operator goes away, calls other directories, and calls you back with the final answer. Iterative DNS is like the operator saying "I don't know, but try calling this other number" — you have to make each call yourself. A CNAME is like being told "Ask for Bob, but his real name is Robert Smith" — you now need to make a second call under the real name.

💭 THINK FIRST · DNS PROBLEMS & ERROR CODES

Not all DNS failures look the same in a packet capture. An NXDOMAIN means the name genuinely doesn't exist. A SERVFAIL means the name might exist but the server can't resolve it. ICMP Port Unreachable means there's no DNS service running at all. Each points to a completely different root cause.

  • DNS queries are being sent but you see ICMP Destination Unreachable (Port Unreachable) replies on port 53. What does this tell you, and what should you check first?
  • What's the practical difference between an NXDOMAIN and a SERVFAIL from a troubleshooting perspective?
  • Why does the DNS client double its retry interval each time it resends an unanswered query (1s, 1s, 2s, 4s…)?
Q1 — ICMP PORT UNREACHABLE ON PORT 53
ICMP Destination Unreachable / Port Unreachable (Type 3, Code 3) on port 53 means the target host is reachable at the IP level, but nothing is listening on UDP port 53 — the DNS daemon is not running. The client has the correct IP address of a host, but that host isn't providing DNS service. First check: Is the DNS service running on that host? Is the client pointing to the right DNS server IP?
Q2 — NXDOMAIN VS SERVFAIL
NXDOMAIN (Rcode 3) means the DNS server definitively authoritative for that domain confirmed: this name does not exist. The domain or hostname is wrong or hasn't propagated yet — fix the name or wait for DNS propagation. SERVFAIL (Rcode 2) means the DNS server tried but couldn't get an answer — perhaps a upstream recursive query timed out or there was an internal server error. SERVFAIL suggests a DNS infrastructure problem; NXDOMAIN suggests a naming problem.
Q3 — WHY EXPONENTIAL BACKOFF?
Exponential backoff (1s → 1s → 2s → 4s) prevents the client from flooding an already-struggling DNS server with repeated rapid retries. If the server is overloaded, constant retries would make it worse. By doubling the wait time, the client gives the server increasingly more time to recover while still checking periodically. This is the same principle behind TCP's retransmission timer — back off to avoid compounding the problem.
Section 3

DNS Problems & Error Codes

DNS errors are returned in the Rcode (Response Code) field of the DNS Flags section. A non-zero Rcode means something went wrong. The specific code tells you exactly what kind of failure occurred.

RcodeNameMeaningLikely Cause
0No ErrorQuery succeededNormal — no action needed
1Format ErrorQuery could not be interpretedMalformed query packet
2Server FailureServer couldn't process queryDNS server internal error or upstream timeout
3NXDOMAINName does not existTypo in hostname, or name hasn't propagated
4Not ImplementedQuery type not supportedServer doesn't support this record type
5RefusedServer refuses to answerPolicy block — e.g. recursive queries not allowed from this IP

ICMP Port Unreachable — No DNS Service Running

If the target IP address responds with ICMP Destination Unreachable / Port Unreachable to DNS queries, it means the host is alive but port 53 is not open — the DNS daemon is not running. The client doesn't receive an NXDOMAIN or SERVFAIL; it gets an ICMP error instead. The client will retry (only knowing one DNS server), and each attempt will be refused the same way.

Client Retry Timers

When a DNS query goes unanswered, the client waits and retries using an exponential backoff pattern. In Wireshark, set the Time column to Seconds Since Previous Displayed Packet to clearly see these gaps:

  • 1st retry: after ~1 second
  • 2nd retry: after ~1 second
  • 3rd retry: after ~2 seconds
  • 4th retry: after ~4 seconds (doubled each time)
Troubleshooting tip To find the root cause of DNS SERVFAIL responses, move Wireshark upstream — place it between the DNS server and its upstream resolvers. The fault may be there, not at the client's DNS server.
🧠
MENTAL NOTE
Rcode 0 = success. Rcode 2 = SERVFAIL (server problem). Rcode 3 = NXDOMAIN (name doesn't exist). Rcode 5 = REFUSED (policy block). ICMP Port Unreachable on port 53 = DNS daemon not running. Client retry pattern is exponential backoff — set Time column to "Seconds Since Previous Displayed Packet" to measure retry intervals clearly.
Analogy
DNS error codes are like postal return stamps. NXDOMAIN is "No such address — this street doesn't exist." SERVFAIL is "We tried to deliver but our sorting office had an internal problem." REFUSED is "We won't accept mail from you." ICMP Port Unreachable is something different — it's like ringing a doorbell and being told "This isn't a post office" — you had the right building but the wrong service entirely.

💭 THINK FIRST · DNS PACKET STRUCTURE

Every DNS packet — whether a tiny query or a large zone transfer — uses the same four-section structure. Understanding what each field means lets you build precise Wireshark filters and read DNS behaviour at a glance. The Transaction ID, TTL, and Flags fields each tell a different story about what's happening in the name resolution process.

  • What purpose does the Transaction ID serve in DNS, and how does Wireshark use it to help analysts?
  • Why does DNS have both an "Answer RR" section AND an "Authority RR" section? When would each contain data?
  • What's the real-world impact of a very short TTL value in DNS responses — who is affected and how?
Q1 — TRANSACTION ID
The Transaction ID (a 2-byte random value) pairs each DNS query with its response. Since DNS uses connectionless UDP, there's no inherent connection to link a query and its answer — the Transaction ID solves this. Starting with Wireshark 1.8, the Transaction ID is shown in the Info column, making it easy to visually match a query packet to its corresponding response. You can filter on a specific ID: dns.id==0x05b5.
Q2 — ANSWER RR vs AUTHORITY RR
The Answer RR section contains records that directly answer the question asked — e.g. the A record with the IP address. The Authority RR section contains records from servers that are authoritative for the domain but may not have the specific record requested — typically NS records pointing to the domain's name servers. You see Authority RRs populated when the queried server doesn't have a direct answer but can refer you to an authoritative source (common in non-authoritative responses and when querying for AAAA records on IPv4-only domains).
Q3 — IMPACT OF SHORT TTL
A short TTL means DNS resolvers discard their cached answer quickly and must query the authoritative server again soon. For clients, this means more DNS queries — and if each web page visit triggers fresh DNS lookups instead of serving from cache, it measurably increases page load time. Very short TTLs are sometimes used intentionally during server migrations to allow fast IP changes, but they significantly increase DNS server load and network traffic. The Riverbed example in this chapter shows a DNS response with a TTL of only 2 minutes — meaning the client had to re-query on every browsing session that lasted longer than 2 minutes.
Section 4

DNS Packet Structure

Every DNS packet uses the same four-section structure regardless of whether it's a query or response:

  1. Questions — the name being queried and the record type requested
  2. Answer Resource Records — direct answers to the query
  3. Authority Resource Records — referrals to authoritative name servers
  4. Additional Resource Records — A records for servers mentioned in Authority section

Transaction ID

A 2-byte random value that links a query to its response. Without it, UDP has no way to match them. Wireshark displays it in the Info column starting from v1.8. Filter: dns.id == 0x05b5

Flags Field Breakdown

QR Bit (Query/Response)
0 = Query, 1 = Response. Filter queries: dns.flags.response==0
Opcode
Type of query. 0000 = standard query (most common). Left at 0000 in responses.
Authoritative Answer (AA)
Set in responses from authoritative servers — the server owns this zone and its answer is definitive.
Truncation (TC)
Response was cut short (exceeded 512 bytes UDP limit). Client must retry over TCP.
Recursion Desired (RD)
Set by the client in queries. Asks the server to perform a recursive lookup on the client's behalf.
Recursion Available (RA)
Set by the server in responses. Indicates this server supports recursive queries.
Rcode (Response Code)
0 = success, 2 = SERVFAIL, 3 = NXDOMAIN, 5 = REFUSED. Filter errors: dns.flags.rcode != 0
Reserved
Always 0. No current use.

DNS Record Types

TypeNamePurpose
AHost AddressMaps hostname → IPv4 address
AAAAIPv6 AddressMaps hostname → IPv6 address
CNAMECanonical NameAlias → real name (requires follow-up A query)
MXMail ExchangeIdentifies mail server for a domain
PTRPointer RecordReverse lookup: IP address → hostname
NSName ServerAuthoritative name servers for a zone
SOAStart of AuthorityZone authority information, serial numbers
TXTText RecordSPF, DKIM, domain verification, arbitrary text

TTL (Time to Live)

Every record in the Answer RR section carries a TTL value specifying how many seconds the receiving resolver may cache that answer. DNS servers actively count the TTL down — querying the same name twice in succession will show the TTL reducing between responses. A very short TTL means frequent re-queries and increased DNS load.

🧠
MENTAL NOTE
Transaction ID links UDP queries to responses. Flags byte: QR=0 query / QR=1 response; RD set by client (please recurse); RA set by server (can recurse); Rcode in response (0=OK, 3=NXDOMAIN, 2=SERVFAIL, 5=REFUSED). TTL in Answer RR = cache lifetime in seconds — short TTL = frequent DNS traffic. CNAME Answer RR Count ≥ 2.
Analogy
A DNS packet is like a restaurant order ticket. The Transaction ID is your table number — the kitchen uses it to match the food back to the right table. The QR bit is whether it's an order (query) or a delivery (response). The RD bit is "please make it for me" vs handing back a raw ingredient list. The TTL is the food's best-before time stamped on the packaging — once it expires, you have to order fresh.

💭 THINK FIRST · FILTERING DNS IN WIRESHARK

Wireshark has two completely different filter systems — capture filters (BPF syntax, applied at capture time) and display filters (Wireshark's own field-based syntax, applied after capture). DNS filters use different syntax in each system, and knowing which to use and when is a practical skill that saves analysis time.

  • Why can't you use "dns" as a capture filter — and what must you use instead? Why does this limitation exist?
  • The filter dns.flags.rcode != 0 shows a yellow background in Wireshark when you type it. Is this a problem? Why does Wireshark warn about != ?
  • How would you build a filter to show only DNS responses that contain more than one answer record — suggesting a CNAME chain?
Q1 — WHY CAN'T YOU USE "dns" AS A CAPTURE FILTER?
Capture filters use the BPF (Berkeley Packet Filter) syntax from tcpdump/libpcap, which operates at the transport layer and below. BPF doesn't understand application protocol names like "dns" — it only understands port numbers, IP addresses, MAC addresses, and protocol types. Because DNS uses port 53, the correct capture filter is port 53. mDNS uses port 5353 so its capture filter is port 5353. Display filters (used after capture) do understand application layers and can use the keyword dns directly.
Q2 — YELLOW BACKGROUND ON != FILTER
The yellow background is a warning, not an error — the filter will work. Wireshark warns about != because for fields that can apply to multiple instances (like ip.addr or tcp.port), != has a counterintuitive result: it matches if ANY instance of the field is not equal, which isn't always what you want. However, dns.flags.rcode is a single-value field that can only appear once per packet, so != works exactly as expected here. The yellow is a precautionary reminder that you should double-check the logic for multi-value fields.
Q3 — FILTER FOR MULTIPLE ANSWER RECORDS
Use dns.count.answers > 1 to show DNS responses with more than one answer record. A CNAME response typically has Answer RR Count = 2 (one CNAME record + one A record for the canonical name). If you want to see responses with exactly 2 answers, use dns.count.answers == 2. Combine with dns.flags.response == 1 to restrict to responses only: dns.flags.response == 1 && dns.count.answers > 1.

💭 THINK FIRST · CASE STUDY — DNS KILLED WEB BROWSING

Slow browsing complaints are tricky. Without a packet capture, the problem could be the web server, the network path, the client hardware, or DNS. This case study shows how a capture pinpointed the cause in minutes — not by finding a dramatic error, but by counting the ratio of DNS requests to DNS responses.

  • How did the analyst prove the problem was DNS — not the web server or the network path — causing the slow page loads?
  • Why did some pages load fast (with no delay) even while the problem was active?
  • What DHCP configuration change would have permanently fixed the problem in this case study?
Q1 — HOW DID THEY PROVE IT WAS DNS?
The analyst built an IO Graph comparing dns.flags.response==0 (requests) to dns.flags.response==1 (responses). The graph showed consistently more requests than responses — DNS queries were going unanswered. They also observed multiple DNS queries going to a remote DNS server followed by a retry to a local one, with large time gaps between them. Once the analyst revisited an already-loaded site (bypassing DNS cache), pages loaded instantly — proving that when DNS was skipped, the web browsing was fast. The network path and web server were never slow; only the name resolution step was.
Q2 — WHY WERE SOME PAGES FAST?
Pages the user had visited recently loaded fast because the IP addresses were still cached in the local DNS resolver cache. The client didn't need to send a DNS query — it already had the answer. Only new sites (or sites whose TTL had expired) triggered a DNS lookup, which then had to fail to the remote DNS server before falling back to the local one. This is why the problem was intermittent — it only manifested for names not already in cache.
Q3 — THE FIX
The fix was to correct the DHCP server's DNS server order. The DHCP server was handing out the remote branch office DNS server as the primary DNS server for all local clients. The correct configuration would place the local DNS server first and the remote one as a secondary fallback (or remove the remote one entirely if the local server handled all zones). This is a one-line DHCP server configuration change that would fix every client on the network simultaneously on next lease renewal.
Section 6 · Case Study

Case Study: DNS Killed Web Browsing

A user complained about slow web browsing — some sites took 10–15 seconds to load; others wouldn't load at all. The problem had appeared overnight. The analyst placed a full-duplex tap between the user's machine and the switch.

What the Capture Showed

For recently-visited sites, browsing was fast — no DNS queries were visible (the client used cached addresses). For new sites, the analyst observed:

  • DNS queries sent to a remote DNS server (at a branch office across the internet)
  • Many of those queries went unanswered (the remote server was unreliable)
  • After waiting, the client retried the query to a local DNS server
  • The local server responded quickly, then the page loaded fast
The smoking gun The IO Graph revealed more DNS requests than responses — unanswered queries were adding seconds of delay before every new page load. Once a site's IP was cached, it loaded instantly — proving the web server and network path were fine.

The IO Graph Technique

Build two lines in Wireshark's IO Graphs:

  • Line 1: dns.flags.response==0 → DNS Requests
  • Line 2: dns.flags.response==1 → DNS Responses

If the request line runs consistently above the response line, queries are going unanswered. This immediately quantifies the DNS problem without opening every packet.

Root Cause & Fix

The DHCP server was incorrectly configured to hand out the remote branch office DNS server as primary to all local clients. Every client on the network was sending their first DNS query on a long WAN hop. The fix: update the DHCP server to serve the local DNS server as primary. All clients pick up the change on next lease renewal.

Lesson Always suspect DNS when browsing is slow but works eventually. The "browsing problem" was never a browsing problem — it was a name resolution problem. A two-minute capture and one IO Graph confirmed the diagnosis and identified the fix.
🧠
MENTAL NOTE
IO Graph with DNS requests vs responses is the fastest way to diagnose DNS health. Requests > Responses = unanswered queries = DNS problem upstream. If re-visiting a site loads fast but first visit is slow → DNS cache miss is the bottleneck. Root cause is almost always DNS server order in DHCP config or an unreachable primary DNS server.
