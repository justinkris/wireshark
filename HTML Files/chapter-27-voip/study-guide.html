💭 THINK FIRST · VOIP PROTOCOL STACK

VoIP separates signaling (setting up the call) from media (the actual voice). This two-layer architecture means that when a call sounds bad, you need to examine both layers independently — SIP tells you whether the call was set up correctly; RTP tells you whether the audio was delivered with acceptable quality.

  • A user reports their VoIP call sounds choppy. Before looking at packets, what are the three main quality metrics you need to measure?
  • Why does RTP use UDP instead of TCP for voice data?
Q1 — THREE KEY VOIP QUALITY METRICS
The three key VoIP quality metrics are: (1) Packet loss — percentage of RTP packets that were dropped. Above 1% is perceptible as audio dropouts. (2) Jitter — variation in packet arrival timing. Above 30ms jitter causes choppy audio even without packet loss (the jitter buffer can't compensate). (3) Latency (delay) — end-to-end delay. Above 150ms is perceptible as an unnatural conversational delay; above 300ms is seriously disruptive.
Q2 — WHY RTP USES UDP NOT TCP
RTP uses UDP because voice communication is delay-sensitive but not loss-sensitive. TCP's retransmission mechanism would introduce variable delay — when a packet is lost, TCP waits for retransmission before delivering subsequent packets. For voice, receiving a retransmitted packet 100ms late is useless — the user already experienced a gap. It's better to simply play silence for the missing interval and continue. UDP delivers packets immediately as they arrive, letting the jitter buffer and codec handle minor losses gracefully.
Section 1

VoIP Protocol Stack Overview

VoIP is built on two protocol layers that operate independently. Understanding this separation is the key to efficient VoIP troubleshooting.

Layer 1 — Signaling: Sets up, manages, and tears down calls. Main protocols:

  • SIP (Session Initiation Protocol) — port 5060 UDP/TCP, 5061 for TLS. The dominant modern standard.
  • H.323 — older enterprise standard, still found in legacy deployments.
  • MGCP / SCCP (Cisco Skinny) — call agent-controlled protocols for managed endpoints.

Layer 2 — Media: Carries digitized voice audio between endpoints.

  • RTP (Real-time Transport Protocol) — UDP-based, carries audio and video samples.
  • RTCP (RTP Control Protocol) — companion to RTP, carries QoS statistics (loss, jitter) alongside the RTP stream.

SIP negotiates which codec and UDP port pair to use; RTP flows directly between endpoints on those dynamically negotiated ports. Common codecs: G.711 (u-law/a-law, 64 kbps, uncompressed, best quality), G.729 (8 kbps compressed, lower bandwidth), Opus (modern, variable bitrate, WebRTC standard).

Two layers, two filters SIP sets up the call (negotiates codec, IP, RTP port). RTP carries the actual voice audio. Analyze separately: filter sip for call control problems, filter rtp for audio quality problems.
🧠
MENTAL NOTE
VoIP = Signaling (SIP, port 5060) + Media (RTP, UDP dynamic ports). SIP = call setup/teardown. RTP = audio stream, UDP (no retransmit). RTCP = companion to RTP with QoS stats. Codecs: G.711 (64 kbps, uncompressed), G.729 (8 kbps compressed). 3 quality metrics: loss <1%, jitter <30ms, latency <150ms.

💭 THINK FIRST · SIP CALL FLOW

The SIP call flow follows a predictable sequence — INVITE with SDP offer, 200 OK with SDP answer, ACK, then RTP begins. Knowing this sequence lets you immediately identify which step failed when a call doesn't connect, and the SDP exchange tells you exactly what codec and port number RTP will use.

  • You see a SIP INVITE followed by a 401 Unauthorized response. What does this mean and what should the caller send next?
  • After the SIP 200 OK is received, what information from that message allows RTP to begin?
Q1 — SIP 401 UNAUTHORIZED
401 Unauthorized means the SIP proxy requires authentication before routing the call. The proxy sent a WWW-Authenticate header containing a challenge (nonce value). The caller should resend the INVITE with an Authorization header containing the response to the challenge (credentials hashed with the nonce using digest authentication). This is the normal SIP digest authentication exchange — the first INVITE without credentials is expected to fail with 401.
Q2 — WHAT THE 200 OK PROVIDES FOR RTP
The 200 OK contains an SDP (Session Description Protocol) answer from the called party. The critical fields are: c= (connection field — the IP address where the callee will receive RTP), m= audio (media line — the UDP port number where the callee will receive RTP), and a=rtpmap lines (the agreed codec). With the callee's IP address and RTP port known, the caller can begin sending RTP audio to that endpoint. RTP starts flowing immediately after the ACK is sent.
Section 2

SIP Call Flow

The SIP call flow follows a defined ladder of messages. Each message has a specific role — recognizing the expected sequence lets you quickly pinpoint where a call failed.

SIP MessageDirectionMeaning
INVITECaller → CalleeInitiate call with SDP offer (codec list, IP, RTP port)
100 TryingProxy → CallerProxy is processing the request
180 RingingCallee → CallerPhone is ringing at destination
200 OKCallee → CallerCall answered with SDP answer (chosen codec, IP, RTP port)
ACKCaller → CalleeConfirm 200 OK received; RTP begins now
[RTP flows]Both directionsVoice audio on agreed UDP port
BYEEither partyEnd the call
200 OKOther partyBYE acknowledged; call complete

SIP response code groups: 1xx = Provisional, 2xx = Success, 3xx = Redirect, 4xx = Client Error (401 = Unauthorized, 403 = Forbidden, 404 = Not Found, 486 = Busy Here, 487 = Request Terminated), 5xx = Server Error, 6xx = Global Failure.

🧠
MENTAL NOTE
SIP call: INVITE(SDP offer) → 100 Trying → 180 Ringing → 200 OK(SDP answer) → ACK → [RTP] → BYE → 200 OK. SDP in INVITE: codec list, my IP, my RTP port. SDP in 200 OK: chosen codec, callee IP, callee RTP port. RTP starts after ACK. Filter: sip. Common codes: 200=OK, 486=Busy, 404=Not Found, 401=Auth required.

💭 THINK FIRST · RTP MEDIA ANALYSIS

RTP carries digitized voice in UDP datagrams. The RTP header fields enable quality measurement — sequence numbers detect loss, timestamps calculate jitter, and the SSRC identifies which stream is which in a multi-party call. Quality degradation above specific thresholds is reliably audible to users.

  • An RTP stream shows sequence numbers 100, 101, 103, 104 (102 is missing). What metric does this affect and can RTP recover the missing packet?
  • An RTP stream shows jitter values increasing from 2ms to 80ms over the call duration. What does this indicate?
Q1 — MISSING RTP SEQUENCE NUMBER
The missing sequence number 102 represents 1 packet loss event. This affects the packet loss metric (and indirectly jitter, as the burst arrival of 103 after the gap creates a timing irregularity). RTP cannot recover the missing packet — UDP has no retransmission mechanism. The codec may use packet loss concealment (PLC) to interpolate the missing audio from adjacent packets, masking brief losses. At typical G.711 rates (1 packet per 20ms), missing packet 102 creates a 20ms gap in the audio.
Q2 — INCREASING JITTER OVER CALL DURATION
Increasing jitter from 2ms to 80ms indicates the network path is becoming progressively more congested or unstable. At 80ms jitter, the jitter buffer (typically 50–150ms deep) may be overwhelmed — some packets arrive too late to play in sequence and must be discarded. The user experiences increasingly choppy audio. Investigate the network path at the time of the jitter increase — IO Graphs overlaid with the RTP stream timing will show if total traffic increased when jitter spiked.
Section 3

RTP Media Analysis

RTP (Real-time Transport Protocol) carries digitized voice samples in UDP datagrams. The RTP header provides the metadata needed to measure call quality.

RTP Header FieldPurpose
VersionAlways 2 for current RTP
Payload Type (PT)Identifies codec: 0 = G.711 u-law, 8 = G.711 a-law, 18 = G.729
Sequence NumberIncrements by 1 per packet — gaps indicate packet loss
TimestampTime of first sample in packet, used for jitter calculation (not wall clock)
SSRCSynchronization Source — unique identifier for each RTP stream
VoIP quality thresholds Packet loss < 1% (above = audible dropouts). Jitter < 30ms (above = choppy audio). Latency < 150ms one-way (above = unnatural conversational delays). Out-of-order packets are rare on LAN, more common on WAN. Above these thresholds users report degraded call quality — Wireshark measures all three from the captured RTP stream.
🧠
MENTAL NOTE
RTP fields: Payload Type (codec ID), Sequence Number (loss/reorder detection), Timestamp (jitter calculation), SSRC (stream identifier). Quality: loss<1%, jitter<30ms, latency<150ms. RTP uses UDP — lost packet = gone, no recovery. G.711: 20ms packets = 50 packets/sec per stream. Filter: rtp. Jitter buffer compensates for network jitter up to ~150ms.

💭 THINK FIRST · WIRESHARK VOIP TOOLS

Wireshark has a dedicated VoIP analysis toolkit in the Telephony menu that goes beyond generic packet analysis. These tools understand the VoIP-specific semantics of SIP and RTP, presenting quality metrics, call timelines, and even audio playback — capabilities impossible with standard filters and packet list analysis.

  • A user reports a 3-second period of silence mid-call. Using Wireshark VoIP tools, how would you locate the cause?
  • You use Telephony → VoIP Calls → Player to play back a call but hear nothing. What are two possible reasons?
Q1 — LOCATING A 3-SECOND SILENCE MID-CALL
(1) Open Telephony → VoIP Calls, find the call, click "Flow Sequence" to see the SIP/RTP ladder diagram. (2) Click "Player" and look for the 3-second gap in the waveform display — the timeline shows exactly when audio was absent. (3) Switch to Telephony → RTP → RTP Stream Analysis for the affected RTP stream and look at the sequence number column — a gap of ~150 sequence numbers (at 50 packets/sec × 3 seconds) at the relevant timestamp indicates packet loss. If no gap in sequence numbers but silence, check for RTP packets with zero-length payloads or codec-level silence suppression. (4) Correlate with IO Graph — overlay the RTP stream with total traffic to see if a network congestion event caused loss.
Q2 — WHY THE VOIP PLAYER PRODUCES NO AUDIO
(1) The RTP is encrypted (SRTP) — without decryption keys, Wireshark can't decode the audio. Check if the packets show as SRTP rather than RTP in the protocol column. (2) The codec is not supported by Wireshark's built-in player — Wireshark's player natively supports G.711 (u-law and a-law). If the call uses G.729, Opus, or another compressed codec, the player may produce silence or garbled output. G.711 calls are most reliably playable.
Section 4

Wireshark VoIP Analysis Tools

Wireshark's Telephony menu provides a suite of VoIP-aware tools that interpret SIP and RTP semantics, surface quality metrics automatically, and can even play back captured voice audio.

ToolHow to AccessWhat It Shows
VoIP CallsTelephony → VoIP CallsAll detected calls with start time, duration, caller, callee, protocol, quality metrics. Select a call → Flow Sequence (SIP ladder) or Player (RTP audio).
RTP StreamsTelephony → RTP → RTP StreamsAll detected RTP streams with packet count, loss%, max delta, max jitter.
RTP Stream AnalysisTelephony → RTP → RTP Stream AnalysisPer-packet detail for a selected stream: sequence numbers, timestamps, delta, jitter, loss markers.
IO GraphsStatistics → IO GraphsOverlay RTP traffic with network events for timing correlation.
Audio playback of captured calls Telephony → VoIP Calls → select call → Player → Play — you can literally listen to the captured voice call through your speakers if the RTP is unencrypted G.711. This is a powerful forensics and QoS troubleshooting tool.
🧠
MENTAL NOTE
VoIP toolkit: Telephony → VoIP Calls (overview + flow + playback). Telephony → RTP → RTP Streams (per-stream quality). RTP Stream Analysis = per-packet jitter/loss detail. Audio playback = VoIP Calls → Player (G.711 works, G.729/SRTP may not). SRTP = encrypted RTP (no playback without keys).
