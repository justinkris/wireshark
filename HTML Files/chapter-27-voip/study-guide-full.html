Analyze Voice over IP (VoIP) Traffic

💡THINK FIRST · PURPOSE OF VoIP

VoIP uses SIP for signaling (call setup/teardown) and RTP for the actual audio stream. SIP uses TCP or UDP; RTP always uses UDP. Why is RTP always UDP and never TCP? And what happens to the conversation quality if even a small percentage of RTP packets are lost?

HINT

Think about what TCP does when it detects packet loss — retransmission. Why would that be worse than just dropping an audio packet?

MODEL ANSWER

RTP must use UDP because TCP retransmissions introduce unpredictable delays. If an audio packet arrives 200ms late (after TCP retransmission), it's USELESS — you can't play audio out of sequence. It's better to play silence (drop the late packet) than to wait for it and play audio out of order. Even 1-2% packet loss makes voice quality terrible; 5%+ makes calls unusable. Jitter (variation in packet arrival times) is equally destructive — RTP receivers use a jitter buffer to smooth out variations, but large jitter exhausts the buffer and causes dropouts.

The Purpose of VoIP

VoIP (Voice over IP) transmits real-time audio over IP networks. The two key protocols are:

  • SIP (Session Initiation Protocol, RFC 3261): Handles call signaling — setup, modification, and teardown. SIP uses TCP or UDP, typically port 5060 (5061 for TLS).
  • RTP (Real-time Transport Protocol, RFC 3550): Carries the actual audio/video media. Always uses UDP with dynamically assigned ports (typically 16384-32767). RTCP (RTP Control Protocol) monitors quality and provides statistics.

VoIP quality metrics (measured by RTCP and analyzable in Wireshark):

  • MOS score: Mean Opinion Score 1-5 (5=excellent, 4=good, 3=fair, 2=poor, 1=bad)
  • Jitter: Variation in packet arrival times — destroys voice quality
  • Packet loss: Even 1% loss noticeably degrades quality
  • Latency: One-way delay >150ms is noticeable; >400ms makes conversation awkward
🧠
MENTAL NOTE
VoIP = SIP (signaling, TCP/UDP port 5060) + RTP (audio, UDP dynamic ports). RTP = always UDP (TCP retransmissions = useless late audio). Quality: <150ms latency, <1% loss, <30ms jitter for good MOS. Use Statistics | VoIP Calls for call analysis. RTP stream: Statistics | RTP | Show All Streams.

💡THINK FIRST · SIP SIGNALING

A SIP INVITE starts a call. The response codes are similar to HTTP. What does a 180 Ringing mean? What does 200 OK mean in the context of a SIP call? And what is the difference between a SIP BYE and a SIP CANCEL?

HINT

Think about the SIP call lifecycle: INVITE → 100 Trying → 180 Ringing → 200 OK → ACK → (call) → BYE → 200 OK.

MODEL ANSWER

180 Ringing: the called party's phone is alerting them (ringing). 200 OK: the call was answered (the callee picked up). ACK: three-way handshake completion for call setup. BYE: end an established call. CANCEL: cancel a pending INVITE that hasn't been answered yet (caller hung up before callee picked up). SIP response code ranges similar to HTTP: 1xx=provisional, 2xx=success, 3xx=redirect, 4xx=client error, 5xx=server error, 6xx=global failure.

Analyze SIP Signaling

SIP is a text-based protocol similar to HTTP. SIP signaling controls call setup, modification (hold, transfer), and teardown.

SIP request methods:

  • INVITE: Request a call session
  • ACK: Acknowledge final response to INVITE (three-way handshake)
  • BYE: Terminate an established call
  • CANCEL: Cancel a pending INVITE (unanswered call)
  • REGISTER: Register user agent with SIP server
  • OPTIONS: Query capabilities
  • REFER: Call transfer
  • SUBSCRIBE/NOTIFY: Event notification (voicemail, presence)

Key SIP response codes: 100 Trying, 180 Ringing, 200 OK, 401 Unauthorized (need credentials), 403 Forbidden, 404 Not Found (user doesn't exist), 486 Busy Here, 487 Request Terminated (call cancelled), 503 Service Unavailable.

The SIP INVITE contains an SDP (Session Description Protocol) body that negotiates the audio codec, RTP port numbers, and session parameters. The 200 OK response also contains an SDP body confirming the agreed parameters. This SDP exchange tells both sides where to send RTP audio.

SIP INVITE CONTAINS SDP

The INVITE message body (SDP) contains: c= IP address (where to send RTP), m= audio port codec-list (RTP port and supported codecs), and a= rtpmap:payload-type codec/sample-rate (codec details). The 200 OK response SDP confirms the chosen codec and the server's RTP port. Wireshark shows both SDP messages — use them to find the RTP port numbers being negotiated.

🧠
MENTAL NOTE
SIP: INVITE→100 Trying→180 Ringing→200 OK→ACK=call setup. BYE=end established call. CANCEL=end pending INVITE. SDP in INVITE/200 OK = negotiate RTP ports and codecs. Filter: sip.Method==INVITE. Response codes like HTTP: 2xx=success, 4xx=client error, 5xx=server error.

💡THINK FIRST · RTP MEDIA STREAMS

RTP packets carry audio data with sequence numbers and timestamps. Unlike TCP sequence numbers, RTP sequence numbers increment by 1 per packet regardless of payload size. RTP timestamps increment by the number of samples per packet. For G.711 (8kHz, 20ms packets), how many samples per packet? And how does Wireshark use sequence numbers and timestamps to detect lost packets and jitter?

HINT

8kHz sample rate × 0.020s per packet = 160 samples per packet. What does a gap in sequence numbers tell you?

MODEL ANSWER

G.711 at 8kHz: 160 samples per 20ms packet. RTP timestamp increments by 160 per packet. A sequence number gap (e.g., 1,2,4 — 3 is missing) indicates a lost packet. Timestamp gaps larger than expected (e.g., timestamp jumps by 320 instead of 160) indicate either a lost packet or silence suppression (VAD). Wireshark: Statistics | RTP | Show All Streams — displays each RTP stream with loss count, max jitter, and stream duration. Click a stream to see packet-by-packet analysis. Wireshark can play back RTP audio: right-click a stream → Play Stream.

Analyze RTP Media Streams

RTP (Real-time Transport Protocol) carries the actual voice data. Key RTP header fields:

  • Payload Type: Codec identifier (0=G.711 μ-law, 8=G.711 A-law, 9=G.722, 18=G.729)
  • Sequence Number: Increments by 1 per packet — gaps indicate packet loss
  • Timestamp: Media sampling time — used for playback synchronization and jitter calculation
  • SSRC: Synchronization Source identifier — unique ID for each RTP stream
  • Marker bit: Set on first packet of a talk spurt (end of silence suppression)

Analyze RTP streams: Statistics | RTP | Show All Streams. This shows each RTP stream with:

  • Source and destination IP:port
  • Payload type and codec
  • Packet count, expected packets, and loss percentage
  • Maximum jitter in milliseconds

To play back captured VoIP audio: select an RTP stream in the RTP Streams window → click Play Streams → hear the actual conversation.

ANALYZE VOIP CALLS

Select Statistics | VoIP Calls to see a summary of all VoIP calls in the trace file. Click a call to see the call flow diagram showing SIP messages, response codes, and timing. Right-click → Player to play the audio. This is extremely useful for diagnosing one-way audio, call quality, and setup failures.

MENTAL NOTE
RTP: sequence number (loss detection) + timestamp (jitter/sync). SSRC = unique stream ID. Payload type = codec. Statistics | RTP | Show All Streams = quality metrics. Statistics | VoIP Calls = call flow diagram. Play captured VoIP: right-click stream → Play. G.711=8kHz, 160 samples/20ms packet. Jitter buffer smooths arrival variation — depletes with high jitter.

💡THINK FIRST · VoIP PROBLEMS

Common VoIP problems: one-way audio, choppy audio, dropped calls. One-way audio is when one side can hear but the other can't. What causes one-way audio in a VoIP call? And if you see RTP packets going in both directions but users report choppy audio, what would you check in Wireshark?

HINT

Think about what's needed for two-way audio: RTP flowing in BOTH directions, correctly addressed, with acceptable quality metrics.

MODEL ANSWER

One-way audio causes: (1) NAT problem — the SIP INVITE sends the internal IP address in the SDP, but the RTP packets should go to the public IP. If NAT traversal (STUN/TURN) isn't working, one side's RTP goes to the wrong address. (2) Firewall blocking one direction of RTP. (3) SIP ALG (Application Layer Gateway) incorrectly modifying SIP headers. Check: are RTP packets present in BOTH directions? If not = NAT/firewall issue. If yes = check quality: jitter >30ms = choppy audio. Loss >1% = choppy. Latency >150ms = noticeable delay.

VoIP Problems & Filters

Common VoIP problems and their Wireshark signatures:

  • One-way audio: RTP flows only in one direction. Check: rtp filter, see if both sides have RTP streams
  • Choppy audio: High jitter or packet loss in RTP streams. Check Statistics | RTP | Show All Streams for loss% and max jitter
  • Call drops: Unexpected BYE or SIP error response. Filter: sip.Method==BYE or sip.Status-Code>=400
  • Registration failures: REGISTER → 401/403/503. Filter: sip.Method==REGISTER
  • No audio path: SIP signaling succeeds (200 OK, ACK) but no RTP flows — NAT traversal failure
  • DTMF (dial tones) not working: Wrong DTMF method (inband vs out-of-band RFC 2833)

CHAPTER SUMMARY

TL;DR — Chapter 27

VoIP uses SIP for call signaling and RTP for real-time audio transport. SIP sets up, modifies, and tears down calls using text-based request/response messages similar to HTTP. RTP carries voice data over UDP — TCP is never used for RTP because TCP retransmissions add unacceptable delays for real-time audio.

Key VoIP quality metrics: latency (<150ms), jitter (<30ms), and packet loss (<1%). Wireshark can analyze all three using Statistics | RTP | Show All Streams. Wireshark can also play back captured VoIP audio and display the complete SIP call flow diagram via Statistics | VoIP Calls.

Review Questions

Q27.1
What is the purpose of SIP?
HINT

SIP is the signaling protocol for VoIP — think call setup, modification, teardown.

ANSWER

SIP (Session Initiation Protocol, RFC 3261) is used to establish, modify, and terminate multimedia sessions (primarily VoIP calls). SIP handles call signaling: the INVITE starts a call, the BYE terminates it, and CANCEL cancels a pending unanswered INVITE. SIP uses TCP or UDP on port 5060 (5061 for TLS). SIP does NOT carry audio — it negotiates the parameters for the audio session (which codec, which RTP ports) using SDP (Session Description Protocol) in the message body.

Q27.2
Why does RTP use UDP instead of TCP?
HINT

Think about what TCP does when packets are lost and why that's worse than silence for real-time audio.

ANSWER

RTP uses UDP because TCP retransmissions add unpredictable delays that are unacceptable for real-time audio. If an RTP packet is lost, a TCP retransmission might arrive 100-500ms later — by which time the audio should have already been played out. A late packet is useless for real-time audio (you can't play audio out of order). It's better to play a brief silence (drop the late packet) than to delay all subsequent audio waiting for retransmission. UDP also has lower overhead, reducing per-packet latency.

Q27.3
What three metrics determine VoIP call quality?
HINT

These metrics are reported by RTCP and shown in Wireshark's RTP analysis.

ANSWER

The three key VoIP quality metrics are: (1) Latency: one-way end-to-end delay — should be <150ms for natural conversation, >400ms makes conversation very awkward. (2) Jitter: variation in packet arrival times — should be <30ms for good quality. Large jitter depletes the jitter buffer and causes audio dropouts. (3) Packet loss: even 1% loss is noticeable in voice quality. These combine into a MOS (Mean Opinion Score) from 1-5, with 4+ being good quality.

Q27.4
What Wireshark statistic window shows all RTP streams with quality metrics?
HINT

Think about the Statistics menu — where can you see all RTP streams and their quality?

ANSWER

Select Statistics | RTP | Show All Streams to see all RTP streams in the trace file. This window shows each stream identified by its SSRC (Synchronization Source), displaying: source IP:port, destination IP:port, payload type (codec), packet count, expected packets, loss percentage, and maximum jitter in milliseconds. Click a stream to analyze it in detail. Select Statistics | VoIP Calls to see the complete SIP call flow diagram and play back the audio.

Q27.5
What causes one-way audio in a VoIP call?
HINT

If one party can hear but not be heard, what network issue is most likely?

ANSWER

One-way audio (one side can hear but cannot be heard) is most commonly caused by a NAT traversal problem. The SIP INVITE contains the caller's IP address in the SDP body — but if the caller is behind NAT, this is a private IP address. The callee tries to send RTP to this private address, which is unreachable from outside the NAT. Other causes: asymmetric firewall rules blocking RTP in one direction, or a SIP ALG (Application Layer Gateway) on a router incorrectly modifying SIP headers. Diagnose by filtering for rtp — if RTP flows in only one direction, NAT/firewall is the likely cause.
