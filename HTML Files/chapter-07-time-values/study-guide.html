💭 THINK FIRST · TIME DISPLAY FORMATS

Wireshark's time column is a configurable window into when packets arrived. The right format for a given analysis task can be the difference between finding a problem in seconds and staring at numbers that don't connect to anything meaningful.

  • You're correlating a Wireshark capture with a firewall log that uses wall-clock timestamps. Which time display format should you use in Wireshark?
  • What is the difference between "Seconds Since Previous Captured Packet" and "Seconds Since Previous Displayed Packet"? When would the two differ?
Q1 — CORRELATING WITH FIREWALL LOGS
Use "Date and Time of Day" (Absolute Time) — this shows the actual wall-clock timestamp for each packet, which directly matches the timestamps in external logs such as firewall logs, syslog, or application logs. The default "Seconds Since Beginning of Capture" is a relative value that has no meaning outside of Wireshark and cannot be directly correlated with any external timestamp. Switch via View → Time Display Format → Date and Time of Day.
Q2 — CAPTURED VS DISPLAYED DELTA
"Seconds Since Previous Captured Packet" measures the gap from the prior packet in the capture file, regardless of any active display filter. "Seconds Since Previous Displayed Packet" measures the gap from the prior packet that is currently visible given the active display filter. The two differ whenever a display filter is active — filtered-out packets contribute to the "captured" delta but are invisible to the "displayed" delta. For example, if you filter to show only HTTP packets, "displayed" deltas show the time between HTTP packets; "captured" deltas show how long elapsed since the immediately prior packet of any type, which may be a TCP ACK in between.
Section 1

Time Display Formats

Wireshark can display time in several formats, configurable via View → Time Display Format. Choosing the right format for your analysis context prevents time wasted mapping relative values to external logs.

FormatBest Used For
Seconds Since Beginning of Capture (default)General analysis, relative timing within a trace
Absolute Date and Time of DayCorrelating with firewall logs, syslog, application logs, alerts
Seconds Since Previous Captured PacketFinding pauses between any two consecutive packets
Seconds Since Previous Displayed PacketMeasuring timing within a filtered view
Seconds Since Reference FrameMeasuring elapsed time from a manually pinned event
UTC Date and TimeCross-timezone correlation with global teams or cloud logs

💭 THINK FIRST · SETTING TIME REFERENCES

Time References let you pin any packet as "time zero" — transforming all subsequent timestamps into elapsed time from that event. This is the precise tool for answering "how long did this transaction take?" without doing mental arithmetic.

  • You want to measure exactly how long a complete HTTP transaction takes from first SYN to last data packet. How would you use Time References to do this?
  • After setting a time reference, do you need to save the file for the reference to persist? Why or why not?
Q1 — MEASURING HTTP TRANSACTION WITH TIME REFERENCE
Right-click the first SYN packet of the connection → Set/Unset Time Reference (or press Ctrl+T). The packet will display "REF" in the Time column. Then switch the time display format to View → Time Display Format → Seconds Since Reference Frame. Now every subsequent packet shows exactly how many seconds elapsed from the SYN. Find the last data packet of the HTTP response and read its Time value — that is the total transaction time from connection start to last byte received. This requires no arithmetic and immediately answers where in the timeline delays occurred.
Q2 — DO TIME REFERENCES PERSIST WHEN YOU SAVE?
No — time references are display-only annotations in your current Wireshark session. They are not stored in the capture file itself (.pcapng format has no field for Wireshark UI state). When you close and reopen the file, or when someone else opens the same file, all time references are gone. This is by design — time references are analysis scratch notes, not part of the evidence. If you need to preserve a reference point, note the packet number and reapply the reference after reopening. Similarly, switching display format back to the default clears the visual effect of the reference without removing it.
Section 2

Setting Time References

A Time Reference pins a specific packet as the zero point — all subsequent time values show the delta from that reference packet. Setting a reference: right-click the packet → Set/Unset Time Reference (or Ctrl+T). The reference packet displays "REF" in the Time column.

You can set multiple references to create checkpoints throughout a trace. Time references do not affect the file — they are display-only annotations that are lost when you close Wireshark.

Measuring application response time with Time Reference Set a time reference on the first SYN of a connection, then switch to View → Time Display Format → Seconds Since Reference Frame. Every packet in the connection now shows elapsed time from connection start — ideal for measuring application response time end-to-end.
🧠
MENTAL NOTE
Time Reference: right-click packet → Set/Unset Time Reference (Ctrl+T). "REF" shows in Time column. Switch to View → Time Display Format → Seconds Since Reference. Non-destructive — doesn't change the file. Use to measure transaction timing from a specific event.

💭 THINK FIRST · DELTA TIMES AND FINDING DELAYS

Delta time is the most direct performance diagnostic in Wireshark. A large delta after a client request points to the server. A large delta after a SYN points to the network. Location in the exchange tells you who is slow.

  • You see a packet with a delta time of 3.2 seconds occurring right after a client sends an HTTP GET request. What does this suggest about where the problem is?
  • You filter to show only TCP packets for a specific stream. Should you use "delta since previous captured" or "delta since previous displayed" to measure timing within that stream? Why?
Q1 — 3.2 SECOND DELTA AFTER HTTP GET
A 3.2-second gap between the client sending an HTTP GET and the server sending its first response strongly suggests a server processing delay, not a network problem. The client sent the request (network delivered it), and the server took 3.2 seconds before responding. You can confirm by checking the RTT — look at the time between the SYN and SYN-ACK in the same connection. If RTT is small (e.g., 2ms), the network is fast and the 3.2-second gap is purely server-side: slow database query, resource contention, application bottleneck, or overloaded server.
Q2 — CAPTURED VS DISPLAYED DELTA FOR A FILTERED STREAM
Use "delta since previous displayed" when measuring timing within a filtered stream. When you apply a filter for a specific TCP stream (e.g., tcp.stream == 5), only the packets from that stream are visible. "Displayed" delta correctly measures the gap between consecutive packets in that stream. "Captured" delta would measure the gap from the prior packet in the entire capture — which could be a packet from a completely different connection that happened to arrive between your stream packets, giving you a meaningless small delta that doesn't reflect the stream's own timing.
Section 3

Delta Times and Finding Delays

The "delta time" between packets is the key to finding performance problems. Adding a Delta Time column lets you instantly spot large gaps. Interpret delta by its position in the exchange:

Large Delta After…Indicates
Client sends HTTP GET or application requestServer processing delay (application or database bottleneck)
Client sends SYNNetwork RTT — high-latency path to the server
Server sends data segmentCould be client-side ACK delay or network loss/retransmit
Any packet (consistent large gaps)Capture system overload — the capture tool is dropping packets

Adding a delta column: right-click any column header → Column Preferences → add a column with field frame.time_delta_displayed. Or right-click the frame.time_delta_displayed field in Packet Details → Apply as Column.

Client delta vs network RTT — two different problems Distinguish between client-side delta (time between sending a request and receiving a response) and network RTT (time between SYN and SYN-ACK). A large client-side delta with small RTT = server processing problem, not network.
🧠
MENTAL NOTE
Delta time = gap between packets. Large delta after request = server delay. Large delta after SYN = network RTT. Add delta column: frame.time_delta_displayed as custom column. Delta since previous captured vs since previous displayed — watch the difference when filtering.

💭 THINK FIRST · INTERPRETING CAPTURE SUMMARIES

The Capture File Properties dialog is the first stop when opening any unfamiliar trace. It tells you what you're working with before you read a single packet — scope, duration, volume, and whether the capture is complete or filtered.

  • You open a capture and the statistics show average packet size of 62 bytes. What kind of traffic is likely dominant in this capture?
  • The Capture File Properties shows a "capture filter" was applied. How does this affect your analysis conclusions?
Q1 — AVERAGE PACKET SIZE 62 BYTES
An average packet size of 62 bytes strongly suggests the capture is dominated by TCP control traffic — ACKs, keepalives, and small handshake packets — rather than data transfer. A TCP ACK with no data payload has a 20-byte IP header, 20-byte TCP header, and 14-byte Ethernet header, totaling 54 bytes. Small deltas for header exchanges and keepalives bring the average near 62 bytes. This pattern is typical of idle or lightly loaded connections, or a trace that was captured during a period of connection maintenance rather than active file transfer. Alternatively, DNS traffic (typically 60–80 bytes) or a scan generating many small probe packets could produce this average.
Q2 — CAPTURE FILTER APPLIED — IMPACT ON CONCLUSIONS
A capture filter means the trace is incomplete by design — only traffic matching the filter was recorded. This critically affects any negative conclusion ("there is no DNS traffic," "host X never communicated with host Y") — those conclusions may be wrong because the traffic was simply filtered out and never captured. Before concluding that something is absent, verify whether the active capture filter would have excluded it. You cannot apply a display filter to see traffic that was never captured — unlike display filters, capture filters permanently discard non-matching packets at capture time. Always check the capture filter in File Properties before making absence-of-evidence conclusions.
Section 4

Interpreting Capture Summaries

The Capture File Properties dialog (Statistics → Capture File Properties) is the first thing to check when you open an unfamiliar trace. It provides: file name and format, capture interface and OS, start/stop time, total duration, total packets, average packet rate, average/min/max packet size, total bytes, and the capture filter used.

Check the capture filter before concluding "not present" Statistics → Capture File Properties also shows the "capture filter" used — if the capture was filtered, you are not seeing all traffic. Check this before concluding "no such packet exists in the trace." Traffic not matching the capture filter was never recorded.
