Measure Slow DNS Response Time

Step 1

Open dns-slow.pcapng. Select View | Time Display Format | Seconds since Previous Displayed Packet.

My Notes
Q1

How much time elapsed between the first and second DNS query for www.ncmec.org?

Your Answer
Model Answer
You should see 1.000620 seconds between the first and second DNS query for www.ncmec.org. This significant 1-second delay reveals a slow retransmission or timeout interval in the DNS resolution process.
Q2

How much time elapsed between the first and second DNS response for www.ncmec.org? Right click on the first DNS response and set a time reference to measure this value.

Your Answer
Model Answer
You should see 0.184489 seconds between the first and second DNS response packet. Note: by the time the second DNS response arrived, the client had already closed the listening port for that response — that's why the client sent an ICMP Destination Unreachable/Port Unreachable response.
Q3

How much time did it take for the server to answer the DNS query in packet 98?

Your Answer
Model Answer
You should see 0.207250 seconds elapsed between the DNS query in packet 98 and the DNS response in packet 107. Set a time reference on packet 98 to measure this precisely.

Measure a High Latency Path

Step 4

Open http-download-good.pcapng. Reset the Time column to Seconds since Previous Displayed Packet.

My Notes
Q4

What is the latency time between the first and second packets of the TCP handshake (packets 1 and 2)?

Your Answer
Model Answer
You should see 0.179989 seconds. This is the round-trip path latency time measured from the SYN to the SYN/ACK — approximately 180ms, which is relatively high and may be caused by geographic distance or slow links along the path.
Q5

Sort the Time column. What is the largest time delay in the trace file?

Your Answer
Model Answer
You should see 2.753091 seconds as the largest time delay in the trace file. This large gap is the single biggest delay in the download session.
Q6

Sort by the Number (No.) column to return to original order. What happened around the largest time delay in the trace file?

Your Answer
Model Answer
A TCP Window Update process occurred at the time of the 2.753091 second delay. The sender stopped transmitting because the receiver's window shrank to zero or near zero, and the delay represents waiting for the receiver to advertise a larger window. Refer to Chapter 13: Use Wireshark's Expert System for more on Window Update packets.

Review Questions
Official WCNA exam-style review questions from Chapter 7. Write your answer before revealing the model answer.
Q7.1

How can the time setting be used to identify the cause of network performance problems?

Your Answer
Model Answer
One key way is to set the Time column to Seconds since Previous Displayed Packet and look for large gaps in time during what should be a continuous streaming process. For example, during a file transfer the data should flow without large gaps — any significant pauses indicate where the bottleneck is occurring, whether at the client, server, or along the path.
Q7.2

You have opened a trace file sent to you from another company. The timestamp only shows millisecond resolution. Why? Can you improve the timestamp resolution of the trace file?

Your Answer
Model Answer
Most likely the analyzer used to capture the trace file could not provide more precise timestamps — the capture hardware or driver only supports millisecond-level timing. You cannot alter the timestamp resolution of captured trace files. The resolution is determined at capture time and is fixed in the saved pcap/pcapng file.
Q7.3

You have opened a trace file that contains 5 separate conversations. How can Time Reference be used to measure the time elapsed in one of the conversations?

Your Answer
Model Answer
Set a Time Reference on the first packet of the conversation you are interested in and scroll to the end of the conversation. The Time column will indicate the time elapsed from the Time Reference packet to the last packet. Alternatively, filter on the conversation of interest using a display filter, then set the Time Reference on the first displayed packet — the last displayed packet's time shows the total elapsed time for that conversation.
