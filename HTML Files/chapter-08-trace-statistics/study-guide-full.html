💡THINK FIRST · PROTOCOL HIERARCHY

You open Protocol Hierarchy and see 'Data' listed under TCP representing 40% of traffic. What does this mean, and what are your next three investigation steps?

HINT

When Wireshark can't identify the application protocol inside TCP, what does it label the payload?

MODEL ANSWER

'Data' = Wireshark dissected TCP but couldn't identify the application protocol — it's running on a non-standard port with no registered dissector. (1) Open Conversations → TCP tab, sort by bytes — find which port numbers carry this traffic; (2) Right-click a conversation → Apply as Filter; (3) Use Analyze → Decode As to try assigning a dissector (HTTP, FTP, etc.); (4) Use Follow TCP Stream to read the raw payload and identify the protocol by its structure and keywords.

Protocol Hierarchy

Open via Statistics → Protocol Hierarchy. Shows a tree of all protocols in the capture with packet count and byte percentage at each layer.

Reading the Tree

Each row is a protocol. Child rows are protocols encapsulated within the parent. Percentage = that protocol's share of total bytes.

  • Right-click any protocol → Apply as Filter to jump to those packets
  • 'Data' under TCP = unknown application protocol (non-standard port or missing dissector)
  • High ARP % = possible ARP storm or misconfigured hosts
  • High ICMP % = possible loop, scan, or error storm
FIRST TRIAGE TOOLOpen Protocol Hierarchy first on any unfamiliar capture. In 10 seconds you know: is this mostly HTTP? DNS-heavy? VoIP (RTP/SIP)? A lot of 'Data' under TCP? This guides every subsequent analysis step.
🧠
MENTAL NOTE
Protocol Hierarchy = protocol distribution by packets and bytes. 'Data' under TCP = unknown app protocol. First-look tool. Right-click → Apply as Filter to isolate. High ARP% = possible storm. High ICMP% = possible error storm or scan.

💡THINK FIRST · CONVERSATIONS AND ENDPOINTS

The Conversations window shows one IP pair responsible for 80% of bytes. What are three different explanations, and what additional information would you check to distinguish them?

HINT

80% from one pair could be normal (large file transfer) or abnormal (exfiltration, DDoS). What context helps distinguish?

MODEL ANSWER

(1) Legitimate bulk transfer: large packet sizes (~1500 bytes), few retransmits, consistent throughput, business-hours timing; (2) Data exfiltration: large outbound bytes to unusual destination IP, encrypted channel, outside business hours; (3) Flood/DDoS: tiny packets at extreme rate, many RSTs, source IPs may be spoofed. Check: Conversations TCP tab for port numbers (what service?), Endpoints for packet size distribution, time of day from absolute timestamps, and whether the destination is internal or external.

Conversations and Endpoints

Conversations

Statistics → Conversations. Shows communicating address pairs at each layer (Ethernet, IPv4, IPv6, TCP, UDP). For each pair: packets and bytes in each direction, duration, relative start time.

Sort by Bytes to find top talkers. Right-click → Apply as Filter to isolate a conversation. Click Follow Stream to open the TCP/UDP reassembly view.

Endpoints

Statistics → Endpoints. One row per unique address. Shows total packets and bytes to/from that host. Identify:

  • Top talkers (sort by bytes)
  • Scanners (many small conversations to many different destinations)
  • Broadcast/multicast sources

GeoIP Mapping

With MaxMind GeoIP databases configured (Preferences → Name Resolution), endpoints show country, city, lat/lon. Click Map for an interactive geographic view.

QUICK FILTERConversations: right-click → Apply as Filter → A ↔ B — instantly filters packet list to show only packets between those two hosts. Faster than typing a display filter manually.
🧠
MENTAL NOTE
Conversations = address pairs (src+dst). Endpoints = individual hosts. Sort Conversations by bytes → top talkers. Sort by duration → long-lived sessions. Right-click → Apply as Filter. Endpoints + GeoIP shows geographic distribution. Scanners: many small conversations to diverse destinations.

💡THINK FIRST · IO GRAPHS

IO Graphs plot packet or byte rate over time. How would you use IO Graphs to identify the exact moment a SYN flood attack started in a 10-minute capture?

HINT

What does a SYN flood look like in terms of packet rate? How do you add comparison lines?

MODEL ANSWER

Add two lines in Statistics → IO Graphs: Line 1 = all traffic (baseline, Y=packets/s); Line 2 = filter 'tcp.flags.syn == 1 and !tcp.flags.ack == 1' (SYN-only packets), Y=packets/s, red. A SYN flood appears as a spike in Line 2 that's not matched by Line 1's overall rate increase proportionally — the SYN rate spikes but ACK rate stays low (connections never complete). The timestamp on the x-axis at the spike marks the attack start. Set interval to 100ms for precise timing.

IO Graphs

Statistics → IO Graphs. Plots packet rate or byte rate over time. Default: one line = all packets, 1-second interval.

Multiple Lines

Add up to 16 lines, each with its own display filter and color. Examples:

  • Line 1: (blank) — all traffic baseline
  • Line 2: tcp.analysis.retransmission — retransmission rate
  • Line 3: http.response.code >= 500 — server errors over time

Y-Axis Options

  • Packets/s, Bytes/s, Bits/s — rate metrics
  • Sum, Min, Max, Avg — of a specific field value (e.g. avg RTT = tcp.analysis.ack_rtt, Y=Avg)

Interval

Adjust 1ms–10s. For burst detection: 100ms. For long-term trends: 10s or 1min.

ADVANCEDPlot tcp.analysis.ack_rtt with Y=Average to graph average RTT over time. A climbing RTT trend = growing congestion. Covered in detail in Chapter 21.
🧠
MENTAL NOTE
IO Graphs: multiple filter lines on same time axis. Compare all traffic vs. retransmissions vs. error responses. A dip in throughput line coinciding with a spike in retransmission line = congestion event. Adjust interval to match the timescale of the phenomenon you're investigating.

💡THINK FIRST · FLOW GRAPH

The Flow Graph shows packets as arrows on a ladder diagram. For what type of analysis is this uniquely suited compared to the packet list?

HINT

Think about multi-party protocols like SIP. How does a ladder diagram differ from reading packets line by line?

MODEL ANSWER

Flow Graph excels at multi-party exchanges: SIP call setup (Client → Proxy → Registrar → Media Server), DHCP DORA (client ↔ relay ↔ server), DNS with recursion. The packet list shows all packets interleaved chronologically — you must mentally reconstruct who talked to whom. The Flow Graph makes this instantly visual: directed arrows between host columns, time flowing down, making stalled handshakes and missing responses immediately obvious.

Flow Graph

Statistics → Flow Graph. Time flows downward; hosts are vertical columns; packets are horizontal arrows with labels.

Options

  • Flow type: TCP flows (SYN/ACK/FIN/RST flags shown) or General flows (all packets, labeled by highest protocol)
  • Limit to displayed packets: respects current display filter — use this to show one conversation

Best Use Cases

  • SIP/VoIP call flow (INVITE, 180, 200, ACK, BYE)
  • TCP three-way handshake verification
  • DHCP DORA exchange
  • DNS query/response with relay hops
  • Any multi-host protocol exchange
TIPApply a display filter to isolate 2-3 hosts BEFORE opening the Flow Graph. A flow graph of 50+ hosts is unreadable — filter first.
🧠
MENTAL NOTE
Flow Graph = ladder diagram, time down. Multi-party exchanges become visual. Always filter first — 50+ hosts = unreadable. TCP flow type labels flags; General type labels by application protocol. 'Limit to displayed packets' is the key option for focusing on one conversation.

TL;DR — CHAPTER 8

First triage order on any capture: (1) Protocol Hierarchy — protocol mix and 'Data' under TCP; (2) Conversations — top talkers, filter on a pair; (3) Endpoints — individual hosts, GeoIP. These four tools give you the big picture before reading a single packet.

Review Questions

Q8.1
You open Protocol Hierarchy and see 'Data' under TCP = 40%. What does this mean and what are your next steps?
HINT

When Wireshark can't identify an application protocol, what does it label it?

ANSWER

'Data' under TCP means Wireshark dissected the TCP layer but couldn't identify the application protocol — running on a non-standard port with no registered dissector. Next steps: (1) Conversations → TCP tab, sort by bytes — find which ports carry this traffic; (2) Apply as Filter to isolate those conversations; (3) Analyze → Decode As to try assigning a dissector; (4) Follow TCP Stream to read the raw payload and identify the protocol by keywords or structure.

Q8.2
In IO Graphs, you want to plot total throughput and retransmission rate on the same graph. Describe the setup.
HINT

IO Graphs support multiple lines with independent filters and Y-axis settings.

ANSWER

Statistics → IO Graphs: Line 1 — filter = empty, Y-axis = Bits/s, color = blue (total throughput); Line 2 — filter = tcp.analysis.retransmission, Y-axis = Packets/s, color = red (retransmission rate). A dip in the blue line coinciding with a spike in the red line confirms retransmissions are causing the throughput drop. Adjust interval to 100ms for finer granularity on burst events.

Q8.3
What is the primary advantage of the Flow Graph over the packet list when analyzing a SIP call setup?
HINT

How many hosts are typically involved in a SIP call? How does the ladder diagram help?

ANSWER

A SIP call may involve: client, SIP proxy, registrar, and media server. The packet list shows all packets in chronological order — you must mentally map each packet to its source and destination. The Flow Graph shows each host as a vertical column with directed arrows between them, time flowing downward. You immediately see which hosts exchanged which messages, in what order, where the call stalled, and which host failed to respond — impossible to grasp at a glance in the flat packet list.
