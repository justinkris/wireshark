💭 THINK FIRST · PROTOCOL HIERARCHY

Protocol Hierarchy is a single-click x-ray of a capture. It answers "what is this capture made of?" in seconds — and an unexpected protocol or a wildly skewed distribution is often the first sign that something is wrong.

  • You open a capture and run Protocol Hierarchy. ARP accounts for 34% of all packets. What are the two most likely causes, and how would you distinguish between them?
  • You run Protocol Hierarchy and see a protocol called "Data" under TCP at 15% — what does this usually mean?
Q1 — 34% ARP — TWO CAUSES AND HOW TO DISTINGUISH
The two most likely causes are (1) an ARP broadcast storm — a device repeatedly sending ARP requests for the same or many IP addresses at high rate, which could indicate a misconfigured or malfunctioning device, a network loop, or a scanner — and (2) a gratuitous ARP flood — a device repeatedly announcing its own IP-to-MAC mapping, common with a misconfigured HSRP/VRRP failover, a cloning error, or a MITM tool. To distinguish: display filter to show only ARP packets, then check whether the source is a single MAC flooding the same target IP (scanner/storm) or sending gratuitous ARPs for its own IP (GARP flood or MITM). Also check whether the ARP requests are answered or unanswered — unanswered ARPs at high rate suggest scanning or a broken device.
Q2 — "DATA" PROTOCOL UNDER TCP
"Data" under TCP in Protocol Hierarchy means Wireshark's dissector could not identify the application protocol running over TCP for those packets — it decoded the TCP layer correctly, but the payload did not match any registered protocol dissector. Common causes: (1) a custom or proprietary application protocol Wireshark doesn't have a dissector for, (2) an encrypted protocol (TLS after the handshake, before Wireshark knows how to decrypt it), (3) a protocol running on a non-standard port that Wireshark doesn't recognize, or (4) TCP stream data segments that are payload continuations with no protocol header to identify. Investigate by following the TCP stream to see the raw content.
Section 1

Protocol Hierarchy

Statistics → Protocol Hierarchy shows the breakdown of all protocols in the capture as a tree, with each protocol's packet count and percentage. This is the fastest single view for understanding what's in a capture. Run it on every new trace — it takes one second and gives you the complete picture.

The hierarchy is filtered by the current active display filter — run it with and without filters to see the full picture vs a focused subset. Look for: unexpected protocols, high percentages of overhead traffic (ARP, ICMP, STP), and the application protocol distribution.

Run Protocol Hierarchy first on every trace Run Protocol Hierarchy first on every new capture — it takes 1 second and gives you a complete overview before you read a single packet. An unexpected protocol at any percentage is worth investigating.

💭 THINK FIRST · CONVERSATIONS AND ENDPOINTS

Conversations and Endpoints collapse the entire capture into a ranked view of who is talking to whom, and how much. Sorting by bytes immediately surfaces the dominant flows — which is always the first question in a bandwidth or performance investigation.

  • In the Conversations view (TCP tab), you see one conversation with 50,000 packets but only 20KB total — another with 100 packets but 200MB. What does each pattern suggest?
  • How do you filter the entire Wireshark packet list to show only traffic between two specific hosts, using the Conversations dialog?
Q1 — 50K PACKETS / 20KB VS 100 PACKETS / 200MB
The first conversation (50,000 packets, 20KB) is dominated by extremely small packets — averaging 0.4 bytes of data per packet. This is characteristic of a TCP keepalive storm, a chatty IoT protocol, a scan or probe traffic where requests have no payload, or a connection with severe retransmission where many control packets are exchanged but no data is delivered. The second conversation (100 packets, 200MB) is a high-throughput bulk data transfer — averaging 2MB per packet, which indicates full-sized frames (near MTU) and efficient TCP congestion window utilization. This is normal for a file transfer, backup, or large HTTP response. The contrast shows that packet count alone is a poor indicator of bandwidth impact — bytes is the right metric for bandwidth analysis.
Q2 — FILTERING FROM CONVERSATIONS DIALOG
In the Conversations dialog (Statistics → Conversations), find the row for the two hosts you want to isolate, then double-click the row or right-click and select "Apply as Filter" → "Selected" → "A ↔ B." Wireshark will automatically apply a display filter to the main packet list showing only traffic between those two hosts. The auto-generated filter will use the address pair from that conversation row (e.g., ip.addr==10.0.0.1 and ip.addr==10.0.0.2 for an IPv4 conversation). You can also choose "Apply as Filter" → "Not Selected" to hide that conversation instead.
Section 2

Conversations and Endpoints

Statistics → Conversations shows pairs of hosts communicating, grouped by protocol (Ethernet, IPv4, IPv6, TCP, UDP). Each row shows: Address A, Address B, packets A→B, bytes A→B, packets B→A, bytes B→A, relative start time, and duration.

Statistics → Endpoints shows each individual host with total packets and bytes. Both views support double-clicking a row to generate a display filter, and right-clicking for Follow Stream or graph options.

💭 THINK FIRST · IO GRAPHS

IO Graphs turn a capture into a timeline — showing when traffic peaks occurred, not just that they occurred. Overlaying a retransmission line on total traffic is one of the most powerful diagnostic combinations in Wireshark: it shows exactly when TCP problems correlated with traffic spikes.

  • You add two lines to IO Graphs — one for all traffic and one for tcp.analysis.flags. What useful information does comparing these two lines give you?
  • The IO Graph shows a traffic spike at t=45 seconds, then drops to near zero. What are the two most likely causes of this pattern?
Q1 — TOTAL TRAFFIC VS TCP.ANALYSIS.FLAGS OVERLAY
Overlaying tcp.analysis.flags on total traffic tells you whether TCP problems correlate with traffic peaks or occur independently. If tcp.analysis.flags spikes align with the total traffic peaks, it suggests the link is saturated and dropping packets under load — a bandwidth or congestion problem. If tcp.analysis.flags spikes occur when total traffic is low, it suggests the problem is not bandwidth-related — it could be a path MTU issue, a specific server problem, or packet loss on a particular link segment regardless of overall utilization. The visual correlation (or lack of it) immediately suggests the root cause category without reading individual packets.
Q2 — TRAFFIC SPIKE THEN DROPS TO NEAR ZERO
The two most likely causes are: (1) A batch job or scheduled transfer completed — the spike represents an active transfer (backup, log upload, software update) that ran for 45 seconds and then finished, after which the connection went idle or closed. (2) Link failure or congestion collapse — the spike caused enough packet loss to trigger TCP congestion window collapse, reducing throughput to near zero as TCP enters slow start and retransmission timeout cycles. You can distinguish these by checking whether there are TCP retransmissions during and after the spike (tcp.analysis.flags filter) — if yes, it's a congestion collapse; if no TCP errors, it was a clean transfer completion.
Section 3

IO Graphs

Statistics → IO Graphs plots packet rate or bit rate over time. The default view shows all traffic as a single line. You can add multiple graph lines with different display filter expressions and colors to overlay them — for example, one line for all traffic, one for TCP retransmissions, one for a specific host.

X-axis = time; Y-axis = packets or bits per second (configurable). The interval setting controls the aggregation period per data point (default 1 second). Use IO Graphs to find when traffic spikes occur, see when a problem started, visualize the impact of a fix, or compare traffic before and after a change.

Overlay retransmissions on total traffic Add a second IO graph line with filter tcp.analysis.flags and color it red — you will see exactly when TCP problems occur relative to overall traffic peaks, immediately indicating whether packet loss is load-correlated.

💭 THINK FIRST · FLOW GRAPH

The Flow Graph is the closest thing Wireshark has to a protocol message sequence chart — it shows who sent what to whom and in what order, which makes it invaluable for understanding complex multi-step application exchanges that are hard to follow in the packet list.

  • What specific information does the TCP Time-Sequence graph reveal that the standard packet list doesn't show clearly?
  • When would you use the Flow Graph (Statistics → Flow Graph) vs the TCP Stream Graph (Statistics → TCP Stream Graphs)?
Q1 — WHAT TCP TIME-SEQUENCE GRAPH REVEALS
The TCP Time-Sequence graph plots sequence numbers on the Y-axis versus time on the X-axis. This reveals: (1) retransmissions — which appear as backward steps or horizontal lines where the sequence number goes back to an earlier value instead of advancing; (2) gaps in the sequence number space — visible as plateaus where the sender stops advancing, indicating lost segments or a zero window; (3) the overall throughput slope — a steep upward slope means fast data transfer, a shallow slope means slow or stalled transfer; (4) window size constraints — if the line plateaus and then advances in steps, the sender is window-limited. These patterns are impossible to see in the packet list where rows are sorted by time, not sequence number position.
Q2 — FLOW GRAPH VS TCP STREAM GRAPH — WHEN TO USE EACH
Use the Flow Graph (Statistics → Flow Graph) when you want to understand the message exchange order across a multi-host, multi-protocol conversation — for example, tracing a full HTTP/DNS/TLS handshake sequence involving multiple hosts. It shows any protocol, any number of hosts, as a ladder diagram. Use the TCP Stream Graph (Statistics → TCP Stream Graphs → Time-Sequence) when you are analyzing the behavior of a specific TCP connection — retransmissions, window size evolution, throughput, sequence number gaps. The TCP Stream Graph is TCP-specific and sequence-number focused; the Flow Graph is protocol-agnostic and order-focused. The Flow Graph answers "what happened first?"; the TCP Stream Graph answers "how did this TCP connection behave?"
Section 4

Flow Graph (Time-Sequence)

Statistics → Flow Graph draws a ladder diagram showing packet exchanges between hosts over time. The horizontal axis represents hosts; the vertical axis is time. Arrows show packets with labels. This visualization makes it easy to see the order of exchanges in a conversation — especially useful for handshake analysis and complex application protocol flows.

The TCP Time-Sequence graph (Statistics → TCP Stream Graphs → Time-Sequence) additionally plots sequence numbers over time, revealing retransmissions and gaps visually as backward steps or plateaus. Best for diagnosing specific TCP connection behavior.

Flow Graph as message sequence chart Statistics → Flow Graph with "All packets" selected gives you a message sequence chart (MSC) of any conversation — invaluable for understanding complex application protocol exchanges and determining the order of events across multiple hosts.
