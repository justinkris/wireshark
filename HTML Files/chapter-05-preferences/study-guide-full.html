💡THINK FIRST · PREFERENCES OVERVIEW

Wireshark preferences are stored per profile. Why does this matter for analysts who work with different protocol environments?

HINT

Think about what needs to change between analyzing VoIP vs. ICS/SCADA vs. web traffic.

MODEL ANSWER

Different analysis contexts need different views: VoIP analysis wants RTP stream details in columns; ICS analysis wants Modbus function codes; web analysis wants HTTP methods. Per-profile preferences let you switch contexts instantly — each profile has its own columns, coloring rules, protocol dissectors, and filter bookmarks. The preferences file is plain text and can be shared with teammates or version-controlled.

Preferences Dialog Overview

Open via Edit → Preferences (Ctrl+Shift+P). The left panel shows a tree of categories:

  • Appearance — layout, fonts, toolbar visibility
  • Capture — default interface, promiscuous mode, default format
  • Filter Expressions — display filter toolbar buttons
  • Name Resolution — DNS, MAC vendor, custom hosts file
  • Protocols — per-protocol dissector settings

Preferences are stored in the active profile directory. Default profile: ~/.config/wireshark/ (Linux/Mac) or %APPDATA%\Wireshark\ (Windows).

🧠
MENTAL NOTE
Preferences are per-profile. Each profile has its own: preferences, colorfilters, columns, filter bookmarks, hosts file. Switching profiles changes the entire analysis environment instantly. Share profile directories to share configurations with teammates.

💡THINK FIRST · COLUMN CONFIGURATION

For troubleshooting TCP performance, what columns would you add beyond the default, and what's the fastest way to add a custom column?

HINT

Think about what metadata is available in each packet that the default columns don't show.

MODEL ANSWER

Add: tcp.time_delta (time since previous segment in same stream — shows per-stream delays), tcp.analysis.bytes_in_flight (current window usage), ip.ttl (spot asymmetric routing). Fastest way: expand Packet Details, right-click the field → 'Apply as Column'. This avoids needing to know the filter field name. For bulk column setup: Edit → Preferences → Appearance → Columns → + → Type = Custom → enter field name.

Column Configuration

Right-click the column header bar to add/remove/resize columns. In Preferences → Appearance → Columns, add columns by type or custom field.

Built-in Column Types (key ones)

  • Relative time — seconds since capture start
  • Delta time (displayed) — time since previous displayed packet
  • Src/Dst port — transport layer ports
  • Protocol — highest dissected protocol

Custom Columns

Right-click any field in Packet Details → Apply as Column. Common custom columns:

  • tcp.time_delta — time since previous TCP segment in same stream
  • ip.ttl — TTL value
  • http.request.method — GET, POST, PUT, etc.
  • dns.qry.name — DNS query name
  • tcp.analysis.bytes_in_flight — bytes not yet acknowledged
QUICK ADDFastest: expand Packet Details → find the field → right-click → Apply as Column. No need to remember the field name.
🧠
MENTAL NOTE
'Delta time (displayed)' is more useful than 'Delta time' when filtering — it shows deltas between visible packets, not hidden ones. Right-click → Apply as Column is the fastest way to add custom columns. Column config is per-profile.

💡THINK FIRST · NAME RESOLUTION

Name resolution translates IPs to hostnames. What are the hidden costs of enabling live DNS resolution during a live capture?

HINT

What happens each time Wireshark sees a new IP address with resolution enabled?

MODEL ANSWER

For each new IP, Wireshark issues a reverse DNS lookup from the capture machine. This means: (1) DNS query packets appear in your capture trace, adding noise; (2) the DNS round-trip adds latency to display updates; (3) failed lookups for RFC 1918 addresses stall the resolver. Best practice: capture with resolution off, then post-capture enable 'Use captured DNS packet data' — this resolves names from DNS responses already in the trace, no additional queries.

Name Resolution Settings

In Preferences → Name Resolution and View → Name Resolution:

  • Resolve MAC addresses — OUI → vendor name (e.g. CiscoSystems). Uses built-in database, no network traffic.
  • Resolve network (IP) addresses — reverse DNS for every IP. Generates DNS traffic. Slow. Off by default.
  • Resolve transport names — port 80 → http. Uses /etc/services. No network traffic.
  • Use captured DNS packet data — resolves from DNS responses in the trace. Preferred.

Custom hosts File

Place a hosts file in the profile directory: one IP hostname pair per line. Loaded at startup. Ideal for lab environments without DNS.

DURING CAPTUREEnable 'Resolve network addresses' only post-capture. During capture, it generates extra DNS queries that appear in the trace and slow the display. Use 'captured DNS data' instead.
🧠
MENTAL NOTE
Name resolution order: hosts file → captured DNS → live DNS. 'Use captured DNS packet data' is best — no side effects. Never enable live DNS resolution during active capture. MAC vendor lookup is safe (no network traffic). Custom hosts file in profile directory for static mappings.

💡THINK FIRST · PROTOCOL PREFERENCES

Two protocol preference settings can make the difference between seeing useful decoded data versus raw bytes. What are they?

HINT

Think about common scenarios where Wireshark can't decode a protocol because of a configuration issue rather than the protocol being unknown.

MODEL ANSWER

(1) TCP checksum validation: when capturing on the sending machine, the NIC computes the checksum after Wireshark sees the packet — Wireshark sees 0x0000 and flags every packet as 'bad checksum'. Disable checksum validation in Preferences → TCP. (2) TLS decryption: add an SSLKEYLOGFILE path to Preferences → TLS. This works with modern ECDHE ciphersuites (unlike RSA-key-only decryption) and lets Wireshark decrypt HTTPS, showing HTTP/2 frames underneath.

Protocol-Specific Preferences

Under Preferences → Protocols — every dissector has its own settings. Key ones:

TCP

  • Validate TCP checksum — disable when capturing locally (NIC checksum offload causes false 'bad checksum' alerts)
  • Allow subdissector to reassemble TCP streams — on by default; required for HTTP/FTP/etc. to decode correctly
  • Track number of bytes in flight — enables window analysis

TLS

  • (Pre)-Master-Secret log filename — path to SSLKEYLOGFILE; decrypts all TLS including ECDHE sessions
  • RSA keys list — add server private key (PEM); only works for RSA key exchange (not ECDHE/PFS)

HTTP

  • HTTP TCP ports — add 8080, 8000, 3000 so Wireshark dissects non-standard HTTP ports
CHECKSUM OFFLOADIf you capture on the sending machine, TCP/UDP checksums may be 0x0000 because the NIC hasn't computed them yet. Every packet appears 'bad checksum'. Fix: Preferences → TCP → uncheck 'Validate the TCP checksum if possible'.
TLS DECRYPTIONSSLKEYLOGFILE works with Chrome/Firefox — set the SSLKEYLOGFILE environment variable before launching the browser, then browse, then open the trace in Wireshark with the key log file configured. This captures session keys for all TLS sessions including ECDHE.
🧠
MENTAL NOTE
Most important protocol prefs: (1) TCP → disable checksum validation when capturing locally; (2) TLS → SSLKEYLOGFILE path to decrypt HTTPS (works with ECDHE, RSA-key-only doesn't); (3) HTTP → add port 8080/8000/3000 for non-standard HTTP ports.

Review Questions

Q5.1
Why should 'Resolve network addresses' be disabled during live capture, and what is the preferred post-capture alternative?
HINT

What side effects does live DNS resolution create during capture?

ANSWER

Live DNS resolution causes Wireshark to issue reverse DNS queries from the capture machine for every new IP. This generates DNS query packets that appear in the trace (adding noise), slows the display (DNS round-trip latency), and may stall for RFC 1918 addresses with no reverse DNS. Post-capture, use 'Use captured DNS packet data' — this resolves names from DNS responses already in the trace file with no side effects. Alternatively, add a custom hosts file to the profile directory for static mappings.

Q5.2
All TCP packets show 'Bad checksum [should be X]' warnings. What is the likely cause and fix?
HINT

Think about where checksums are computed in modern NICs.

ANSWER

The NIC uses checksum offloading — it computes and fills in the TCP checksum in hardware before the frame leaves the machine. When capturing on the sending machine, Wireshark captures the packet before the NIC fills in the checksum, seeing 0x0000. Fix: Edit → Preferences → Protocols → TCP → uncheck 'Validate the TCP checksum if possible'. This suppresses the false alerts. The NIC still computes and validates checksums on the wire.

Q5.3
How do you add a column showing HTTP request methods (GET, POST, etc.) for all HTTP packets?
HINT

There's a quick way that doesn't require knowing the field name.

ANSWER

Open any HTTP GET packet → expand the HTTP tree in Packet Details → find 'Request Method: GET' → right-click → 'Apply as Column'. Wireshark immediately adds the column. Alternatively: Edit → Preferences → Appearance → Columns → '+' → Type = Custom → field name = http.request.method. The column shows GET/POST/PUT/DELETE/etc. for HTTP packets and is blank for non-HTTP packets.
