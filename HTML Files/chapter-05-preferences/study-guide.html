💭 THINK FIRST · PREFERENCES OVERVIEW

Wireshark's preference system is layered — global settings can be set by administrators, and personal settings override them per-profile. Understanding where preferences are stored is essential when moving installations or troubleshooting configuration issues.

  • A colleague's Wireshark looks completely different from yours — different colors, columns, and protocol decoding. You're both using the same version. What's the most likely cause?
  • Where are personal Wireshark preferences stored, and why does this matter when you move to a new computer?
Q1 — DIFFERENT APPEARANCE SAME VERSION
The most likely cause is that you are each using different profiles. Wireshark profiles are completely independent configurations — each has its own preferences file, color rules, display filters, and column layout. If your colleague created or inherited a customized profile, everything about the interface can differ despite running the same Wireshark version. Switch profiles via the profile indicator in the bottom-right corner of the Wireshark window, or Edit → Configuration Profiles.
Q2 — PERSONAL PREFERENCES STORAGE
Personal preferences are stored in the personal profile directory: on macOS at ~/.config/wireshark/, on Windows at %APPDATA%\Wireshark\. When you move to a new computer, your Wireshark will have only the global defaults from the installation directory — all your personal preferences, column layouts, color rules, and saved filters are gone unless you copy the personal profile directory to the new machine. This is why exporting or backing up the personal profile directory is important for analysts who have invested time in configuration.
Section 1

Preferences Dialog Overview

Access Wireshark preferences via Edit → Preferences (Ctrl+Shift+P on Windows/Linux, Cmd+Comma on macOS). The dialog has a tree of categories on the left: Appearance (layout, font, columns), Capture, Expert, Filter Expressions, Name Resolution, Protocols (one entry per protocol), and Statistics.

Settings are stored in two locations: the personal profile directory (on macOS: ~/.config/wireshark/; on Windows: %APPDATA%/Wireshark/) contains your personal overrides, and the program installation directory contains global settings that apply to all users. Personal settings always override global settings.

Profile-specific preferences Changes made in Preferences apply to your current profile. If you switch profiles (Chapter 11), each profile can have its own preference overrides — allowing you to maintain different configurations for different analysis tasks.
🧠
MENTAL NOTE
Preferences = Edit → Preferences (Ctrl+Shift+P). Stored in personal profile directory (~/.config/wireshark/ on macOS). Global settings live in install dir, personal settings override them. Each profile has its own prefs.

💭 THINK FIRST · COLUMN CONFIGURATION

The Packet List columns are your primary analysis dashboard. The default columns give you relative time, addresses, ports, and info — but a few strategic additions can transform troubleshooting speed, especially for latency and conversation analysis.

  • You're troubleshooting application latency. Which single column addition would give you the most immediate insight into where delays are occurring?
  • You want to always see the TCP stream index in your packet list without manually adding it each time. What's the most efficient way to make this permanent?
Q1 — BEST COLUMN FOR LATENCY TROUBLESHOOTING
Adding a "Delta time" column (time since previous frame) gives the most immediate insight into latency. Large delta values jump out visually and immediately show you where in the packet sequence delays are occurring — between a request and a response, or during a handshake. You can sort by this column to find the largest gaps in the entire trace, pinpointing exactly which exchange is slow without reading individual timestamps.
Q2 — MAKING TCP STREAM INDEX PERMANENT
The most efficient method is to find any TCP packet in the Packet Details pane, expand the TCP header, right-click the "Stream index" field, and select "Apply as Column." This immediately adds it as a permanent column in the Packet List for all future captures. The column is saved to your current profile's preferences and persists across sessions. Alternatively, go to Preferences → Appearance → Columns and add a custom column with the field name tcp.stream.
Section 2

Column Configuration

The Packet List columns are fully configurable via Preferences → Appearance → Columns. You can add, remove, reorder, and resize columns. The most powerful shortcut: right-click any field in the Packet Details pane → "Apply as Column" — this is the fastest way to add any protocol field as a permanent column.

ColumnPurpose
Absolute TimeWall-clock timestamp — correlate with logs and external events
Delta TimeTime since previous frame — instantly spot large gaps and delays
Source / Destination PortUseful when analyzing server traffic with multiple services
TCP Stream IndexGroups packets into conversations — track a single session
Expert SeverityHighest expert event level for the frame — surface problems at a glance
Apply as Column shortcut Right-click any field in the Packet Details pane → "Apply as Column" — this creates a permanent column in the Packet List for that field across all future captures. No need to navigate to Preferences for any specific protocol field.
🧠
MENTAL NOTE
Columns: Preferences → Appearance → Columns. Right-click Packet Details field → Apply as Column (fastest method). Useful additions: Absolute Time, Delta time, TCP stream index, Expert severity. Reorder by drag-and-drop in Preferences or in the column header area.

💭 THINK FIRST · NAME RESOLUTION SETTINGS

Name resolution makes captures more readable but comes with hidden costs — particularly network name resolution, which actively generates DNS traffic during a live capture. Knowing when to enable each type is a professional discipline.

  • You're doing a live capture and Wireshark is sending DNS queries. What setting is causing this, and how do you stop it?
  • MAC address name resolution shows "Cisco_xx:xx:xx" for a device. What does this tell you, and what does it not tell you?
Q1 — LIVE CAPTURE DNS QUERIES FROM WIRESHARK
Network Name Resolution is enabled. When this setting is active, Wireshark issues DNS queries for every IP address it encounters — attempting to resolve them to hostnames for display. During a live capture, this means Wireshark itself becomes a source of DNS traffic that appears in your capture, polluting the trace with your own analysis activity. Disable it via Preferences → Name Resolution → uncheck "Resolve network (IP) addresses." You can always re-enable it when analyzing a saved file offline.
Q2 — MAC OUI RESOLUTION — WHAT IT TELLS AND DOESN'T
The "Cisco_" prefix tells you the OUI (Organizationally Unique Identifier) — the first 3 bytes of the MAC address — is registered to Cisco Systems. This tells you the network interface card or device was manufactured by Cisco (or uses a Cisco-assigned MAC prefix). It does not tell you what type of Cisco device it is (router, switch, phone, camera), what software it runs, or even whether it is currently functioning as a Cisco product (a cloned MAC or spoofed address could show a Cisco OUI on any device).
Section 3

Name Resolution Settings

Name resolution controls whether Wireshark translates raw addresses into human-readable names. Three types of resolution are available, each with different behavior and cost:

TypeWhat It ResolvesCost / Risk
MAC Address ResolutionMAC OUI prefix → manufacturer name (e.g., "Apple_xx:xx:xx")Safe — uses local OUI database, no network traffic
Network Name ResolutionIP addresses → hostnames via DNSIssues DNS queries — generates traffic, slows analysis on large files
Transport Name ResolutionPort numbers → service names (e.g., 80 → http)Safe — uses local services database, no network traffic
Network name resolution during live capture Network name resolution during live capture generates DNS queries — this pollutes your capture with your own analysis traffic. Disable it unless analyzing a saved file where no live network is involved.
🧠
MENTAL NOTE
3 name resolution types: MAC OUI (manufacturer), Network (IP→hostname via DNS), Transport (port→service name). Disable network resolution during live capture — it generates DNS traffic. Enable only when analyzing saved .pcapng files. MAC OUI resolution is safe to leave on.

💭 THINK FIRST · PROTOCOL-SPECIFIC PREFERENCES

Protocol preferences let you change how Wireshark interprets specific protocols — from decrypting TLS to suppressing false checksum errors. The most impactful settings are a handful of TCP and TLS options that every analyst should know by heart.

  • Wireshark shows all TCP sequence numbers starting at 0. A colleague says the actual ISN was 2,847,123,091. Who's right?
  • You need to decrypt captured HTTPS traffic. What file do you need, and how do you configure Wireshark to use it?
Q1 — RELATIVE SEQUENCE NUMBERS
Both are right — they're looking at different things. Wireshark's "Relative sequence numbers" preference (enabled by default under Preferences → Protocols → TCP) resets the Initial Sequence Number (ISN) to 0 for display purposes only. The actual ISN transmitted on the wire was 2,847,123,091 — that's what your colleague sees if they have relative sequence numbers disabled, or if they look at the raw packet bytes. Relative sequence numbers make it easier to read TCP streams by showing byte offsets from 0, but they're a display convenience only and do not alter the actual captured data.
Q2 — DECRYPTING HTTPS WITH TLS KEY LOG FILE
You need a TLS pre-master secret log file (also called an SSLKEYLOGFILE). This file is generated by the browser (Chrome or Firefox) when the SSLKEYLOGFILE environment variable is set before launching the browser — the browser writes the session keys to that file as connections are established. In Wireshark, go to Preferences → Protocols → TLS and enter the path to the log file in the "(Pre)-Master-Secret log filename" field. Wireshark will use these keys to decrypt the TLS sessions it finds in the capture. This works for modern TLS 1.2 and 1.3 without needing the server's private key.
