POP — Post Office Protocol

Purpose of POP

POP (Post Office Protocol) is a popular method for retrieving email, defined in RFC 1939. IMAP (Internet Message Access Protocol, RFC 1730) is another common retrieval protocol. POP itself does not provide security in email data transfer; third-party applications provide that added functionality. This chapter covers POP and SMTP (Simple Mail Transfer Protocol).

POP does not maintain a persistent connection — the connection is established to retrieve email and then terminated upon successful completion.

Analyze Normal POP Communications

In Figure 297 Wireshark's Info column provides enough detail on POP communications to interpret the entire process. The POP user provides their username and password. The POP server opens the mailbox and tells the user that one message is waiting (11,110 bytes long). The client asks for the Unique Identification Listing (UIDL) before issuing the RETR command, and the POP server begins sending the data over multiple TCP packets if necessary.

Upon successful download, the client sends the delete command (DELE). The server responds indicating it has deleted the message. The POP communications are then terminated by the client.

Analyze POP Problems

POP communication problems can begin with the TCP connection process and can also be affected by high latency and packet loss. As shown in Figure 298, a client cannot even log in to the POP server — the server indicates it is too busy. Before the -ERR response, there is another indication of a problem: the client had to issue two TCP handshake requests (SYN) to make the connection. This trace indicates a capacity issue at the POP server.

POP Packet Structure

POP packet structures are very simple. Requests consist of a Request Command and Request Parameter. Responses consist of a Response Indicator and Response Description. Key request commands:

CommandPurpose
USERProvide user name
PASSProvide password
STATObtain server status
LISTList messages and sizes
RETRRetrieve a message
DELEDelete a message
UIDLUnique ID List — list all email IDs [RFC2449]
PIPELININGServer can accept multiple commands at once [RFC2449]
QUITTerminate the connection

There are only two response indicators used in POP communications: +OK and -ERR. Figure 300 shows an email response beginning with the indicator and description. We can follow the POP mail message header to identify the path the packet took through mail exchange servers.

Filter on POP Traffic

Capture filter: tcp port 110. Display filter: pop (shows only POP command and email traffic, not TCP handshake or ACKs). To view all related packets: tcp.port==110 or a conversation filter.

FilterWhat It Matches
pop.response.indicator=="+OK"POP +OK responses
pop.response.indicator=="-ERR"POP -ERR responses
pop.request.command=="USER"POP USER commands
(pop.request.command=="USER") && (pop.request.parameter=="Fred")USER commands for a specific username (case sensitive)
(pop.response.indicator=="+OK") && (pop.response.description contains "octets")Email UIDL values and lengths — useful for spotting spam with attachments
🧠
MENTAL NOTE
POP runs on TCP port 110 and uses only two response indicators: +OK and -ERR. The RETR command retrieves a message; DELE removes it after download. Spam-filled mailboxes can cause multi-minute download times even when the user is unaware of the spam — look for hundreds of sequential RETR commands as the indicator.

SMTP — Simple Mail Transfer Protocol

Purpose of SMTP

SMTP is the de facto standard for sending email, defined in RFC 5321. It uses Sender-SMTP and Receiver-SMTP processes. By default, SMTP communications are not secure. The default port is 25, though many ISPs and firewalls block port 25 to combat spam. SMTP messages are delivered in Internet Message Format (RFC 2822).

📷Figure 301 — open trace file to view
Figure 301. SMTP messages are delivered in Internet Message Format [smtp-normal.pcapng]

Analyze Normal SMTP Communications

After a successful TCP handshake, the SMTP server responds with code 220 indicating the service is ready; the greeting also identifies the server and signals ESMTP support. The client sends HELO (standard) or EHLO (extensions supported). When the server sends its capability list — for example, indicating it supports pipelining — the client can send additional commands without waiting for each response.

📷Figure 302 — open trace file to view
Figure 302. An SMTP client sends an email message [smtp-normal.pcapng]

The SMTP client sends MAIL FROM with its source email address. Next, RCPT TO identifies the recipient. The DATA command signals readiness to send; the server responds with 354 Start Mail Input, after which the client transmits the email. Once the email is sent, the client issues QUIT to begin connection termination.

Analyze SMTP Problems

SMTP communication problems can begin at the TCP connection level and can also be affected by high latency and packet loss. If the SMTP server responds with numerical codes above 399, it is indicating a problem with the email transmission process.

📷Figure 303 — open trace file to view
Figure 303. A host is running a relay test against the SMTP server [smtp-strange.pcapng]

Figure 303 shows an unusual SMTP pattern: a host's email program performs an SMTP relay test by generating a series of MAIL FROM addresses to test whether the server will accept them. This could be caused by malware or a deliberate spam test (here, NetScanTools Pro was used). One server response (packet 42) sends code 554 with the text "Validating Sender." Many RCPT TO lines generate 553 Invalid Recipient. After each attempt, the sending program generates a RST. Email communications should be baselined — refer to Chapter 28 for details.

Filter on SMTP Traffic

Capture filter: tcp port 25. Display filter: smtp (shows commands and data only; TCP handshake and ACKs hidden). To view all packets: tcp.port==25.

FilterWhat It Matches
smtp.req.command=="EHLO"Client and server support extensions
(smtp.req.command=="MAIL") && (smtp.req.parameter=="FROM: <user@domain.com>")Email from a specific sender
(smtp.req.command=="RCPT") && (smtp.req.parameter=="TO: <user@domain.com>")Email to a specific recipient
smtp.response.code > 399Server indicates a problem with email transmission
🧠
MENTAL NOTE
SMTP runs on TCP port 25. The server greets with 220; the session ends with QUIT. EHLO (extensions) vs HELO (standard) is set by capability negotiation. Response codes 220/250/354 are success; any code above 399 indicates an error. MTU mismatches can silently abort DATA transfer — look for an ICMP Type 3 Code 4 arriving after the DATA segment to identify this condition.

Case Studies

Case Study 1
SMTP Problem — Scan2Email Job
Submitted by: Christian Kreide

Facts: 1) Scan device was a multifunctional device (MFD). 2) The device was connected to the SMTP server via an IPsec VPN over the Internet. 3) The scan device supported passive MTU discovery and did not allow IP fragmentation.

Symptoms: Without Wireshark, the Scan2Email job was simply aborted by an unknown cause. With Wireshark, the SMTP handshake worked fine, but data transmission failed as a router claimed a packet size issue by sending an ICMP Type 3 Code 4 (Fragmentation Needed) packet. The MFD did not resend the rejected packet using a smaller MTU even though Path MTU Discovery is supported on the MFD.

Cause: The customer used a Cisco PIX firewall performing TCP sequence number randomization. The TCP sequence number of the original MFD packet differed from the TCP sequence number in the TCP header carried by the ICMP Type 3 Code 4 packet. The MFD rejected the ICMP packet because it never sent a TCP (SMTP) packet with that altered sequence number — a security function that prevented Path MTU Discovery from working correctly.

Solution: (a) Reduce the MTU size on the VPN gateway router to at most the max MTU defined in the received ICMP Type 3 Code 4 packet. (b) Allow IP fragmentation on the MFD.

TL;DR — Chapter 25 Summary

POP and SMTP communications are used to receive and send email, respectively. POP communications rely on a username and password; basic SMTP communications do not authenticate the sender. Both POP and SMTP run over TCP. Oftentimes, an authorized POP communication must be established before an SMTP communication can be established.

POP and SMTP communications rely on clear-text request commands. There are only two response indicators in POP communications: +OK or -ERR. SMTP responses use numerical codes. Response codes greater than 400 indicate there is a problem with the SMTP communications.

Review Questions

Q25.1What is the purpose of POP? What is the purpose of SMTP?
Answer: POP is an application used to retrieve email from a mail server to a client device. SMTP is the de facto standard used for sending email between systems. Both run over TCP — POP on port 110 by default, SMTP on port 25.
Q25.2What command is used by a POP client to request that the POP server download emails to the client?
Answer: The POP client issues a RETR command to retrieve messages. The RETR command is followed by a message number parameter indicating which message to retrieve.
Q25.3What are the two POP response codes?
Answer: The two POP response indicators are +OK (success) and -ERR (failure). These are the only two response indicators used in all POP communications.
Q25.4What is the difference between an SMTP EHLO and HELO message?
Answer: HELO initiates a standard SMTP session. EHLO initiates an SMTP session from a sender that supports SMTP mail service extensions (ESMTP). The server signals ESMTP support in its 220 greeting, prompting the client to use EHLO.
Q25.5What is the syntax for capture and display filters for POP communications?
Answer: Capture filter: tcp port 110. Display filter: pop. To see all packets including the TCP handshake: tcp.port==110.
Q25.6What is the syntax for capture and display filters for SMTP communications?
Answer: Capture filter: tcp port 25. Display filter: smtp. To see all packets including the TCP handshake: tcp.port==25.
