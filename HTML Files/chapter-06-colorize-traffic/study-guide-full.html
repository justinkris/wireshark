💡THINK FIRST · COLORIZING OVERVIEW

Coloring rules are evaluated top-to-bottom and the first match wins. A TCP retransmission appears red even though a later 'TCP' rule would color it green. Why, and what does this mean for rule ordering?

HINT

If a packet matches both the first and fifth rule, which color does it get?

MODEL ANSWER

The first matching rule wins — the packet gets that rule's color and rule evaluation stops. So the 'Bad TCP' rule (which matches tcp.analysis.flags) must appear before the general 'TCP' rule — otherwise all TCP traffic (including retransmissions) would be colored green by the general TCP rule before 'Bad TCP' gets a chance to match. More specific rules must always appear above more general rules that would also match the same traffic.

Colorizing Traffic Overview

Wireshark applies background and foreground colors to packets based on coloring rules — display filter expressions paired with a color. Open via View → Coloring Rules.

Rules are evaluated top-to-bottom; first match wins. Each rule has: name, filter expression, foreground color, background color.

Toggle colorization globally: View → Colorize Packet List.

RULE FILEColoring rules are stored in colorfilters in the active profile directory. Import/export via the buttons in the Coloring Rules dialog. Share the file with teammates or import specialized rule sets (VoIP, ICS, DNS analysis).
🧠
MENTAL NOTE
First match wins — evaluate rules top-to-bottom. Specific rules above general rules. Coloring is purely cosmetic — no effect on capture or analysis. 'colorfilters' file in profile directory — shareable. Toggle with View → Colorize Packet List.

💡THINK FIRST · DEFAULT COLORING RULES

What is the 'Bad TCP' default coloring rule's filter expression, and why does it come first in the list?

HINT

What does tcp.analysis.flags match? Why must it come before the general TCP rule?

MODEL ANSWER

'Bad TCP' matches tcp.analysis.flags && !tcp.analysis.window_update — this catches retransmissions, out-of-order segments, duplicate ACKs, zero-window conditions, and RSTs. It must come first because a later 'TCP' rule matches all TCP traffic including these problem packets. If 'Bad TCP' were below 'TCP', every retransmission would be colored green (normal TCP) rather than red (problem), defeating the purpose of the alert coloring.

💡THINK FIRST · CUSTOM COLOR RULES

You want to highlight all HTTP 4xx and 5xx error responses in bright orange. Write the filter and explain where to place it in the rule list.

HINT

What filter field represents HTTP response codes? Where must this rule appear relative to the TCP and UDP rules?

MODEL ANSWER

Filter: http.response.code >= 400. Place above the general TCP (green) rule — otherwise TCP would match HTTP error packets first and color them green. Placement: below the 'Bad TCP' rule (to not interfere with TCP retransmission coloring) and above the general TCP rule. In View → Coloring Rules, click '+', name it 'HTTP Errors', enter the filter, choose orange background, click OK, then drag the rule to the correct position.

Creating Custom Color Rules

In View → Coloring Rules → + button:

  1. Enter a descriptive Name
  2. Enter a valid display filter
  3. Pick foreground/background colors
  4. Position the rule — drag above general rules that would match the same traffic first

Temporary Conversation Colors

Right-click any packet → Colorize with Filter → Color 1–10. Applies a temporary color using the src/dst pair. Reset with View → Reset Coloring Rules. Use to visually separate multiple streams during analysis without editing permanent rules.

Disable Without Deleting

Uncheck the checkbox next to a rule — it's skipped but preserved. Toggle for different analysis phases.

🧠
MENTAL NOTE
Custom rules: specific before general. 'Colorize with Filter' (right-click) = temporary session color — cleared on close. Rules stored in 'colorfilters' profile file. Import/export to share. Uncheck to disable without deleting.

Using Color for Rapid Analysis

Strategic coloring accelerates triage:

  • Red packet list — retransmissions, resets, or ICMP errors dominating; network or server problem
  • Purple clusters — SYN/FIN patterns; count connections being established/torn down
  • All gray — broadcast storm; most traffic is broadcasts
  • Blue dominant — UDP-heavy traffic; could be VoIP, DNS, NTP, or multicast

Analysis Workflow

  1. Look for red (errors first)
  2. Look for purple patterns (connection lifecycle)
  3. Assess overall color mix (protocol distribution at a glance)
  4. Use Colorize with Filter to isolate one conversation for focused analysis
ANALYST TIPCreate custom 'Application Error' rules for your environment: http.response.code >= 400 (HTTP errors), dns.flags.rcode != 0 (DNS failures), smtp.response.code >= 500 (SMTP delivery failures). Color them bright red or orange for instant triage.
🧠
MENTAL NOTE
Color triage workflow: (1) spot red clusters = errors; (2) spot purple = session boundaries; (3) color mix = protocol distribution; (4) Colorize with Filter = isolate one stream temporarily. Color narrows WHERE to look, not WHAT the problem is.

Review Questions

Q6.1
A TCP retransmission appears red in Wireshark even though the general 'TCP' rule would color it green. Why?
HINT

Consider rule ordering and the first-match principle.

ANSWER

The 'Bad TCP' coloring rule appears at the top of the default rule list and matches tcp.analysis.flags (which includes retransmissions). Since rules are evaluated top-to-bottom and the first match wins, the retransmission matches 'Bad TCP' first and is colored red. It never reaches the general 'TCP' (green) rule. This is by design — the rule list ordering is intentional, with error conditions taking priority over general protocol coloring.

Q6.2
You want to add a coloring rule for DNS queries (not responses) in bright blue. Write the filter and explain where to place it.
HINT

What field distinguishes a DNS query from a response? Where must this rule go relative to existing rules?

ANSWER

Filter: dns.flags.response == 0 (matches queries; response == 1 for responses). Place above the general UDP rule — DNS is UDP-based, so the UDP rule would match DNS first and color it light blue. If there's already a general 'dns' rule, place the new query-specific rule above it so it fires first for query packets.

Q6.3
What is the difference between a permanent coloring rule and a temporary conversation color?
HINT

How long does each persist? Where is each stored?

ANSWER

Permanent coloring rules are stored in the profile's 'colorfilters' file and persist across Wireshark restarts — they apply to any capture file opened with that profile. Temporary conversation colors (right-click → Colorize with Filter → Color N) apply only to the current session and are cleared when Wireshark closes or View → Reset Coloring Rules is selected. Temporary colors are useful for separating streams during active analysis without permanently modifying the rule set.
