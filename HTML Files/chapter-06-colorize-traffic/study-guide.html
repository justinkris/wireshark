💭 THINK FIRST · COLORIZING TRAFFIC OVERVIEW

Coloring rules use the same display filter syntax you already know — meaning any filter expression you can type in the filter bar can become a coloring rule. The key discipline is rule ordering: first match wins, so priority determines what you see.

  • Wireshark has two coloring rules: Rule A filters http and Rule B filters tcp. A single HTTP packet matches both. Which color does it get, and why?
  • You want to hide all color coding temporarily without deleting your rules. What's the fastest way?
Q1 — RULE PRECEDENCE WHEN BOTH MATCH
The packet gets the color of whichever rule appears higher in the list — Rule A (http) if it is listed before Rule B (tcp). Wireshark evaluates rules top-to-bottom and stops at the first match. Because HTTP traffic is also TCP traffic, both rules match, but only the first one encountered wins. This is why high-priority or more specific rules (like "Bad TCP") must be placed at the top of the rule list — if a general rule like "tcp" is higher, it will shadow everything below it.
Q2 — TOGGLING ALL COLOR OFF WITHOUT DELETING RULES
Use View → Colorize Packet List to toggle all colorization on or off with a single menu click. This is a toggle — it does not delete or modify any of your coloring rules. All rules remain intact and are immediately re-applied when you toggle colorization back on. This is useful when you want to see the raw packet list without visual noise, or when comparing a monochrome view to a colorized one.
Section 1

Colorizing Traffic Overview

Wireshark uses colorization rules to apply background and foreground colors to packets in the Packet List pane based on display filter expressions. Rules are evaluated top-to-bottom — the first matching rule wins. Access via View → Coloring Rules. Toggle all color with View → Colorize Packet List.

Color rules use the same display filter syntax as the filter bar — any valid display filter expression can become a color rule. This means you can colorize by protocol, host, port, flag value, or any combination.

Top rule wins — ordering is critical Color rules evaluate top to bottom — the first matching rule wins. Put your highest-priority rules (e.g., "bad TCP") at the top so they are not overridden by less important rules lower in the list.

💭 THINK FIRST · DEFAULT COLORING RULES

The default rule set is designed to surface the most common and most urgent events first — TCP problems in high-contrast black-on-red, common protocols in softer pastels. Knowing what each default color means lets you triage a capture visually before reading a single packet detail.

  • You see a cluster of black-on-red packets in your capture. Before looking at the packet details, what do you already know just from the color?
  • The default HTTP rule colors packets light green. But an HTTPS (port 443) packet is colored light blue (TCP). Why doesn't the HTTP rule match HTTPS?
Q1 — BLACK ON RED PACKETS — WHAT YOU KNOW BEFORE READING DETAILS
Black-on-red (or black on red-orange) corresponds to the "Bad TCP" default rule, which uses the filter tcp.analysis.flags. You already know these packets have TCP analysis events flagged by Wireshark's analysis engine — most commonly retransmissions, duplicate ACKs, fast retransmissions, zero windows, or window full conditions. You know there is a TCP-layer problem worth investigating — likely either packet loss (retransmissions), a slow receiver (zero window), or congestion. The color alone tells you to focus here before reading any other packets.
Q2 — WHY HTTPS IS BLUE NOT GREEN
The default HTTP coloring rule uses the filter http, which matches packets that Wireshark's HTTP dissector has decoded as HTTP protocol. HTTPS (TLS on port 443) is not decoded as HTTP at the protocol layer — Wireshark sees it as TLS (or just TCP if it cannot decrypt it). The http display filter only matches packets where Wireshark can parse the HTTP protocol headers, which requires unencrypted HTTP. Since HTTPS is encrypted and the HTTP dissector cannot read the payload, it does not match the http filter and falls through to the generic tcp rule (light blue) instead.

💭 THINK FIRST · CREATING CUSTOM COLOR RULES

Custom color rules let you make the captures most relevant to your environment immediately visible. A handful of well-chosen rules — DNS failures, HTTP errors, a specific host — can turn a generic Wireshark into a tuned monitoring tool for your network.

  • You want to highlight all packets where a DNS response returned an error. What display filter would you use as a color rule, and what color would you choose to make it stand out?
  • A colleague sent you their Wireshark coloring rules file. How do you import it?
Q1 — DNS ERROR COLOR RULE
Use the filter dns.flags.rcode != 0 — this matches any DNS response where the return code is not zero (zero = success). Non-zero rcodes include NXDOMAIN (3, name doesn't exist), SERVFAIL (2), REFUSED (5), and others. For color, a high-contrast combination like red background with white text makes DNS failures immediately visible against the lighter protocol colors. You could also use orange-on-black for visibility. Add this rule near the top of your Coloring Rules list so it takes precedence over the default UDP (light yellow) rule that would otherwise match DNS packets.
Q2 — IMPORTING A COLORING RULES FILE
Go to View → Coloring Rules → Import (the button is in the Coloring Rules dialog). Select the file your colleague sent — Wireshark coloring rules are saved in a text file typically named colorfilters. The imported rules are added to your current rule set. If there are name conflicts or you want to replace your entire rule set, you can also directly replace the colorfilters file in your profile directory (~/.config/wireshark/ on macOS) with the shared file, then restart Wireshark.
Section 3

Creating Custom Color Rules

To create a custom rule: View → Coloring Rules → New (or + button). Enter a name, the display filter expression, and choose foreground/background colors. Common custom rules analysts add:

Rule NameFilterPurpose
My Hostip.addr == 192.168.1.100Highlight all traffic to/from your analysis machine
Problem Hostip.addr == X.X.X.XBright color for a specific misbehaving IP
DNS Failuresdns.flags.rcode != 0Failed DNS responses (NXDOMAIN, SERVFAIL, etc.)
HTTP Errorshttp.response.code >= 400Server-side HTTP errors (4xx, 5xx)
Colorize Conversation — quick temporary highlight Right-click any packet in the Packet List → "Colorize Conversation" to instantly apply a temporary highlight to all packets in the same conversation. Choose "Reset Coloring" to remove it. This is useful for quick session tracing without creating a permanent rule.

💭 THINK FIRST · USING COLOR FOR RAPID ANALYSIS

A well-configured color scheme transforms the Packet List from a raw log into a visual dashboard. The first thing an experienced analyst does when opening an unfamiliar capture is a color sweep — letting the eyes find patterns before the brain reads individual fields.

  • You open a capture and see mostly light-blue TCP packets with occasional black-on-red. What should be your first analysis step?
  • Why would you want different coloring rule sets for security analysis vs network performance analysis?
Q1 — MOSTLY BLUE TCP WITH OCCASIONAL BLACK-ON-RED
Your first step should be to apply the filter tcp.analysis.flags to isolate only the black-on-red packets and examine them. The black-on-red color tells you these are TCP analysis events — retransmissions, duplicate ACKs, zero windows, or similar problems. "Occasional" bad TCP packets amid mostly clean traffic suggests an isolated problem rather than a persistent congestion issue. Look at the delta time before each bad TCP packet to determine if these are timeout-based retransmissions (gap of 1+ seconds) or fast retransmissions (milliseconds) triggered by duplicate ACKs — this distinction points to where the problem lives.
Q2 — SEPARATE RULE SETS FOR SECURITY VS PERFORMANCE
Security and performance analysis have fundamentally different "what is interesting" priorities. A security analyst wants to highlight unusual protocols, unexpected source IPs, port scans, RST storms, and known malware C2 patterns — things invisible or irrelevant to a performance analyst. A performance analyst wants to highlight retransmissions, zero windows, large deltas, and specific application-tier errors like HTTP 5xx. A single rule set optimized for one domain clutters the view for the other. Since Wireshark profiles each store their own coloring rules, you can switch between a "Security" profile and a "Performance" profile via the profile selector at the bottom right — instant context switching without any manual rule edits.
Section 4

Using Color for Rapid Analysis

A well-configured color scheme turns the Packet List into a visual dashboard. Use the following strategy when opening any new capture:

  1. Visual sweep first — scan for black-on-red clusters (Bad TCP = retransmission problem) or unexpected protocol colors (anomalous traffic).
  2. Colorize Conversation — right-click a packet of interest → Colorize Conversation to isolate a single session in a busy trace without filtering.
  3. Export and share — View → Coloring Rules → Export to share your tuned rule set with your team. Everyone sees the same visual cues.
  4. Use profiles — color rules are profile-specific. Maintain separate profiles for security analysis vs performance analysis.
Share your color rules with your team Export your custom coloring rules as a file and share them with your team — everyone sees the same visual cues, making collaborative analysis faster and reducing the learning curve for new analysts.
