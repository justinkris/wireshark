Analyze User Datagram Protocol (UDP) Traffic

💭 THINK FIRST · UDP HEADER STRUCTURE

UDP's header is just 8 bytes — four two-byte fields. Its simplicity is its strength: minimum overhead, no connection setup, no ordering, no retransmission. Understanding what it sacrifices explains exactly when UDP is the right choice and when it isn't.

  • UDP provides no reliability mechanisms. What three guarantees does TCP provide that UDP deliberately omits, and why would an application choose UDP despite this?
  • The UDP checksum field is optional (it can be set to 0x0000 to indicate "not computed") in IPv4. Why might an application skip the checksum?
Q1 — THREE TCP GUARANTEES UDP OMITS
TCP provides: (1) Ordered delivery — segments are numbered and reordered if needed. (2) Reliable delivery — unacknowledged segments are retransmitted. (3) Flow control — sender rate is adjusted to prevent receiver overflow. UDP omits all three. Applications choose UDP when: low latency matters more than guaranteed delivery (VoIP, gaming — a retransmitted voice packet arrives too late to be useful), the application implements its own reliability (DNS — if no reply comes, the resolver retries), or broadcast/multicast is required (UDP supports it, TCP does not). The overhead of TCP's reliability mechanisms adds latency and complexity that many real-time applications cannot afford.
Q2 — SKIPPING THE UDP CHECKSUM
Computing a checksum adds CPU overhead on every packet. For very high-throughput applications (streaming, network storage) the checksum computation cost is non-trivial. If the lower layers already provide error detection (e.g., Ethernet FCS) and the application can tolerate occasional bit errors (lossy audio/video streaming), skipping the UDP checksum eliminates that overhead. In IPv6, however, the UDP checksum is mandatory (cannot be zero) because IPv6 does not have a header checksum, so the UDP checksum provides the only IP-layer payload integrity check.
Section 1

UDP Header Structure

UDP (RFC 768) is a connectionless, best-effort transport protocol. Its header is exactly 8 bytes — the smallest possible for a usable transport layer.

FieldSizePurpose
Source Port16 bitsSending port (may be 0 if unneeded)
Destination Port16 bitsReceiving process port
Length16 bitsUDP header + data length in bytes (min=8)
Checksum16 bitsError detection (optional in IPv4, mandatory in IPv6)

Total UDP overhead = 8 bytes header + 20 bytes IP header = 28 bytes per datagram (vs 40+ bytes for TCP). This minimal overhead makes UDP ideal for high-volume, latency-sensitive applications.

Identifying UDP in Wireshark UDP is identified in the IP header by Protocol=17. In Wireshark, apply display filter udp to show all UDP datagrams. The source and destination ports are visible in the packet summary line.
🧠
MENTAL NOTE
UDP = 8 bytes, 4 fields: src port, dst port, length, checksum. No connection state, no retransmission, no ordering. Protocol=17 in IPv4. Checksum optional IPv4, mandatory IPv6. Total overhead 28 bytes vs 40+ TCP.

💭 THINK FIRST · COMMON UDP APPLICATIONS

Knowing which well-known applications use UDP and on which ports is essential for quickly making sense of an unfamiliar capture. It's also critical for firewall rule analysis.

  • DNS uses UDP port 53. Under what conditions does DNS switch to TCP, and what do you look for in a capture to confirm this switch happened?
  • DHCP uses UDP on both port 67 and port 68. Why are two different ports needed, and what is the DHCP conversation sequence you'd expect to see in a capture?
Q1 — WHEN DNS SWITCHES TO TCP
DNS switches to TCP in two scenarios: (1) When a DNS response exceeds 512 bytes (the original RFC 1035 UDP limit) — the server sets the Truncation (TC) bit, and the client retries the same query over TCP. (2) Zone transfers (AXFR queries) always use TCP because they transfer entire DNS zones which can be many megabytes. In a capture, you'd see the UDP DNS query and a response with TC=1, then immediately after, a TCP SYN to port 53 followed by the full DNS response over TCP. The display filter tcp.port == 53 isolates the TCP DNS traffic.
Q2 — DHCP PORTS AND DORA SEQUENCE
DHCP uses port 67 (server) and port 68 (client) because the protocol must work before the client has an IP address. The server listens on port 67. The client sends from port 68 to port 67. Two ports are needed so the OS can demultiplex DHCP responses to the right process (DHCP client on port 68). The DORA sequence in a capture: (1) DHCP Discover — broadcast from 0.0.0.0 to 255.255.255.255 (no IP yet). (2) DHCP Offer — server unicasts/broadcasts an offered IP. (3) DHCP Request — client broadcasts requesting the offered IP. (4) DHCP ACK — server confirms the lease. In Wireshark, filter: bootp or dhcp.

💭 THINK FIRST · UDP PROBLEMS

Because UDP has no built-in error recovery, application-layer or network problems show up differently than with TCP. Lost packets, missing responses, and port-closed errors require specific patterns to identify.

  • You're analyzing a VoIP call that users report as choppy and breaking up. In the RTP UDP stream, what specific packet-level evidence would confirm this is packet loss rather than a codec or server problem?
  • How does a UDP port-closed condition manifest in a packet capture? Which protocol delivers the error notification?
Q1 — RTP PACKET LOSS EVIDENCE
Evidence of packet loss in an RTP stream: (1) Gaps in RTP sequence numbers — RTP headers contain a sequence number; if the sequence jumps from 1050 to 1055, packets 1051–1054 were lost in transit. (2) Gaps in RTP timestamps — the RTP timestamp advances in fixed increments per packet; missing increments confirm dropped packets. (3) RTCP RR (Receiver Report) packets showing a non-zero "fraction lost" or "cumulative lost" field. In Wireshark, use the Telephony → RTP → RTP Streams tool to see statistics including jitter, max delta, and packet loss percentage. A codec or server problem would show up as malformed RTP payloads, or as connection-level issues, not as missing sequence numbers.
Q2 — UDP PORT CLOSED IN A CAPTURE
When a host receives a UDP packet and no application is bound to that destination port, the host sends ICMP Destination Unreachable — Port Unreachable (type 3, code 3) back to the sender. This is the only feedback mechanism for UDP port-closed conditions — there is no TCP RST equivalent for UDP. In a capture, you see the UDP packet arrive at the destination, then an ICMP type 3 code 3 immediately following it, sourced from the destination host's IP. For firewalls that drop rather than reject, you won't see the ICMP at all — the sender simply times out waiting for an application response.
Section 3

UDP Problems

UDP has no built-in error recovery. Problems appear as: ICMP error messages (port unreachable), unanswered requests (no response to UDP queries), or application-visible data corruption (no checksum or bit errors).

UDP packet loss is invisible at the transport layer UDP packet loss is invisible at the transport layer — there's no "packet lost" notification in UDP itself. Applications must implement their own detection. In RTP, look for sequence number gaps. In DNS, look for retried queries. In DHCP, look for repeated DISCOVER packets.
UDP port closed — ICMP type 3 code 3 ICMP type 3, code 3 (Port Unreachable) is the closest UDP equivalent to TCP RST. If you see it, the destination host is alive but no application is listening on that UDP port.
🧠
MENTAL NOTE
UDP port closed = ICMP type 3 code 3 (not a TCP RST). Packet loss = invisible in UDP — detected via RTP sequence gaps, DNS retries, DHCP repeated DISCOVERs. No retransmission mechanism — application must handle retries. High delta times between request/response = slow server or network delay.

💭 THINK FIRST · FILTERING UDP IN WIRESHARK

UDP filters pair port-based matching with payload size or ICMP error detection. Combined, they let you quickly isolate specific UDP applications and their associated error conditions.

  • You want to find all DNS traffic in a trace including both UDP and TCP DNS. What single display filter covers both?
  • How would you build a filter to find all UDP packets that received an ICMP Port Unreachable response — i.e., packets that hit a closed UDP port?
Q1 — FILTER FOR ALL DNS TRAFFIC
Use dns as the display filter — Wireshark's DNS dissector recognizes DNS over both UDP port 53 and TCP port 53. The filter dns will match all DNS traffic regardless of transport. For explicit transport specification: (udp.port == 53) || (tcp.port == 53).
Q2 — FILTER FOR CLOSED UDP PORT
There's no single direct filter linking a UDP packet to its ICMP Port Unreachable response, but you can find all ICMP Port Unreachable messages with icmp.type == 3 && icmp.code == 3. Each such ICMP packet contains the original triggering packet's IP header + first 8 bytes of UDP header in the ICMP data field — in Wireshark you can expand the ICMP packet and see the embedded original destination port. Alternatively, filter icmp.type == 3 to find all ICMP unreachable messages and then examine which ones are code 3.
