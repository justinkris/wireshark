💭THINK FIRST · UDP PURPOSE & PROBLEMS

UDP provides connectionless transport with no reliability guarantees — no handshake, no sequencing, no retransmissions. Broadcast and multicast traffic flows over UDP. Problems are usually detected as missing responses or unexpected ICMP Destination Unreachable replies.

  • How does a UDP-based application recover from packet loss, given that UDP itself provides no recovery mechanism?
  • A firewall blocks UDP traffic to port 161 (SNMP) silently — no ICMP Port Unreachable is sent. How does the trace file look different from a case where ICMP responses are returned?

Model Answer 1: UDP itself cannot recover from packet loss — it has no ACK mechanism or retransmission timer. Each UDP-based application must implement its own reliability if it needs it. DNS retries with its own timeout and retry count. TFTP implements its own ACK/retry cycle. RTP uses sequence numbers to detect gaps and may use redundancy or interpolation to conceal lost audio. If an application doesn't implement retransmission, the packet is simply lost.

Model Answer 2: When the firewall silently discards packets, the trace shows only the outbound UDP packets with no responses at all. You'd see: UDP request, UDP request (retry), UDP request (retry again)... with no ICMP or UDP replies. In contrast, when ICMP Port Unreachable is returned, Wireshark shows alternating: UDP request [colored], ICMP Destination Unreachable/Port Unreachable response [colored differently]. The Wireshark default coloring rules make the striped pattern of request/ICMP pairs visually obvious.

The Purpose of UDP

UDP provides connectionless transport services. Broadcast and multicast traffic flows over UDP. The UDP header port fields identify the application using the transport. The UDP header is always exactly 8 bytes. UDP is defined in RFC 768.

Common UDP applications: DHCP/BOOTP, SIP, RTP, DNS, TFTP, NTP, SNMP, and streaming video.

💭THINK FIRST · UDP PACKET STRUCTURE

The UDP header has exactly four fields and is always 8 bytes. The Length field is technically redundant — it can be derived from the IP Total Length field. The checksum is optional and may be set to 0x0000 when not used.

  • The UDP Length field is redundant because the IP header already tells you how much data follows the IP header. Why was it included in the UDP header design?

Model Answer: The UDP Length field provides the length of the UDP payload from the perspective of the UDP layer itself, which makes it easier for the UDP receiving process to parse the packet without having to reference the IP layer. It allows UDP to be processed independently, using only its own header rather than looking back at the IP header. While technically redundant from an information perspective, it makes the protocol self-contained at its own layer — consistent with the layered model principle of each layer carrying what it needs.

Dissect the UDP Packet Structure

The UDP header is defined with Protocol value 17 (0x11) in the IP header. The header is always 8 bytes:

📷Figure 222 — open trace file to view
Figure 222. The UDP header is only 8 bytes long [dns-misc.pcapng].
FieldSizeDescription
Source Port2 bytesListening port for response packets. In some cases defines the application sending. Ephemeral for client processes.
Destination Port2 bytesTarget application/process. Well-known port for server side.
Length2 bytesLength of UDP header + data. Redundant but self-contained at the UDP layer. Minimum value = 8 (header only, no data).
Checksum2 bytesCovers UDP header + data + pseudo-header from IP (source/dest addr, protocol, UDP length). Optional — may be 0x0000 when not used.

Case Study 1
Troubleshooting Time Synchronization
Submitted by: Delfino L. Tiongco, ESU Seattle Networks Branch

I was asked to troubleshoot a switch that was not getting updates from our NTP (Network Time Protocol) server. Further investigation revealed that a few routers and switches were also not synchronizing with the NTP server.

I opened a Technical Assistance Center (TAC) case with Cisco and we went to troubleshoot the issue. We found out that all NTP traffic (udp.port==123) was being forwarded by the router to the NTP server before the last switch. So it was not a Cisco routing issue.

I started using Wireshark to determine where the traffic from the NTP server was going. To my surprise, the next hop for the Layer 2 traffic from the NTP server was going to the firewall instead of the nearest switch and router. The NTP server was not configured with our default gateway. Reconfiguring the NTP server fixed the problem.

So, again — Wireshark to the rescue!

TL;DR — Chapter Summary

UDP offers connectionless transport services. The UDP header itself is a simple 8-byte header primarily used to define the port number of the services supported. The checksum field in the UDP header may not even be used (0x0000).

When a target does not support services on the desired port, the target responds with an ICMP Destination Unreachable/Port Unreachable response. When a firewall silently discards UDP, no responses appear in the trace. When a firewall returns ICMP, a striped pattern of UDP/ICMP pairs is visible.

UDP itself cannot recover from packet loss — applications must implement their own retransmission logic.

Review Questions

Q19.1 What is the purpose of UDP?
A19.1 UDP provides connectionless transport services. The UDP header identifies the application using the transport in the port fields.
Q19.2 How does a UDP-based application recover from packet loss?
A19.2 UDP itself is connectionless so it cannot help recover from packet loss. Applications must use their own retransmission process including timeout value and retry count.
Q19.3 Why would a UDP packet contain a checksum value of 0x0000?
A19.3 Since the UDP checksum is optional, this field may contain 0x0000 when UDP checksums are not used.
