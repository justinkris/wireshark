💭THINK FIRST · TCP CONNECTION SETUP & TEARDOWN

TCP connections begin with a three-way handshake (SYN, SYN/ACK, ACK) and end with FIN or RST. During the handshake, both sides exchange their Initial Sequence Numbers (ISNs) and negotiate capabilities like MSS, Window Scaling, and SACK. A connection refusal is indicated by a RST in response to a SYN.

  • If a TCP SYN receives no response at all (no SYN/ACK and no RST), what are the three possible explanations? How would you determine which is true?
  • Why does the sequence number increment by 1 after a SYN packet even though no data bytes were actually sent?

Model Answer 1: Three possibilities when no response: (a) the SYN packet didn't arrive at the target — lost somewhere along the path; (b) the SYN/ACK response was lost on the return path back to the sender; (c) a host-based firewall on the target silently discarded the SYN packet. To determine which: move Wireshark to a point closer to the target server. If you can see the SYN arrive but no SYN/ACK is generated, it's a firewall on the target. If you can't see the SYN arrive at all, there's path loss. If you see SYN/ACK sent but not received, the return path is broken.

Model Answer 2: RFC 793 defines the SYN flag as consuming one sequence number even though it carries no data. This ensures the SYN itself is acknowledged — the next expected sequence number after SYN is ISN+1. The same rule applies to FIN — it consumes one sequence number. This is often called the "phantom byte" because no actual data was sent, but the sequence number moves forward. Without this mechanism, there would be no way to reliably acknowledge the control flags themselves.

Three-Way Handshake

TCP connections are established through a three-way handshake. The basic process requires three packets: SYN → SYN/ACK → ACK.

The SYN packets synchronize the sequence numbers — this is how both sides will keep track of the sequence of data exchanged. TCP/IP stacks may include data in the third packet of the handshake (the ACK). RFC 793 states this is "perfectly legitimate."

During the handshake, TCP options are negotiated:

OptionNumberLengthPurpose
MSS24 bytesMaximum Segment Size — maximum payload bytes. Hosts use the lowest common denominator.
Window Scale (WSOPT)33 bytesMultiplier to scale Window Size field above 65,535 bytes. Must be in both SYN packets.
SACK Permitted42 bytesEnables Selective Acknowledgments. Must be in both SYN packets.
TCP Timestamps810 bytesAccurate RTT calculation and PAWS (Protection Against Wrapped Sequence Numbers).
NOP1N/APadding to 4-byte boundary. Four NOPs in a row = router may have stripped a TCP option.

Connection Refusal & Teardown

If the target server has no process listening on the requested port, it responds to the SYN with a TCP Reset (RST/ACK).

If ICMP Destination Unreachable is returned to a TCP SYN (codes 1, 2, 3, 9, 10, 11), most likely the target port is firewalled through software on the target system. If no response is received to a SYN: (a) SYN didn't arrive, (b) SYN/ACK was lost, or (c) host-based firewall silently discarded the SYN.

TCP connections can be terminated with FIN (implicit, graceful) or RST (explicit, abrupt). FIN means "I have no more data to send" — the other side can still send. RST immediately terminates the connection.

Use netstat -a to see current TCP connection states: ESTABLISHED, CLOSE_WAIT, TIME_WAIT, etc.

🧠
MENTAL NOTE
Handshake: SYN → SYN/ACK → ACK. Three packets. ISN exchanged in SYN packets. SYN consumes 1 seq# (phantom byte). FIN also consumes 1 seq#. RST = refused connection. RST in response to SYN = port closed. ICMP to SYN = firewalled port (verbose firewall). No response to SYN = (a) SYN lost, (b) SYN/ACK lost, or (c) silent firewall. TCP options must match: if client doesn't offer SACK/Window Scale in SYN, server won't use them either.

💭THINK FIRST · PACKET LOSS RECOVERY

TCP detects and recovers from packet loss through two mechanisms: the receiver generates Duplicate ACKs requesting the missing segment (Fast Recovery), and the sender's RTO timer expires triggering a retransmission. SACK improves this by acknowledging out-of-order data so the sender only retransmits what's actually missing.

  • Fast Recovery is triggered by 3 identical ACKs. Why 3 and not 1 or 2? What would happen if a retransmission was triggered by just 1 Duplicate ACK?
  • SACK Left Edge and Right Edge values indicate what has been received AFTER a gap. Why does this let the sender avoid retransmitting data it has already confirmed as received?

Model Answer 1: Three Duplicate ACKs is the threshold because 1 or 2 might be caused by innocent packet reordering rather than actual loss. If you trigger retransmission on just 1 Duplicate ACK, you'd retransmit packets that were simply reordered and were about to arrive anyway — unnecessary retransmissions that waste bandwidth. By waiting for 3, you have enough confidence that the original packet was truly lost. On high-latency paths, you may see more than 3 Duplicate ACKs before the retransmission arrives, because more packets continue flowing during the gap.

Model Answer 2: Without SACK, when a retransmission is sent, the sender has no way to know which data beyond the gap has been received. It must retransmit everything from the missing packet onward (go-back-N). With SACK, the receiver uses the Left Edge and Right Edge values to say "I have bytes X through Y, just give me the missing piece before X." The sender can then send only the missing segment without resending the data that's already in the receiver's buffer. This dramatically reduces unnecessary retransmissions, especially when multiple packets are lost.

How TCP Tracks & Recovers from Packet Loss

Sequence & Acknowledgment Numbers

Each side selects its own Initial Sequence Number (ISN). Each side increments the Sequence Number by the number of data bytes sent. The Acknowledgment Number indicates the next sequence number expected from the other side.

Key equation: Next Expected Sequence Number = Current Seq# + Data Bytes Sent

By default, Wireshark uses Relative Sequence Numbering — starting at 0 for readability. Disable this in TCP preferences to see actual ISN values.

Fast Recovery (Receiver Detects Loss — Duplicate ACKs)

When a receiver notes an expected sequence number is skipped, it sends an ACK requesting the missing segment. Wireshark marks these as Duplicate ACKs. When the sender receives three identical ACKs, it retransmits the missing packet without waiting for the RTO.

Figure 229. High latency paths may cause more than three identical ACKs [http-download-bad.pcapng].

RTO Timeout (Sender Detects Loss)

If a data packet is sent and not acknowledged before the TCP Retransmission Timeout (RTO) timer expires, the sender retransmits using the original sequence number. TCP uses a backoff algorithm — the wait time approximately doubles for each retransmission attempt until the packet is acknowledged or after five retransmissions the host gives up.

Figure 230. The HTTP server retransmits a packet when the RTO expires [tcp-problem.pcapng].

Selective Acknowledgments (SACK)

SACK must be negotiated during the TCP handshake (SACK Permitted option in both SYN packets).

📷Figure 231 — open trace file to view
Figure 231. This TCP host supports Selective ACKs [http-download-bad.pcapng].

When SACK is in use, Duplicate ACKs contain a Left Edge and Right Edge value in the TCP options area. These values acknowledge data received after the missing packet. The sender only needs to retransmit what's missing — not everything after the gap.

(2) RTO timeout = sender's timer expires, retransmits with backoff (~doubles each attempt, 5 max). SACK negotiated in handshake (both sides must support). 💭THINK FIRST · FLOW CONTROL & WINDOW SCALING

TCP flow control uses the receiver's advertised window size to limit how many unacknowledged bytes can be in flight. The two-byte Window field caps this at 65,535 bytes without Window Scaling. Window Scaling allows much larger windows by multiplying the Window field value by a scale factor established during the handshake.

  • A Zero Window condition means the data transfer has stopped. Who is responsible for restarting the transfer, and how does the sender know when it can send again?

Model Answer: The receiver is responsible for restarting the transfer. When a Zero Window is advertised, the sender stops sending data. The receiver's application must pull data out of the receive buffer, freeing space. Once space is available, the receiver sends a Window Update packet — a no-data TCP packet advertising a non-zero window size. The sender waits for this Window Update and then resumes. In Expert Info, Window Update appears in the Chats tab (it's a good event). The sender may also send Zero Window Probes (1 byte) to check if the window has reopened.

TCP Flow Control & Window Management

TCP Sliding Window

The TCP sliding window defines how many bytes can be outstanding (unacknowledged) at a time. The window is controlled by three factors: the receiver's TCP buffer space, the sender's transmit buffer, and the amount of traffic the network can handle.

Window Scaling

The TCP Window Size field is only 2 bytes (max 65,535). Window Scaling (TCP option 3) multiplies this value by a scale factor established during the TCP handshake. If a client does not include Window Scale in its SYN, the server will not use it either.

📷Figure 241 — open trace file to view
Figure 241. Wireshark can calculate the true window value based on the scale factor from the TCP handshake [http-cnn2011.pcapng]. Window field 16,425 × scale factor 4 = Calculated Window 65,700.

If Wireshark doesn't see the TCP handshake, it marks Window Size Scaling Factor as -1. If it sees the handshake but no Window Scaling is used, it marks it as -2.

Nagling and Delayed ACKs

The Nagle algorithm buffers outgoing TCP data if there is a previous unacknowledged segment outstanding — this reduces the "small packet problem." It can slow communications for small data transfers and is disabled in many TCP implementations.

Delayed ACKs reduce the number of ACK packets by waiting to ACK either (a) when a second segment arrives within 200ms, or (b) when the 200ms Delayed ACK timer expires. Typically you see an ACK for every other TCP segment received. Delayed ACK problems appear in the TCP Time-Sequence graph as 200ms delays.

🧠
MENTAL NOTE
Window Size field = 2 bytes, max 65,535. Window Scaling multiplies it (factor in SYN). Zero Window = receiver buffer full; data transfer halted. Only recovery: Window Update from receiver (Expert Info: Chats tab). Zero Window Probe = sender sends 1 byte to check if window opened. Congestion window (cwnd) = lower of: receiver window, sender buffer, network capacity. Delayed ACKs: ACK every 2nd segment or after 200ms. Nagle: buffer small outgoing packets when ACK pending.

💭THINK FIRST · TCP HEADER FIELDS & FLAGS

The TCP header is typically 20 bytes but can be longer with options. The Flags field contains 9 bits that control connection setup (SYN), teardown (FIN, RST), data urgency (PSH, URG), and acknowledgment (ACK). The tcp.flags summary value lets you build precise filters.

  • What is the difference between a packet with PSH+ACK flags and a packet with just ACK? When would you see each in a typical HTTP connection?

Model Answer: PSH+ACK tells both the sender and receiver to bypass buffering and deliver data immediately to the application. An application sends PSH when it wants the other side to receive data right away rather than wait for more data to fill the buffer. In HTTP you'd see PSH+ACK on the GET request (the browser wants the response immediately) and on the last data segment of the HTTP response (server signals end of its data). Pure ACK packets (no data, no PSH) are the acknowledgments themselves — they carry no application payload, just the TCP acknowledgment field.

Dissect the TCP Packet Structure

The TCP header is typically 20 bytes. IP Protocol field value 6 (0x06) = TCP.

💭THINK FIRST · TCP PREFERENCES

Wireshark's TCP preferences control how TCP traffic is analyzed and displayed. The Calculate Conversation Timestamps setting and the tcp.time_delta column are among the most powerful tools for spotting performance problems in TCP connections.

  • Why would you want to add a custom column for tcp.time_delta, and how would you use it to find the worst-performing TCP connection in a trace file?

Model Answer: tcp.time_delta shows the time since the previous packet in the same TCP stream. Adding it as a column and sorting by it immediately reveals the largest gaps between packets in any conversation — high values indicate latency, retransmission waits, or application delays. For example, if a specific database conversation shows 3-second gaps while all others are milliseconds, you've isolated the slow application or connection. This is much faster than scrolling through timestamps manually, especially in a trace file with hundreds of simultaneous TCP streams.

Case Study 1
Connections Require Four Attempts
Submitted by: Todd DeBoard and Team, Tyco Electronics Corporation

We had a chronic trouble report from a remote user who reported needing to make four connection attempts with our remote access client before getting a successful connection. The failure happened at boot but not while traveling away from his hometown.

Technical support told him it sounded like an ISP problem, but the ISP denied blocking traffic. After months of repeated calls, we installed Wireshark and ran targeted tests.

Wireshark showed us plain as day that when the client was first run after a power cycle, it would always try initiating connections using the same TCP port and would increment it by one for subsequent attempts. The first three connection attempts received no response, but responses were received for the fourth.

Armed with the Wireshark packet capture, we had the user contact his ISP again. This time, with Wireshark evidence in hand, they confirmed they were in fact blocking the ports in question and would open them for our remote access gateway IPs.

Note: One wonders how many other ISP customers were experiencing the same issue and wondering why their remote access required so many attempts.

TL;DR — Chapter Summary

TCP offers connection-oriented transport services. TCP data is sequenced and acknowledged to ensure data arrives. TCP offers automatic retransmission for lost segments and flow control to avoid saturating a network or TCP host.

TCP communications begin with a three-way handshake (SYN, SYN/ACK, ACK). During data transfer, the Sequence Number field counts up by data bytes sent. If a packet is lost, retransmissions are triggered by Duplicate ACKs (Fast Recovery) or an RTO timeout. Three identical ACKs trigger a retransmission.

Selective Acknowledgments reduce unnecessary retransmissions during packet loss. Window Scaling increases the advertised receive buffer above 65,535 bytes. Zero Window stops all data transfer until a Window Update is received. Wireshark's TCP Expert notifications detect packet loss, window zero conditions, retransmissions, and out-of-order packets.

Review Questions

Q20.1 What is the purpose of TCP?
A20.1 TCP offers connection-oriented transport, data sequencing and acknowledgment, and automatic recovery for lost packets.
Q20.2 What three packets establish a TCP connection?
A20.2 The three packets of the TCP handshake are SYN, SYN/ACK, and ACK.
Q20.3 What is the purpose of the Sequence Number field? What is the purpose of the Acknowledgment Number field?
A20.3 The Sequence Number field uniquely tracks each TCP segment; it increments by the number of data bytes sent. The Acknowledgment Number field indicates the next expected sequence number from the other TCP host.
Q20.4 How does a TCP host refuse a connection request?
A20.4 TCP hosts set the Reset (RST) bit in a response to a TCP SYN packet to refuse a TCP connection.
Q20.5 How does a TCP-based application recover from packet loss?
A20.5 If the sender times out waiting for an acknowledgment, it generates a retransmission. If a receiver notices a missing segment, it sends Duplicate ACKs. Upon receipt of three identical ACKs the TCP sender generates a Fast Retransmission.
Q20.6 What is the maximum value that can be used in the TCP Window field?
A20.6 The TCP Window field is a two-byte field. The maximum value is 0xFFFF or 65,535. To use larger window size values, TCP peers must support Window Scaling (TCP option 3).
