Questions

Q1

Open ftp-clientside.pcapng. What types of TCP problems are seen in this trace file? What is the window size scaling factor of the FTP client?

Your Answer
Model Answer
TCP problems in FTP traces commonly include retransmissions (lost packets), duplicate ACKs (gap in received data), and zero window advertisements (server buffer full). Use Analyze > Expert Information to see a categorized list. The window scale factor is negotiated in the SYN and SYN-ACK packets as a TCP option — expand "Options > Window Scale" in the SYN packet's TCP header to find the multiplier (e.g., scale factor 4 means the advertised window is multiplied by 2^4 = 16). Without window scaling, the maximum receive window is limited to 65,535 bytes.
Q2

Open http-cnn2011.pcapng. Are the KeepAlive packets starting at packet 139 maintaining a single TCP connection? Packet 1306 is a Retransmission—are we downstream from the point where packet loss occurred?

Your Answer
Model Answer
TCP KeepAlive packets are probe segments sent with a sequence number one less than the next expected byte and zero data bytes — they verify the remote endpoint is still alive. A retransmission at packet 1306 (same sequence number sent again) means the original packet was lost somewhere in the network. If we are seeing the retransmission, we are downstream from the sender — meaning we captured the packet at the sender side after it was resent, OR we are between the sender and the point of loss and capturing the retransmit. If we were upstream from the loss point, we would see the original packet but not the retransmission.
Q3

Open http-download-bad.pcapng. Does this connection support SACK? Does it support window scaling? What do the SACK left and right edge values in packet 136 indicate? In packet 679, what sequence number is 10.0.52.164 waiting for?

Your Answer
Model Answer
Wireshark uses relative sequence numbers by default, starting both sides of a connection at 0 for readability. The actual ISN (Initial Sequence Number) is a large random value chosen by the TCP stack. After the SYN packet sets the ISN, the sequence number in the next packet (the third packet of the handshake, the ACK) increments by 1 even though no data bytes were sent — this is because RFC 793 defines that SYN and FIN each consume one sequence number as if they were one byte of data.
Q4

Open http-google2011.pcapng. How many TCP connections were required to load the site? Do both sides of each connection support the same MSS?

Your Answer
Model Answer
Count the number of distinct TCP connections by looking at SYN packets — each SYN initiates one connection. HTTP/1.1 may reuse connections via Keep-Alive, so the actual number of connections can be less than the number of requests. The MSS (Maximum Segment Size) is negotiated in the SYN and SYN-ACK via the MSS TCP option. Each side advertises its own receive MSS; the actual maximum segment size used is the minimum of the two advertised values. A mismatch between sides is normal but can indicate different MTU paths.
Q5

Open http-msnbc.pcapng. What is the window scale factor supported by the msnbc.com server? Does every TCP host support window scaling and SACK?

Your Answer
Model Answer
The window scale factor is visible in the SYN and SYN-ACK packets' TCP options — look for "WS: X" in the Options section. If the server does not include a Window Scale option in its SYN-ACK, window scaling is disabled for that connection even if the client offered it. SACK (Selective Acknowledgment) support is negotiated via the "SACK permitted" TCP option in the SYN — check each unique connection's handshake to see if all servers and the client include this option. Not all servers support window scaling or SACK.
Q6

Open sec-justascan.pcapng. Does the target support window scaling? Does it support SACK? How many TCP connections were successful?

Your Answer
Model Answer
In a TCP SYN scan, window scaling and SACK support are determined from any successful SYN-ACK response — the scanner learns the target's TCP capabilities from the handshake options. Successful connections are identifiable as SYN packets that received a SYN-ACK reply (rather than RST or no response). Count TCP streams where the three-way handshake completed (SYN → SYN-ACK → ACK) to get the number of open ports found. Filter `tcp.flags.syn==1 && tcp.flags.ack==1` to see all SYN-ACK responses.
Q7

Open tcp-137port.pcapng. Follow the TCP stream. What service is running over this port? How can you configure Wireshark to dissect this traffic properly?

Your Answer
Model Answer
Port 137 is assigned to NetBIOS Name Service (NBNS). Follow the TCP stream (Ctrl+Alt+Shift+T or right-click > Follow > TCP Stream) to see the raw application-layer conversation. If Wireshark does not automatically recognize the traffic, force it to dissect as NBNS by right-clicking a packet > Decode As > select NBNS or the appropriate protocol. The stream content will reveal whether this is a genuine NBNS session or an unexpected service running on that port.
Q8

Open tcp-con-up.pcapng. What is the actual TCP starting sequence number used by the client? Why did the TCP sequence number increment between packets 1 and 3? Does this connection support SACK and window scaling?

Your Answer
Model Answer
The actual Initial Sequence Number (ISN) is visible in the SYN packet's raw Sequence Number field. Wireshark displays relative sequence numbers by default (starting at 0) for readability — disable this via Preferences > Protocols > TCP > uncheck "Relative sequence numbers". The sequence number increments by 1 between the SYN (packet 1) and the ACK (packet 3) even though no data bytes were sent — this is because RFC 793 specifies that SYN and FIN flags each consume exactly one sequence number, as if they were a single byte of data. SACK and window scaling are both visible in the SYN Options.
Q9

Open tcp-fin-3way.pcapng. Do you see a 'phantom byte' in this 3-way FIN process?

Your Answer
Model Answer
The "phantom byte" is the sequence number consumed by the FIN flag itself. Like SYN, a FIN packet advances the sequence number by 1 even though it carries no application data — the receiver's ACK for the FIN acknowledges (seq+1) to confirm receipt of the FIN itself. In a simultaneous or sequential close, you can observe this by comparing the sequence number in the FIN packet against the acknowledgment number in the reply — the ACK will be exactly 1 higher than the FIN's sequence number despite zero bytes of payload being transferred.
Q10

Open tcp-handshake-problem.pcapng. What is the purpose of the PUSH flag in packets sent from 67.161.32.69?

Your Answer
Model Answer
The PUSH (PSH) flag in TCP tells the receiving TCP stack to deliver buffered data immediately to the application layer rather than waiting to accumulate more data. Without PSH, TCP's receive buffer might hold small amounts of data waiting for more to arrive before passing it up. Applications set PSH when sending interactive small messages (such as SSH keystrokes or HTTP headers) where immediate delivery matters more than throughput efficiency. The 14-byte payload visible in these packets from 67.161.32.69 would cause unnecessary delay if held in a receive buffer.
Q11

Open tcp-problem.pcapng. What sequence number is not being acknowledged? What can you determine about window scaling support of the two hosts?

Your Answer
Model Answer
The unacknowledged sequence number is visible in the repeated Duplicate ACK packets — the acknowledgment number in each Duplicate ACK is the sequence number the receiver is still waiting for. The sender keeps retransmitting that sequence number because the receiver never stops requesting it. Window scaling support is determined by whether the WS option appeared in the SYN/SYN-ACK handshake — if one side did not include WS in its SYN, scaling is disabled and the window is capped at the raw 16-bit value (max 65,535 bytes), potentially limiting throughput on high-latency paths.
