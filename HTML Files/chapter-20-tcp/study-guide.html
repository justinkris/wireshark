💭 THINK FIRST · TCP HEADER FIELDS

The TCP header is 20 bytes minimum, but every field tells a story about the state of the connection. Being able to read a TCP header in Wireshark is a prerequisite for diagnosing any application-layer problem.

  • What is the purpose of the TCP checksum, and what does it cover? If a TCP segment has a bad checksum, what typically happens?
  • The TCP header has a Data Offset (header length) field. Why does TCP need this when UDP's header is always exactly 8 bytes?
Q1 — TCP CHECKSUM PURPOSE AND BAD CHECKSUM
The TCP checksum covers the TCP header, TCP payload, and a pseudo-header derived from the IP header (source IP, destination IP, protocol=6, and TCP segment length). It's an error detection mechanism. If a segment arrives with an invalid checksum, the receiving host silently discards it — no notification is sent. The sender will eventually time out and retransmit. Modern network adapters often offload checksum calculation to hardware (TCP Checksum Offload), which means Wireshark capturing at the OS level may show "Bad checksum" warnings for locally-generated packets before the NIC computes the real checksum — this is a Wireshark artifact, not a real error.
Q2 — WHY TCP NEEDS DATA OFFSET
TCP has an Options field that can extend the header beyond the minimum 20 bytes. Common TCP options include Maximum Segment Size (MSS), Window Scale, Timestamps, and SACK Permitted — each negotiated during the handshake. Because the header length is variable (20–60 bytes), TCP needs the Data Offset field to tell the receiver where the TCP data starts. UDP has no Options field — it's always exactly 8 bytes, so no length field is needed for the header (though the Length field covers header + data).
Section 1

TCP Header Fields

The TCP header is 20 bytes minimum, up to 60 bytes with options. TCP provides reliable, ordered, connection-oriented data transfer — the foundation of HTTP, HTTPS, FTP, SSH, and most application protocols.

💭 THINK FIRST · THE THREE-WAY HANDSHAKE

The three-way handshake doesn't just establish a connection — it negotiates critical parameters (MSS, window scale, SACK) that determine the entire connection's behavior. What the handshake negotiates shapes performance for the life of the connection.

  • What specifically is being "synchronized" in the SYN and SYN-ACK packets — and why must both sides do it?
  • The MSS (Maximum Segment Size) is negotiated in the TCP options during the handshake. What happens if one side has MSS=1460 and the other has MSS=1000? How does this affect the connection?
Q1 — WHAT SYN SYNCHRONIZES
SYN synchronizes the Initial Sequence Number (ISN) — a randomly chosen 32-bit number that identifies the starting byte position for that side's data stream. Both sides must synchronize their own ISN because TCP is a bidirectional protocol; each direction is an independent data stream. The client's SYN announces "my data starts at ISN=X." The server's SYN-ACK acknowledges that ("I received your ISN, I'll expect byte X+1 next") and simultaneously announces its own ISN for the reverse direction. The client's ACK completes the exchange. Without this synchronization, neither side would know which bytes it's receiving in the acknowledgment number field.
Q2 — MSS MISMATCH
Each side announces the maximum TCP segment size it will accept from the other side. When MSS values differ, the lower value is used in each direction for the relevant side's sending. Since MSS=1000 is smaller, the host with MSS=1460 must send segments no larger than 1000 bytes to the peer with MSS=1000, even though it could receive segments up to 1460 bytes. The connection still works but at reduced efficiency — the smaller MSS means more segments to transmit the same amount of data, increasing header overhead and acknowledgment traffic. Mismatched MSS is common in VPN scenarios where the VPN tunnel adds overhead and reduces the effective MTU.
Section 2

Three-Way Handshake

The TCP three-way handshake establishes connection parameters before data transfer. The three steps: SYN → SYN-ACK → ACK.

StepFlagsFrom→ToSequenceAckWhat happens
1 SYNSYNClient→ServerISN=X—Client announces initial sequence number

3 ACKACKClient→ServerX+1Y+1Client acknowledges server's ISN

TCP Options negotiated during handshake: MSS (max segment size the sender will accept), Window Scale (multiplier for the 16-bit window field, allowing windows > 65535 bytes), SACK Permitted (selective acknowledgment support), Timestamps (round-trip time measurement, PAWS).

Measuring network RTT in Wireshark In Wireshark, look for the [SYN], [SYN, ACK], [ACK] labels in the Info column. The time delta between the SYN and SYN-ACK is the network round-trip time to the server. A large delta here indicates high-latency path to the server, not application slowness.

💭 THINK FIRST · SEQUENCE NUMBERS & ACKNOWLEDGMENTS

Sequence and acknowledgment numbers are how TCP tracks every byte in flight. Reading them in Wireshark is the key to understanding retransmissions, duplicate ACKs, and data ordering — the heart of TCP reliability.

  • What is a duplicate ACK, and why does TCP use three duplicate ACKs as a signal that a segment was lost — rather than waiting for a timeout?
  • Wireshark shows "TCP Previous segment not captured." Is this always a sign of packet loss, or could it mean something else?
Q1 — DUPLICATE ACK AND FAST RETRANSMIT
A duplicate ACK is an acknowledgment sent immediately when a receiver gets a segment with a sequence number higher than expected — meaning a gap exists. The receiver says "I got segment 1001, I'm still waiting for segment 900" by repeating the ACK for 900. One or two duplicate ACKs might indicate out-of-order delivery (common in multi-path networks). Three consecutive duplicate ACKs is TCP's Fast Retransmit trigger — the RFC standardizes three duplicates as strong evidence that a segment was lost (not just reordered), because reordering rarely skips three segments. Fast Retransmit immediately resends the missing segment without waiting for the retransmission timeout (RTO), which could be hundreds of milliseconds, dramatically speeding recovery.
Q2 — "PREVIOUS SEGMENT NOT CAPTURED"
"TCP Previous segment not captured" in Wireshark can mean: (1) Actual packet loss — the segment was truly dropped in the network. (2) Capture artifact — Wireshark missed the segment due to high packet rates or the capture started mid-stream. A key distinction: if you see this on the very first segments when you start a capture on an existing connection, it's almost certainly a capture artifact (you missed the connection setup). If you see it mid-stream during an established connection with consistent previous capture coverage, it's more likely actual packet loss. Also, asymmetric captures (only seeing one direction) can make the other direction's data look missing.
Section 3

Sequence Numbers and Acknowledgments

TCP uses 32-bit sequence numbers to track every byte in the stream. The sequence number in each segment indicates the byte position of the first data byte in that segment. The acknowledgment number indicates the next byte the receiver expects from the other side.

Wireshark uses Relative Sequence Numbers by default — it resets ISN to 0 for readability. You can disable this in Preferences → TCP to see actual sequence numbers.

💭 THINK FIRST · TCP FLOW CONTROL & WINDOWING

The TCP receive window controls how much data can be in-flight at once — it's the primary performance governor for high-bandwidth connections. A shrinking window, a zero window, or a mismatch between bandwidth-delay product and window size are all performance bottlenecks visible in Wireshark.

  • A client is receiving data and its receive window drops from 65535 to 0. What does this mean, and what happens to the TCP connection?
  • Why does a large bandwidth-delay product (BDP) require large TCP windows? What happens if the window is too small for the BDP?
Q1 — ZERO WINDOW
A window of 0 means the receiver's buffer is full — it cannot accept any more data. The sender must stop sending immediately and wait. The sender sets a "persist timer" and periodically sends Window Probe packets (1-byte segments) to ask the receiver if it has freed up buffer space. If the receiver has processed the buffered data and has room again, it sends a Window Update with a non-zero window. In a capture this appears as: data segments → TCP Window Full → TCP Zero Window → TCP Window Update. This sequence is a sign of a slow receiver (application not processing data fast enough) or insufficient receive buffer memory, not a network problem.
Q2 — BANDWIDTH-DELAY PRODUCT AND WINDOW SIZE
The bandwidth-delay product (BDP) = bandwidth × round-trip time. This represents the amount of data that can be "in flight" at any given moment to fully utilize the link. If the TCP window is smaller than the BDP, the sender runs out of window and must stop and wait for ACKs before sending more — the link is underutilized. Example: a 100 Mbps link with 100ms RTT has a BDP of 100,000,000 × 0.1 = 10,000,000 bytes = ~10 MB. But the basic TCP window field is only 16 bits (max 65535 bytes). Without Window Scaling (TCP option that multiplies the window by a factor up to 2^14), you can only have 65,535 bytes in flight — far less than the 10MB needed to fill a 100Mbps/100ms pipe. This is the classic "long fat network" problem.
Section 4

Flow Control and Windowing

The TCP window size field tells the sender how many bytes the receiver can accept before needing an acknowledgment. It's the primary flow control mechanism — the receiver controls the sender's rate by adjusting the window.

The Window Scale option (negotiated in the handshake) multiplies the window size field by 2N (where N is 0–14), allowing windows up to 230 = 1 GB. Modern OS implementations use window scaling by default.

TCP Zero Window is a receiver problem, not a network error TCP Zero Window is not a network error — it means the application is too slow to consume data. Common causes: application bottleneck, insufficient memory, or an overloaded server. The network path is fine; the receiving end needs attention.
Window analysis filters Useful window-analysis filters: tcp.window_size == 0 (zero window), tcp.analysis.window_full (sender hit the window limit), tcp.analysis.window_update (receiver reopened the window).
🧠
MENTAL NOTE
Window = receive buffer space available. Zero window = receiver full, sender must stop. Window Scale option needed for BDP > 65535 bytes. BDP = bandwidth × RTT. tcp.analysis.window_full + Zero Window + Window Update sequence = slow receiver, not network loss.

💭 THINK FIRST · TCP PROBLEMS & ERRORS

Most TCP problems fall into one of four categories: packet loss (retransmissions), connection refused (RST), slow receiver (zero window), or high latency (large delta times). Wireshark's TCP analysis colorization makes most of these immediately visible.

  • What is the difference between a TCP retransmission and a TCP fast retransmission? Under what condition does each occur?
  • You see a TCP RST in the middle of an established connection. What are two scenarios that could cause this?
Q1 — RETRANSMISSION VS FAST RETRANSMISSION
A regular TCP retransmission occurs when the retransmission timer (RTO) expires without an acknowledgment arriving. The RTO starts at ~1 second and doubles with each unacknowledged retransmission (exponential backoff). This can take several seconds. A TCP Fast Retransmission is triggered immediately (without waiting for the RTO) when three duplicate ACKs arrive — the receiver is actively signaling that a specific segment is missing. Fast Retransmit dramatically speeds recovery from isolated segment loss because it doesn't require waiting for the timeout. In Wireshark, regular retransmissions appear as tcp.analysis.retransmission; fast retransmissions appear as tcp.analysis.fast_retransmission.
Q2 — MID-CONNECTION RST
Two scenarios for mid-connection RST: (1) Connection reset by remote application — the remote application called close() abruptly (e.g., a crash, or a server that rejects the connection after examining application data). The RST immediately terminates the connection with no graceful teardown. (2) Stateful firewall timeout — the firewall between the two hosts dropped the connection state because it was idle too long. The next packet from one side arrives at the firewall with no state entry, and the firewall sends a forged RST to both sides. This is why long-idle connections through firewalls suddenly break — the firewall's state table has aged out the entry. Fix: TCP keepalives, or configure the firewall's idle timeout to match application requirements.

Diagnosing retransmission type by delta time If you see retransmissions, look at the delta time between the original segment and the retransmission — the gap tells you whether it's a fast retransmit (milliseconds, triggered by dup ACKs) or a timeout-based retransmit (1+ seconds, triggered by RTO expiry). Timeout retransmits have a huge performance impact.

💭 THINK FIRST · TCP CONNECTION TEARDOWN

TCP has two completely different ways to end a connection — a graceful four-way FIN handshake and an abrupt RST. Which one you see in a capture tells you a lot about how and why the connection ended.

  • Explain the difference between a TCP FIN teardown and a TCP RST teardown. What does each mean for any in-transit data?
  • In a TCP FIN teardown, why are four packets needed instead of two? Why can't both sides close simultaneously in one round-trip?
Q1 — FIN TEARDOWN VS RST TEARDOWN
A FIN teardown is graceful — it signals that the sender has no more data to send but is still willing to receive. Each side independently sends a FIN and waits for the other to acknowledge. In-transit data already in the pipeline is delivered before the connection closes. A RST teardown is abrupt — the connection is immediately terminated, all unacknowledged data is discarded, and any data in flight is lost. No FIN/ACK exchange occurs. RST is used for errors, crashes, or firewall intervention. From the remote side, FIN teardown results in a clean EOF on the socket; RST results in a "connection reset by peer" error.
Q2 — WHY FOUR PACKETS FOR FIN TEARDOWN
TCP is full-duplex — each direction is independent. When the client sends FIN, it means "I'm done sending," but the server may still have data to send. The server sends ACK to acknowledge the client's FIN, then continues sending its remaining data. Only after the server has finished sending its own data does it send its own FIN. The client then ACKs the server's FIN. That's four packets: FIN (client) → ACK (server) → FIN (server) → ACK (client). The delay between the server's ACK and FIN is called "half-close" — the connection is open in one direction only. Both sides can only close simultaneously if neither has data left to send after the first FIN, which produces a simultaneous close (rare but valid).
Section 6

TCP Connection Teardown

TCP connections can end in two ways: graceful FIN teardown (4 packets) or abrupt RST teardown (1 packet).

StepFlagsDirectionMeaning
1FIN, ACKClient→ServerClient done sending
2ACKServer→ClientServer acknowledges FIN
3FIN, ACKServer→ClientServer done sending
4ACKClient→ServerClient acknowledges server FIN

The TIME_WAIT state: after the final ACK, the active closer enters TIME_WAIT for 2×MSL (Maximum Segment Lifetime, typically 60 seconds on Linux, 240 seconds on Windows). This ensures delayed packets from the old connection don't corrupt a new one on the same port pair.

Visualizing teardown in Wireshark In Wireshark, filter tcp.flags.fin == 1 to see all FIN packets and visualize the teardown. A clean teardown is: FIN → ACK → FIN → ACK. If you see FIN → RST instead of FIN → ACK, something aborted the connection.
🧠
MENTAL NOTE
FIN teardown = 4 packets (half-duplex close per side). FIN = "done sending, can still receive." RST = "connection aborted, data discarded." TIME_WAIT = 2×MSL after active close (prevents port reuse collision). Filter: tcp.flags.fin==1 and tcp.flags.reset==1.
