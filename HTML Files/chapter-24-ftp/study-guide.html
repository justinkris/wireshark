💭 THINK FIRST · FTP OVERVIEW

FTP's two-channel design separates control (commands) from data (file content). Understanding that these are two distinct TCP connections explains both FTP's firewall problems and why credentials appear separately from file content in Wireshark captures.

  • A user says they uploaded a sensitive file via FTP. What can you determine about that transfer using Wireshark?
  • What is the fundamental difference between SFTP and FTP — are they related protocols?
Q1 — WHAT YOU CAN DETERMINE ABOUT AN FTP UPLOAD
On the FTP control channel (port 21): you can see the STOR command (the filename being uploaded), the login sequence (USER and PASS commands — including the plaintext password), and the server's response codes. On the FTP data channel: you can see the actual file content in the ftp-data stream, and use File → Export Objects → FTP-DATA to extract the file. Everything is cleartext — content, credentials, and filename are fully visible.
Q2 — SFTP VS FTP
SFTP (SSH File Transfer Protocol) and FTP are completely unrelated protocols despite the similar name. SFTP runs as a subsystem of SSH on port 22, encrypts everything (including credentials and file data), and has entirely different protocol mechanics. FTPS (FTP over TLS/SSL) is TLS-encrypted FTP, but still uses the same FTP command structure. FTP = port 21, completely cleartext. SFTP = port 22, completely encrypted.
Section 1

FTP Overview

FTP uses two separate TCP connections: (1) Control channel — TCP port 21, always open for the session. All commands (authentication, directory, transfer commands) travel here as cleartext text. (2) Data channel — negotiated for each file transfer or directory listing. Carries the actual file content or directory listing.

FTP is entirely cleartext — all commands, passwords, and file content are unencrypted. Use ftp filter for the control channel and ftp-data for file transfers.

FTP transmits passwords in plaintext FTP transmits usernames and passwords as plaintext. Filter ftp and Follow TCP Stream — the PASS command contains the literal password. This is why FTP is prohibited in most security policies. Use SFTP (port 22, SSH-based) or FTPS (FTP over TLS) instead.
🧠
MENTAL NOTE
FTP = 2 TCP channels: Control (port 21, always open, cleartext commands) + Data (port 20 active/negotiated passive, file content). ALL cleartext — credentials and file content visible. SFTP = SSH-based (port 22, encrypted, different protocol). FTPS = FTP over TLS. Filter: ftp (control), ftp-data (transfers).

💭 THINK FIRST · ACTIVE VS PASSIVE MODE

The active vs passive distinction determines WHO initiates the data connection. This distinction is critical because it determines whether FTP works through firewalls and NAT. Understanding which mode is being used explains why FTP transfers may succeed or fail.

  • An FTP client can log in and list directories but file transfers always fail. Is this more consistent with an active or passive mode problem?
  • In Wireshark, you see a PORT command in the FTP control stream. What information does it contain and who initiates the data connection?
Q1 — ACTIVE VS PASSIVE MODE FAILURE
More consistent with an active mode problem. In active mode, the server initiates the data connection back to the client — this incoming connection is typically blocked by client-side firewalls and NAT. The control session (login, LIST) works fine because the client initiates it outbound. Actual file transfers fail because the server can't initiate the inbound data connection to the client. Fix: switch the FTP client to passive mode where the client initiates both connections.
Q2 — PORT COMMAND FORMAT AND WHO INITIATES
PORT command format: PORT a,b,c,d,e,f where a.b.c.d is the client's IP address and the port number is calculated as e×256+f. For example PORT 192,168,1,100,196,134 means the client is listening on 192.168.1.100 port (196×256)+134=50310. The SERVER initiates the data connection FROM port 20 TO the client's announced IP:port.
Section 2

Active vs Passive FTP Mode

Active Mode (PORT command): Client announces which port it's listening on via PORT command. Server initiates data connection FROM its port 20 TO the client's announced port. Problem: firewalls and NAT block incoming connections from the server to the client.

Passive Mode (PASV command): Client sends PASV. Server responds with IP:port it's listening on. Client initiates data connection to the server. Firewall-friendly since client always initiates. Modern FTP clients default to passive mode.

EPSV = Extended Passive Mode (IPv6 compatible version of PASV).

ModeCommandWho Initiates DataFirewall Behavior
ActivePORTServer → ClientOften blocked (inbound from server)
PassivePASVClient → ServerFirewall-friendly (client initiates)
Extended PassiveEPSVClient → ServerFirewall-friendly, IPv6 compatible
Identify mode in Wireshark In Wireshark, look for PORT (active) or PASV (passive) commands in the FTP control stream. If transfers fail in active mode, a firewall blocking the server-initiated inbound connection is almost certainly the cause.
🧠
MENTAL NOTE
Active (PORT): server→client data connection, blocked by most firewalls/NAT. Passive (PASV): client→server data connection, firewall-friendly, modern default. Data filter: ftp-data. PASV response contains IP+port for client to connect to. PORT command contains client IP+port for server to connect to.

💭 THINK FIRST · FTP COMMANDS

FTP's command set reveals exactly what happened in a session — what files were transferred, what directories were accessed, whether login succeeded or failed. Knowing these commands lets you reconstruct a complete FTP session just from the control channel stream.

  • You see FTP response code 530 repeated 10 times. What is happening and what would you check to determine if it's a brute-force attack?
  • An FTP session shows TYPE I command. What does this mean for how the file data is transmitted?
Q1 — CODE 530 AND BRUTE-FORCE DETECTION
Code 530 is "Login incorrect" — the authentication failed 10 consecutive times. To determine if it's a brute-force attack: check the USER command in each failed attempt — if the same username with different passwords is tried, it's a password-guessing attack against a known account. If different usernames are tried, it's a username enumeration + password attack. Also check the inter-attempt timing — brute force tools typically probe at machine speed (milliseconds between attempts), while a legitimate user who forgets their password will have human-speed delays (seconds between attempts).
Q2 — TYPE I (BINARY MODE)
TYPE I (Image type, also called Binary mode) means the file data will be transferred byte-for-byte without any character translation. TYPE A (ASCII mode) performs line-ending conversion, which corrupts binary files. For any binary file (executables, images, archives), TYPE I must be used. If you see TYPE A followed by a binary file transfer, expect file corruption.
Section 3

FTP Commands and Response Codes

FTP commands travel on the control channel as cleartext text. Every command and response is readable by filtering ftp and using Follow TCP Stream.

💭 THINK FIRST · FTP ANALYSIS IN WIRESHARK

FTP analysis in Wireshark combines control-channel inspection (reading commands and responses as text) with data-channel analysis (extracting transferred files). The combination of Follow TCP Stream and Export Objects gives you a complete picture of the FTP session.

  • How would you use Wireshark to recover a file transferred over FTP during a security incident?
  • You see FTP response code 425 "Can't open data connection." What FTP concept explains this, and what configuration change would fix it?
Q1 — RECOVERING A FILE FROM AN FTP CAPTURE
(1) Filter ftp-data to see all data transfer packets. (2) File → Export Objects → FTP-DATA — Wireshark reassembles the FTP data stream and presents each transferred file. Select the file and click Save. (3) Alternatively, right-click a ftp-data packet → Follow → TCP Stream to see the raw transferred content. For binary files, switch the stream view to "Raw" to save the bytes correctly.
Q2 — CODE 425 AND THE FIX
Code 425 means the server couldn't open the data connection. In active mode, this means the server tried to connect back to the client on the port announced in the PORT command, but was blocked (firewall or NAT). Fix: configure the FTP client to use passive mode (PASV) — the client then initiates the data connection outbound, which works through firewalls and NAT.
Section 4

Analyzing FTP in Wireshark

FTP display filters:

FilterWhat It Shows
ftpAll FTP control traffic
ftp-dataFTP data transfers only
ftp.request.command == "PASS"Login password packets
ftp.response.code == 530Failed login attempts
ftp.response.code == 226Completed file transfers
ftp.request.command == "RETR"File download commands
ftp.request.command == "STOR"File upload commands

Analysis workflow:

  1. Filter ftp to see control channel.
  2. Follow TCP Stream to read full session as text — commands, responses, and plaintext password in order.
  3. Filter ftp-data to find transfers.
  4. File → Export Objects → FTP-DATA to extract transferred files.
  5. Time delta between RETR command and 226 response = transfer time.
Export Objects — the primary FTP forensic technique File → Export Objects → FTP-DATA extracts every file transferred during the FTP session. This is the primary forensic technique for recovering files from FTP captures.
🧠
MENTAL NOTE
FTP analysis: Filter ftp → Follow TCP Stream (read plaintext session including PASS) → Filter ftp-data → File → Export Objects → FTP-DATA (extract files). Failed logins: ftp.response.code==530. Transfer timing: delta between RETR and 226 response. PASS = plaintext password always visible.
