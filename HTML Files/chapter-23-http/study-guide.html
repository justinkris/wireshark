💭 THINK FIRST · HTTP REQUEST AND RESPONSE

HTTP is a text-based protocol layered over TCP. Every HTTP transaction follows a strict request-response format that is fully readable in plain-text captures. Understanding this structure is the prerequisite for interpreting any web application behavior in Wireshark.

  • You Follow a TCP Stream and see HTTP request headers but the response body looks like garbled binary. What is the most likely explanation?
  • HTTP/1.1 requires a "Host" header in every request. What problem was this header designed to solve?
Q1 — BINARY-LOOKING RESPONSE BODY
The response body is compressed — the server used Content-Encoding: gzip or deflate (or br for Brotli). The compressed bytes appear as binary in the raw stream. Wireshark can decompress gzip HTTP content automatically — check Edit → Preferences → Protocols → HTTP → "Allow subdissector to decompress body." With decompression enabled, Wireshark will show the decoded plaintext content in the packet details rather than raw compressed bytes.
Q2 — WHY THE HOST HEADER EXISTS
The Host header allows one IP address to serve multiple websites (virtual hosting). Before HTTP/1.1, a web server at a single IP could only serve one website because there was no way for the client to specify which domain it wanted. The Host header tells the server which virtual host (domain name) the client is requesting, so multiple domains can share one IP address and one physical server. This is how CDNs and web hosting providers serve thousands of domains from shared infrastructure.
Section 1

HTTP Request and Response Structure

HTTP is a text-based, stateless protocol that runs over TCP. Port 80 for plaintext HTTP, port 443 for HTTPS (HTTP over TLS). Every HTTP interaction is a request-response pair.

HTTP/1.1 Request structure:

  1. Request line — METHOD /path HTTP/1.1
  2. Headers — key: value pairs, one per line
  3. Blank CRLF line — separates headers from body
  4. Optional body — present for POST, PUT, PATCH requests

HTTP/1.1 Response structure:

  1. Status line — HTTP/1.1 STATUS_CODE Reason Phrase
  2. Response headers — key: value pairs
  3. Blank CRLF line
  4. Response body — the content (HTML, JSON, image, etc.)
Enable TCP reassembly for full HTTP decode Enable Preferences → TCP → "Allow subdissector to reassemble TCP streams" to see HTTP requests and responses as complete transactions rather than scattered segments. Without this, large HTTP messages split across multiple TCP segments show as incomplete. Follow TCP Stream (right-click → Follow → TCP Stream) shows the full plaintext conversation.
🧠
MENTAL NOTE
HTTP: request line + headers + blank line + body. Response: status line + headers + blank line + body. TCP port 80 (HTTP), 443 (HTTPS). TCP reassembly must be enabled for multi-segment HTTP decode. Follow TCP Stream shows full plaintext conversation. gzip compression = body appears binary (Wireshark can decompress).

💭 THINK FIRST · HTTP METHODS AND STATUS CODES

HTTP methods define what action the client wants, and status code ranges group server responses by outcome. Memorizing the status code ranges (2xx=success, 4xx=client error, 5xx=server error) lets you immediately classify a server's response when analyzing HTTP traffic.

  • You see HTTP response code 304 Not Modified. What does this mean from a performance perspective?
  • You filter http.response.code >= 400 and see hundreds of 404 errors. What might this indicate about a client or automated tool?
Q1 — 304 NOT MODIFIED AND PERFORMANCE
304 means the client sent a conditional GET (with If-Modified-Since or If-None-Match headers) and the server confirmed the cached version is still current. The server returns no body — only the status code. This is a performance win — the browser reused its cached copy instead of downloading the resource again. High 304 rates indicate effective HTTP caching. From a capture perspective, 304 responses are tiny compared to 200 responses carrying full content bodies.
Q2 — HUNDREDS OF 404 ERRORS
Hundreds of 404 (Not Found) errors suggest a client is requesting resources that don't exist. This could be: (1) a misconfigured application generating bad URLs; (2) a web scraper or crawler hitting broken or moved links; or (3) a scanner or attacker probing for known vulnerability paths such as /wp-admin, /.env, /phpmyadmin, or known CMS file paths. Legitimate browsers browsing properly linked pages rarely generate 404s in bulk. Check the request URIs in Statistics → HTTP → Requests to see which paths are failing.

💭 THINK FIRST · HTTP HEADERS

HTTP headers reveal far more than the URL — they expose the client's browser and OS, session cookies, authentication credentials, and caching state. For security analysis, request headers like Authorization and Cookie are primary targets; for performance analysis, Cache-Control and Transfer-Encoding explain data transfer behavior.

  • You see Authorization: Basic dXNlcjpwYXNzd29yZA== in an HTTP request header. What does this reveal, and how serious is it?
  • What does a Transfer-Encoding: chunked header mean for how the HTTP response body is transmitted?
Q1 — AUTHORIZATION: BASIC IS PLAINTEXT CREDENTIALS
Authorization: Basic means the client is using HTTP Basic Authentication. The value after "Basic " is base64-encoded — NOT encrypted. base64 is trivially reversible: dXNlcjpwYXNzd29yZA== decodes to user:password — the actual username and password in readable form. Without HTTPS, this credential is completely exposed to anyone capturing the network traffic. This is a serious security risk: the credential can be decoded in seconds by any analyst or attacker with access to the capture. Always use HTTPS when Basic Auth is involved.
Q2 — TRANSFER-ENCODING: CHUNKED
Chunked transfer encoding means the server doesn't know the total content length when it starts sending — the body is broken into size-prefixed chunks, each sent as it becomes available. Each chunk is preceded by its size in hexadecimal, followed by the chunk data, followed by CRLF. A zero-length chunk marks the end. In Wireshark, you'll see the response segments with chunk size markers in the packet details. The Content-Length header is absent when chunked encoding is used. Wireshark reassembles chunked content automatically when TCP reassembly is enabled.

💭 THINK FIRST · HTTP/2 AND WIRESHARK HTTP TOOLS

HTTP/2 changes the fundamental structure of HTTP — it's binary instead of text, multiplexes multiple requests over one TCP connection, and nearly always runs over TLS. Most HTTP/2 traffic appears encrypted in Wireshark without TLS decryption configuration. Understanding how to use Wireshark's built-in HTTP statistics windows provides fast protocol-level summaries without reading individual packets.

  • You're analyzing HTTP/2 traffic but the content shows as encrypted. What must you configure in Wireshark to decrypt it?
  • Using Statistics → HTTP → Packet Counter, you see 40% of responses are 503. What does this tell you about the server?
Q1 — DECRYPTING HTTP/2 IN WIRESHARK
Wireshark needs a TLS pre-master secret log file. Set the SSLKEYLOGFILE environment variable in Chrome or Firefox before starting the browser session, capture the traffic, then configure Wireshark: Preferences → Protocols → TLS → Pre-Master-Secret log filename. This provides the session keys needed to decrypt the TLS that wraps HTTP/2 (h2). RSA private key decryption does NOT work for HTTP/2 since modern TLS 1.3 uses ephemeral key exchange (ECDHE), making past key captures useless. SSLKEYLOGFILE is the only reliable method.
Q2 — 40% OF RESPONSES ARE 503
HTTP 503 is "Service Unavailable" — the server is receiving requests but actively refusing them because it's overloaded or a backend dependency is down. 40% of responses being 503 is a severe server-side failure, not a client or network problem. Investigate: look at response times for successful requests, check server CPU and memory, and examine which specific endpoints generate 503s (Statistics → HTTP → Requests shows the URL breakdown). A backend database, microservice, or upstream dependency outage is the most common cause of sustained 503s.
Section 4

HTTP/2 and Wireshark HTTP Tools

HTTP/2 is a major revision of the protocol. Key differences from HTTP/1.1:

  • Binary framing — HTTP/2 uses binary frames instead of text. Not human-readable without Wireshark decode.
  • Multiplexing — Multiple request/response streams run in parallel over a single TCP connection.
  • HPACK header compression — Redundant headers are compressed across requests.
  • Server push — Server can proactively send resources before the client requests them.
  • Always TLS in practice — HTTP/2 uses ALPN negotiation to advertise "h2" over TLS. Plaintext HTTP/2 (h2c) is rarely used.

Wireshark decodes HTTP/2 frames when TLS is decrypted: DATA, HEADERS, SETTINGS, PING, RST_STREAM, GOAWAY. Display filter: http2

Wireshark HTTP statistics tools:

  • Statistics → HTTP → Packet Counter — Full breakdown of request methods and response codes. Fastest way to profile an HTTP capture.
  • Statistics → HTTP → Requests — List of all requested URIs and their frequency.
  • Statistics → HTTP → Load Distribution — Breakdown by server host/IP.
  • File → Export Objects → HTTP — Extract files transferred over HTTP (images, scripts, downloads).
Statistics → HTTP → Packet Counter Statistics → HTTP → Packet Counter is the fastest way to see the entire HTTP method and status code profile of a capture. Run it first on any web application capture to understand the overall request/response distribution before diving into individual packets.
🧠
MENTAL NOTE
HTTP/2 = binary, multiplexed, TLS (h2). Filter: http2. HTTP/2 decrypt: SSLKEYLOGFILE env var → Prefs → TLS → pre-master secret log. HTTP stats: Statistics → HTTP (Packet Counter, Requests, Load Distribution). Export objects: File → Export Objects → HTTP. Without TLS decryption = only encrypted TLS frames visible.
