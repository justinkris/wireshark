💭THINK FIRST · HTTP OVERVIEW & FILTERING

HTTP uses a request/response model over TCP. The client sends a request with a Method (GET, POST, etc.) and the server responds with a Status Code. For analysis, using the http display filter shows only HTTP application packets — you miss the TCP handshake and ACKs. Use tcp.port==80 to see everything.

  • Why does the http display filter give a partial view of a web browsing session? When would you prefer http vs tcp.port==80?
  • A user complains that the first visit to a website is slow but subsequent visits are fast. What HTTP mechanism explains this, and what would you look for in a trace file?

Model Answer 1: The http filter only shows packets where Wireshark's HTTP dissector has identified application-layer HTTP content. When TCP stream reassembly is enabled, data packets are combined into reassembled streams and Wireshark shows only the reassembled packets (not the individual TCP data segments). TCP handshake, ACKs, and FIN/RST packets don't contain HTTP application data so they're filtered out. Use tcp.port==80 when you need to see the full TCP conversation including handshake timing and retransmissions. Use http when you just want to see which pages were requested and what status codes came back.

Model Answer 2: HTTP caching. After the first visit, the browser stores page elements locally. On subsequent visits, the browser sends requests with the IfModified-Since modifier containing the date/time of the cached version. If the server hasn't changed the content, it returns HTTP 304 Not Modified, and the browser loads the cached version without downloading it again. In the trace file, look for GET requests containing "IfModified-Since" and responses of "304 Not Modified" — these confirm cache is being used and explain why the first load is slow while repeat visits are fast.

HTTP — Purpose & Normal Communications

HTTP (Hypertext Transfer Protocol) is the application used when someone browses (unsecured) on the Internet. HTTP uses a request/response model. HTTP v1.1 (RFC 2616) is the current version. HTTP uses TCP as transport — most commonly on port 80.

By default, Wireshark is configured to dissect HTTP on 9 ports: 80, 3128, 3132, 5985, 8080, 8088, 11371, 1900, and 2869. If HTTP traffic is running on another port, add it to the HTTP preferences.

TIP: Disable Stream Reassembly for Clearest HTTP View For the clearest view of HTTP traffic in the Packet List pane, disable Allow subdissector to reassemble TCP streams in TCP preferences. This enables you to see all HTTP GET requests and HTTP response codes in the Packet List pane Info column.

HTTP Statistics

Select Statistics | HTTP for three statistics windows:

  • Load Distribution: Lists all HTTP servers contacted and number of requests. Reveals website dependencies and CDN partners (e.g., a single www.espn.com page may contact 35 servers).
  • Packet Counter: Lists all Status Code responses. Instantly spots 4xx Client Errors and 5xx Server Errors.
  • HTTP Requests: Lists each item requested from each HTTP server.

💭THINK FIRST · HTTP METHODS & STATUS CODES

HTTP methods define what the client wants to do (GET, POST, PUT, DELETE). Status codes define the outcome. Codes 1xx=informational, 2xx=success, 3xx=redirect, 4xx=client error, 5xx=server error. Anything above 399 means something went wrong.

  • What is the difference between a 301 Moved Permanently and a 302 Found redirect? When analyzing a slow website, why would multiple 301/302 redirects matter?

Model Answer: 301 Moved Permanently tells the client and any search engines that the resource has moved forever — browsers will cache this redirect and go directly to the new location next time. 302 Found means the resource is temporarily at a different location — browsers won't cache it. When analyzing slow websites, multiple redirects matter because each 3xx response requires the client to establish a new TCP connection (or reuse an existing one) to the redirected URL, adding one full round trip per redirect. If a website has 3 levels of redirects, it adds 3 extra TCP+DNS round trips before the actual content starts flowing.

TIP Build a coloring rule for HTTP errors: http.response.code >= 400. Spot server or client issues instantly in the Packet List pane without opening each packet.
CAUTION: Don't Troubleshoot Delays Before FIN/RST If you see a large delay before a packet with the FIN or RST bit set, do not waste time troubleshooting it. These packets can be sent long after the user has finished getting the required data. The user doesn't notice this delay. Focus instead on delays during the active data exchange.

HTTP Request Structure Key Fields

  • Host: Required in HTTP/1.1. Identifies target host and port. If no port, default (80) is assumed.
  • User-Agent: Browser and OS information.
  • IfModified-Since: Date of cached version. Server returns 304 if content unchanged.
  • Referer: Previous website that linked to current one.
  • Accept: Acceptable content types the client can handle.
  • Connection: Type of connection preferred (Keep-Alive, close).

💭THINK FIRST · HTTPS & TLS ANALYSIS

HTTPS uses TLS over TCP port 443. After the TCP handshake, a TLS handshake negotiates a cipher suite and authenticates the server. The client offers a list of cipher suites; the server chooses. Wireshark can decrypt HTTPS traffic if you have the server's private RSA key.

  • During a TLS handshake, the client sends a Client Hello with 34 cipher suites. Who decides which one is used, and what determines their preference order?

Model Answer: The server selects the cipher suite from the client's offered list (Server Hello). The client's list is ordered by preference (strongest/preferred first). The server selects based on its own policy — typically it picks the strongest suite it supports from the client's list, but it may prefer its own order. In enterprise environments, servers are often configured to prefer Perfect Forward Secrecy (PFS) suites like ECDHE over older RSA key exchange to improve security. In the Client Hello, the first listed cipher = client's top preference. What the server actually selects may differ from the client's top choice.

Analyze HTTPS / TLS Communications

HTTPS uses HTTP over Transport Layer Security (TLS) on TCP port 443. RFC 2818 defines HTTPS. RFC 2246 defines TLS 1.0 (based on SSL 3.0, but not interoperable).

TLS Handshake

After the TCP handshake, a TLS handshake occurs. Filter: ssl.record.content_type==22 to view TLS handshake packets.

StepPacketDirectionKey Content
1Client HelloClient → ServerTLS version, Session ID (0=new), 28 random bytes, list of cipher suites supported
2Server Hello + Certificate + Server Hello DoneServer → ClientChosen cipher suite, 28 random bytes, Session ID (32 bytes), server X.509 certificate
3Client Key Exchange + Change Cipher Spec + FinishedClient → ServerPremaster secret, "all future messages from client will be encrypted"
4Change Cipher Spec + FinishedServer → Client"All future messages from server will be encrypted"

Session ID = 0 in Client Hello → new session. Non-zero Session ID → resumed session (faster).

Decrypt HTTPS Traffic

To decrypt HTTPS in Wireshark: (1) Obtain the server's private RSA key. (2) Copy it to your Wireshark system. (3) Configure Edit | Preferences | Protocols | SSL RSA Keys list with: server IP, port (443), protocol (http), and key file path. (4) Open the HTTPS trace file — traffic will be decrypted. A "Decrypted SSL data" tab appears below the Packet Bytes pane.

CAUTION The RSA private key can only be obtained from the server side. You cannot decrypt HTTPS traffic from a client capture unless you have access to the server's private key.
TIP: Delays Before Encrypted Alerts May Be OK When you see an established TLS handshake, data exchange, a large delay, then an Encrypted Alert followed by FIN/RST — the alert is most likely a close_notify (normal graceful TLS shutdown). Don't troubleshoot this delay.
🧠
MENTAL NOTE
TLS handshake: Client Hello → Server Hello+Cert+Done → Client Key Exchange+Change Cipher → Server Change Cipher. Client offers cipher suite list; server selects. Session ID=0 = new session. TLS handshake filter: ssl.record.content_type==22. Decrypt = need server private RSA key + configure SSL preferences RSA Key List. close_notify Encrypted Alert + FIN = normal TLS shutdown. TCP reassembly must be ON to see all 4 TLS handshake packets.

Case Studies

Case Study 1
HTTP Proxy Problems
Submitted by: Richard Hicks, Senior Sales Engineer, Edge Security Solutions, Celestix Networks

A common troubleshooting scenario: requests through a simple packet-filtering router work fine, but the same request through an application layer proxy (ISA Server) fails.

A customer called reporting HTTP 502 errors accessing a third-party web-based application when going through a Microsoft ISA Server 2006 proxy. The application worked when going through a router directly.

Knowing that ISA performs application layer traffic inspection, I immediately reproduced the error and captured traffic on both sides of the proxy.

The key finding: looking at the response from the application server, the trace showed that the request was using HTTP 2.0. There is no RFC specification for HTTP 2.0! The ISA firewall, with its deep application layer inspection capabilities, limits communication over TCP port 80 to only valid, RFC-compliant HTTP. Since HTTP 2.0 was technically an RFC violation, the ISA firewall denied the traffic and returned a 502 Bad Gateway.

Uncovering these details would not have been possible without Wireshark. Capturing on both sides of the proxy was the key to finding the violation.

TL;DR — Chapter Summary

HTTP uses a request/response model to transfer data. HTTP uses TCP transport — most commonly port 80. Clients send commands (GET, POST) and servers respond with status codes. Codes greater than 399 identify errors. Watch for IfModified-Since requests and 304 Not Modified responses indicating cached pages.

HTTPS uses TLS to create a secure HTTP connection. After the TCP handshake, a TLS handshake negotiates cipher suite and authentication. The client offers cipher suites; the server selects one. Wireshark can decrypt HTTPS with the server's private RSA key configured in SSL preferences.

Review Questions

Q23.1 What HTTP response code indicates the page was found and returned successfully?
A23.1 HTTP response code 200 OK indicates the desired page was located and returned successfully.
Q23.2 How is an HTTP 404 Not Found categorized?
A23.2 A 404 Not Found is categorized as a Client Error (4xx range), even though it may be caused by a broken link on a website rather than an actual client mistake.
Q23.3 How can you determine that a client is loading web pages out of cache?
A23.3 Look for the IfModified-Since request modifier from the client, or a response code 304 Not Modified from the server, indicating the client loaded the page from cache.
Q23.4 What display filter should you AVOID if you want to view the TCP handshake and ACKs during a web browsing session?
A23.4 The http display filter will not display the TCP handshake or ACKs. Use tcp.port==80 to view the entire HTTP conversation.
Q23.5 What is the HTTP request method used to send data up to an HTTP server?
A23.5 HTTP clients use POST to send data up to an HTTP server (e.g., form submissions).
Q23.6 What is the syntax for capture and display filters for HTTP traffic on port 80?
A23.6 Capture filter: tcp port http. Display filter: http (app layer only) or tcp.port==80 (entire conversation).
Q23.7 How do you configure Wireshark to always recognize port 444 as an SSL/TLS port?
A23.7 Select Edit | Preferences | Protocols | HTTP and add port 444 in the SSL/TLS ports section.
Q23.8 What steps are required to decrypt HTTPS traffic with Wireshark?
A23.8 Obtain the server's RSA private key and copy it to your Wireshark system. Configure Edit | Preferences | Protocols | SSL → RSA Keys list with the server IP, port, protocol (http), and key path. Load the HTTPS trace file — Wireshark will decrypt the traffic.
Q23.9 Which side offers cipher suites and which side selects the cipher suite in HTTPS?
A23.9 The HTTPS client offers a list of acceptable cipher suites (in the Client Hello). The HTTPS server selects the cipher suite to use for the communication (in the Server Hello).
