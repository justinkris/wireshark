Questions

Q1

Open client_init_renego.pcap. Export SSL Session Keys using File | Export SSL Session Keys. What is the session key in this trace file?

Your Answer
Model Answer
The exported NSS Key Log file records entries in the format CLIENT_RANDOM <32-byte-client-random> <48-byte-master-secret>. In a client-initiated re-negotiation trace you will see two CLIENT_RANDOM entries — one for the original handshake and one for the re-negotiated session. The re-negotiation begins with a new ClientHello sent by the client on the existing TCP connection (no FIN/SYN first). Load the key file via Edit > Preferences > Protocols > TLS > Pre-Master-Secret log filename to decrypt application data in the trace.
Q2

Open http-500error.pcapng. How can you filter on all HTTP server errors?

Your Answer
Model Answer
HTTP 500 Internal Server Error responses are filtered using http.response.code >= 500, or more specifically http.response.code == 500. The 5xx class of errors indicates that the server encountered an error it couldn't recover from — in this trace likely a backend database or scripting engine failure. Contrast with 4xx (client errors, e.g. 404 Not Found) and 3xx (redirections, e.g. 302 Moved Temporarily), which require different filter ranges.
Q3

Open http-espn2007.pcapng. Select Statistics | HTTP | HTTP Packet Counter. How many redirections are in this trace file? How many client errors? How many GET requests were required?

Your Answer
Model Answer
The HTTP Packet Counter (Statistics > HTTP > HTTP Packet Counter) groups responses by class. The 2007 ESPN trace is notable for its high number of 3xx redirections — each one forces the client to issue a brand-new GET to a different URL, multiplying round trips before any content loads. Every redirect adds at least one RTT of latency: the client must receive the 302, parse the Location header, and initiate a fresh TCP connection. Reducing redirections became a major web-performance objective precisely because of traces like this one.
Q4

Open http-espn2011.pcapng. How many GET requests were required? Is this more efficient than in 2007?

Your Answer
Model Answer
The 2011 trace shows a reduced GET count and fewer redirections compared to 2007, indicating ESPN consolidated its CDN routing and removed intermediate redirect hops over those four years. Fewer GETs means fewer TCP handshakes, less DNS resolution, and lower latency to first byte — a direct user-experience improvement. Compare the two traces side-by-side in the HTTP Packet Counter to quantify the reduction in 3xx responses, which is the clearest signal of architectural cleanup.
Q5

Open http-espn2012.pcapng. How many GET requests were required in 2012? How many sites did we connect to? Were there any redirections?

Your Answer
Model Answer
By 2012 the GET count is higher again — not from redirections, but from heavier use of embedded third-party content (ad networks, analytics, social buttons). Each new domain requires a fresh DNS resolution and TCP handshake, which is why the number of connected sites is noticeably higher than in 2011. Use Statistics > HTTP > Requests to see a per-host breakdown. Redirections (3xx) may be present but the growth driver is domain proliferation, a characteristic of the ad-heavy web of that era.
Q6

Open http-facebook.pcapng. How many GET requests were required to load the main page? Why did the client have to send another DNS query late in the process? What was the last item to load?

Your Answer
Model Answer
Facebook's main page required a large number of GET requests because every embedded asset (scripts, CSS, images, Like buttons, tracking pixels) is fetched individually. A late DNS query mid-load is triggered when the browser encounters a resource from a domain it hasn't resolved yet — typically a third-party ad network or analytics beacon whose hostname wasn't in cache. The last item to load is almost always a tracking pixel or analytics call (often a 1×1 GIF or a POST to a beacon endpoint) that fires after the DOM is interactive, reporting page-load metrics back to the server.
Q7

Open http-fault-post.pcapng. How many times did we try to send information to the HTTP server? Should you troubleshoot the 11 second delay before packet 29? What host are we trying to POST to?

Your Answer
Model Answer
Multiple POST attempts indicate the TCP connection succeeded but the server never returned a valid response — the application layer retried after a timeout. The 11-second delay before packet 29 is a TCP retransmission timeout (RTO), not an application-level wait — verify using the tcp.analysis.retransmission filter to confirm packet 29 is a retransmit of an earlier segment. The Host header in the HTTP POST request reveals which server we're targeting; look for it in the HTTP dissection of any POST packet. POSTs cannot be pipelined like GETs, so each failed attempt must complete (or time out) before the next one starts.
Q8

Open https-justlaunchpage.pcapng. What is the 95 second delay followed by? What site did we connect to? How many cipher suites were offered? Which cipher suite was chosen? How long did the website load take?

Your Answer
Model Answer
An Encrypted Alert immediately following a 95-second gap is almost certainly a close_notify alert (value 0) — the TLS equivalent of a graceful connection shutdown. The close_notify tells the peer that no more data will be sent; the subsequent FIN packets confirm clean termination rather than an error. The connected site is visible in the TLS ClientHello's Server Name Indication (SNI) extension. The offered cipher suites are listed in the ClientHello; the server's chosen suite appears in the ServerHello. Total page-load time spans from the first SYN to the last HTTP response — use the frame timestamp delta.
Q9

Open https-ssl3session.pcapng. What problems occur during the HTTPS connection? How many cipher suites were offered? Which cipher suite was chosen?

Your Answer
Model Answer
SSL 3.0 was deprecated by RFC 7568 due to the POODLE vulnerability — a padding oracle attack enabling decryption of CBC-mode ciphertext without the server's private key. In this trace watch for Alert messages indicating a protocol version rejection, or a downgrade where the client offers TLS but the server falls back to SSL 3.0. The cipher suite chosen in an SSL 3.0 session is typically RC4 or a CBC-mode block cipher — both considered cryptographically broken today. Count the suites in the ClientHello's cipher_suites list to answer the offered-suites question.
Q10

Open http-winpcap.pcapng. Does this client have website elements in cache? What is the largest delay? What OS is the WinPcap server running? What is the size of new.gif? What does new.gif contain?

Your Answer
Model Answer
Yes — 304 Not Modified responses confirm that the client sent If-Modified-Since (or If-None-Match) conditional GETs, meaning it has cached copies of those resources and is validating them rather than re-downloading. The largest delay is typically the initial DNS resolution or the first full-content download; use Statistics > TCP Stream Graphs > Time-Sequence to identify it visually. The server OS appears in the HTTP Server response header (e.g. "Apache/2.x (Win32)"). new.gif's size is in the Content-Length header of its response; export it via File > Export Objects > HTTP to inspect its actual pixel content.
Q11

Open sec-nessus.pcapng. Apply a tcp.port==80 filter. What does this indicate about services on port 80?

Your Answer
Model Answer
Filtering on tcp.port==80 in a Nessus scan trace reveals rapid sequential SYN packets to port 80 across many destination IPs — the classic signature of a port scan's service-enumeration phase. Targets responding with SYN-ACK have port 80 open (HTTP running); RST responses indicate the port is closed; no response suggests a firewall is silently dropping the probe. The pattern — same port, many hosts, sub-millisecond spacing — is unmistakable in Wireshark and would trigger any IDS alert rule for TCP port scanning.
