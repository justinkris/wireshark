💭 THINK FIRST · TOP PERFORMANCE CAUSES

Most network performance complaints trace back to one of five root causes. The critical skill is identifying WHICH cause applies — the location of the delay in the packet capture is the diagnostic clue. A large delta after a SYN means latency; a large delta after an application request means server processing time.

  • A user says "the network is slow." You see SYN→SYN-ACK = 3ms, and HTTP GET→first response = 8 seconds. Where is the problem and who should you escalate to?
  • What is the single most important display filter to apply first when analyzing any TCP performance problem?
Q1 — WHERE IS THE PROBLEM AND WHO TO ESCALATE TO
The problem is the application server, not the network. The 3ms SYN→SYN-ACK delta shows excellent network RTT — the network path to the server is fast and healthy. The 8-second gap between the HTTP GET and the first response byte is the server's processing time — the server took 8 seconds to generate the response. This is an application-layer problem: escalate to the web server team or application developers, not the network team.
Q2 — MOST IMPORTANT FIRST FILTER
tcp.analysis.flags — this single filter surfaces ALL TCP problems instantly: retransmissions, duplicate ACKs, zero windows, out-of-order segments, and lost segments. It's the fastest first-pass filter for any TCP performance investigation. Start here before applying more specific filters.
Section 1

Top Causes of Performance Problems

Five performance problem categories account for the vast majority of network complaints. Each has a distinct packet signature in Wireshark:

  1. High network latency — large RTT between client and server, visible as a large delta between SYN and SYN-ACK.
  2. Packet loss — segments dropped in transit, causing retransmissions and TCP congestion control engagement.
  3. Slow server response — server takes too long to process requests (application or database latency), visible as a large delta between the last request byte and the first response byte.
  4. Client-side issues — slow application on client, insufficient resources, or a client-side processing bottleneck, often visible as slow ACKs or delayed application data.
  5. Network congestion — bandwidth saturation causing queuing delays, often co-occurring with retransmissions and window issues.
The diagnostic question: where does the large delta appear? After a SYN → network latency. After an application request → server processing time. After data packets with no response → retransmission/loss or receiver zero window. The location of the time gap determines the cause and the owner.
🧠
MENTAL NOTE
5 performance root causes: Network latency (RTT), Packet loss (retransmissions), Slow server (processing delay), Client issues (slow ack), Congestion (saturation). Diagnose by finding WHERE the large delta is. Always start with: tcp.analysis.flags. Delta after SYN = network. Delta after app request = server. Retransmissions = loss.

💭 THINK FIRST · HIGH LATENCY DIAGNOSIS

Network latency (RTT) and server processing time are two completely different problems that produce similar user experience: slowness. The key is measuring RTT independently of server processing time. The TCP handshake gives you pure network RTT — the time before the server even processes the application request.

  • How do you distinguish "the server is far away (high RTT)" from "the server is slow (high processing time)" using Wireshark?
  • A TCP connection has RTT=150ms and a 65,535-byte receive window with no Window Scaling. What is the maximum achievable throughput on this connection?
Q1 — HIGH RTT VS SLOW SERVER
Measure RTT from the TCP handshake: time from SYN (client) to SYN-ACK (server). This is pure network round-trip time — the server sends SYN-ACK immediately upon receiving SYN, before any application processing. If SYN→SYN-ACK=2ms but HTTP GET→response=4000ms, the network is fast and the server is slow. If SYN→SYN-ACK=400ms and GET→response=500ms, the network latency itself is the dominant factor. Compare these two deltas to separate the problems cleanly.
Q2 — BDP THROUGHPUT CALCULATION
Maximum throughput = Window Size / RTT = 65,535 bytes / 0.150 seconds ≈ 437,000 bytes/sec ≈ 3.5 Mbps. This is the bandwidth-delay product (BDP) limitation: the TCP window limits how much data can be in-flight, and with 150ms RTT you can only send 65,535 bytes before needing an acknowledgment. To saturate a 100Mbps link with 150ms RTT you'd need a window of 100,000,000 bps × 0.15s / 8 = 1.875 MB — far larger than 65,535 bytes. Window Scaling is required for high-bandwidth, high-latency paths.
Section 2

High Network Latency Diagnosis

Network latency measurement in Wireshark uses the TCP handshake as the ground truth for pure network round-trip time:

  1. TCP handshake RTT — time from SYN (sent) to SYN-ACK (received) = pure network round-trip time with no application processing involved.
  2. Time Reference method — set a Time Reference on the SYN packet (right-click → Set/Unset Time Reference), then switch to "Seconds Since Reference" column to measure every subsequent event from that baseline.
  3. RTT graph — Statistics → TCP Stream Graphs → Round-Trip Time plots RTT per segment over the full connection duration, revealing whether latency is constant or spikes.

High latency impact on throughput: every TCP acknowledgment requires one RTT. BDP = bandwidth × RTT determines the window size needed to fully utilize a link. If the receive window is smaller than the BDP, the sender must stop and wait for ACKs — the link sits idle during each wait.

Don't confuse server processing time with network latency If SYN→SYN-ACK RTT is 5ms but the application response takes 3 seconds, the network is fine — the server is the bottleneck. Measure RTT FIRST before blaming the network. A large GET→response delta with a small SYN→SYN-ACK delta is always a server problem.
🧠
MENTAL NOTE
Measure RTT: SYN to SYN-ACK delta. Time reference on SYN → "Seconds Since Reference." RTT graph: Statistics → TCP Stream Graphs → Round-Trip Time. BDP = bandwidth × RTT = window needed to fill the pipe. High RTT alone + low retransmissions = distant server. High RTT + retransmissions = congested path. Server response time = delta between app request and first response byte — separate from RTT.

💭 THINK FIRST · PACKET LOSS ANALYSIS

Packet loss has dramatically different performance impacts depending on whether recovery uses Fast Retransmit (milliseconds, triggered by 3 dup ACKs) or RTO timeout retransmit (1+ seconds, triggers congestion window reset). The time gap between the original packet and its retransmission tells you which occurred — and how bad the performance impact is.

  • You see both tcp.analysis.retransmission and tcp.analysis.fast_retransmission in a capture. Which represents the more severe performance impact and why?
  • How do you determine if packet loss is occurring in one direction only?
Q1 — RETRANSMISSION VS FAST RETRANSMISSION SEVERITY
Regular tcp.analysis.retransmission (timeout-based, RTO retransmit) is more severe. It occurs after the retransmission timer expires — typically 1 second minimum, doubling with each failure (exponential backoff). During this wait time, the sender sends nothing. TCP also enters slow-start after an RTO retransmit, dramatically reducing the congestion window. tcp.analysis.fast_retransmission (triggered by 3 dup ACKs) occurs within milliseconds — the sender doesn't wait for a timeout. Fast Retransmit uses TCP Fast Recovery (not slow-start), maintaining much higher throughput. The tell: look at the delta between the original packet and the retransmission — milliseconds = fast retransmit (relatively minor), 1+ seconds = RTO timeout (major performance hit).
Q2 — IDENTIFYING ONE-DIRECTIONAL LOSS
Apply a display filter for one direction at a time. For client→server: ip.src == [client IP] and tcp.analysis.retransmission. For server→client: ip.src == [server IP] and tcp.analysis.retransmission. If only one direction shows retransmissions, the loss is occurring on that path segment. For the most definitive answer, compare simultaneous captures from both endpoints — if only one side sees retransmissions, the loss is occurring between the two capture points.
Section 3

Packet Loss and Retransmission Analysis

Packet loss diagnosis workflow:

  1. Filter tcp.analysis.flags — surfaces all TCP problems instantly as a first pass.
  2. Count retransmissions — apply tcp.analysis.retransmission and check what percentage of total TCP segments are retransmissions. Above 1% is significant.
  3. Distinguish types — fast retransmit (milliseconds delta, tcp.analysis.fast_retransmission, recovery via 3 dup ACKs) vs timeout retransmit (1+ second delta, RTO-based, devastating to throughput).
  4. Identify direction — add source IP to the filter to isolate which path is dropping packets.
  5. Correlate with IO Graphs — overlay tcp.analysis.retransmission as a filter on IO Graph to identify when in time the loss clusters.
FilterWhat It Shows
tcp.analysis.flagsALL TCP analysis events
tcp.analysis.retransmissionAll retransmissions (both types)
tcp.analysis.fast_retransmissionFast retransmit (3 dup ACKs trigger)
tcp.analysis.duplicate_ackDuplicate acknowledgments
tcp.analysis.lost_segmentApparent missing segments
tcp.analysis.zero_windowZero window announcements

MENTAL NOTE
Packet loss: tcp.analysis.flags first. Retransmission % >1% = significant. Fast retransmit = ms delta, 3 dup ACKs trigger, less severe (Fast Recovery). RTO timeout = 1+ sec delta, exponential backoff, severe (slow-start resets cwnd). Direction: add ip.src to retransmit filter. IO Graph overlay: retransmissions vs total traffic = find when loss clusters.

💭 THINK FIRST · SLOW SERVER DETECTION

A slow server leaves a unique signature: small network RTT (SYN→SYN-ACK) combined with a large delta between the application request and the first response byte. This pattern definitively separates network problems from application problems and tells you exactly where to escalate.

  • You capture the same HTTP transaction from both the client and the server. The client sees a 2-second response time; the server also sees a 2-second delay between receiving the GET and sending the response. What does this tell you?
  • Multiple clients simultaneously experience 5-second HTTP response times to the same server, but RTT is only 5ms. What is the most likely cause?
Q1 — DELAY MEASURED ON SERVER SIDE
The 2-second delay exists on the SERVER SIDE — the server received the GET and took 2 seconds to process it before sending a response. This is definitively an application or database problem: a slow query, a resource bottleneck on the server (CPU, memory, disk I/O), or a dependency on an upstream service that's slow. The network is ruled out: the delay was measured from the moment the GET arrived at the server, so network transmission time is already excluded. Escalate to the server/application team immediately.
Q2 — MULTIPLE CLIENTS SAME DELAY
Multiple clients experiencing the same delay simultaneously, with healthy RTT, indicates the server is overloaded — not a per-connection or network issue. A single slow connection could have many causes, but when ALL clients see the same degradation at the same time, the bottleneck is shared infrastructure. Most likely: server CPU/memory saturation, database query slowdowns, connection pool exhaustion, or the application waiting on a slow upstream service. Use Statistics → Service Response Time to quantify average response time across all captured sessions.
Section 4

Slow Server and Application Detection

Slow server detection workflow:

  1. Find the application request packet (HTTP GET, DNS query, SQL). Set a Time Reference on it (right-click → Set/Unset Time Reference).
  2. Find the first server response packet. The delta from the reference = server processing time.
  3. Compare to network RTT (SYN→SYN-ACK). Small RTT + large response delta = server problem.
  4. Multiple simultaneous connections with same delay = server overloaded, not a per-connection issue.
  5. Statistics → Service Response Time (for HTTP, DNS, etc.) provides protocol-level response time statistics across all sessions in the capture.
The key formula for isolating server time Server Response Time = (time of first response byte) − (time of last request byte). If this is large but SYN→SYN-ACK RTT is small, the problem is the application server. Escalate to the app team, not the network team.
🧠
MENTAL NOTE
Slow server = large delta between last request byte and first response byte, with small SYN→SYN-ACK RTT. Multiple clients same delay = server overloaded. Measure: time reference on GET → find first response byte delta. Service response time: Analyze → Statistics → Service Response Time. tcp.analysis.flags shows loss; delta times show latency; combine both for full picture.
