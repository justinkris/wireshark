Find the Top Causes of Performance Problems

Diagnosing latency, packet loss, misconfigurations, and application faults

"The first rule when analyzing network performance is: watch the Time column."
MY QUESTIONS▾
MY NOTES
💭THINK FIRST · HIGH LATENCY▾

Identifying delays in a trace file starts with the Time column. Sort by Seconds since Previous Displayed Packet to spot large gaps — but always filter on a single conversation first.

  • Why should you filter on a single conversation before sorting the Time column?
  • What is the difference between frame.time_delta and frame.time_delta_displayed, and why is the latter unreliable for filtering?
Q1: If your trace contains multiple conversations, sorting the Time column without filtering mixes deltas from different conversations — you could see a large gap between the last packet of one connection and the first packet of another, which is not a true per-connection delay.
Q2: frame.time_delta compares the current packet to the previous captured frame. frame.time_delta_displayed compares to the previous displayed frame — but if you then filter on frame.time_delta_displayed > 1, you are changing which frames are displayed and re-evaluating the time delta, creating circular logic. Use frame.time_delta after filtering on a conversation instead.

Identify High Latency Times

High latency times can be caused by distance (as in the case of satellite communications), queuing delays along a path, processing delays, etc. Problems may also arise in the resolution process — DNS problems may prevent a host from obtaining the IP address for a target host. Incorrect subnet mask values may cause a host to perform discovery for a local host that is, in fact, remote.

Filter on TCP Conversation Times

This is a great option for detecting latency in TCP conversations. Select Edit | Preferences | Protocols | TCP and enable Calculate Conversation Timestamps. Now you can apply filters based on the tcp.time_delta field value:

tcp.time_delta > 1
tcp.time_delta > 1 && tcp.flags.fin==0 && tcp.flags.reset==0

The second filter excludes connection teardown delays — it is common for an application to take its time shutting down a connection long after you have moved on.

Point to Slow Processing Times

When a host does not have sufficient processing power or memory or an application does not respond in a timely manner, gaps in the response times may be seen between requests and replies. These gaps may be accompanied by other evidence such as a TCP window size of zero or a TCP window size smaller than the TCP MSS value. Application responses may also indicate an overloaded condition.

💭THINK FIRST · PACKET LOSS▾

Packet loss causes TCP retransmissions and application timeouts. To find WHERE packet loss is occurring, move your analyzer along the path — when you stop seeing both the original packet and the retransmission, you have passed the point of loss.

  • Why does packet loss in TCP without Selective ACK (SACK) cause MORE retransmissions than actually needed?
  • How do you determine which direction on a path to move your Wireshark capture point when investigating packet loss?
Q1: Without SACK, a TCP sender cannot know which specific out-of-order packets were received. When a timeout expires, it must retransmit from the last unacknowledged sequence number forward — potentially re-sending many packets that were already received successfully.
Q2: If you see both the original packet AND the retransmission at your current capture point, the loss has not occurred yet — the dropping device is downstream (closer to the receiver). Move toward the receiver. When you stop seeing the original packet, you have found the loss point.

Find the Location of Packet Loss

Packet loss can affect performance when the receiver must request retransmissions and wait for those retransmissions before passing data to the application. For example, when packet loss occurs on a TCP connection that does not support Selective ACKs, numerous packets may be retransmitted as the receiver cannot acknowledge receipt of data after the lost packet.

In a UDP-based application, the retransmission timeout value is dictated by the application itself. An application that is slow to request retransmission will affect the overall performance of the application.

📷Figure 345 — open trace file to view
Figure 345. The DHCP client is slow to retransmit the DHCP Discover packet — almost 6 seconds before the first retry.

If you are capturing traffic in the infrastructure and you see the original packet and the retransmission, you are upstream from (at a point before) the point of packet loss. "Upstream" means you are closer to the sender of the data. To find out where packet loss is occurring, move along the path until you no longer see the original packet and retransmissions to find out exactly where the packets are being dropped. Packet loss typically occurs at interconnecting devices such as switches and routers.

📷Figure 346 — open trace file to view
Figure 346. A single point of massive packet loss kills the network IO rate — TCP does not handle large congestion window losses well.

MENTAL NOTE
Finding packet loss: If you see original + retransmission, you are upstream from the drop — move downstream (toward receiver). When you stop seeing original packet, you have found the loss point. For TCP without SACK: one lost packet triggers retransmission of all subsequent packets. For UDP: retransmission timeout is application-defined. Packet loss events typically occur at switches and routers.

💭THINK FIRST · MISCONFIGURATIONS▾

Various misconfigurations affect network performance: QoS that causes queuing, suboptimal MTU sizes forcing small packets, and routing redirections that add hops.

  • How can you detect a suboptimal TCP segment size in a file transfer, and what might cause it?
  • What does an IO Graph with a "heartbeat" pattern indicate about how traffic is being handled along the path?
Q1: Create a custom column for tcp.len or graph AVG(*)tcp.len in an Advanced IO Graph. If the segment size is consistently below the negotiated MSS (e.g., 512 bytes instead of 1460), a router is likely fragmenting packets due to a lower MTU on an intermediate link, or PMTUD has failed.
Q2: A heartbeat IO Graph pattern indicates that traffic is being held in a queue (prioritized below other traffic) and released in bursts. Each burst of data followed by silence represents traffic being queued and then emptied as higher-priority traffic clears the queue.

Watch Signs of Misconfigurations

Various misconfigurations can affect network performance. For example, video multicast traffic that is prioritized below file transfer, voice and email traffic may be held in queues along a path. This traffic may cause a "heartbeat" effect on the IO Graph as shown in Figure 347.

📷Figure 347 — open trace file to view

Analyze Traffic Redirections

The most common redirections seen on a network are based on default paths that may not be optimal or available. This could be a default gateway that does not offer the best route to the target network (responding with an ICMP redirection packet). Another common redirection is seen in web browsing sessions when a browsing client connects to a website only to be redirected to other sites to build the pages.

📷Figure 348 — open trace file to view
Figure 348. The web browsing client is redirected to another site — this generates an additional DNS query and TCP handshake.

Watch for Small Payload Sizes

If a 500 MB file is exchanged in 512 byte segments instead of 1,460 byte segments, the data exchange will require 665 more data packets to complete the transfer. An example would be when two distant TCP hosts complete the handshake process indicating the MSS value of 1,460 bytes, but part of the network path only supports an MTU size of 512. Traditional path discovery using ICMP Type 3/Code 4 messages (Fragmentation Needed, but Don't Fragment Bit Set) is covered in RFC 1191, Path MTU Discovery.

Consider creating a column for tcp.len to display the payload size of the data packets. In addition, consider creating an IO Graph to depict the payload size of traffic. Use the AVG(*)tcp.len value in an Advanced IO Graph.

📷Figure 349 — open trace file to view
Figure 349. Graphing tcp.len shows a suboptimal segment size used for the data transfer.

Look for Congestion

Congestion along a network path may cause packet loss, queuing, or throttling back of possible throughput maximums. A window zero condition is one example of possible congestion at a receiving host. When a host hits a window size of zero, no data can be sent — the IO drops to zero bytes/second. Window Scaling enables a host to exponentially increase the window size and is defined as a TCP option during the handshake process (RFC 1323).

🧠
MENTAL NOTE
Misconfigurations: Heartbeat IO Graph = QoS queuing. HTTP redirects add extra DNS queries and TCP handshakes. Small segment sizes (below MSS) = likely MTU mismatch along path — check ICMP Type 3/Code 4. TCP zero window = receiver has no buffer space. Window Scaling (RFC 1323) allows exponential window size increases. Use tcp.len column or AVG(*)tcp.len IO Graph to detect small payloads.

💭THINK FIRST · APPLICATION FAULTS▾

Application faults manifest as error response codes (HTTP 404), slow server responses, or stopped data reads. Always measure the actual delay incurred before concluding that errors are causing user-visible problems.

  • How would you determine whether a server is the bottleneck versus a network path issue?
  • Why should you not automatically assume that 100 error responses during a file location process are causing a noticeable delay?
Q1: First compare the TCP handshake roundtrip time (path latency). Then look at the time between the GET/ACK and the server response. If path latency is low but the server takes many seconds to respond to a request, the server is the bottleneck. If path latency is high even during the handshake, the network path is the issue.
Q2: You must measure the total delay consumed by the error responses. If 100 errors occur but each takes only 1 millisecond, the total impact is 100 milliseconds — unnoticeable to a user. Do not get fixated on traffic that seems to indicate a fault but does not affect performance.

Identify Application Faults

Application faults may manifest themselves through dissected response codes or by simply not allowing efficient data flow. One of the more commonly experienced faults is when an HTTP 404 Not Found response is received by a web browsing client. No data is transferred from the target page after this condition and no redirection takes place.

Note Any Name Resolution Faults

Name resolution faults, whether DNS, LDAP, NetBIOS Name Service or another name resolution process, can be significantly detrimental to network performance. These types of errors are typically quite evident in the trace file.

Although some processes may appear to cause problems, consider the amount of delay time incurred by each process. You may find that a process only takes 100 milliseconds — hardly noticeable to the user. Do not get fixated on traffic that seems to indicate a fault but does not affect performance.

Case Studies

Case Study 1
One-Way Problems
Submitted by: P.C., Sr. Network Technician

P.C. (Sr. Network Technician) investigated a bizarre WAN problem: files could be transferred from branch office #1 to branch office #2, but not in reverse. The transfer would stall and generate errors.

Wireshark showed packet loss only when transferring in one direction. By moving Wireshark closer to the WAN router, the team found the specific switch that was dropping the packets — they captured traffic both before and after going through the switch.

The trace files were sent to the switch vendor. They accepted the evidence immediately — the packet captures clearly showed exactly where the problem was. The vendor sent a replacement card for the switch, which fixed the problem.

Case Study 2
The Perfect Storm of Network Problems
Submitted by: P. Erskine, Network Analyst

P. Erskine (Network Analyst) investigated slow file transfers in one direction between Server A and Server B. The same file transferred in opposite directions showed vastly different times: 8 seconds from A to B, 157 seconds from B to A.

With Wireshark installed directly on both servers, captures from Server A showed normal traffic. Captures from Server B showed many Duplicate ACKs coming in from Server A — Server B was resending data as requested. Investigation revealed an "intelligent security device" along the path that was stripping the Selective ACK (SACK) option from TCP handshakes and periodically generating Duplicate ACKs on behalf of Server A.

Without SACK, Server B had to retransmit more packets than necessary whenever it thought one was lost. The security device was creating phantom packet loss. After capturing on both sides of the "intelligent security device," they could watch it strip SACK options and inject Duplicate ACKs. Wireshark includes an Expert Warning: "4 NOP in a row — a router may have removed some options."

TL;DR — Chapter 29 Summary

Poor network performance is typically due to delays, packet loss, misconfigurations, faulty applications, poorly-designed applications, non-optimized hosts or applications, redirections, network or host congestion or name resolution faults.

The first problem to watch for is delay. Consider setting Wireshark's Time column to "Seconds since Previous Displayed Packets." Sort the Time column to spot large gaps in time. Delays can occur due to high path latency, QoS settings, client congestion or server congestion. Packet loss also affects network performance — when TCP-based traffic experiences packet loss, TCP automatically attempts to recover. UDP-based traffic relies on the applications to define the timeout values and retry counts.

Applications that are either misconfigured or poorly designed (transferring files using minimal packet sizes) can also affect performance. Name resolution problems (or any other resolution problems) can completely disrupt network communications.

Review Questions

Q29.1. How can you quickly spot large gaps in time between packets of a conversation?
A: Set the Time column to "Seconds since Previous Displayed Packet", filter on a single conversation and then sort the Time column so the largest values are at the top.
Q29.2. What are the steps involved in finding the source of packet loss during a TCP-based file transfer process?
A: Move the analyzer along the path to determine the point when you see the original packet and the retransmission — packet loss has not occurred yet. The device dropping packets is downstream (closer to the receiver) from your current location.
Q29.3. Which graph can you create to display small packet sizes during a file transfer process?
A: Graph the AVG(*)tcp.len value in an Advanced IO Graph.
Q29.4. What condition occurs when a TCP receiver has no buffer space available?
A: When a TCP receiver runs out of buffer space, it advertises a window zero condition.
Q29.5. When analyzing a trace file of a file transfer process you notice over 100 error responses during the file location process. Can you assume this will always cause a delay noticeable by the client?
A: No. You must analyze the total amount of delay incurred by the errors before stating that they are causing a noticeable effect.
