    Chapter 29: Performance Problems

    Chapter 29 focuses on diagnosing network performance problems — slow applications, high latency, packet loss, and bandwidth bottlenecks. You'll apply a systematic methodology using Time, Conversations, I/O Graphs, and TCP analysis tools to locate and characterize performance issues.

    Guided Analysis — Performance Methodology
    Concept — Q1
    Describe the 4-step performance problem methodology: (1) identify the symptom, (2) establish timing, (3) isolate direction, (4) check the path. What Wireshark tools support each step?
    (1) Symptom: Statistics > Summary for overall rates; Expert Info for TCP errors. (2) Timing: I/O Graph to see when the slowdown occurred; Time column to measure delays between packets. (3) Direction: Conversations window sorted by bytes to find which endpoint is saturating the link. (4) Path: TTL analysis and TCP RTT to estimate latency per hop; look for large delta times between request and response packets.
    Concept — Q2
    What is the TCP 'time to first byte' (TTFB), and how do you measure it in Wireshark? What does a high TTFB indicate?
    TTFB is the time from when a client sends an HTTP GET request to when the server begins sending the response. In Wireshark, select the HTTP GET packet as a reference frame (Ctrl+click), then look at the relative time of the first 200 OK or data packet from the server. High TTFB (> 200ms) usually indicates server-side processing delay, not network latency — the network round-trip is typically 10-50ms.
    Concept — Q3
    A user reports 'slow downloads.' You open a trace and see many TCP retransmissions. How do you determine whether the problem is on the client side or the server side of the network?
    Identify where the capture was taken relative to client and server. Then examine which side sends the retransmissions: if the server is retransmitting (retrans from server IP), the problem is between the server and the capture point. If the client is retransmitting (retrans from client IP), the problem is between the client and the capture point. Apply tcp.analysis.retransmission && ip.src == [server-ip] vs ip.src == [client-ip] to isolate each direction.
    Optional Traces
    http-download-bad.pcapng
    Apply tcp.analysis.flags to see all TCP errors. Then use I/O Graph with a second line for tcp.analysis.retransmission. Does the retransmission rate correlate with throughput drops?
    Any slow-response trace
    Measure server response time: find an HTTP GET, then look at the timestamp of the first 200 OK byte. Calculate TTFB. Compare to the TCP RTT (measured from SYN to SYN-ACK timing). Is the TTFB much larger than the RTT?
    Any trace — bandwidth calculation
    Go to Statistics > Summary. Note the average Mbps. Then go to Statistics > Conversations and find the top conversation — what % of total bandwidth does it consume? Is one conversation monopolizing the link?
    Review Questions
    Review Q29.1
    What is the difference between network-caused latency and server-caused latency, and how do you distinguish them in a trace?
    Network latency appears in the TCP handshake timing — the time between SYN and SYN-ACK reflects the round-trip path delay. Server latency appears after the handshake: the time between a client's request (HTTP GET) and the server's first response byte. If TCP RTT (SYN→SYN-ACK) is 5ms but TTFB is 800ms, the server is the bottleneck, not the network.
    Review Q29.2
    What does a 'TCP Zero Window' indicate, and how would you filter for it?
    Zero Window means the receiving side's buffer is full — it cannot accept more data. The sender must pause until the receiver opens the window. This typically indicates the application is not consuming data fast enough (slow application on the receiving end), not a network problem. Filter: tcp.analysis.zero_window. Often followed by 'TCP Window Update' when the receiver is ready again.
    Review Q29.3
    How do you use Wireshark's Expert Info to quickly assess the severity of problems in a trace?
    Go to Analyze > Expert Information (or click the Expert Info button on the status bar). Errors (red) are the most severe — TCP resets, malformed packets. Warnings (yellow) are significant — retransmissions, zero windows, duplicate ACKs. Notes (cyan) are informational — window updates, keepalives. A trace with 500 warnings but 0 errors suggests TCP congestion rather than protocol errors.
