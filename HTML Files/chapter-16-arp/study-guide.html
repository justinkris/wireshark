💭 THINK FIRST · THE PURPOSE OF ARP

IP addresses are logical identifiers — routers use them for routing decisions. But on a local Ethernet segment, frames are delivered using MAC addresses. ARP is the glue that maps one to the other. Without it, IP communication on a local network is impossible.

  • Why does a host need to know a MAC address to communicate, even though it already knows the destination's IP address?
  • ARP requests are broadcasts, but ARP replies are unicasts. Why the asymmetry?
Q1 — WHY IS MAC ADDRESS NEEDED?
Ethernet switches operate at Layer 2 and forward frames based on MAC addresses, not IP addresses. When a host wants to send data to another host on the same LAN, it must build an Ethernet frame with a destination MAC address in the header — the NIC hardware and the switch use this MAC to get the frame to the right physical port. IP addresses exist in the Layer 3 header inside the frame, and while routers use IPs for forwarding decisions, the actual delivery on each LAN segment is always done using MAC addresses in the outer Ethernet header.
Q2 — WHY BROADCAST REQUEST BUT UNICAST REPLY?
The requesting host sends a broadcast (ff:ff:ff:ff:ff:ff) because it doesn't yet know the MAC of the target — that's the whole point of the ARP request. Every device on the segment receives the broadcast. Only the device whose IP matches the request sends a reply, and since the requester's MAC address is included in the ARP request packet, the responder already knows exactly where to send the unicast reply. Broadcasting the reply would be wasteful and would generate unnecessary traffic on all other hosts.
Section 1

The Purpose of ARP

ARP (Address Resolution Protocol) resolves a known IP address into a MAC address on a local network segment. It operates at the boundary between Layer 2 (Ethernet) and Layer 3 (IP). ARP is defined in RFC 826.

ARP at a glance ARP Request: broadcast — "Who has IP X? Tell IP Y."
ARP Reply: unicast — "IP X is at MAC aa:bb:cc:dd:ee:ff."
ARP operates only on the local subnet — it cannot cross a router boundary.

The ARP Cache

Both Windows and Linux maintain an ARP cache — a table mapping IP addresses to MAC addresses. Successful ARP replies are stored in this cache for a period (typically 2 minutes on Windows, variable on Linux). Subsequent communications to the same IP skip the ARP exchange and use the cached MAC directly. You can view the cache with arp -a on both Windows and Linux.

🧠
MENTAL NOTE
ARP = IP → MAC resolution. Request = broadcast (ff:ff:ff:ff:ff:ff). Reply = unicast. Local subnet only — does not cross routers. Cache stores results (~2 min Windows). EtherType = 0x0806 for ARP frames. Check cache with arp -a.

💭 THINK FIRST · NORMAL ARP OPERATIONS

A normal ARP exchange is fast — typically two packets. Understanding the exact field values in an ARP request and reply lets you spot immediately when something isn't quite right.

  • In an ARP request, the target MAC address field is set to all zeros (00:00:00:00:00:00). Why? What would an ARP reply's target MAC field contain?
  • You capture a trace and see hundreds of ARP requests from the same source IP in less than a second. What two very different scenarios could explain this?
Q1 — TARGET MAC ALL ZEROS
In the ARP request, the target MAC is all zeros because the sender doesn't know it yet — that's why it's sending the request in the first place. The sender knows the target IP but not the MAC. In the ARP reply, the target MAC field contains the MAC address of the original requester — the device answering the ARP fills in the requester's MAC (which it learned from the request's sender hardware address field) so the frame can be unicast back correctly.
Q2 — HUNDREDS OF ARP REQUESTS IN SECONDS
Two explanations: (1) Network scanning — a host is running an ARP scan (like arp-scan or nmap -PR) to discover all live hosts on the subnet. This is a normal administrative or reconnaissance activity, but also the first phase of an ARP poisoning attack. (2) ARP broadcast storm — a misconfigured device or a network loop is causing ARP requests to be generated and rebroadcast rapidly, consuming bandwidth. The distinction is context: a scan sends sequential requests to different target IPs; a storm usually shows the same request being repeated rapidly to the same target or an unusually high packet rate from a single source.

💭 THINK FIRST · GRATUITOUS ARP

Gratuitous ARP is an ARP request where a host asks "Who has my own IP address?" — and that makes it very useful, but also very exploitable. It's used for both legitimate network operations and ARP cache poisoning attacks.

  • What are two legitimate reasons a host would send a Gratuitous ARP, and how can you tell them apart in a capture?
  • How does an attacker exploit Gratuitous ARP to perform a man-in-the-middle attack?
Q1 — LEGITIMATE USES OF GRATUITOUS ARP
Two legitimate uses: (1) Duplicate IP detection — when a host joins the network or gets a new IP, it sends a Gratuitous ARP for its own address. If another device replies (someone else has this IP), the host detects the conflict and can refuse the address or alert the user. DHCP clients do this after receiving a lease. (2) Cache refresh after NIC change — if a server's NIC is replaced and gets a new MAC address, the server sends a Gratuitous ARP to force all other hosts on the subnet to update their ARP cache entries with the new MAC. High-availability clusters do this when a failover occurs, forcing clients to send traffic to the new active node's MAC. In a capture, post-DHCP GARP looks isolated; failover GARP is typically preceded by a link-down/up event.
Q2 — MAN-IN-THE-MIDDLE VIA GRATUITOUS ARP
An attacker sends unsolicited Gratuitous ARP replies claiming "192.168.1.1 (the gateway) is at MY MAC address." Because ARP has no authentication, hosts accept this and update their ARP cache, now mapping the gateway's IP to the attacker's MAC. All traffic destined for the gateway is now sent to the attacker instead. The attacker forwards it to the real gateway (to avoid detection), reads or modifies it, and returns the response — a classic man-in-the-middle position. In Wireshark, this appears as unsolicited ARP replies arriving with a new MAC for an already-known IP, often flagged as "duplicate use of IP" in the Expert Information.
Section 3

Gratuitous ARP

A Gratuitous ARP is an ARP request where the sender's IP and the target IP are the same — the host is asking "who has my own IP?" No reply is expected from healthy networks. It serves several legitimate purposes but is also abused for ARP cache poisoning.

How to identify in Wireshark Wireshark labels these automatically. The Info column shows: Gratuitous ARP for 192.168.1.50 (Request). The sender IP and target IP fields both contain the same address.

Legitimate Uses

  • Duplicate IP Detection: Host sends GARP on startup; if someone replies, there's an IP conflict. Windows displays an error and DHCP clients reject the lease.
  • Cache Update After MAC Change: Replacing a NIC or a high-availability failover sends GARP to force all neighbors to update their ARP caches with the new MAC.

ARP Cache Poisoning (Attack Use)

An attacker broadcasts unsolicited Gratuitous ARP replies, falsely claiming that a critical IP (e.g., the default gateway) maps to their MAC address. Hosts update their caches without verification, redirecting traffic to the attacker. This is ARP poisoning / ARP spoofing.

Security indicator Wireshark's Expert Information flags "Duplicate IP address detected" when two different MACs claim the same IP. This is a critical indicator of ARP poisoning or a misconfiguration. Filter: arp.duplicate-address-detected
🧠
MENTAL NOTE
Gratuitous ARP = sender IP == target IP. No reply expected. Legitimate uses: duplicate IP detection (startup) and MAC/NIC change cache refresh. Malicious use: ARP poisoning — unsolicited replies with attacker's MAC for victim's IP. Wireshark flags "duplicate IP" in Expert Info. MitM attack relies on ARP having no authentication.
Analogy
Gratuitous ARP is like a new employee on their first day walking into the office and announcing "Hi everyone, I'm Alex — just wanted to make sure no one else is using my desk!" Legitimate. But an attacker doing the same thing is like a con artist walking into the mailroom and loudly telling everyone "Oh by the way, the CEO moved offices — his mail comes to me now." No one checks the claim. All the CEO's mail gets delivered to the attacker.

💭 THINK FIRST · ARP PROBLEMS

Most ARP problems on real networks stem from two root causes: duplicate IP addresses (two hosts with the same IP) and incorrect subnet configuration (a host ARPs for addresses it should reach via the gateway). Both produce characteristic patterns in a capture.

  • How does a duplicate IP address manifest in a packet capture, and what specific packet sequence would you expect to see?
  • A host sends an ARP request for 10.0.2.5 but it's on the 10.0.1.0/24 network. What misconfiguration does this reveal?
Q1 — DUPLICATE IP IN A CAPTURE
A duplicate IP appears when two hosts respond to the same ARP request — you see two ARP replies with the same IP but different MAC addresses. In practice, you often see: (1) a Gratuitous ARP from a newly connected host getting no reply (normal), then (2) a second host sends an ARP reply for the same IP when other hosts query it — causing the ARP cache of querying devices to flip-flop between two MACs as each host periodically refreshes its cache. Wireshark's Expert Information flags this as "Duplicate IP address detected" and you can filter with arp.duplicate-address-detected. Symptoms at the user level: intermittent connectivity, one of the two hosts can't communicate reliably.
Q2 — ARP FOR AN ADDRESS ON A DIFFERENT SUBNET
The host has an incorrect subnet mask configured. The host calculates that 10.0.2.5 is on its local subnet (because of the wrong mask, e.g., /8 instead of /24), so instead of routing the traffic to the default gateway, it tries to ARP directly for 10.0.2.5. The ARP request goes unanswered (10.0.2.5 is on a different physical segment), the connection fails, and the user sees a timeout. The correct configuration would use a /24 mask, which would make the host recognize 10.0.2.5 as off-subnet and send traffic to the default gateway instead. This is one of the most common causes of "can't reach this specific server" problems.
Section 4

ARP Problems

Duplicate IP Addresses

When two hosts share the same IP address, ARP responses from both will appear in captures. The ARP cache of other hosts becomes unstable — flipping between the two MACs as each host re-ARPs. The result is intermittent communication failure for one or both conflicting hosts.

What you see in Wireshark Two ARP replies for the same IP with different source MAC addresses. Expert Info: "Duplicate IP address detected for X.X.X.X — use filters below."

Incorrect Subnet Mask

A host with an incorrectly broad subnet mask (e.g., /8 instead of /24) will believe remote hosts are local and attempt to ARP for them instead of routing to the gateway. The ARP goes unanswered and the connection fails silently.

ARP Broadcast Storms

In networks with switching loops (or misconfigured spanning tree), ARP broadcasts can multiply and flood the network. This consumes CPU on every host receiving the broadcasts and can saturate link bandwidth. A very high rate of ARP requests visible in a capture is an early indicator.

🧠
MENTAL NOTE
Duplicate IP = two ARP replies with same IP but different MACs → intermittent connectivity. Incorrect subnet mask = host ARPs for remote IPs instead of routing to gateway → silent connection failure. ARP storm = high rate of ARP broadcasts → network loop or misconfiguration. All flagged in Expert Information.

💭 THINK FIRST · FILTERING ARP IN WIRESHARK

ARP filters let you quickly isolate requests, replies, Gratuitous ARP, and specific IP or MAC addresses. Knowing these filters turns a cluttered capture into a focused ARP analysis in seconds.

  • What is the display filter to show only ARP packets where a specific IP address (e.g., 192.168.1.100) is the sender?
  • How would you use a capture filter to record only ARP traffic — and why would you want to limit an ARP capture?
Q1 — FILTER FOR SPECIFIC SENDER IP
Use arp.src.proto_ipv4 == 192.168.1.100 to show only ARP packets where 192.168.1.100 is the sender's protocol (IP) address. This will show both ARP requests and replies sent by that host. To see all ARP traffic involving that IP (as sender or target), combine with: arp.src.proto_ipv4 == 192.168.1.100 || arp.dst.proto_ipv4 == 192.168.1.100.
Q2 — CAPTURE FILTER FOR ARP ONLY
The capture filter is simply arp — BPF recognizes "arp" as a valid protocol keyword. You would limit to ARP-only capture when diagnosing specific ARP issues (duplicate IPs, poisoning) on a busy network where other traffic would fill the capture buffer. On a high-traffic LAN, a 5-second capture of all traffic might contain millions of packets, but filtering to ARP alone makes it manageable and focused. The trade-off is you lose the ability to see the surrounding context (e.g., the TCP connections that follow the ARP exchanges).
