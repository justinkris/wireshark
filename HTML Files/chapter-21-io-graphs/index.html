Questions

Q1

Open http-download-bad.pcapng. Create an IO Graph to depict packet loss, Duplicate ACKs and retransmissions. Create an Advanced IO Graph to compare TCP data transferred to tcp.analysis.flags. How can you make the relationship between these two elements clearer?

Your Answer
Model Answer
IO Graphs count the entire size of each packet including all headers (Ethernet, IP, TCP/UDP) plus the payload. This is different from a throughput measurement that might only count application-layer payload bytes. The total packet count including overhead is what appears in the Y axis when you select Bytes/Tick.
Q2

Open http-download-good.pcapng. Create the same Advanced IO Graph. What does the graph suggest about the relationship between tcp.analysis.flags and data throughput?

Your Answer
Model Answer
An empty or nearly empty IO Graph usually means you selected a packet traveling in the wrong direction for a unidirectional graph (like the Round Trip Time or TCP Time-Sequence graphs). These graphs only plot traffic flowing in one direction. Select a packet in the opposite direction and regenerate the graph.
Q3

Open http-downloadvideo.pcapng. How do you create an Advanced IO Graph showing the average window size advertised by 24.4.7.217 throughout the trace file?

Your Answer
Model Answer
Apply a conversation filter to one of the additional graph lines (Graph 2 through Graph 5) while keeping Graph 1 as the unfiltered baseline. The difference between the overall traffic line and the conversation-filtered line visually shows how much of total traffic belongs to that specific conversation.
Q4

Open net-latency-au.pcapng. How can you use an Advanced IO Graph to depict delays between packets?

Your Answer
Model Answer
The SUM(*) calculation adds up the value of a specified field across all packets within each tick interval and plots the cumulative sum. For example, SUM(*) with tcp.len would plot the total bytes of TCP payload data transferred per tick, providing a more accurate throughput picture than raw packet counts.
Q5

Open sec-clientdying.pcapng. Do all TCP hosts support SACK? How can you add a column to the Packet List pane to quickly identify whether SACK is enabled in TCP handshake packets?

Your Answer
Model Answer
The Round Trip Time graph plots the time between each TCP data packet and its corresponding ACK packet. Wireshark calculates this by matching sequence numbers in data packets to the acknowledgment numbers in ACK packets and measuring the time between them.
Q6

Open smb-filexfer.pcapng. What issues are noted by the Expert? What could be causing them? Why are there Previous Segment Lost indications without Duplicate ACKs or Retransmissions?

Your Answer
Model Answer
An ideal TCP Time-Sequence graph shows a smooth, steep diagonal line running from the lower-left corner to the upper-right corner. This pattern indicates consistent, uninterrupted data transfer where sequence numbers advance steadily over time with no retransmissions, out-of-order packets, or window zero stalls.
Q7

Open tcp-bad-download-again.pcapng. Why is a TCP Time-Sequence graph based on packet 2 almost empty? Build a Round Trip Time graph. What is the highest RTT(s) value?

Your Answer
Model Answer
A TCP Time-Sequence graph based on packet 2 appears nearly empty because packet 2 is an ACK with no payload — it carries sequence numbers but no data bytes. Wireshark's Time-Sequence graph plots the data flow for the stream direction of the selected packet. An ACK traveling in the "upstream" direction (from receiver back to sender) has no data bytes to plot on the sequence axis; only data packets produce visible points. Select a packet in the data-carrying direction (downstream) and regenerate the graph. The RTT graph will show the highest delay spike at whatever moment packet loss or receiver-side processing caused the longest ACK delay.
Q8

Open tcp-uploadproblem-largefile.pcapng. Examine the Expert Infos window for primary issues. How can you graph and compare all traffic, lost segments, and retransmissions? At what point did throughput become throttled?

Your Answer
Model Answer
Expert Information (Analyze > Expert Information) categorizes TCP anomalies into Errors, Warnings, Notes, and Chats — look for "TCP Previous segment not captured", "TCP Retransmission", and "TCP Duplicate ACK" counts. To graph three overlaid lines: Advanced IO Graph > Graph 1 = all traffic (empty filter), Graph 2 = `tcp.analysis.lost_segment`, Graph 3 = `tcp.analysis.retransmission`. The throughput throttle point is where the Graph 1 (data) line drops sharply while Graphs 2 and 3 (loss and retransmit indicators) spike — this crossover marks when packet loss caused TCP's congestion window to collapse.
Q9

Open tcp-youtubebad.pcapng. Use the Window Scaling graph to determine how the calculated window size changes.

Your Answer
Model Answer
The Window Scaling graph (Statistics > TCP Stream Graphs > Window Scaling) plots the receiver-advertised window size over time alongside the in-flight bytes. A healthy download shows a large, stable window that lets many packets be in-flight simultaneously. When the window drops sharply toward zero, the receiver's buffer is full (Zero Window condition) and the sender must pause — this stall is visible as a flat region in the sequence graph. Recovery after zero window produces a sawtooth pattern. YouTube video buffer fill-then-pause behavior produces clearly visible periodic window collapses.
Q10

Open udp-mcastream-queued2.pcapng. Can you see the queuing issue in the IO Graph? Which axis setting helps identify erratic IO rates?

Your Answer
Model Answer
A queuing problem in a UDP multicast stream appears in the IO Graph as periodic bursts of very high packet rate alternating with periods of near-zero traffic — the sender is buffering data and releasing it in bursts rather than transmitting at a steady rate. Set the Y-axis to Bytes/Tick (rather than Packets/Tick) to see the data volume per interval more clearly, revealing the burst magnitude. The standard Packets/Tick view can mask the severity of bursts if packet sizes vary. Reducing the tick interval (e.g., from 1s to 0.1s) increases resolution and makes burst timing more visible.
