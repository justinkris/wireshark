💭 THINK FIRST · IO GRAPHS OVERVIEW

IO Graphs translate raw packet data into time-based visualizations — spikes, dips, and flat lines that would take hours to detect by scrolling through a packet list. The graph is always scoped to whatever display filter is active.

  • You have a 10-minute capture of a slow file transfer. Using IO Graphs, what would you look for to determine if the slowness is caused by network congestion vs a slow server?
  • The IO Graph shows the same traffic level throughout the capture with no visible problems. Does this mean there are no TCP issues?
Q1 — IO GRAPH: CONGESTION VS SLOW SERVER
Overlay two lines: one for all traffic and one for tcp.analysis.flags. If you see traffic spikes coinciding with TCP problem spikes (retransmissions, zero windows), network congestion is likely — the TCP errors cluster exactly when traffic peaks. If the throughput is consistently low with few TCP errors and the transfer data line is flat, the bottleneck is at the server or receiver — the network has capacity but the sender isn't filling it. Also look for TCP zero-window events (tcp.analysis.zero_window) at times when throughput drops — that points to a slow receiving application rather than network loss.
Q2 — FLAT IO GRAPH ≠ NO TCP ISSUES
No. IO Graphs show traffic volume over time — they reveal throughput and timing patterns but do not surface individual TCP problems like retransmissions or duplicate ACKs. A consistent traffic line might mask a steady drizzle of retransmissions that represent 5% of traffic — visible in IO Graphs only if you add a separate line for tcp.analysis.flags. Always pair IO Graph analysis with a tcp.analysis.flags filter check in the packet list to catch individual TCP errors that the aggregate view hides.
Section 1

IO Graphs Overview

Statistics → IO Graphs plots packet count or byte rate over time. The x-axis is time; the y-axis is packets/sec or bytes/sec. By default, one graph line shows all traffic in the capture.

IO Graphs are invaluable for: finding when traffic spikes occurred, identifying periods of packet loss (dips in TCP throughput), comparing traffic volume before and after a change, and visualizing the impact of a failure. The interval setting (tick interval) controls granularity — a smaller interval shows more detail but produces a noisier graph.

Display filter scoping IO Graphs apply to the currently active display filter — set a filter first to graph only the traffic you care about, or leave it blank to graph everything. This makes IO Graphs a powerful way to visualize one application's traffic volume across a capture.
🧠
MENTAL NOTE
IO Graphs: Statistics → IO Graphs. X = time, Y = packets or bits/sec. Default = all traffic. Apply display filter first to scope the graph. Tick interval = granularity (1s default). Shows spikes, dips, and patterns invisible in the packet list.

💭 THINK FIRST · CUSTOMIZING IO GRAPHS

The real power of IO Graphs comes from layering multiple filtered lines on one plot. Overlaying tcp.analysis.flags on top of overall traffic instantly reveals whether TCP problems correlate with traffic volume — a correlation that points to saturation, not random loss.

  • You overlay tcp.analysis.flags on an IO Graph and see red spikes that perfectly align with the overall traffic peaks. What does this tell you about the likely root cause?
  • How would you use the Y-axis "AVG" value type with the tcp.analysis.ack_rtt field to detect latency trends?
Q1 — TCP PROBLEMS ALIGNED WITH TRAFFIC PEAKS
When TCP errors spike at exactly the same times as overall traffic peaks, it strongly indicates network saturation — the link or device is becoming overwhelmed at high load, causing packet drops. This is a congestion problem, not a random hardware failure or endpoint issue. The fix is to reduce traffic, increase bandwidth, implement QoS, or find why one traffic type is dominating. If the TCP errors were random hardware or endpoint errors, they would appear at a constant rate regardless of traffic volume — not correlated with peaks.
Q2 — AVG OF tcp.analysis.ack_rtt FOR LATENCY TRENDS
Set a graph line's Y-axis value type to AVG and specify tcp.analysis.ack_rtt as the field. Wireshark will compute the average ACK round-trip time across all segments in each tick interval and plot it over time. This produces a latency trend line — if the average RTT climbs steadily during a transfer, it indicates increasing network congestion (queueing delay building up). A sudden RTT spike followed by a return to baseline suggests a brief congestion event. This is equivalent to a lightweight in-capture ping test for every TCP segment.
Section 2

Customizing IO Graphs

IO Graphs support multiple simultaneous graph lines. Each line has: a display filter expression (only those packets are graphed), a color, a line style (line, impulse, filled area, dot), and a Y-axis value type (packets/sec, bytes/sec, bits/sec, or a specific field aggregate like MIN/MAX/AVG of a numeric field).

Key multi-line strategy: Line 1 = all traffic (blue), Line 2 = tcp.analysis.flags (red). This overlay immediately shows whether TCP problems coincide with traffic peaks. You can also graph the average of a specific numeric field — e.g., avg of tcp.analysis.ack_rtt to visualize round-trip time trends.

The essential two-line overlay Add a second line with filter tcp.analysis.flags in red. Now you can see exactly WHEN TCP problems cluster relative to overall traffic. If problems peak during traffic spikes, the network is saturated. If problems occur randomly regardless of traffic, the cause is elsewhere.
🧠
MENTAL NOTE
Multi-line IO Graphs: each line = its own filter + color + style + Y-value type. Y types: packets/sec, bytes/sec, bits/sec, or field aggregate (AVG/MIN/MAX of numeric field). Key overlay: all traffic (blue) + tcp.analysis.flags (red). Can graph tcp.analysis.ack_rtt avg to visualize RTT trend.

💭 THINK FIRST · TCP STREAM GRAPHS

TCP Stream Graphs give you five different lenses on a single TCP connection — each revealing a different failure mode. Retransmissions appear as backward steps, bottlenecks appear as throughput dips, and window issues appear as ceiling effects on the data rate.

  • The TCP Time-Sequence (Stevens) graph shows a flat horizontal line for several seconds in the middle of a transfer. What does this mean?
  • The Throughput graph drops to zero repeatedly at regular intervals. What TCP mechanism typically causes this pattern?
Q1 — FLAT LINE ON TIME-SEQUENCE GRAPH
A flat horizontal line on the Time-Sequence graph means the sender has stopped advancing sequence numbers — no new data is being sent. The most common causes are: (1) a zero-window condition where the receiver's buffer is full and it has told the sender to stop, or (2) congestion control — the sender has hit its congestion window limit and is waiting for ACKs to open up more sending space. To differentiate, look at the packet list during that period: zero-window packets from the receiver confirm the first scenario; if the window is non-zero but segments are being retransmitted, it is congestion control.
Q2 — THROUGHPUT DROPPING TO ZERO REPEATEDLY
Regular drops to zero in the throughput graph are the signature of TCP slow-start repeatedly triggering after packet loss. Each drop occurs when the congestion window is reset due to a retransmission timeout or three duplicate ACKs — TCP interprets this as severe congestion and drops the congestion window to one segment. The "regular" pattern suggests a predictable loss event (e.g., a consistently congested link or a periodic process on the server). Look in the packet list for retransmission events immediately before each throughput drop to confirm.

💭 THINK FIRST · READING GRAPH PATTERNS

Graph patterns are a language — flat lines, stair-steps, saw-teeth, and spikes each tell a specific story about what the network or endpoints are doing. Learning to read them means moving from "something is slow" to "here is exactly why."

  • You see a saw-tooth pattern in the Throughput graph. Where would you look in the packet list to find the specific packets causing each throughput drop?
  • The RTT graph shows a sudden spike from 5ms to 800ms and then returns to 5ms. What could cause this pattern, and is it a problem if it only happens once?
Q1 — FINDING SAW-TOOTH CAUSE IN PACKET LIST
Each throughput drop in a saw-tooth pattern corresponds to a congestion window reset triggered by packet loss. To find the culprit packets: note the timestamps of the throughput drops in the graph, then return to the packet list and filter tcp.analysis.flags. Look for retransmissions or duplicate ACKs in the packet list whose timestamps align with the drop points in the graph. Each throughput drop should have a preceding retransmission event — that retransmission is the root cause of each saw-tooth cycle. Clicking on a point in TCP Stream Graphs can also navigate you to the corresponding packet in the list.
Q2 — SINGLE RTT SPIKE FROM 5MS TO 800MS
A single RTT spike could be caused by: transient network congestion (a brief queue buildup at a router), a retransmission where the ACK comes back much later, a CPU spike on the remote server causing a delayed ACK, or a temporary routing change. A single isolated spike is generally not serious — it indicates a momentary event that self-corrected. It becomes a problem if it is persistent, causes retransmissions, or coincides with an application timeout (many applications have timeouts in the 500ms–5s range, so an 800ms spike could trigger an application-level error even if the TCP connection survives).
Section 4

Reading and Interpreting Graph Patterns

Common patterns and what they mean:

  1. IO Graph flat line at zero for a period → no traffic captured (possible capture gap or interface issue).
  2. IO Graph traffic spike followed by sharp drop → burst then connection teardown or filter applied.
  3. Time-Sequence graph stair-step → sender is stopped and waiting (zero window or congestion control).
  4. RTT graph sudden spike then baseline return → brief network congestion event.
  5. Throughput saw-tooth pattern → TCP slow-start and congestion avoidance cycling, repeated packet loss triggering congestion window resets.
Saw-tooth throughput: the congestion signature A saw-tooth throughput graph (rise then sharp drop, repeat) is the signature of repeated TCP congestion events. Each drop is a congestion window reset triggered by loss or duplicate ACKs. Find the corresponding packets in the packet list to identify the root cause.
🧠
MENTAL NOTE
Graph patterns: Flat zero = no traffic/gap. Spike+drop = burst then stop. Stair-step time-sequence = sender stalled (zero window or congestion). RTT spike = brief congestion. Saw-tooth throughput = repeated congestion events (each drop = cwnd reset). Stair-step = window-limited sender.
