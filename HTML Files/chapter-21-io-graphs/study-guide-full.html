💭THINK FIRST · IO GRAPHS

IO Graphs plot the entire packet (headers + payload). You can layer display filters across five color-coded channels to compare overall traffic to problem traffic. The tick interval controls time resolution. Logarithmic scale makes relationships visible when values differ greatly.

  • If you open a trace and the IO Graph shows a large gap where no traffic is plotted, what could this indicate about the network connection or capture process?
  • You want to compare overall traffic to TCP Expert problem packets in the same graph. Describe which filters you'd apply to each channel.

Model Answer 1: A large gap indicates there were no packets during that time interval — either the network connection was completely idle (no traffic at all), the capture process was paused or stopped and restarted (check for gaps in timestamps), or a TCP Zero Window condition froze data transfer and the application simply waited. Click on the area just before or after the gap to jump to that location in the trace file and investigate what happened.

Model Answer 2: Channel 1 (black): no filter — this shows all traffic. Channel 2 (red): tcp.analysis.flags && !tcp.analysis.window_update (Bad TCP). Channel 3 (green): tcp.analysis.retransmission. Channel 4 (blue): tcp.analysis.lost_segment. Use the Fbar style on channels 2-4 so the bars don't block the overall traffic line. If the difference between overall and problem counts is huge, use a logarithmic Y axis.

Generate Basic IO Graphs

Select Statistics | IO Graphs to plot the packets per second rate of all traffic in the trace file. IO Graphs depict the total amount of bytes including data and headers. You can graph five traffic channels in standard and advanced IO Graph modes.

X and Y Axis Settings

X axis tick intervals: 0.001s, 0.01s, 0.1s, 1s (default), 10s, 1min, 10min. Y axis units: Packets/Tick, Bytes/Tick, Bits/Tick, Advanced.

Y axis scale: Auto (default), manual (10 to 2 billion), or Logarithmic. Use logarithmic scale when comparing values of very different magnitudes (e.g., total traffic vs. retransmissions).

As of Wireshark 1.8, the IO Graph supports Smooth (moving average from M.avg4 to M.avg1024) to smooth erratic graph lines.

💭THINK FIRST · ADVANCED IO GRAPHS

Advanced IO Graphs add CALC functions (SUM, MIN, AVG, MAX, COUNT, LOAD) to graph the values of specific packet fields rather than just counting packets. This unlocks deep performance analysis — graphing bytes in flight, RTT, sequence number growth, and command load.

  • To measure how much TCP application data (not headers) is flowing between two specific hosts, which CALC function and field would you use, and what additional filter would you apply?

Model Answer: Use CALC: SUM(*) with field tcp.len. Add a display filter for the specific conversation, e.g., ip.addr==192.168.1.1 && ip.addr==10.0.0.1. This sums up only the TCP payload bytes (excluding headers) for each tick interval for traffic flowing between those two hosts. Each channel can have its own filter, so you could add a second channel for the reverse direction with a different filter to see upload vs. download separately.

💭THINK FIRST · TCP-SPECIFIC GRAPHS

Wireshark provides three TCP-specific graphs: Round Trip Time (time between data and ACK), Throughput (bytes per second), and Time-Sequence (sequence numbers over time with window line). All three are unidirectional — if empty, select a packet in the opposite direction. The Time-Sequence (tcptrace) graph is the most informative.

  • In a TCP Time-Sequence (tcptrace) graph, what does it mean visually when you see: (a) vertical I-bars stacking at the same X position and (b) a gap with no I-bars?

Model Answer: (a) Vertical I-bars stacking at the same X position (same time) means you are upstream from packet loss — you're seeing the original packet AND its retransmission(s) at the same or similar sequence numbers. Multiple bars at the same sequence number = multiple transmission attempts. (b) A gap with no I-bars (no sequence number advance) means you are downstream from packet loss — the sequence numbers you expect to see simply never arrived at this capture point. The trace shows what's missing from the receiver's perspective.

TCP Round Trip Time, Throughput & Time-Sequence Graphs

Round Trip Time Graph

Select Statistics | TCP Stream Graph | Round Trip Time Graph. Plots the time between a TCP data packet and the corresponding ACK. X axis = TCP sequence number. Y axis = round trip time in seconds. Unidirectional — select a data packet (not an ACK) before opening.

Consistent vertical stripes indicate packet loss — when multiple Duplicate ACKs are sent for the same sequence number, multiple ACK "responses" are plotted at that sequence number. Use +/- keys to zoom in/out.

Throughput Graph

Select Statistics | TCP Stream Graph | Throughput Graph. Plots throughput in bytes per second using dots only. Unidirectional — if empty, select a packet going in the reverse direction.

TCP Time-Sequence Graph (tcptrace)

Select Statistics | TCP Stream Graph | Time-Sequence Graph (tcptrace). The most information-rich TCP graph.

Each TCP segment is plotted as an "I bar" — taller I bars contain more data. In an ideal transfer, I bars run smoothly from the lower-left to the upper-right.

The grey window line shows the receive buffer space. When I bars meet the grey window line, a Zero Window condition has occurred (data transfer frozen). Window Probe packets are shown as small ticks along the horizontal zero window line.

Upstream from packet loss: see duplicate I bars (same sequence number, two different times). Downstream from packet loss: see gaps in I bars (missing sequence numbers).

Duplicate ACKs appear as numerous ticks along the receive line. RTO-triggered retransmissions appear without preceding Duplicate ACKs.

The Window Scaling graph (Statistics | TCP Stream Graph | Window Scaling Graph) plots the calculated window size over time to show Zero Window conditions.

CAUTION At present, Wireshark does not allow saving the TCP Time-Sequence graph. Use a screen capture utility (e.g., SnagIt) to capture and print it.
🧠
MENTAL NOTE
All TCP graphs are unidirectional. If empty: select a packet in the other direction. RTT Graph: time between data → ACK. Throughput: bytes/sec. Time-Sequence: sequence numbers over time. Ideal Time-Sequence = smooth diagonal line lower-left to upper-right. Vertical stripes = packet loss + Dup ACKs. Upstream loss: duplicate I bars. Downstream loss: gaps in I bars. Window line meeting I bars = Zero Window. Zoom: +/- keys.

Case Studies

Case Study 1
Watching Performance Levels Drop
Submitted by: Mark R., Sr. Network Technician

We were plagued with intermittent complaints from end users who said their machines locked up occasionally when going to the Internet. All traffic went through a proxy server on port 8080.

We captured trace files of traffic to/from port 8080 and told users to contact us when they had a lock up. When we looked at the trace files we kept seeing the client reporting "TCP Zero Window" and then 10 seconds or so go by before the client system sent a TCP reset. We recognized this as a problem with client resources — data wasn't being pulled out of the TCP buffer in a timely manner.

We examined the client machines to see what was running. We found a bunch of clients were using Dropbox to sync pictures and videos. Those were the users that complained, and it always happened when they synchronized their Dropbox folders. Dropbox was consuming so much of the system's I/O resources that the TCP receive buffer wasn't being emptied fast enough.

Once we disabled Dropbox on their systems, they could browse just fine.

Case Study 2
Graphing RTT to the Corporate Office
Submitted by: Christy Z., Network Administrator

To compare round trip times between different branch offices and the corporate headquarters, we used AVG(*) with tcp.analysis.ack_rtt in Advanced IO Graphs. We used three filters, one for each branch office (based on network addresses), graphed on separate channels.

The results showed that round trip times to the 10.2 and 10.4 networks were much higher than to the 10.3 network — matching complaints from those branch office users about slow file transfers.

We refined the graphs to separate traffic by port number on the slow branch. The results showed SMB traffic (port 445) had much higher RTT than HTTP or NTP to that branch. This pointed us to investigate QoS settings. We discovered QoS configurations had been altered in preparation for a VoIP rollout, placing port 445 traffic at a lower priority. Adjusting the QoS settings resolved the performance complaints.

TL;DR — Chapter Summary

Wireshark's IO Graph, TCP Round Trip Time Graph, Time-Sequence Graph and Throughput Graph build pictures of TCP data flow and can help identify the cause of network performance problems. Advanced IO Graphs enable CALC values such as SUM(*), COUNT(*), MIN(*), MAX(*) and LOAD(*) with display filters.

The Round Trip Time Graph tracks the time between data being transmitted and the associated TCP ACK. Throughput Graphs plot total bytes at specific points in time. TCP Time-Sequence Graphs plot individual TCP packets based on sequence number changes over time. An ideal Time-Sequence graph plots from lower-left to upper-right along a smooth diagonal line.

Review Questions

Q21.1 How much of a packet is counted when plotting an IO Graph?
A21.1 The entire packet including payload and headers is counted in IO Graphs.
Q21.2 What is the likely cause of an empty graph?
A21.2 Most likely the graph is unidirectional and you have selected a packet traveling in the wrong traffic direction before building the graph.
Q21.3 How can you use an IO Graph to plot overall traffic compared to a single conversation?
A21.3 Apply a conversation filter on a second graph channel, leaving the first channel with no filter to show all traffic.
Q21.4 What is the purpose of the SUM(*) calculation in an advanced IO Graph?
A21.4 SUM(*) adds up the value of a field (such as tcp.len) for each tick interval and plots the total value on the graph.
Q21.5 On what data is the Round Trip Time graph based?
A21.5 Wireshark calculates and plots the time between a data packet and the corresponding ACK packet (tcp.analysis.ack_rtt).
Q21.6 What is an ideal pattern to see in a TCP Time-Sequence graph?
A21.6 The ideal TCP Time-Sequence graph pattern is a steep, smooth slope from the lower-left corner to the upper-right corner, indicating consistent data transfer without gaps or retransmissions.
