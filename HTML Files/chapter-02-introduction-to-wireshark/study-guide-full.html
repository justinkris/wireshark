💡THINK FIRST · WIRESHARK CREATION & HISTORY

Gerald Combs created Wireshark because commercial analyzers cost $5,000–$20,000 and his employer limited him to tcpdump and snoop. tcpdump already existed as an open-source tool when he started. Why build an entirely new GUI application instead of improving tcpdump — and what does that design choice reveal about where the real gap in network analysis tooling was?

HINT

Think about the difference between capturing packets and interpreting them. A CLI tool outputs raw data; a GUI tool presents structured, clickable, color-coded protocol hierarchies. Who benefits from each?

MODEL ANSWER

tcpdump captures packets and prints human-readable summaries, but it requires the analyst to know exactly what to look for before running the command — you specify filters and columns in advance and read text output. Wireshark's GUI lets you capture everything, then drill down interactively: click a packet, see the protocol tree expand, click a field, see which bytes it occupies. This interactive drill-down is fundamentally different from CLI analysis — it allows analysts to discover what they didn't know to look for. The gap was accessibility: network analysis was possible with CLI tools, but required deep expertise to use effectively. Wireshark democratized the process by making the protocol structure visible and navigable to anyone. The GUI also enables multi-stream colorization, IO graphs, protocol hierarchy views, and follow-stream display — none of which translate well to a CLI tool.

Wireshark Creation and Maintenance

Wireshark is the world's most popular network analyzer. Available for free to all as an open source tool, Wireshark runs on a variety of platforms and offers the ideal "first responder" tool for IT professionals.

In 1997, the analysis world was dominated by commercial network analyzers that ranged in price from $5,000 to $20,000. The cost was prohibitive to most business and information technologists. Gerald Combs was one of these technologists who felt the budget constraints of the expensive commercial tools. Prior to creating Ethereal, Gerald Combs was lugging around a Sniffer portable at the University of Missouri in Kansas City. The budget issues at his next job at a small Internet service provider limited his tools to tcpdump and snoop. He decided to create his own network analyzer program.

Gerald Combs originally released his network analyzer program under the name Ethereal (version 0.2.0) on July 14, 1998, although Gerald's original development notes are dated several months earlier (late 1997). When Gerald began working with CACE Technologies in June 2006, trademark ownership issues of the name Ethereal forced the development efforts to move to the new name, Wireshark. CACE Technologies was purchased by Riverbed Technology in 2010.

Wireshark is maintained by an active community of developers from all over the world. For more information on the Wireshark developers, see Thanks to the Wireshark Developers or select Help | About Wireshark | Authors from the Main Menu. Currently there are approximately 700 developers credited with building and enhancing Wireshark. There are between 10 and 20 active developers at any given time.

💡THINK FIRST · CAPTURE INTERFACES

WinPcap, libpcap, and AirPcap are all described as "link-layer interfaces" but they are not interchangeable. What determines which one is used — and crucially, why does Wireshark need a completely separate library (the Wiretap Library) just to OPEN saved trace files when these capture drivers already handle raw packets?

HINT

Live capture and opening a file are fundamentally different operations. One involves hardware, the other involves reading bytes from disk. What does each library actually do?

MODEL ANSWER

The capture library is determined by the host OS and adapter type: libpcap for Unix/Linux/macOS, WinPcap for Windows hosts, and AirPcap specifically for 802.11 wireless capture on Windows. These drivers bypass the OS network stack to receive raw frames at the link layer during live capture. Opening a saved trace file is an entirely different operation — no live network traffic is involved, and the file may have been created by a completely different tool on a different OS. The Wiretap Library handles all file format parsing and translation, allowing Wireshark to read pcap, pcap-ng, Microsoft NetMon, Network General Sniffer, Endace ERF, and dozens of other formats. The two components serve orthogonal purposes: capture drivers access the wire in real time; the Wiretap Library reads structured bytes from disk. This separation is why opening a Sniffer .cap file in Wireshark works even on a Linux host where WinPcap never ran.

Capture Packets on Wired or Wireless Networks

When Wireshark is connected to a wired or wireless network, traffic is processed by either the WinPcap, AirPcap or libpcap link-layer interface, as illustrated in Figure 11.

Libpcap

The libpcap library is the industry standard link-layer interface for capturing traffic on *NIX hosts. Information regarding patches related to libpcap can be found at www.tcpdump.org.

WinPcap

WinPcap is the Windows port of the libpcap link-layer interface. WinPcap consists of a driver that provides the low-level network access and the Windows version of the libpcap API (application programming interface). Visit www.winpcap.org for more information on WinPcap and WinPcap-capable utilities.

AirPcap

AirPcap is a link-layer interface and network adapter used to capture 802.11 traffic on Windows operating systems. AirPcap adapters operate in passive mode to capture WLAN data, management and control frames. Visit www.riverbed.com/us/products/cascade/airpcap.php for more information on AirPcap adapters.

💡THINK FIRST · OPEN VARIOUS TRACE FILE TYPES

The Wiretap Library lets Wireshark open dozens of trace file formats from competing products. From a practical standpoint, why would an organization ever need to open a trace file from a competing product rather than just recapturing the traffic themselves?

HINT

Network analysis is often forensic work. Think about incidents, compliance audits, and the reality that trace files may be the only record of a past event.

MODEL ANSWER

Three real-world scenarios make this critical: (1) A security incident from six months ago was captured by a Network General Sniffer — that Sniffer no longer exists, but the trace file is the only evidence. (2) A vendor provides a trace file from their proprietary analyzer tool as proof that their system behaved correctly during a customer dispute. (3) A branch office uses a NetMon-based capture while headquarters uses Wireshark — sharing trace files between sites is standard practice. In each case, recapturing is impossible (the event is in the past or the same conditions can't be reproduced). The Wiretap Library preserves access to historical forensic evidence regardless of which tool originally created the capture. The alternative — refusing to read competitor formats — would make Wireshark useless in multi-tool environments, which is every enterprise environment.

💡THINK FIRST · UNDERSTAND HOW WIRESHARK PROCESSES PACKETS

Wireshark dissectors chain together — each one reads a type field and hands off to the next dissector. If you disable the UDP dissector in Analyze | Enabled Protocols, what happens to DNS and DHCP traffic, and why does this reveal something fundamental about how protocol layering actually works in Wireshark?

HINT

Think about what must happen for Wireshark to know a packet is a DNS packet. What has to be successfully decoded first?

MODEL ANSWER

Disabling the UDP dissector causes Wireshark to stop decoding all traffic that uses UDP at the transport layer — including DNS, DHCP, SNMP, and dozens of other application protocols. The Protocol column for those packets shows "UDP" (or possibly just raw data) rather than their application-layer name. This demonstrates a concrete consequence of protocol layering: the DNS dissector can only activate if Wireshark has already decoded the IP header (which gives it the protocol field = 17 for UDP), and then the UDP header (which gives it the destination port = 53 for DNS). Each dissector depends on the one below it completing successfully. If you disable UDP entirely, Wireshark stops the chain at Layer 4 and never reaches Layer 7. This is why disabling seemingly low-level dissectors has such a wide blast radius. As a caution note in the book states: "Be careful with this setting. If you disable a protocol, higher protocols and applications will not be decoded."

Understand How Wireshark Processes Packets

Trace files that are processed by libpcap, WinPcap or AirPcap or are opened up with the Wiretap Library are processed in the core engine as shown in Figure 13.

Core Engine

The core engine is described as the "glue code that holds the other blocks together." It coordinates the dissectors, plugins, display filters, and the graphical toolkit.

Dissectors and Plugins and Display Filters

Dissectors (also referred to as decodes), plugins (special routines for dissection) and display filters (used to define which packets should be displayed) are applied to the traffic at this time. Dissectors decode packets to display field contents and interpreted values.

When a packet comes in, Wireshark detects the frame type first and hands the packet off to the correct frame dissector (Ethernet, for example). After breaking down the contents of the frame header, the dissector looks for an indication of what is coming up next. For example, in an Ethernet header the value 0x0800 in the Type field indicates that IPv4 is coming up next. The Wireshark Ethernet dissector hands the packet off to the IP dissector. The IP dissector works its magic on the IP header and looks to the Protocol field in the IP header to identify the next portion of the packet. If the value is 0x06 (TCP), the IP dissector hands the packet off to the TCP dissector. This process continues until there are no further indications of another possible dissection.

Disabling a Protocol May Blind YouBe careful with this setting. If you disable a protocol, higher protocols and applications will not be decoded. For example, if you disable UDP, then applications that use UDP (such as DHCP and DNS) will not be decoded either as shown in Figure 34.

GIMP Toolkit (GTK+)

GIMP GTK+ is the graphical toolkit used to create the graphical user interface for Wireshark and offers cross-platform compatibility. For more information on GTK+, visit www.gtk.org.

💡THINK FIRST · USE THE START PAGE AND NINE GUI ELEMENTS

The Status Bar in Wireshark shows five distinct elements. If you were designing a training exercise for a new analyst opening a trace file for the first time, which single Status Bar element would you tell them to check first — and what would it immediately reveal about the capture without selecting any packet?

HINT

Each element of the Status Bar answers a specific question about the capture. Think about which question is most important to answer before beginning analysis.

MODEL ANSWER

The Expert Info button (the colored circle on the far left) is the single most diagnostic element to check first. Its color immediately tells you the highest severity problem in the entire capture: Red = Errors (serious — TCP retransmissions, connection resets), Yellow = Warnings (concerning), Cyan = Notes (informational), Blue = Chats (normal expected behaviors), Green = Packet comments only (no expert items), Grey = Nothing flagged. Before selecting any packet or applying any filter, the Expert Info button gives you a triage-level summary: "this capture has serious TCP errors" vs. "this capture looks clean." The Packet Information column (second-most useful) immediately shows how many packets total vs. displayed — if displayed is less than total, a display filter is already active and you may not be seeing everything. Checking these two elements first prevents hours of analysis on filtered or miscategorized data.

💡THINK FIRST · NAVIGATE WIRESHARK'S MAIN MENU

The Analyze menu contains "Decode As" which forces a specific dissector onto non-standard port traffic. The Statistics menu contains IO Graphs which can overlay display-filtered traffic against total traffic. If you could only teach a new analyst two menu items to accelerate their analysis, which two would you choose — and what does each reveal that nothing else can?

HINT

Think about the two most common blockers new analysts face: not recognizing the protocol on a non-standard port, and not seeing traffic patterns over time. What tools directly address each?

MODEL ANSWER

The two most high-impact menu items for new analysts are: (1) Analyze | Follow TCP Stream — this instantly reassembles the selected TCP stream and shows the human-readable application conversation (HTTP commands, FTP credentials, IRC messages) in a single window. It collapses hundreds of packets into a readable dialogue and reveals application behavior without understanding any individual packet. (2) Statistics | IO Graphs — this plots the packet or byte rate over time and lets you overlay a display-filtered dataset (e.g., tcp.analysis.retransmission) against total traffic. It reveals timing patterns, traffic spikes, sustained low-bandwidth periods, and retransmission storms that are completely invisible when looking at individual packet rows. These two tools together answer "what happened?" (follow stream) and "when and how severely did it happen?" (IO graph) — the two most fundamental questions in any analysis session.

Navigate Wireshark's Main Menu

The Main Menu consists of eleven sections. Unlike the Main Toolbar, Filter Toolbar, Wireless Toolbar and Status Bar, you cannot hide the Main Menu.

File Menu Items

  • File | Open — Wireshark refers to your User Interface preferences to determine which directory to open.
  • File | Open Recent — configure max entries via Edit | Preferences → "Open Recent" max list entries (default 10).
  • File | Merge — combine multiple trace files. Use Mergecap for chronological ordering (File | Merge does NOT order packets by arrival time).
  • File | Import — import an ASCII text file and save it in pcap or pcap-ng format. Can append dummy headers if the ASCII file did not contain such headers.
  • File | File Set — work with a series of files linked together by Wireshark. Select File | File Set | List Files to move quickly between the files.
  • File | Export — export entire trace file or defined packets. Export Specified Packets, Export Packet Dissections (text/CSV/XML/PDML/JSON), Export Selected Packet Bytes, Export SSL Session Keys, Export Objects (HTTP, DICOM, SMB, TFTP).

Edit Menu Items

  • Mark Packets (Ctrl+M) — temporary black background and white foreground in the Packet List pane. Mark all displayed packets with Ctrl+Shift+M. Marking is temporary — cleared when you reopen the trace file.
  • Time Reference (Ctrl+T) — used to measure the time from one packet to another in a trace file. The Time column value after the REF indicates when packets arrived compared to the Time Reference packet. Temporary setting.
  • Time Shift (since Wireshark 1.8) — alter the timestamps of packets in a trace file. Used when you want to merge two trace files taken a long time apart in order to graph their contents.
  • Edit or Add Packet Comment — add a comment to a packet. The trace file must be saved in pcap-ng format to retain the comment. The packet comment field is named pkt_comment.
  • Edit | Preferences — User Interface, Capture, Printing, Name Resolution, Filter Expressions, Statistics, Protocols settings.

View Menu Items

  • View | Time Display Format — critical for troubleshooting. Use "Seconds Since Previous Displayed Packet" to sort the Time column and identify large gaps in time. This is one of the most important settings to understand and use when troubleshooting performance.
  • View | Name Resolution — MAC layer, network layer (host name), transport layer (port name) resolution. By default, Wireshark resolves first three bytes of MAC addresses and the port number in use. Enabling network name resolution causes Wireshark to send DNS PTR queries for every IP address — potentially flooding your DNS server.
  • View | Colorize Conversations — make specific conversations more visible in a trace file. These are temporary colorizations only, applied each time you open that trace file until you restart Wireshark or switch profiles. Remove with View | Reset Coloring 1-10.
  • View | Coloring Rules — persistent settings maintained in the colorfilters file. You can have a unique set of coloring rules in each profile. The coloring rule for Bad TCP changed as of Wireshark 1.8 — Window Update is now excluded from Bad TCP.

Analyze Menu Items

  • Display Filters — over 105,000 possible display filters. Display filters can be applied during a live capture or when viewing a saved trace file. With a few exceptions, display filters do not use the same syntax as capture filters. Display filters do use the same syntax as coloring rules.
  • Display Filter Macros — create macros for more complex display filters. The macros contain the syntax and structure of the display filter and the argument placement.
  • Apply as Column — after selecting a field in the Packet Details pane, right-click and select Apply as Column. A new column is added to the Packet List pane to the left of the Info column.
  • Analyze | Apply as Filter / Prepare a Filter — Apply as Filter immediately applies the filter to the traffic; Prepare a Filter lists the filter in the display filter field but does not apply it yet, allowing you to modify before applying.
  • Decode As — force Wireshark to use a specific dissector on traffic it would not normally recognize. For example, applying the IRC dissector to traffic on port 18067. This is a temporary setting — use User Specified Decodes to save it.
  • Follow TCP/UDP/SSL Stream — reassemble the selected stream and display it in human-readable form. If you find yourself constantly focused on the ASCII interpretations in the Packet Bytes pane, consider following the stream for faster interpretation.
  • Expert Info — Wireshark identifies unusual or interesting traffic in a trace and applies a categorization and colorization. The button on the far left of the Status Bar links to the Expert Infos window.

Statistics Menu Items

  • Summary — packet and byte counts, time elapsed, capture filter information. Also shows trace file annotations and marked packet data.
  • Protocol Hierarchy — packet count, byte count and percentage of all traffic in the trace file for each protocol. Particularly useful for detecting protocol anomalies (Chapter 32: Analyze Suspect Traffic).
  • Conversations and Endpoints — identify the most active hosts or conversations. GeoIP mapping available via Statistics | Endpoints | IPv4 or IPv6 window.
  • IO Graphs — view the total amount of bytes in a saved or unsaved trace file. Run while capturing to see a dynamic view. Using display filters, you can compare specific traffic against total traffic (e.g., all traffic vs. TCP Duplicate ACKs).
  • Statistics | HTTP — load distribution list, HTTP requests by server/address, packet counter info.

Tools and Internals Menu Items

  • Tools | Firewall ACL Rules — builds Cisco IOS (standard and extended), IP Filter (ipfilter), IPFirewall (ipfw), Netfilter (iptables), Packet Filter (pf), or Windows Firewall (netsh) rules directly from a selected packet source IP.
  • Tools | Lua — Lua is "a powerful, fast, lightweight, embeddable scripting language." Lua can be used to add functionality to applications. Lua scripts can be created to prototype a dissector.

💡THINK FIRST · USE THE MAIN TOOLBAR FOR EFFICIENCY

The Main Toolbar has seven sections. The Navigation section includes "Go to Corresponding Packet" which links ACKs to their data packets. Why is this particularly valuable for TCP analysis — and what would you have to do manually to find the corresponding packet without it?

HINT

Consider a trace file with 20,000 packets. A Duplicate ACK at packet 15,432 references data in packet 12,019. Without Go to Corresponding Packet, how do you get there?

MODEL ANSWER

Without Go to Corresponding Packet, you would need to: (1) Note the sequence number in the Duplicate ACK's ACK number field, (2) manually scroll through thousands of packets looking for the original data packet with that sequence number, or (3) build a display filter like tcp.seq==1234567 and search. In a 20,000-packet trace, this manual process could take many minutes. Go to Corresponding Packet automates this by doubling-clicking the linked packet reference in the TCP SEQ/ACK Analysis section of the Packet Details pane — Wireshark instantly jumps to the referenced packet. This is especially important for analyzing retransmissions (which packet was lost?), Duplicate ACKs (what data is being re-requested?), and TCP handshake responses (which SYN does this SYN-ACK correspond to?). The Filter Toolbar's auto-complete feature (showing all 105,000+ possible display filters as you type) is similarly high-value — it eliminates the need to memorize filter syntax.

Use the Main Toolbar for Efficiency

The Main Toolbar contains the icon-based navigation for Wireshark which provides a faster method to perform many common tasks. The Main Toolbar is separated into seven sections as shown and defined below.

Focus Faster with the Filter Toolbar

The Filter Toolbar consists of a Display Filter button (marked just "Filter"), the display filter area, the display filter drop-down, Expression, Clear and Apply and the recently-added Save buttons. Wireshark includes a display filter auto-complete feature — begin typing in the display filter area and Wireshark lists all possible filters beginning with that string. Color coding helps avoid common display filter mistakes.

As of Wireshark 1.8 you can save a set of buttons on the filter toolbar to quickly load your favorite display filters. These Filter Expressions can be built inside the Preferences area or by creating a display filter and clicking Save in the display filter area.

💡THINK FIRST · WORK FASTER USING RIGHTCLICK FUNCTIONALITY

Right-clicking in the Packet Details pane offers both "Apply as Filter" and "Prepare a Filter" — and also "Apply as Column." These three options are easy to confuse. Describe a specific analysis scenario where you would use each of the three options, and explain why the other two would be inferior choices in each case.

HINT

Think concretely: when do you want to immediately narrow the view (filter), when do you want to build a compound filter (prepare), and when do you want to add a field as a persistent column?

MODEL ANSWER

(1) Apply as Filter: You clicked on a DNS response packet and right-clicked the "Destination: 192.168.1.100" field. You want to see all packets to/from that specific host immediately. Apply as Filter instantly narrows the Packet List to that host. (2) Prepare a Filter: You want to filter for a specific host but only if they are using HTTPS. Right-click "Source: 192.168.1.100" → Prepare a Filter → this populates the filter bar with ip.src==192.168.1.100. You then manually edit it to ip.src==192.168.1.100 && tcp.port==443 before pressing Enter. Prepare lets you refine before committing. (3) Apply as Column: You're analyzing TCP performance and want to see the Calculated Window Size for every packet without expanding the TCP header each time. Right-click "Calculated window size: 65536" in the TCP header → Apply as Column. Now that value appears as a persistent column in every row. This is faster than applying a filter — it enriches the view rather than narrowing it.

Work Faster Using RightClick Functionality

Many Wireshark tasks can be completed quickly using rightclick functionality. Different rightclick options are available for the Packet List pane, Packet Details pane and Packet Bytes pane. Different rightclick windows appear depending on where you clicked in each pane as well.

Packet List Pane (right-click on a packet)

  • Apply as Filter / Prepare a Filter — generate a display filter based on the packet you clicked
  • Conversation Filter — filter for the complete conversation involving this packet
  • Colorize Conversation — temporarily colorize this conversation to track it visually
  • Follow TCP/UDP/SSL Stream — reassemble and display the stream in a readable window
  • Copy — copy Summary (Text), Summary (CSV), As Filter, Bytes, Printable Text Only, Hex Stream, Binary Stream
  • Mark Packet (toggle) — temporary black/white highlight
  • Ignore Packet (toggle) — remove from display (Reload File to restore)
  • Set Time Reference (toggle) — set time reference for measuring elapsed time
  • Time Shift — alter timestamps of this packet
  • Edit or Add Packet Comment — save a comment inside the pcap-ng file; comment saved in pkt_comment field

Packet Details Pane (right-click on a field)

  • Expand All / Collapse All — expand/collapse all protocol layers
  • Apply as Column — add the selected field as a persistent column in the Packet List pane. Right-click the new column heading to rename, align, hide, or remove it.
  • Apply as Filter / Prepare a Filter — generate a display filter based on the exact field value clicked
  • Copy — Description, Fieldname, Value, As Filter, Bytes, Offset Hex, Printable Text Only, Hex Stream, Binary Stream
  • Wiki Protocol Page — open the Wireshark Wiki page for the selected protocol in your default browser
  • Filter Field Reference — open the display filter reference list for the selected protocol in your browser
  • Resolve Name — temporary single-IP DNS PTR lookup for the right-clicked IP address. The host name information is not saved when you close the trace file. Avoid enabling global network name resolution (which floods your DNS server with PTR queries) — use Resolve Name for targeted single-IP lookups instead.
  • Protocol Preferences — quick access to per-protocol settings (same as Edit | Preferences | Protocols). Settings saved and in effect next time you start Wireshark.

Right Click | Apply As Column

This option offers a fast way to add a column to the Packet List pane. For example, right-clicking the Calculated Window Size field in a TCP header and selecting Apply as Column adds a new column showing the window size value for every packet. To add the column shown in the book, open http-espn2011.pcapng, right click on the Calculated Window size field in the TCP header and select Apply as Column.

Don't Kill Wireshark PerformanceTo display custom columns, Wireshark must look inside packets to locate the desired field and extract the contents of that field to display in the Packet List pane. All this work adds overhead to Wireshark and may slow down the process of displaying trace file contents or update the list of packets in real-time while capturing. In my opinion there are some instances where giving up this performance is necessary to speed up the overall troubleshooting process.

Case Study 1
Detecting Database Death
Submitted by: Bill Bach, Goldstar Software, Inc.
🖼️
C2-CS1.png
Save to all-casestudy-pictures/C2-CS1.png
A network engineer sits at a workstation with three separate terminal windows open: one labeled "CLIENT TRACE" showing a packet with -1 in a highlighted field, one labeled "SERVER TRACE" showing the same -1 value traveling across a network cable, and one labeled "DATABASE VENDOR TRACE" showing 0 instead. The engineer points at the database vendor window with a magnifying glass, expression of discovery. In the background, a frustrated application developer on the phone gestures at a whiteboard reading "We ALWAYS pass -1!". A timeline on a wall shows "19/20 times: -1, 1/20 times: 0" with the rare occurrence circled in red. On a second monitor, Wireshark is open with a TCP stream followed and the parameter field highlighted. The office has technical equipment and multiple network switches visible. Flat simple cartoon style, bold outlines, bright colours. Minimal text labels: "CLIENT TRACE: -1", "SERVER TRACE: -1", "DB VENDOR LOG: 0", "Communications module bug", "19/20 correct 1/20 broken".

I was troubleshooting an application problem for a client, which started as a simple "Database Version 6 or Higher Required" message for a given file. More interesting were the facts: A) the database files was already in version 6 format, and B) the error only spewed spontaneously, about 1/10 of the time, and sometimes it would report on a different database file.

After working on this issue for a while and quadruple-checking all the usual suspects, we were stumped and decided to enable the database vendor's trace feature. This feature is very handy because it reports to a simple text file every database request and every corresponding reply — a great troubleshooting aid for unusual problems like this. Of course, that text file grows VERY rapidly in a production environment and really takes a toll on performance, so we had to use it sparingly.

After several attempts of testing at random, we finally managed to capture a series of events with the "Database Version..." message getting returned. Upon digging through an 80MB trace file, we were able to locate the database request where the version number was requested. Interestingly, the application had provided a 0 value for one of the parameters, instead of a -1 (which indicates that the file version should be returned). With the 0 in there, no file version was returned, which explains why a 0 got returned for the file version, and subsequently the program complained about the version number.

So, we complained to the application vendor, who dug through the code and could find NO instances of ever passing a 0 -- they ALWAYS passed a "-1" to get the database version. Strange.

Back to the database trace file again, we watched a "normal" application launch and indeed confirmed that 19 times out of 20, the database file version was being requested, but only periodically was the parameter a 0. More strange!

On a lark, we decided to capture traffic from the same application startup process, capturing both a trace with the version request working and one with it not working. As expected, when the version request worked, we saw the -1 value getting passed from the application to the server. However, when the version request failed, we saw -- a -1 value! Most strange!

We took another trace on the server side. Again, though, we had EVERYTHING running at the same time. We watched as the application sent a -1 for the version request, the -1 was seen in the workstation-side trace file, the -1 was seen in the server-side trace file, and a 0 was seen by the database vendor trace file. Aha! Finally, indisputable proof!

When we provided this information to the database vendor, they did a detailed review of their own networking code and indeed found a case where some functions (and the version request was one of them) could have parameters overwritten with a 0. Since it was occurring in the communications module, the database feature only saw the 0 value and responded accordingly. The next week, we had a new communications module from the developer and things were working once again.

What did we learn?

  • A) You need to involve the application developer, the backend developer, AND a networking professional to troubleshoot some issues.
  • B) You may need multiple network traces (at the client and at the server) to watch packets going through the network.
  • C) Just because a vendor provides a trace log, doesn't mean that you can rely on it!
TL;DR — Chapter 2 Summary

Introduction to Wireshark

From its humble beginnings as Ethereal, Wireshark has matured to a feature rich tool for analyzing wired and wireless network traffic. As long as you stay within the laws and corporate policies that regulate use of Wireshark, you can troubleshoot and secure your network more efficiently with an inside look at network communications.

All versions of Wireshark use packet capture drivers to capture traffic on wired and wireless networks and the Wiretap Library to open various types of trace files. Wireshark supports a common interface across multiple platforms with menu-based, icon-based or rightclick functionality for trace file manipulation and interpretation.

Review Questions

Q2.1
What is the purpose of WinPcap?
HINT

WinPcap is platform-specific. Think about what a "link-layer interface" does and which operating system it targets — and what it replaces on that platform.

ANSWER

WinPcap is the Windows port of the libpcap link-layer interface. WinPcap consists of a driver that provides the low-level network access and the Windows version of the libpcap API for packet capture. It enables Wireshark to bypass the Windows network stack and capture raw frames at the link layer on Windows hosts.

Q2.2
What is the purpose of Wireshark's dissectors?
HINT

Consider what information exists in a raw packet byte stream versus what Wireshark shows you in the Packet Details pane — and what has to happen in between.

ANSWER

Wireshark dissectors decode packets to display field contents and interpreted values. Each dissector handles one protocol layer and chains to the next based on type field values found in headers. An HTTP packet uses multiple dissectors chained together: Ethernet (reads EtherType 0x0800) → IP (reads Protocol 6) → TCP (reads Port 80) → HTTP dissector. Disabling a lower-layer dissector prevents all higher-layer protocols from being decoded.

Q2.3
What is the purpose of the Wiretap library?
HINT

The Wiretap Library is NOT the capture driver — it activates when you open a saved file, not during live capture. Think about what problem it solves for analysts working in multi-tool environments.

ANSWER

The Wireshark Wiretap Library enables Wireshark to read a variety of trace file formats including Microsoft Network Monitor, Network General Sniffer, WildPackets OmniPeek, Endace ERF, and many others. It abstracts format differences so Wireshark can open any supported trace file regardless of which tool originally captured it or which OS it was captured on.
