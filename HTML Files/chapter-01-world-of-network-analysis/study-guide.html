💭 THINK FIRST · WHY NETWORK ANALYSIS

Packet analysis is the ground truth of networking — it shows you exactly what crossed the wire, not what a device or log summarizes. Before you dive in, consider what logs and SNMP can and cannot tell you about a network problem.

  • A network engineer says "the router logs show no errors." A user says "the web page loads slowly." Which source do you trust more, and why?
  • Name two types of problems that packet analysis can detect that SNMP and logs cannot.
Q1 — LOGS VS PACKET CAPTURE FOR SLOW PAGE LOADS
The packet capture is more trustworthy for diagnosing slow page loads. Router logs report events the router considers noteworthy — they won't record a slow application response, high TCP RTT, or inefficient HTTP behavior unless those specifically trigger a log entry. A packet capture shows the actual bytes exchanged, timestamps between requests and responses, TCP retransmissions, and the exact time the server took to respond. "No errors in the logs" only means no errors the router was configured to log — it says nothing about application-layer latency, network path inefficiency, or server response time.
Q2 — PROBLEMS ONLY PACKET ANALYSIS DETECTS
Two examples: (1) TCP retransmissions — a packet is sent, lost, and resent. SNMP and logs will show the connection succeeded, but only a packet capture reveals the retransmissions that added latency. (2) Application protocol errors — a server sends an HTTP 200 OK but the response body is malformed or truncated. Logs record the 200 status; only a packet capture shows the actual bytes returned and reveals the malformation. Other examples include ARP cache poisoning, SYN floods, and misconfigured keepalives — all invisible in logs but immediately visible in a capture.
Section 1

Why Network Analysis Matters

Network analysts use packet analysis to troubleshoot connectivity, measure performance, verify security, and audit application behavior. Wireshark is a packet analyzer (sniffer) that captures frames off the wire and decodes them into human-readable protocol fields. Unlike logs and SNMP, which summarize events, packet captures show the exact bytes exchanged — the ground truth of network communication.

The ground truth principle Packet analysis is the only technique that lets you see exactly what was sent and received, not what a device or application reports it sent.

💭 THINK FIRST · ANALYST TYPES

Three analyst roles use the same tool — Wireshark — but look at completely different fields and patterns. The questions they ask shape what they filter for. Before reading, consider how a security analyst and a network analyst would look at the same capture differently.

  • A security analyst and a network analyst are both looking at the same capture. What would each one focus on first?
  • If an application analyst sees high response times but no TCP retransmissions, where should they look next?
Q1 — SECURITY VS NETWORK ANALYST FOCUS
A network analyst would first look at Layers 1–4: are there duplicate IPs (ARP conflicts), DHCP failures, routing issues, high TCP retransmission rates, or incorrect subnet configurations? They'd check the Conversations view, look at TCP flags, and examine routing paths. A security analyst would look for reconnaissance indicators — port scans, unexpected outbound connections, protocols on non-standard ports, DNS requests to unusual domains, or encrypted traffic to suspicious IPs. They might apply a filter for tcp.flags.syn==1 to find connection attempts, or check for large data transfers that could indicate exfiltration. Same capture, completely different mental models.
Q2 — HIGH RESPONSE TIMES WITH NO RETRANSMISSIONS
If response times are high but TCP shows no retransmissions, the network path is likely not the bottleneck. The application analyst should next look at the server's time-to-first-byte: how long between the client's request and the server's first response packet? If that delta is large (e.g., 2–3 seconds), the server application itself is slow — database query, backend processing, or application code. They could also examine application-layer headers (HTTP status codes, response sizes) and check whether slow queries are hitting a specific URL or endpoint. The network is clean; the problem is in the application or server stack.
Section 2

Types of Network Analysts

Three analyst roles use Wireshark differently. (1) Network/IT analysts focus on Layers 1–4 — connectivity, routing, duplicate IPs, DHCP failures. (2) Security analysts look for scanning, malware callbacks, unusual protocols, exfiltration. (3) Application analysts focus on Layers 5–7 — slow response times, malformed requests, application errors. Understanding your role determines which protocols and fields you focus on.

All three hats Most real-world analysts wear all three hats at different times. Wireshark handles all three perspectives — it's the same tool, just filtered differently.

💭 THINK FIRST · CAPTURE PLACEMENT

Where you place your capture device determines what you can see. A tap and a SPAN port both copy traffic, but they behave very differently under load — and in forensics, the difference can mean the difference between catching an attacker and missing the evidence.

  • You're investigating a suspected data exfiltration. Should you use a TAP or a SPAN port, and why?
  • A SPAN port shows a connection was established, but the user says the application never connected. How could a SPAN port cause this discrepancy?
Q1 — TAP VS SPAN FOR EXFILTRATION INVESTIGATION
Use a TAP. In a forensics investigation, completeness is mandatory — you cannot afford to miss any packet. A TAP is a passive inline hardware device that copies every frame regardless of switch CPU load, including malformed frames and error frames that a SPAN port might drop. A SPAN port shares the switch's CPU and can drop mirrored packets when the switch is busy, and some SPAN implementations do not forward frames with errors (which may be exactly what an attacker sends). For exfiltration forensics, a missed packet could be the packet that contains the stolen data or the C2 callback — a TAP guarantees you see everything.
Q2 — SPAN PORT DISCREPANCY EXPLANATION
A SPAN port under load can drop mirrored packets even while the actual switch forwarding path is unaffected. The switch's primary job is forwarding frames at line rate — mirroring is a secondary function that consumes extra CPU and memory. If the switch was busy when the critical application packets were transmitted, the SPAN port may have dropped those mirrored copies while the real packets were successfully forwarded. The result: the SPAN capture appears to show an incomplete or failed connection, while the actual hosts exchanged data normally. This is why SPAN ports can be misleading — what you see in the capture may not reflect what actually happened on the wire.
Section 3

Network Tap vs SPAN Port (Capture Placement)

Where you capture determines what you see. Two primary methods: (1) Network TAP (Test Access Point) — a passive physical device inserted inline that copies all traffic without affecting it. TAPs are the gold standard: they see all traffic including errors, and they don't miss packets under load. (2) SPAN port (Switched Port ANalyzer) / Mirror port — a switch feature that copies selected port traffic to a designated analysis port. SPAN is cheaper and easier to deploy but can drop packets under load, may not copy all error frames, and half-duplex SPAN can combine both directions into one direction.

SPAN under load SPAN ports can drop packets when the switch CPU is busy — a TAP never drops because it's passive hardware.
Forensics preference For security forensics, always prefer a TAP — a SPAN might miss the exact malicious packet that matters.
🧠
MENTAL NOTE
TAP = inline passive hardware, sees ALL traffic including errors, never drops packets. SPAN = switch feature, easier/cheaper, can miss packets under load, may not forward error frames. Forensics and baselining: prefer TAP. Quick field analysis: SPAN is acceptable.

💭 THINK FIRST · PATH OF A PACKET

Every packet travels through multiple layers — and at each router hop, something changes while something stays constant. Understanding what changes and what doesn't is fundamental to reading packet captures correctly.

  • A packet leaves a client and passes through two routers before reaching a server. What changes in the Ethernet header at each router, and what stays the same?
  • Wireshark captures at Layer 2. What information is available to you that would NOT be visible if you captured only at Layer 3 (IP)?
Q1 — WHAT CHANGES AT EACH ROUTER HOP
At each router hop, the Ethernet frame is stripped and rebuilt: the source MAC address changes to the router's outgoing interface MAC, and the destination MAC changes to the next hop's MAC (either the next router or the final server). What stays the same: the source and destination IP addresses (unless NAT is involved). This is fundamental to how routing works — IP addresses are end-to-end identifiers, while MAC addresses are only hop-to-hop identifiers valid on the local segment. If you capture on the same segment as the server, you'll see the last router's MAC as the source, not the original client's MAC. This is why you can't track the original client's MAC across routers.
Q2 — LAYER 2 CAPTURE VS LAYER 3 ONLY
Capturing at Layer 2 gives you: (1) The full Ethernet header — source and destination MAC addresses, allowing you to identify devices on the local segment even if they share an IP (ARP poisoning detection). (2) The Ethernet type field, which tells you the Layer 3 protocol (IPv4, IPv6, ARP, VLAN-tagged, etc.). (3) The Frame Check Sequence (FCS) — the Layer 2 error detection field. A bad FCS indicates physical-layer errors (bad cable, faulty NIC, EMI). (4) VLAN tags (802.1Q) if present. (5) ARP packets, which exist only at Layer 2 and are invisible to Layer 3-only captures. All of this context is lost if you only capture at the IP layer.
Section 4

Path of a Packet Through a Network

Trace the journey of a packet from application to wire: (1) Application generates data. (2) Transport layer (TCP/UDP) adds port numbers and breaks data into segments. (3) Network layer (IP) adds source/destination IP addresses and routing info. (4) Data Link layer (Ethernet) adds source/destination MAC addresses and frames the packet for the local segment. (5) Physical layer converts bits to electrical/optical/radio signals. At each router hop, the MAC addresses change (new hop's MAC) but the IP addresses stay constant. Wireshark captures at the Data Link layer — it sees the complete frame.

Wireshark captures at Layer 2 Wireshark captures at Layer 2 — you see the full Ethernet frame including the MAC header and FCS. Everything above that (IP, TCP, application) is payload inside the frame.
🧠
MENTAL NOTE
Packet journey: App → TCP/UDP (ports) → IP (addresses) → Ethernet (MACs) → Physical (bits). Wireshark captures at L2 — sees full Ethernet frame. MAC changes per hop; IP stays constant. FCS (frame check sequence) = Layer 2 error detection.
