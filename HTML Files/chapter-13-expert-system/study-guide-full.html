💡THINK FIRST · EXPERT INFORMATION OVERVIEW

The Expert Information System flags protocol anomalies automatically. Why is it more useful to open Expert Information BEFORE reading through the packet list?

HINT

Think about the difference between reactive analysis (reading packets looking for problems) and proactive triage (seeing a summary of known anomalies first).

MODEL ANSWER

Expert Information provides a prioritized list of anomalies — you immediately know if there are TCP errors, DNS failures, HTTP errors, checksum issues, or protocol violations in the capture. This guides where to spend your analysis time. Without Expert Info, you might spend an hour reading packets before discovering the key error. With Expert Info, you see '47 TCP retransmissions, 12 zero windows, 3 RSTs' in 10 seconds and can jump directly to those packets — reactive vs. systematic triage.

Expert Information System Overview

Open via Analyze → Expert Information. Also accessible by clicking the colored dot in the bottom-left status bar.

The Expert window groups detected anomalies by severity and event group, showing: group name, severity, description, protocol, and count. Double-click any entry to jump to the first occurrence in the packet list.

Status Bar Indicator

The dot in the bottom-left status bar shows the highest severity level currently in the capture:

  • Green dot — only Chat events (lowest severity)
  • Cyan dot — Note level events
  • Yellow/Orange dot — Warning level events
  • Red dot — Error level events (highest severity)

A red dot is your first visual signal to open Expert Information before anything else.

FIRST STEPWhen opening an unfamiliar capture, look at the status bar dot. Red = open Expert Information immediately. Check what types of errors dominate — this directs your entire analysis.

MENTAL NOTE
Expert Information: Analyze → Expert Information. Status bar dot = highest severity color (red = errors). Double-click any entry to jump to that packet. Expert Information is the first thing to check in any problem capture — it summarizes known anomalies automatically.

💡THINK FIRST · SEVERITY LEVELS

Expert Information uses four severity levels: Error, Warning, Note, and Chat. Give a specific example of a protocol event at each level.

HINT

Think about what constitutes a definite protocol error vs. something suspicious but possibly normal.

MODEL ANSWER

Error: TCP checksum error (definite protocol violation; packet corrupted or checksum offload issue). Warning: TCP retransmission (a segment was not acknowledged in time — indicates packet loss or congestion). Note: TCP SYN/FIN (session boundary events; not errors but noteworthy). Chat: TCP connection establishment (the three-way handshake; lowest severity, just informational logging of normal operations). Higher severity = more likely to be an actual problem.

Expert Information Severity Levels

Four severity levels from highest to lowest:

'Bad Checksum' at Error level = often checksum offload artifact, not real corruption. Warnings are most actionable for performance troubleshooting.

Expert Event Groups

Expert events are organized into groups by protocol and event type:

TCP Groups (most common)

  • Retransmission — segment sent again after timeout
  • Fast Retransmission — sent after 3 duplicate ACKs
  • Spurious Retransmission — retransmitted but original was received (ACK crossed in transit)
  • Duplicate ACK — same ACK number sent multiple times (signals gap in received data)
  • Zero Window — receiver's buffer full; sender must stop
  • Window Full — sent data fills the receiver's window
  • Keep-Alive — TCP keepalive probes
  • Out-of-Order — segments arriving out of sequence

Other Protocol Groups

  • DNS — query timeouts, error response codes (NXDOMAIN, SERVFAIL)
  • HTTP — 4xx and 5xx response codes
  • ICMP — destination unreachable, time exceeded messages
  • Checksum — bad TCP/UDP/IP checksums
🧠
MENTAL NOTE
TCP Expert groups: Retransmission (timeout-based), Fast Retransmission (3 dupacks), Spurious Retransmission (unnecessary), Duplicate ACK (gap signal), Zero Window (receiver buffer full), Window Full (sender-side). Spurious retransmissions indicate capture delay or ACK reordering, not actual loss.

💡THINK FIRST · FILTERING ON EXPERT INFORMATION

You want to show only packets that Wireshark flagged as Expert events of Warning level or higher. How do you build this display filter?

HINT

Expert severity values are numeric. What filter field represents the severity?

MODEL ANSWER

Use expert.severity which is a numeric field. Values: Chat = 200000, Note = 500000, Warning = 1000000, Error = 2000000. To show Warning and above: expert.severity >= 1000000. More practically, use specific TCP expert flag filters: tcp.analysis.retransmission or tcp.analysis.zero_window or tcp.analysis.duplicate_ack. Or simply tcp.analysis.flags as an existence test to show any packet that triggered a TCP expert event.

Filtering on Expert Information

Display filters to focus on expert events:

General Expert Filters

  • expert — all packets with any expert event
  • expert.severity >= 1000000 — Warning and above
  • expert.severity == 2000000 — Error level only

Specific TCP Expert Flags

  • tcp.analysis.flags — any TCP expert event (existence test)
  • tcp.analysis.retransmission — retransmissions
  • tcp.analysis.fast_retransmission — fast retransmissions
  • tcp.analysis.duplicate_ack — duplicate ACKs
  • tcp.analysis.zero_window — zero window advertisements
  • tcp.analysis.window_full — window full (sender-side)
  • tcp.analysis.lost_segment — gap detected in sequence numbers
  • tcp.analysis.out_of_order — out-of-order segments

From Expert Window

In the Expert Information dialog, right-click any event group → Apply as Filter — automatically generates the correct display filter for that event type.

QUICK WORKFLOW(1) Open Expert Information; (2) Sort by count, highest first; (3) Double-click the most frequent error to jump to a sample packet; (4) Apply as filter to see all packets of that type; (5) Investigate root cause from the filtered view.
🧠
MENTAL NOTE
Expert filters: expert.severity >= 1000000 (Warning+), tcp.analysis.flags (any TCP expert event), specific flags: tcp.analysis.retransmission, .duplicate_ack, .zero_window, .lost_segment. Right-click in Expert window → Apply as Filter auto-generates the correct expression. Sort Expert window by count to find the most frequent issue.

Review Questions

Q13.1
Describe the four Expert Information severity levels from highest to lowest and give one example of a TCP event at each level.
HINT

Think about what constitutes a definite error vs. something notable but possibly normal.

ANSWER

Error (red): TCP bad checksum — a definite protocol violation (or checksum offload artifact). Warning (orange): TCP retransmission — a segment was resent after timeout, indicating packet loss. Note (cyan): TCP SYN or FIN — connection establishment/teardown events; noteworthy but normal. Chat (gray): TCP connection established — logging of the completed three-way handshake; purely informational.

Q13.2
What display filter shows only packets that triggered TCP Expert events (any severity)?
HINT

Look for a filter field that tests if ANY tcp.analysis flag was set.

ANSWER

tcp.analysis.flags — this is an existence test that matches any packet where Wireshark set at least one TCP analysis flag (retransmission, duplicate ACK, zero window, out-of-order, etc.). It's the broadest TCP expert filter. For specific events: tcp.analysis.retransmission, tcp.analysis.zero_window, tcp.analysis.duplicate_ack, tcp.analysis.out_of_order.

Q13.3
You open a capture and see a red dot in the Wireshark status bar, but the only Error-level events in Expert Information are 'TCP Bad Checksum'. Should you be concerned about network corruption?
HINT

What commonly causes TCP checksum errors that are NOT real data corruption?

ANSWER

Not necessarily — 'TCP Bad Checksum' at the Error level is a very common false positive caused by NIC checksum offload. When capturing on the sending machine, the NIC fills in the TCP checksum in hardware after Wireshark copies the packet — Wireshark sees 0x0000 (unfilled) and flags it as a bad checksum. This is a Wireshark artifact, not actual network corruption. Fix: Edit → Preferences → Protocols → TCP → uncheck 'Validate the TCP checksum if possible'. If checksums are still bad after disabling validation, then investigate further for actual corruption.
