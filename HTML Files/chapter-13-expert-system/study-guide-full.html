💭 THINK FIRST · WIRESHARK EXPERT INFO

Wireshark's Expert Information system automatically classifies anomalous packets into four severity levels — Error, Warning, Note, and Chat — based on rules defined in each protocol's dissector. The TCP dissector generates the most expert notifications.

  • If you open a trace file and the Expert Info button on the Status Bar is red, what does that tell you before you've looked at a single packet?
  • Why might the Expert System mark a packet as Out-of-Order when it's actually a retransmission? What does this tell you about the limitations of automated analysis?

Model Answer 1: A red Expert Info button indicates that at least one packet in the trace file triggered an Error-level Expert notification. This is the highest severity — it means Wireshark found a malformed packet or a dissector error. You should open Expert Info immediately and start from the Errors tab. Warnings (yellow) and Notes (cyan) indicate less severe issues.

Model Answer 2: Wireshark detects Out-of-Order when a packet contains a lower sequence number than the previous packet in the stream. If the original packet of a retransmission occurred almost 800ms earlier, Wireshark may not relate the new packet to the original and instead flags it as Out-of-Order. This shows that the Expert System works on pattern matching within a sliding window — it can't always know the full context. Always verify by checking the Acknowledgment Number and comparing timestamps before concluding what type of event occurred.

Let Wireshark's Expert Information Guide You

Wireshark's Expert Information is defined in the dissectors. For example, the TCP Expert Information is maintained in the packet-tcp.c file. You can access this file on www.wireshark.org when you select Develop | Browse the Code.

Expert Information is classified into one of four categories:

CategoryColorDescription
ErrorsRedPacket or dissector errors
WarningsYellowUnusual responses from the application/transport
NotesCyan (Light Blue)Unusual responses that may be part of a recovery process
ChatsBlueInformation about the workflow
CommentsGreenPacket annotations (pkt_comment)
NoneGreyNo expert notifications

Each category is represented under a different tab in the Expert Infos window. There is also a Packet Comments tab (for packet annotations) and a Details tab that lists all Errors, Warnings, Notes, Chats and packet comments in a single location.

CAUTION Prior to Wireshark 1.8, TCP Fast Retransmissions fell under Warnings while Retransmissions and Duplicate ACKs fell under Notes. As of Wireshark 1.8, Fast Retransmissions were moved to Notes to keep the related traffic together. Check your Wireshark version when interpreting Expert Info tabs.

Launch Expert Info Quickly

Open the Expert Infos window by clicking on the Expert Info button on the left of the Status Bar or choose Analyze | Expert Info from the menu. The Expert Info button is color coded according to the highest level of classification of Expert Information listed.

Colorize Expert Info Elements

By default, Wireshark colors packets that match the tcp.analysis.flags coloring rule with a black background and red foreground. These packets are listed in either the Expert Info Warnings or Notes tabs. Expanding the Frame section shows the coloring rule that a packet matches.

For example, in Figure 177, the packet matches the Bad TCP coloring rule that uses the string tcp.analysis.flags && !tcp.analysis.window_update. You can change the colorization of these packets by editing the coloring rules.

Filter on TCP Expert Information Elements

Apply a display filter for tcp.analysis.flags to show packets that match the Expert Info Notes and Warnings triggers. Figure 178 shows the result of applying a tcp.analysis.flags display filter to an entire trace file. This is a fast method to detect TCP-based problems in a trace file.

TIP Consider creating and saving tcp.analysis.flags && !tcp.analysis.window_update as a Filter Expression button called "Bad TCP." When you open trace files, click your new Bad TCP Filter Expression button to locate the most common TCP-related network problems.

You can create a display filter to examine packets that meet a specific Expert Info severity level:

expert.severity==error
expert.severity==warn
expert.severity==note
expert.severity==chat

Another display filter is available for packets that are part of a specific Expert Info group (expert.group==<group>). Some key Expert Info groups include:

  • Checksum — a checksum was invalid
  • Sequence — sequence number was not correct or indicated a retransmission
  • Malformed — malformed packet or dissector bug
  • Protocol — invalid field value (possible violation of specification)

💭 THINK FIRST · TCP EXPERT NOTIFICATIONS

The TCP dissector defines 15 Expert notifications covering retransmissions, window problems, keep-alives, out-of-order packets, and port reuse. Understanding what triggers each one allows you to pinpoint whether a problem is at the sender, receiver, or network level.

  • What is the fundamental difference between a Retransmission (triggered by RTO expiry) and a Fast Retransmission (triggered by Duplicate ACKs)? Why does this matter for diagnosing packet loss?
  • A Zero Window condition points to a problem at the receiver, not the network. What specifically causes Zero Window, and what is the only recovery mechanism?

Model Answer 1: A Retransmission occurs when the sender's TCP Retransmission Timeout (RTO) timer expires — the sender gave up waiting for an ACK and resent the segment. A Fast Retransmission occurs within 20ms of receiving three identical ACKs (the original ACK plus 2 Duplicate ACKs) — the receiver proactively asked for the missing segment. Fast Retransmissions mean the receiver detected loss before the RTO, so the gap is smaller. Both indicate packet loss but Fast Retransmission is a sign that the fast recovery mechanism is working.

Model Answer 2: Zero Window occurs when the receiver's application is not reading data from the TCP receive buffer fast enough, causing the buffer to fill up completely. The receiver advertises a window size of zero, which stops the sender from sending any more data. The only recovery is a Window Update packet from the receiver — this packet carries no data but announces a non-zero window size. Until that Window Update arrives, data transfer is completely halted.

Key TCP Expert Concepts

What Triggers Duplicate ACK?

A receiver tracks incoming TCP sequence numbers. If a packet is detected as missing (the expected sequence number is skipped), the receiver generates an ACK indicating the next expected sequence number. A TCP host that supports Fast Recovery will continue to generate Duplicate ACKs. When the sender receives three identical ACKs (the original ACK and two Duplicate ACKs), it assumes there is packet loss and resends the missing packet regardless of whether the RTO expired. A high number of Duplicate ACKs may also indicate high latency.

What Triggers Zero Window?

When a receiver has no receive buffer space available, it sends Zero Window packets indicating the TCP window size is zero. This shuts down data transfer to the receiver. Data transfer will not resume until the receiver sends a Window Update packet with a sufficient window size. The underlying cause is an application that is not pulling data out of the receive buffer fast enough — this might be caused by an underpowered system, too many CPU-intensive applications, or a slow application.

What Triggers Out-of-Order?

Out-of-order packets often indicate that data traffic travels along multiple paths to get to the destination. Data streams traveling along multiple paths may encounter different latency times, triggering unnecessary retransmissions if a receiver times out waiting for a packet. These indications can also be seen when a queuing device does not forward packets in the same order in which they arrived.

What Triggers Window Update?

A Window Update packet contains no data but indicates that the sender's TCP window size field value has increased. These are actually good packets — a client just advertised a larger receive buffer space, indicating an application picked up some data from the receive buffer. Window Updates are the only recovery for a Zero Window condition.

CAUTION Prior to Wireshark 1.8, Window Updates were colorized as Bad TCP when they are actually good events. As of Wireshark 1.8, the Bad TCP coloring rule explicitly excludes Window Updates: tcp.analysis.flags && !tcp.analysis.window_update.

What Triggers 4 NOP in a Row?

"4 NOP in a row — a router may have removed some options" is triggered when Wireshark sees the illogical pattern 01:01:01:01 (4 NOPs) in a TCP SYN or SYN/ACK packet. A NOP is used to pad a TCP option so it ends on a 4-byte boundary. This is typically a router issue — a router has likely stripped off a TCP header option (such as Selective ACK) and replaced it with 4 NOPs. A server may believe a client does not support SACK because the option was wiped out in the TCP handshake.

You can create a coloring rule to identify these packets: tcp.options contains 00:00:00:00

TIP To disable the Expert feature, disable Analyze TCP sequence numbers in the TCP preferences. Note that your filter for tcp.analysis.flags will yield no results when this is disabled.

Case Studies

Case Study 1
Expert Info Catches Remote Access Headaches
Submitted by: Guy Talbot, CISSP, Conseiller Principal en Sécurité de l’Information et Réseautique

I am a network architect for a large organization. Our network consists of close to 2,000 sites and includes more than 100,000 workstations. I am usually not involved in network incidents unless: (1) things really get out of hand; (2) nobody else can figure out what is happening; or (3) my boss decides I need to get involved.

A technician came into my office indicating that the call center is receiving multiple complaints from users stating that Internet access is very slow or is not available at all. Level 1 and 2 technicians and even the network analysts couldn't understand the causes. All the affected sites are on low speed (ADSL) access and are using the Internet through a web proxy service. Level 1 technicians are already using the bypass option as a workaround, so this is a situation where I needed to get involved.

The local networks could almost certainly be eliminated as the cause because everything was fine when bypassing the web proxy service. But approximately 1,000 sites were still using the web proxy without issues. So we had a selective network problem.

We deployed "USBTSHARK" — USB drives with TShark and WinPcap configured as a service on Windows workstations, capturing all traffic in 200MB chunks. We sent these to local administrators at affected sites.

Looking at the different tabs of the Expert Info, I eventually came across an oddity — the number of Duplicate ACKs was a little on the high side. When I isolated the impacted sessions, I noticed that the Duplicate ACKs indicated lost frames and sometimes the lost frames were eventually resent and acknowledged. In certain situations, however, the web proxy server retransmitted the last acknowledged frame instead of retransmitting the lost frame. After a few rounds of this, the workstation would reset the session.

Analysis of the TCP header showed the session was using the SACK option. But the values of the TCP sequence numbers in the TCP header and those in the SACK option field were completely different — the Acknowledgement number was 4141, but the left and right edges in the SACK option were 975,687,856 and 975,690,616.

A multi-point trace revealed that the TCP headers were being modified between the two WAN routers. The WAN operator eventually confirmed that Cisco's Firewall blade module had a feature called "TCP randomization" designed to mitigate ISN vulnerability (RFC 793). This feature replaced ISNs with "more secure" ISNs but could not maintain the new sequence numbers in the SACK option field. The result: the proxy server received contradicting information about which frames had been received and repeatedly retransmitted the wrong segment. The TCP randomization feature could not be fully disabled in this configuration.

Note from Laura: For more information on Selective ACK (SACK), refer to Chapter 20. For details on the TCP randomization feature, visit www.cisco.com/warp/public/707/cisco-sa-20010301-ios-tcp-isn-random.shtml.

TL;DR — Chapter Summary

Wireshark's Expert System offers a quick look at traffic that hints of network problems or unusual activity. There are six sections in the Expert System: Errors, Warnings, Notes, Chats, Details and Packet Comments. The Expert Info button on the Status Bar indicates the highest level of Expert notification triggered in the trace file. Clicking on this button is the fastest way to launch the Expert Infos window.

Expert Info details for a protocol are maintained in the protocol's dissector. TCP has the largest number of Expert notifications defined at this time. To view all the TCP Expert notifications, apply a display filter for tcp.analysis.flags. By default, Wireshark has a coloring rule for this traffic.

You should always verify problems identified by the Expert System.
