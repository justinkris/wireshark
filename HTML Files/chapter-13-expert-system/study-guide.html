💭 THINK FIRST · EXPERT SYSTEM OVERVIEW

The expert system processes every packet against hundreds of protocol heuristics and presents the results in one consolidated view. It's the fastest triage tool in Wireshark — one glance at the status bar badge tells you whether the capture has serious problems.

  • You open a capture and the expert status bar badge is red. Before reading a single packet, what do you already know?
  • There are 2,000 packets in a capture but the Expert Information dialog shows only 12 events. What does this tell you about the other 1,988 packets?
Q1 — RED BADGE MEANING
At least one packet in the capture triggered an Error-level event — the most severe category. This could be a malformed packet, a bad checksum, or a serious protocol violation. You don't yet know which protocol or packet, but the expert system has flagged something worth investigating immediately. Open Analyze → Expert Information to see the full list sorted by severity.
Q2 — 12 EVENTS IN 2,000 PACKETS
The other 1,988 packets generated no expert events — they are protocol-conformant from Wireshark's perspective. Expert events are the exception, not the rule; most normal traffic generates no events at all. The 12 events are exactly where to start your investigation.
Section 1

Expert Information System Overview

Wireshark's Expert Information system automatically analyzes each packet and flags protocol anomalies using built-in heuristics. It runs continuously in the background as packets are captured or loaded.

Access: Analyze → Expert Information, or click the colored status bar badge in the bottom-left corner of the Wireshark window.

Status badge colors:

  • Red — Error (highest severity): at least one serious protocol violation detected.
  • Yellow/Orange — Warning: probable problems such as TCP retransmissions.
  • Cyan/Teal — Note: informational events worth reviewing.
  • Gray — Chat: normal protocol behavior events only.
  • No badge — no expert events detected.

The Expert Information dialog lists all events grouped by severity. Double-click any event to jump directly to that packet in the Packet List.

First step — check the expert badge The expert badge is the first thing to check after opening any unfamiliar capture. Its color tells you in one glance whether there are serious problems (red) or the capture looks clean. Then open Expert Information for the full event list.

💭 THINK FIRST · SEVERITY LEVELS

The four severity levels create a triage hierarchy. Errors demand immediate attention; Warnings are probable problems; Notes are informational context; Chat events are normal protocol behavior. Working top-down through these levels focuses your investigation on what matters most.

  • Expert Information shows a Warning for "TCP Retransmission." Is this always a network problem? What additional context do you need?
  • What is the most likely reason Expert Information shows many Error-level checksum events when you capture your own machine's traffic?
Q1 — TCP RETRANSMISSION WARNING IN CONTEXT
Not necessarily. A single TCP retransmission in a 10,000-packet capture might be a momentary glitch. Context needed: count of retransmissions as a percentage of TCP traffic (above 1% is significant), whether retransmissions cluster in time (visible on the IO Graph), and whether it's a fast retransmit (triggered by 3 dup ACKs, milliseconds gap) or a timeout retransmit (1+ second gap). Volume and timing determine severity.
Q2 — CHECKSUM ERRORS ON LOCAL TRAFFIC
TCP/UDP Checksum Offload — modern NICs compute checksums in hardware after the OS has already passed the packet to Wireshark. Wireshark captures the pre-checksum packet and reports the checksum as incorrect, but the checksum is computed correctly by the NIC before transmission. This is a false positive. Fix: Edit → Preferences → Protocols → TCP → uncheck "Validate TCP checksum if possible." The same setting exists for UDP.
Section 2

Expert Information Severity Levels

Expert events are assigned one of four severity levels, from most to least critical:

  1. Error — serious protocol violations, malformed frames, application-level errors. These prevent or severely disrupt normal operation.
  2. Warning — conditions indicating likely problems: TCP retransmissions, out-of-order segments, duplicate ACKs, zero window events.
  3. Note — informational events worth noting but not necessarily problems: TCP resets, connection close events, window updates.
  4. Chat — normal protocol events: TCP SYN, HTTP GET requests, DNS queries. Expected in every capture.

Triage strategy: always address Errors first, then Warnings. Notes and Chat are context, not problems.

💭 THINK FIRST · EVENT GROUPS

Expert events are grouped by root cause, not just severity. The Sequence group identifies TCP reliability problems; the Application group surfaces application-layer errors; the Malformed group marks corrupt packets. Knowing which group matters for your investigation focuses your filter and your attention.

  • You're troubleshooting slow HTTP responses. Which Expert Information event group should you check first?
  • You see both Sequence-group Warnings and Application-group Warnings. What does the combination of TCP retransmissions AND HTTP 503 responses suggest about the root cause?
Q1 — WHICH GROUP FOR SLOW HTTP
Start with the Application group — it catches HTTP 4xx/5xx response codes that indicate server-side errors. Then check the Sequence group — TCP retransmissions under Application-layer errors would indicate the network is also struggling under the same load. Checking both together reveals whether it's a pure application problem or a combined network-and-application problem.
Q2 — RETRANSMISSIONS + HTTP 503 COMBINATION
The combination suggests the web server is overloaded: TCP retransmissions indicate the server (or path to it) is dropping packets under load, while HTTP 503 (Service Unavailable) is the server explicitly telling clients it cannot handle more requests. Root cause is likely server resource exhaustion — not a pure network problem. The fix is at the server or load balancer, not the network path.
Section 3

Expert Event Groups

Expert events are organized into groups that reflect the root cause category, making it easier to focus your investigation:

  • Sequence — TCP sequence number problems: retransmissions, duplicate ACKs, lost segments, out-of-order. Most actionable for performance problems.
  • Checksum — detected checksum errors. Usually a NIC offload artifact. Typically suppress in preferences.
  • Malformed — packets violating protocol structure: incomplete headers, fields outside allowed ranges.
  • Application — application-layer errors: HTTP 4xx/5xx status codes, FTP error codes, DNS NXDOMAIN and SERVFAIL.
  • Protocol — general protocol events: SYN, FIN, RST. Typically Note severity.
  • Request/Response — response time tracking for matched request-response pairs.

💭 THINK FIRST · FILTERING EXPERT INFO

Expert events are filterable using display filter fields, letting you integrate expert analysis with the standard packet list view. This is more powerful than the Expert Information dialog alone — you can combine expert filters with protocol filters to narrow to exactly the problematic subset.

  • Write a display filter that shows only packets with Expert Warning or higher severity.
  • The expert system shows "TCP Previous segment not captured." Is this always actual packet loss, or could it be a Wireshark artifact?
Q1 — FILTER FOR WARNING OR HIGHER
expert.severity >= 8 (Warning = 8, Error = 32 in Wireshark's internal encoding). Some versions require _ws.expert.severity >= 8. If one form doesn't work in your Wireshark version, try the other — both access the same data.
Q2 — PREVIOUS SEGMENT NOT CAPTURED
It can be either. If seen on the very first packets of a capture of an already-established connection, it's a capture artifact — Wireshark missed the earlier segments because the capture started mid-stream. If seen mid-capture during an established connection where all prior segments were present, it's more likely actual packet loss. Distinguish by checking whether the gap occurs at the start of the capture (artifact) or occurs after previously unbroken coverage (real loss).
Section 4

Filtering on Expert Information

Expert system data is accessible as display filter fields, enabling integration with the packet list and combination with other protocol filters.

FilterWhat It Shows
expert.severity >= 32All Error-level events
expert.severity >= 8Warnings and higher (Warning + Error)
expert.group == "Sequence"All TCP sequence issues
expert.message contains "Retransmission"All retransmission events
expert.message contains "Zero Window"Zero window events
_ws.expert.severity >= 8Alternative prefix (some Wireshark versions)

Severity numeric values: Chat = 2, Note = 4, Warning = 8, Error = 32.

expert.group values: "Sequence", "Checksum", "Malformed", "Application", "Protocol", "Request/Response".

Version compatibility — expert prefix Some Wireshark versions use the _ws.expert.severity prefix instead of expert.severity. If one doesn't work, try the other. Both access the same expert system data.
