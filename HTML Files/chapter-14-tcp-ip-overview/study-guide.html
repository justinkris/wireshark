💭 THINK FIRST · THE PROTOCOL STACK

The TCP/IP stack is not just an academic model — every field Wireshark shows you belongs to a specific layer. Understanding which layer owns which header tells you exactly where to look when something goes wrong.

  • When Wireshark shows you a frame, it expands into multiple protocol headers. Which layer of the TCP/IP model owns each of those headers, and what is each header's job?
  • A packet has an IP TTL of 1 and is traveling through a router. What happens — and which layer makes that decision?
Q1 — WHICH LAYER OWNS WHICH HEADER?
The Ethernet frame header is Layer 2 (Data Link) — it carries source/destination MAC addresses and the EtherType field that identifies the Layer 3 protocol. The IP header is Layer 3 (Network) — it carries source/destination IP addresses, TTL, and the Protocol field identifying the Layer 4 protocol. TCP/UDP headers are Layer 4 (Transport) — they carry port numbers, sequence/acknowledgment numbers (TCP), and connection state. The application data is Layer 7 (Application). Each layer adds its own header when sending and strips it when receiving — a process called encapsulation and decapsulation.
Q2 — TTL=1 AT A ROUTER
The router decrements the TTL from 1 to 0 and drops the packet. The router then sends an ICMP Time Exceeded message back to the original sender. This is a Layer 3 (Network layer) decision — routers operate at Layer 3 and make forwarding decisions based on the IP header. The TTL mechanism prevents packets from looping forever in mis-configured networks. Traceroute exploits this behavior deliberately by sending packets with TTL=1, 2, 3, etc. to map each hop's IP address via the ICMP Time Exceeded replies.

Wireshark maps directly to these layers When you expand a frame in Wireshark's packet details pane, each collapsible section corresponds to one protocol layer: Frame → Ethernet II → Internet Protocol → TCP/UDP → Application payload.

Encapsulation and Decapsulation

When a host sends data, each layer encapsulates the data from the layer above by wrapping it in its own header (and sometimes trailer). When a host receives a frame, each layer decapsulates — strips its own header and passes the remainder up. Routers only examine and modify Layers 1–3; they don't touch TCP/UDP headers or application data.

MENTAL NOTE
TCP/IP has 4 layers: Application, Transport (TCP/UDP), Internet (IP/ICMP/ARP), Network Access (Ethernet/Wi-Fi). Wireshark shows each layer as an expandable section. Routers read/modify Layers 1–3 only. Encapsulation adds headers going down the stack; decapsulation strips them going up.

💭 THINK FIRST · ADDRESS RESOLUTION CHAIN

Typing a URL triggers a cascade of protocol exchanges before a single byte of HTTP data is sent. Understanding this multi-step chain lets you instantly locate where a connection attempt stalled in a packet capture.

  • What is the exact sequence of protocol steps a host performs before it can send the first TCP SYN packet to a remote web server by hostname?
  • ARP only works on the local subnet. How does a host reach a server on a different network — and what role does the default gateway play in the ARP conversation?
Q1 — FULL SEQUENCE BEFORE THE FIRST SYN
First, the host checks its local DNS cache. If no hit, it sends a DNS query (UDP port 53) to its configured DNS server and waits for the A record response containing the server's IP address. Next, it checks its ARP cache for the destination's MAC address. If the destination is on the same subnet, it ARPs for the server's MAC directly. If it's on a different subnet (the typical case for internet servers), it ARPs for the default gateway's MAC address instead. Once it has the gateway's MAC, the host builds the Ethernet frame with the gateway's MAC as destination, puts the server's IP in the IP header, and sends the first TCP SYN. This DNS → ARP → TCP sequence is visible in every fresh connection capture.
Q2 — REACHING A DIFFERENT NETWORK VIA GATEWAY
ARP is a broadcast protocol and broadcasts don't cross router boundaries — so a host can't ARP directly for a server on another subnet. Instead, the host compares the destination IP against its own subnet mask. If the destination is outside its subnet, the host sends the packet to its default gateway (router). It ARPs for the gateway's MAC address (if not cached), puts the gateway's MAC in the Ethernet frame's destination field, but keeps the final server's IP address in the IP header. The router then forwards the packet toward the server, substituting its own outbound MAC address at each hop. The IP addresses remain constant end-to-end; MAC addresses change at every hop.
Section 2

The Address Resolution Chain

Before a host can send application data to a remote server, it must resolve three things: the server's IP address (DNS), the next-hop MAC address (ARP), and establish a transport connection (TCP). In Wireshark, you'll see this chain play out in sequence on every fresh connection.

Step-by-Step: Browser Requests a Web Page

  1. DNS Query: Host checks local cache. Cache miss → sends UDP DNS query to configured DNS server → receives A record with server IP.
  2. ARP (for gateway): Host determines server is on a remote subnet → broadcasts ARP Request for default gateway's MAC → receives ARP Reply with gateway MAC.
  3. TCP Handshake: Host sends SYN to server IP (framed to gateway MAC) → SYN-ACK → ACK. Connection established.
  4. HTTP Request: Host sends GET request. Server responds with page content.
Exam tip: MAC vs IP addresses across hops The destination IP address in the IP header stays constant from source to destination. The destination MAC address in the Ethernet header changes at every router hop — it always holds the MAC of the next-hop device, not the final destination.

Cache Behavior

Both DNS and ARP use caches to avoid repeating lookups. If you see a connection capture without a DNS or ARP exchange at the start, the host already had the answer cached from a prior session. To force the full chain in a test capture, flush the caches first: ipconfig /flushdns (Windows) and arp -d *.

🧠
MENTAL NOTE
Resolution chain order: DNS → ARP → TCP handshake → Application data. Remote subnet = ARP for gateway MAC (not server MAC). IP address = constant end-to-end. MAC address = changes at every router hop. Missing DNS or ARP at connection start = cached result.
Analogy
The resolution chain is like mailing a physical letter to someone you only know by name. First you look up their street address in a directory (DNS). Then you check whether they live on your street or need to go via the post office (ARP / gateway check). If they're far away, you hand the letter to your local post office (gateway), who stamps it and forwards it — but your original addressee's name on the envelope never changes, just the hands that carry it.

💭 THINK FIRST · THE WIRESHARK ANALYSIS PROCESS

Wireshark doesn't tell you what's wrong — it shows you the packets and you draw the conclusions. Having a consistent analysis workflow means you find the root cause faster and don't waste time chasing symptoms.

  • What should you do first when you open an unfamiliar trace file — before applying any display filters or diving into individual packets?
  • Why is it important to establish a baseline of "normal" traffic before trying to identify problems?
Q1 — FIRST STEPS WITH AN UNKNOWN TRACE FILE
Start with Statistics → Capture File Properties to understand the time range, packet count, and data rate. Then use Statistics → Protocol Hierarchy to see which protocols are present and their proportions — this gives you a bird's-eye view before you read a single packet. Next, check Statistics → Conversations and Statistics → Endpoints to identify the most active hosts and connections. Only after this survey should you apply display filters and dive into individual streams. Jumping straight to packets without context means you may spend time on irrelevant traffic.
Q2 — WHY BASELINE FIRST?
Without knowing what normal looks like, you can't reliably identify abnormal. A baseline tells you the expected protocol mix, typical response times, normal bandwidth utilization, and which hosts communicate with which. When you then capture a "problem" scenario, you compare it against the baseline — deviations point you toward the root cause. For example, if you don't know that a certain server normally generates 5% of traffic, you might flag its traffic as suspicious. Baselines are especially critical for security analysis where subtle behavioral changes indicate intrusion.
Section 3

The Wireshark Analysis Process

Effective packet analysis follows a structured workflow. Without a process, analysts spend hours in the weeds of individual packets without finding the cause. The recommended approach is top-down: start broad, then narrow.

Analysis Workflow

  1. Survey the trace: File properties, Protocol Hierarchy, Conversations, Endpoints.
  2. Identify anomalies: Unexpected protocols, abnormal talkers, error packets.
  3. Filter to the problem area: Apply display filters to narrow scope.
  4. Follow the stream: Use Follow TCP/UDP Stream to read the full conversation.
  5. Examine timestamps: Look for large delta times that indicate delays.
  6. Form and test hypotheses: Apply what you know about the protocol to explain each anomaly.
Key statistics windows Protocol Hierarchy (Statistics menu) shows the breakdown of all protocols in a capture as a percentage of total packets and bytes. It's the single fastest way to spot unexpected protocols or dominant traffic types.

Capture Location Matters

Where you place a capture determines what you can see. Capturing on the client side shows what the client sends and receives. Capturing on the server side shows what the server sees. Capturing on both sides simultaneously can reveal asymmetric routing problems where packets take different paths in each direction.

🧠
MENTAL NOTE
Analysis order: Survey → Identify anomalies → Filter → Follow stream → Check timestamps → Hypothesize. Always start with Statistics → Protocol Hierarchy. Capture location determines visibility — client-side vs server-side captures show different perspectives. Baseline before problem comparison.

💭 THINK FIRST · CASE STUDY

In a real trace, you won't see just one protocol — you'll see the full resolution chain unfold in order. The ability to read that chain and spot a missing step is what separates a skilled analyst from someone who just knows filters.

  • In a trace file, you see a TCP SYN immediately followed by a TCP RST from the destination. What does this tell you about the destination host?
  • A host sends repeated DNS queries but you never see any DNS responses in the trace. What are the two most likely explanations?
Q1 — SYN FOLLOWED BY RST
A TCP RST from the destination in response to a SYN means the destination host is reachable at the IP layer (the RST came back), but there is no service listening on that TCP port. The host received the SYN, found no process bound to that port, and immediately sent a RST to reject the connection. This is different from a timeout (where nothing comes back) and from an ICMP Port Unreachable (which would come from a router, not the destination host). This pattern is useful for confirming whether a service is running on a specific port.
Q2 — DNS QUERIES WITH NO RESPONSES
The two most likely causes are: (1) The DNS server is unreachable or down — the queries leave the host but the server never receives them, or the server is overwhelmed and dropping requests. (2) The capture point is asymmetric — you are only capturing outbound traffic from the client. The DNS responses are traveling on a different path and are not visible in this capture. Always confirm whether a missing response means "never sent" or "captured on a different interface/VLAN." The easiest way to distinguish these is to check whether any traffic from the DNS server's IP appears in the capture at all.
Section 4 · Case Study

Reading the Resolution Chain in a Capture

A fresh connection to a new remote server produces a predictable sequence in Wireshark. Knowing this sequence lets you instantly spot which step failed when a connection doesn't work.

What a Healthy Capture Looks Like

  1. Packet 1: DNS query from client to DNS server (UDP, port 53)
  2. Packet 2: DNS response from DNS server — A record with IP
  3. Packet 3: ARP broadcast — "Who has 192.168.1.1?" (gateway)
  4. Packet 4: ARP reply — gateway MAC address
  5. Packet 5: TCP SYN (client → server, Ethernet destination = gateway MAC)
  6. Packet 6: TCP SYN-ACK (server → client)
  7. Packet 7: TCP ACK — handshake complete
  8. Packet 8+: Application data (HTTP GET, etc.)
Diagnostic shortcut If a connection fails, find the last successful packet in this sequence. Everything after it is where the problem lies. If you see DNS responses but no SYN, the connection isn't being attempted. If you see SYNs with no SYN-ACK, the server is unreachable or the port is blocked.
Cache hits skip steps A returning visitor will skip DNS (IP already cached) and ARP (MAC already cached). The capture then starts directly at the TCP handshake. This is normal — not a problem.
🧠
MENTAL NOTE
Fresh connection sequence: DNS query → DNS response → ARP → TCP SYN → SYN-ACK → ACK → Data. Find the last successful step to locate the failure point. SYN + RST = port closed on destination. SYN + no reply = host unreachable or port filtered. No DNS responses = DNS server down OR capture asymmetry.
