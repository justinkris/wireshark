    TCP/IP Functionality Overview

    💡THINK FIRST · TCP/IP FUNCTIONALITY OVERVIEW▾

    The TCP/IP stack is described as layered — ARP at the link layer, IP at the internet layer, TCP/UDP at transport, and applications above. Network faults are often diagnosed by working from the bottom up. If a client can successfully ARP and get a response, but cannot complete a DNS query, which layer has a problem — and what does that tell you about where to look next in the trace?

    HINT

    ARP success means the link layer and local network are working. DNS uses UDP port 53. If ARP works but DNS fails, think about what sits between Layer 2 success and Layer 7 application failure.

    MODEL ANSWER

    A successful ARP means the link layer is functional and the client can reach the local network. DNS uses UDP at transport (Layer 4) and IP at the internet layer (Layer 3). If ARP works but DNS fails, the problem is somewhere in IP routing, the UDP transport, or the DNS application itself — not the local link. In Wireshark you would filter dns to see if queries are being sent and check whether responses arrive, then check if ICMP Destination Unreachable messages appear (indicating routing or port problems). Working bottom up prevents chasing application-layer symptoms when the real fault is a routing table entry or a misconfigured DNS server IP.

    In order to troubleshoot or secure a network using Wireshark, you must possess a solid understanding of TCP/IP communications. The next twelve chapters examine the most common traffic patterns seen on a TCP/IP network.

    Key TCP/IP protocols at each layer:

    • IPv4/IPv6 (Internet layer): routable network layer protocol used by routers to make forwarding decisions. Layer 3 switches route traffic well.
    • TCP (Transport layer): connection-oriented, provides sequencing and acknowledgment services. Mapped to Layer 4 (Transport Layer) of the OSI Model.
    • UDP (Transport layer): connectionless transport layer service. Port fields in UDP headers define the application in use.
    • RIP and OSPF (Internet layer): routing protocols that provide network and path information exchange between routing devices.
    • ICMP/ICMPv6 (Internet layer): provides network information and is used for ping. ICMPv6 checks for duplicate IPv6 addresses.
    • DNS: hostname to IP address resolution. When you type telnet station3, DNS resolves station3 to its IP address.
    • DHCP: dynamic client configuration — IP address, default gateway, DNS server settings and more.
    • ARP: hardware address lookup for local devices. Also enables duplicate IPv4 address detection.

    Many network faults or breaches can be attributed to the TCP/IP protocol or application layer. When troubleshooting, work from the bottom up: physical and data link layers first (can packets be sent with correct checksums?), then move up the stack to identify where the problem becomes visible.

    Follow the Multi-Step Resolution Process

    💡THINK FIRST · THE MULTI-STEP RESOLUTION PROCESS▾

    TCP/IP uses up to six resolution steps before a single packet can be sent. Some steps generate network traffic; others are silent. If you open a trace file and see only a TCP SYN as the very first packet — no ARP, no DNS — what can you conclude about the state of the client's caches before the capture began?

    HINT

    Each resolution step either uses a cache (silent) or generates traffic (visible). If you see no ARP and no DNS at the start of a trace, both caches already had the required information.

    MODEL ANSWER

    A trace that begins immediately with a TCP SYN (no ARP, no DNS) tells you: (1) the client already had the target MAC address in its ARP cache — no ARP broadcast needed; (2) the client already had the target IP address in its DNS resolver cache (or used a local hosts file) — no DNS query needed; and (3) the port number was found in the local etc/services file (silent). All resolution work was done from cache. This is normal for repeat connections within the TTL window. To see the full resolution process, clear the ARP cache (arp -d) and DNS cache (ipconfig /flushdns on Windows) before capturing.

    TCP/IP uses a multi-step resolution process when a client communicates with a server. Using the example of a client (10.1.0.1/8) connecting via FTP to CORPFS1 (10.2.99.99):

    Step 1: Port Number Resolution

    The user types ftp CORPFS1. FTP uses port 21 for commands. The client looks up the port number in the etc/services file. The port is placed in the TCP header destination port field. The client uses a dynamic (ephemeral) source port.

    Does NOT generate network traffic.

    Step 2: Network Name Resolution (Optional)

    If a hostname (not an IP) was used, the resolver process runs in order: (1) check DNS resolver cache, (2) check the local hosts file, (3) send a DNS query to the configured DNS server.

    If no DNS server responds, the client cannot build the packet and the connection fails.

    May or may not generate traffic (cache hit = no traffic; DNS query = traffic).

    Step 3: Route Resolution — When Target is Local

    The client compares its own network address to the target using the subnet mask. With client IP 10.1.0.1 and mask 255.0.0.0 (network 10.0.0.0/8), CORPFS1 at 10.2.99.99 is on the same network — go to Step 4.

    Different masks yield different results — a wrong subnet mask is a common cause of ARP-for-remote-target symptoms.

    Does NOT generate network traffic.

    Step 4: Local MAC Address Resolution

    If the target is local, the client checks its ARP cache for the hardware address. If not cached, it sends an ARP broadcast. Upon receiving an ARP reply, the client updates its ARP cache.

    May or may not generate traffic (cache hit = no traffic; ARP query = traffic).

    Step 5: Route Resolution — When Target is Remote

    If the target is remote, the client checks its local routing tables for a host or network route. If no specific entry exists, the client uses the default gateway — sending the packet to the gateway and trusting it knows the route.

    Does NOT generate network traffic.

    Step 6: Local MAC Address Resolution for a Gateway

    The client resolves the MAC address of the next-hop router (default gateway). Checks the ARP cache first; sends an ARP broadcast if not cached.

    May or may not generate traffic (cache hit = no traffic; ARP query = traffic).

    Build the Packet

    💡THINK FIRST · BUILD THE PACKET & TRACE ANALYSIS▾

    When you examine a trace file and see DNS queries at the start but no ARP, what does that tell you about which caches were populated and which were empty? And if you see the opposite — ARP at the start but no DNS — what can you infer about the client connection?

    HINT

    Each resolution step either uses cache (produces no packets) or queries the network (produces visible packets). Use the presence or absence of ARP and DNS as evidence about cache state.

    MODEL ANSWER

    DNS queries at the start but no ARP means the client needs to resolve the hostname to an IP (DNS cache was empty or expired) but already has the MAC address of the target or gateway in its ARP cache. No ARP but DNS queries means the MAC cache is populated but the IP is not known. No ARP and no DNS means both caches were warm — the client had everything needed to send the first packet immediately. If the client ARPs for an IP that appears to be on a remote network, suspect a misconfigured subnet mask that is too short, causing the client to incorrectly believe a remote host is local.

    📷Figure 182 — open trace file in Wireshark to view this screen

    When all resolution steps complete successfully, the client has gathered:

    • Destination MAC address (from ARP cache or ARP query)
    • Destination IP address (from DNS cache, hosts file, or DNS query)
    • Source and destination port numbers (from etc/services)

    This is all the information needed to build and send the first packet.

    📷Figure 183 — open trace file in Wireshark to view this screen
    Figure 183. Following the process of browsing to a website [http-riverbed-one.pcapng]

    Examining http-riverbed-one.pcapng (cleared DNS and browser cache before visiting www.riverbed.com):

    1. No ARP queries in the trace file. The client (24.6.173.220) already has the required MAC addresses in its ARP cache. Run arp -a on the client to view ARP cache contents.
    2. DNS queries for www.riverbed.com appear — the client does not have the IP in DNS cache. The client runs both IPv4 and IPv6 stacks, so it queries both A record (IPv4) and AAAA record (IPv6). The DNS response in packet 2 provides the IPv4 address (208.70.196.59) and caches it for 2 minutes (the TTL). The AAAA response in packet 4 contains only the authoritative name server — no IPv6 address — so the client cannot reach www.riverbed.com over IPv6.
    3. Packet 5: TCP SYN using dynamic source port 8369 to destination port 80, sent to the MAC address of the default gateway and IP address of www.riverbed.com.

    Visiting again via http-riverbed-two.pcapng (89 seconds later): no DNS queries at the start — the client now has the desired IP addresses in DNS cache. Some earlier DNS responses had very short TTLs, so some names need re-resolving. Total packet count is 319 vs. 1,492 in the first trace — page elements loaded from browser cache.

    If you opened http-riverbed-one.pcapng and did not see HTTP 200 OK in the Info column of packet 13, consider disabling the Wireshark preference "Allow subdissector to reassemble TCP streams" while analyzing these trace files.

    Watching the traffic enables us to point the finger at the problem — and also point the finger at the areas that are not part of the problem.

    When our email connections stopped working suddenly and Outlook sat in a state of confusion, we grabbed a trace file of the traffic.

    We could see the ARP process followed by the DNS request for smtp.packet-level.com. The response provided the correct IP address of the SMTP server. Then the problem appeared.

    We saw the client make a handshake attempt to the SMTP server. No answer. The client tried again and again. Still no answer.

    The problem could be along the path or at the SMTP server itself. We saw successful TCP handshake processes when trying to connect to the SMTP server on another port we knew was open. We could connect from another location on that other port as well. It felt like the path was not the problem — the SMTP server was the problem.

    Restarting the SMTP server restored access to email services.

    By examining the traffic we could rule out problems with: the local network interface card, the ARP discovery process, and the DNS server. Analyzing the traffic takes out so much of the guesswork.

    TL;DR — Chapter 14 Summary

    TCP/IP Analysis Overview

    TCP/IP communications must follow a standard set of rules that includes numerous resolution processes to determine the port numbers to use, the target IP address, the route to use and the target hardware address.

    If one of the resolution processes is unsuccessful, a host cannot communicate with another host. Some of the resolution processes generate traffic on the network — others do not. In some instances, a host can obtain information from cache or local tables. If the information cannot be obtained locally, the host can query a target on the network.

    These resolution processes include port number resolution, network name resolution, route resolution, and local MAC address resolution (for the target or a gateway). DNS and ARP queries are commonly seen during the resolution process.

    Review Questions

    Q14.1
    What file is referenced to determine the port to use in a communication when the application does not explicitly specify a port?
    HINT

    This file exists on every host and maps service names to well-known port numbers. It is consulted during Step 1 of the resolution process.

    ANSWER

    The client references the etc/services file to determine which port to use for a communication. For example, FTP is mapped to port 21 in this file. The port number from this file is placed in the TCP (or UDP) header destination port field of the outgoing packet.

    Q14.2
    What can you assume when a client does not generate a DNS query to resolve a target's IP address?
    HINT

    There are two ways a client can know an IP address without querying a DNS server. Think about the two places a resolver checks before sending a DNS query.

    ANSWER

    When a client does not generate a DNS query to resolve a target IP address, you can assume the client either has the target IP address in its DNS resolver cache (from a previous query that has not yet expired) or the client has a local hosts file that maps the hostname to an IP address. Either source allows the resolver to return the answer without network traffic.

    Q14.3
    What configuration fault might cause a host to ARP for a remote target?
    HINT

    ARP is non-routable — it only works on the local network segment. If a client ARPs for a remote target, it must believe that target is local. What determines whether a target is considered local or remote?

    ANSWER

    The client might have a subnet mask that is too short. For example, if a client with IP address 10.2.4.5 has a subnet mask of 255.0.0.0 instead of 255.255.0.0, the client calculates that all 10.x.x.x addresses are on the local network. It will ARP for any target with an IP starting with 10 — even hosts on remote networks across a router. Since ARP is non-routable, the ARP broadcast never reaches the remote target, and the connection fails.

    Quick Reference

    etc/services
    File on every host mapping service names to port numbers. Referenced in Step 1 (Port Number Resolution). Does not generate traffic.
    DNS Resolution (Step 2)
    Order: DNS resolver cache → local hosts file → DNS server. If all fail, client cannot build the packet.
    ARP Resolution (Step 4)
    Local MAC address lookup. Check ARP cache first; broadcast if not cached. Run arp -a to view current ARP cache.
    Default Gateway (Step 5/6)
    Used when target is remote. Client sends to gateway MAC and trusts it knows the route. ARP resolves gateway MAC.
    No ARP in trace
    Client already had the required MAC address in ARP cache before capture began.
    No DNS in trace
    Client already had the target IP in DNS resolver cache or has a hosts file entry.
    ARP for remote target
    Suspect misconfigured subnet mask that is too short — client incorrectly thinks remote host is local.
