💭 THINK FIRST · THE TCP/IP STACK

TCP/IP is a layered protocol suite. Routers are called "Layer 3 devices" and switches "Layer 2 devices" — but these designations come from the OSI Model, not the TCP/IP Model. Understanding which protocols operate at which layer tells you exactly where a problem can occur.

  • Why do network engineers still call switches "Layer 2 devices" even though TCP/IP — not OSI — is what actually runs on the network? What would be lost if we abandoned the OSI layer numbering?
  • ARP, DNS, DHCP, and ICMP all provide supporting services. Which of these generates network traffic that is visible in Wireshark, and which can succeed silently from cache?

Model Answer 1: The OSI layer numbering gives engineers a vendor-neutral shorthand for describing where a device operates — "Layer 2" instantly communicates MAC-address switching, "Layer 3" means IP routing. Without it, every vendor would invent their own vocabulary. The TCP/IP Model only has 4 layers with less granular distinctions, so the OSI Model's 7-layer structure remains the industry lingua franca for troubleshooting and design.

Model Answer 2: ARP generates traffic only when the target MAC isn't in the ARP cache — if it is in cache, no packets are sent. DNS generates traffic only when the name isn't in DNS resolver cache or the hosts file. DHCP always generates traffic on first association (there's no cache). ICMP generates traffic when it's the chosen mechanism (e.g., ping) but some ICMP is silent (e.g., a redirect that's already cached). Port resolution is always silent — it uses the local etc/services file.

TCP/IP Functionality Overview

In order to troubleshoot or secure a network using Wireshark (or any network analyzer), you must possess a solid understanding of TCP/IP communications. In the next twelve chapters we examine the most common traffic patterns seen on a TCP/IP network.

Figure 179 depicts the key TCP/IP stack elements next to the TCP/IP Model (formerly referred to as the "DoD Model") and the OSI Model. Although TCP/IP elements match up nicely with the TCP/IP Model, the OSI Model is still referred to constantly in our industry. "Layer 2" devices (switches) and "Layer 3" devices (routers) obtain the numerical designation based on the OSI Model, not the TCP/IP Model.

Many network faults or breaches can be attributed to TCP/IP protocol or application issues. When we troubleshoot from the bottom up, we first look for errors at the physical and data link layers — can a host send bits onto the wire? Are those packets properly formed with a correct checksum? Next we move up the TCP/IP stack to determine if problems are visible. To recognize these problems, we need to know what normal behavior is.

💭 THINK FIRST · THE RESOLUTION PROCESS

Before a client can send application data, it must complete up to six resolution steps: port number lookup, DNS name resolution, route determination, and MAC address resolution (for local target or gateway). Only some of these steps generate network traffic — others are silent when information is available in cache.

  • If you open a trace file of a client browsing to a website and see no ARP packets and no DNS packets at all, what can you conclude about the client's cache state?
  • A host with IP 10.1.22.4/16 (subnet mask 255.255.0.0) needs to reach 10.2.99.99. Is the target local or remote? What if the subnet mask were 255.0.0.0 instead?

Model Answer 1: No ARP means the client already has the required MAC addresses in its ARP cache — it knows where to send the packets at the data link layer. No DNS means the client already has the target IP addresses in its DNS resolver cache or a matching entry in a local hosts file. The client had all the information it needed without asking the network. This is exactly what you expect on a return visit to a recently-visited website.

Model Answer 2: With /16 (255.255.0.0): 10.1.22.4 is on network 10.1.0.0 and 10.2.99.99 is on network 10.2.0.0 — they are on different networks, so the target is remote. The client must use its default gateway. With /8 (255.0.0.0): both addresses are on network 10.0.0.0 — the target appears local and the client will ARP for it directly. A subnet mask that is too short causes the client to ARP for hosts that are actually on the other side of a router — those ARP broadcasts will receive no reply and the connection will fail.

Follow the Multi-Step Resolution Process

TCP/IP uses a multi-step resolution process when a client communicates with a server, as shown in Figure 180. In our example, both the client and the server are on the same network. This process includes the following steps:

  1. Define the source and destination ports (port number resolution) used by the application.
  2. Resolve the target name to an IP address (network name resolution), if necessary.
  3. If the target is on the local network, obtain the hardware address of the target (local MAC address resolution).
  4. If the target is remote, identify the best router to use to get to the target (route resolution).
  5. If the target is remote, identify the MAC address of the router (local MAC address resolution again).

Step 1: Port Number Resolution

In our example, the user has typed ftp CORPFS1. FTP typically uses port 20 or a dynamic port to transfer data and port 21 for commands. The port number is contained in the etc/services file on the client. This number would be placed in the TCP header destination port field of the outbound packet. This process does not generate traffic on the network.

Step 2: Network Name Resolution (Optional)

If an explicit destination IP address has been defined by the client, this step is not necessary. If the client has defined a destination host name (CORPFS1), the resolver process is required to obtain the IP address. The name resolution specification dictates a specific order:

  1. Look in DNS resolver cache for the name.
  2. If not in cache, examine the local hosts file (if one exists).
  3. If the hosts file does not exist or the name is not there, send requests to the DNS server.

If no DNS server can resolve the name, the client cannot build the packet. This process may generate traffic on the network (DNS query/reply) only if the name is not in cache or the hosts file.

Step 3: Route Resolution — When the Target is Local

The client compares its own network address to the target network address using its subnet mask to determine if the target is local or remote. Consider the possible results for a client at 10.1.22.4:

Client IPSubnet MaskResult
10.1.22.4255.0.0.0CORPFS1 (10.2.99.99) is local — go to Step 4
10.1.22.4255.255.0.0CORPFS1 (10.2.99.99) is remote — go to Step 5
10.2.22.4255.255.0.0CORPFS1 (10.2.99.99) is local — go to Step 4

This process does not generate traffic on the network.

Step 4: Local MAC Address Resolution

If the destination device is local, the client must resolve the MAC address of the local target. First the client checks its ARP cache. If it does not exist, the client sends an ARP broadcast looking for the target's hardware address. Upon receipt of an ARP response, the client updates its ARP cache. This process may generate traffic on the network (ARP request/reply) only if the MAC address is not in cache.

Step 5: Route Resolution — When the Target is Remote

If the destination device is remote, the client must perform route resolution to identify the appropriate next-hop router. The client looks in its local routing tables for a host or network route entry for the target. If neither entry is available, the client checks for a default gateway entry. This process does not generate traffic on the network.

TIP The default gateway offers a path of "blind faith" — since the client does not have a route to the destination, it sends the packet to the default gateway and just hopes the default gateway can figure out what to do with the packet. Default gateways typically either forward the packet, send an ICMP redirection pointing to a better local router, or reply with ICMP Destination Unreachable.

Step 6: Local MAC Address Resolution for a Gateway

The client must resolve the MAC address of the next-hop router or default gateway. The client checks its ARP cache first. If the information does not exist, the client sends an ARP broadcast to get the MAC address of the next-hop router and updates its ARP cache. This process may generate traffic on the network (ARP request/reply for the router) only if the router MAC is not in cache.

Figure 183. Following the process of browsing to a website [http-riverbed-one.pcapng].

When examining http-riverbed-one.pcapng (DNS cache and browsing history cleared), we learn:

  1. No ARP queries in the trace file — the client already has the required MAC addresses in ARP cache.
  2. DNS queries for www.riverbed.com appear — the client does not have the IP address in DNS cache.
  3. The client receives a DNS response with the IPv4 address in packet 2. The TTL is only 2 minutes.
  4. An AAAA (IPv6) query returns no IPv6 address — the client cannot reach www.riverbed.com via IPv6.
  5. In packet 5, the client begins the TCP handshake with a SYN using dynamic source port 8369 and destination port 80, sent to the hardware address of the default gateway.

When examining http-riverbed-two.pcapng (visiting 89 seconds later), there are no DNS queries at the start for names whose TTL had not yet expired. The total packet count drops from 1,492 to only 319 because both DNS information and browser page elements load from cache.

MENTAL NOTE
6-step resolution process: (1) Port lookup via etc/services — silent. (2) DNS name resolution — may generate traffic. (3) Route determination (local vs remote) — silent. (4) ARP for local target — may generate traffic. (5) Route resolution for remote target — silent. (6) ARP for gateway — may generate traffic. Steps that generate traffic: 2 (DNS), 4 (ARP local), 6 (ARP gateway). If any resolution step fails, the host cannot communicate. A too-short subnet mask causes the client to ARP for a remote host — ARP will never get a reply.

Case Study 1
Absolving the Network from Blame
Submitted by: Laura Chappell

Watching the traffic enables us to point the finger at the problem and also point the finger at the areas that are not part of the problem.

When we noticed our email connections weren't working suddenly and Outlook just sat there in a state of confusion, we grabbed a trace file of the traffic.

We could see the ARP process to locate the DNS server followed by the DNS request for smtp.packet-level.com. The response provided us with the correct IP address of the SMTP server.

Then the problem appeared. We saw the client make a handshake attempt to the SMTP server. No answer. The client tried again and again. Still no answer.

The problem could be along the path or at the SMTP server itself. We saw successful TCP handshake processes when trying to connect to the SMTP server on another port that we knew was open. We tried to connect to the SMTP port from another location and experienced the same problem. We could connect successfully to the other port, however. It felt like the path was not the problem and that the SMTP server was the problem.

Restarting the SMTP server restored access to email services.

By examining the traffic we could rule out problems with the local network interface card, the ARP discovery process and the DNS server. Analyzing the traffic takes out so much of the guesswork.

TL;DR — Chapter Summary

TCP/IP communications must follow a standard set of rules that includes numerous resolution processes to determine the port numbers to use, the target IP address, the route to use and the target hardware address.

If one of the resolution processes is unsuccessful, a host cannot communicate with another host. Some of the resolution processes generate traffic on the network — others do not. In some instances, a host can obtain information from cache or local tables. If the information cannot be obtained locally, the host can query a target on the network.

These resolution processes include port number resolution (silent — uses etc/services), network name resolution (DNS — may generate traffic), route resolution (silent — routing tables), and local MAC address resolution (ARP — may generate traffic) for the target or a gateway.

Review Questions

Q14.1 What file is referenced to determine the port to use in a communication when the application does not explicitly specify a port?
A14.1 The client references the etc/services file to determine which port to use for a communication.
Q14.2 What can you assume when a client does not generate a DNS query to resolve a target's IP address?
A14.2 When a client does not generate a DNS query, you can assume the client either has the target's IP address in DNS resolver cache or the client has a local hosts file with the required entry.
Q14.3 What configuration fault might cause a host to ARP for a remote target?
A14.3 The client might have a subnet mask that is too short. For example, if a client with IP address 10.2.4.5 has a subnet mask of 255.0.0.0 instead of 255.255.0.0, the client will ARP for any target that has an IP address starting with 10 — even hosts that are actually on the other side of a router.
