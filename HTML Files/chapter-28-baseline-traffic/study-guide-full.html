Baseline "Normal" Traffic Patterns

Creating and using baseline trace files to identify anomalies

"You cannot identify unusual traffic unless you are aware of the usual traffic on your network."
MY QUESTIONS▾
MY NOTES
💭THINK FIRST · BASELINING PURPOSE▾

Baselining is the process of creating trace files that depict normal communications on the network. Without a baseline, you cannot distinguish unusual traffic from normal traffic.

  • If a user complains about performance today but the issue has since stopped, how could a baseline trace file from last month help diagnose the problem?
  • How can a baseline help during a security breach investigation?
Q1: You can filter the current traffic by removing traffic patterns that match the baseline — the remainder (unusual traffic) becomes visible. The baseline also helps quantify performance differences: compare packet rates, response times, and IO rates between the normal baseline and the problem capture.
Q2: The baseline tells you which protocols, ports, applications, and hosts are normally seen. Any traffic that deviates from the baseline — unexpected protocols, unknown hosts, unusual port usage — becomes a strong indicator of a security breach. For example, if IRC or TFTP suddenly appear on a network that does not normally use them, a host may be compromised.

Understand the Importance of Baselining

Baselining is the process of creating a set of trace files that depict "normal" communications on the network. Having baselines that were created before network problems or security breaches occur can speed up the process of identifying unusual network activity. Ultimately, baselines enable you to resolve problems more effectively and efficiently.

Your baseline process may consist of more than trace files — the process could also include images of the client screens or server screens and summary data, IO Graph information and network maps.

One method of using baselines is to identify normal traffic patterns on a problem network. For example, if a user complains about performance one day, you can take the trace file of the current traffic. Referring back to your baseline trace file you can filter out "normal" traffic and focus on the unusual traffic. This can reduce your troubleshooting time significantly.

In a security breach situation, knowing the normal protocols, applications and traffic patterns helps you spot unusual communications. For example, if your hosts never use Internet Relay Chat, but you suddenly begin seeing this type of traffic, your host may be infected with a bot.

💭THINK FIRST · BASELINE TYPES▾

A comprehensive baseline strategy covers all major network activities: broadcasts/multicasts, boot sequences, login/logout, idle time, application launch, web browsing, name resolution, throughput tests, wireless connectivity, and VoIP.

  • For which baseline type must you capture traffic on a separate tap rather than from the host running Wireshark, and why?
  • What should be captured during application launch baselining that would not typically be visible in a running application trace?
Q1: Boot up and login sequence baselines cannot be captured on the host running Wireshark — the host must be powered off or logged out. You must tap into an existing network connection (as close to the client as possible), start capturing, then boot up or log in from the baseline host.
Q2: Application launch baselining should capture the discovery process (DNS lookups, initial connection to servers), interdependencies (other servers contacted), TCP options set in the handshake, initial IO rate, and any failures or retries during the startup sequence — all of which may be invisible during normal steady-state operation.

Baseline Types

Baseline Broadcast and Multicast Types and Rates

Baseline your broadcast and multicast traffic to identify a sudden increase in this traffic rate or to identify new hosts on the network in a passive manner. Key questions: Who is broadcasting? What application is using broadcasts? What is the typical broadcast rate in packets per second? Who is multicasting? What is the typical multicast rate?

Baseline Protocols and Applications

Creating a baseline of normal protocols and applications on the network can help you spot breached hosts. Key questions: Which applications are running on the network? What protocols are used? What UDP and TCP ports are in use? What routing protocol is in use? What ICMP traffic is seen on the network?

Baseline Boot Up Sequences

Analyzing the boot up sequence is important since this sequence sets up the client configuration and performance for the remaining up time. This baseline cannot be captured based on traffic to and from the host running Wireshark — you must tap into an existing network connection, start capturing, and then boot up the baseline host. Key questions: What is involved in the initial DHCP startup sequence? What applications generate traffic during startup?

Baseline Login/Logout Sequences

The login sequence should be baselined each time a new configuration is deployed. This baseline may also require tapping into an existing network connection and logging in from the baseline host separately. Key questions: What discovery process takes place during login? What server does the client connect to? How many packets does a typical login require? Are there any login dependencies?

Baseline Traffic during Idle Times

Watching the traffic flowing to and from a host during idle time (when no one is using the host) is important to identify background traffic that automatically occurs. Key questions: What protocols or applications are seen during idle time? What hosts are contacted? How frequently does the idle traffic occur?

Baseline Application Launch Sequences and Key Tasks

Key applications should be baselined to identify interdependencies and the general ports and startup procedure. Key questions: What discovery process is the application dependent upon? Is the application TCP-based or UDP-based? What port(s) does the application use? What hosts are contacted when the application starts? How many packets/how much time until the launch is complete? What is the IO rate during the launch sequence? Are there any failures or retries during the launch?

Baseline Web Browsing Sessions

Create a baseline of web browsing sessions to the most popular web hosts to determine typical behavior and latency times. Key questions: What browser is used? What is the name resolution response time? What is the round trip latency between the client and the target server? What is the application response time for a page request? Are there any HTTP errors?

Baseline Name Resolution Sessions

Problems during the name resolution process can have a significant impact on performance. Key questions: What name and type is being resolved? What is the IP address of the target name server? What is the round trip response time for the name resolution process?

Baseline Throughput Tests

Consider using an application such as iPerf to perform throughput tests. Capture the trace file during the test to graph the IO rate and spot any performance problems already occurring. Key questions: What is the Kbytes per second rate in each direction? What was the packet loss rate? What was the latency in each direction? Save the IO Graph from throughput tests.

Baseline Wireless Connectivity

Just as important as the site survey before WLAN deployment, the baseline of the WLAN traffic once the network is in place helps identify and solve problems later. Key questions: What packets are involved with the connection establishment to the access point? What encryption method is used? Were there WLAN retries? What is the beacon rate? Copy and save the Statistics | WLAN Traffic baseline information.

Baseline VoIP Communications

Understanding the basic VoIP traffic patterns (including call setup and actual call processes) will help speed up comparative analysis at a later date. Focus on the jitter rate, packet loss rate and call setup procedures. Key questions: What protocol is used for the call setup? What is the jitter rate? Is there any packet loss? Are there any SIP error responses?

Case Studies

Case Study 1
Login Log Jam
Submitted by: Anonymous

One customer was shocked to learn their login sequence required over 70,000 packets. They felt their login process was slow, but assumed the problem was due to the increased number of connections the server had to deal with in the morning hours.

The slow login process was due to the high packet rate exchanged before completion of the login process. During an update process, the client roaming profile had been set up improperly to download numerous fonts and data that had been in cache on the original host — data that should never have been in the original image to be copied down to the client upon login.

After research into the traffic, a list of elements was created that should be excluded from the profile to speed up the login process. The users actually noticed the difference and commented on it — a shock to the IT department!

Case Study 2
Solving SAN Disconnects
Submitted by: Robert M., Network/Connectivity Team Lead, Xerox Corporation

Robert M. (Network/Connectivity Team Lead, Xerox) investigated a Multifunction Printer that continuously failed to scan documents to a Storage Area Network (SAN) device using SMB protocol. He received two traces from a field technician: one of the failure process and one of a successful scan to a Windows workstation.

After sorting the scans to show only traffic going between the printer and the destination, the printer was able to negotiate an SMB connection and ask for access to the destination folder. The printer would then immediately send a TCP FIN after a positive SMB response from the SAN.

Comparing the SMB response from the SAN to the working one from the workstation revealed that the last line of the Tree Connect ANDX Response in the SMB header failed to announce the file system type (in this case NTFS). Since the printer was unsure of the file system, it dropped the connection. Changes to the SAN configuration resolved the issue.

TL;DR — Chapter 28 Summary

Baselines should be created when the network is running properly. These baselines can be used for comparative analysis sessions later when performance suffers or a security breach is suspected. You cannot identify unusual traffic unless you are aware of the usual traffic on your network.

A comprehensive baseline strategy covers broadcast and multicast traffic, general protocols and applications, boot up sequences, login and logout sequences, idle time traffic, application launch sequences, web browsing sessions, name resolution sessions, throughput tests, wireless connection processes, and VoIP call setup and calls.

Review Questions

Q28.1. What is the purpose of a baseline?
A: Baselining is the process of creating a set of trace files that depict "normal" communications on the network. Compare unusual traffic patterns to your baseline to identify anomalies.
Q28.2. How can you obtain a baseline of a boot up sequence?
A: You cannot obtain a boot up baseline on the actual host you are analyzing. You must tap into an existing network connection, start capturing with Wireshark, and then boot up the baseline host.
Q28.3. Why should you baseline traffic during idle times?
A: Baselining idle time traffic helps you identify background traffic that automatically occurs when no one is actively using the host — traffic that may interfere with your troubleshooting if not identified as "normal."
